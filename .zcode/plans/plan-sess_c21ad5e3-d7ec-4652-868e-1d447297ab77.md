# PO 去 PO 后缀 + 时间写入全部切数据库时钟

## Context

两件事：① 37 个 PO 类去掉 `PO` 后缀，只留表名驼峰（`RoomPO` → `Room`）；② 全项目所有写入数据库的时间一律改用数据库时钟（SQL `NOW()` / `DATE_ADD(NOW(), …)`），不再用 Java `LocalDateTime.now()`。起因：用户认为 `createDirectRoom` 里 Java 造时间喂 PO 不优雅，升级为全局口径。盘点确认：37 个 PO 改名零命名冲突；时间改造的硬联动点是「Java 回填时间被下游消费」的链路（HTTP 响应、WS 推送、排序键），用 insert 后点查回读解决。

## 两条贯穿原则（改造判据）

1. **Java 只产生「时长/相对量」，DB 产生「绝对时刻」**：`now+15min` 支付截止、租约 `now+5min`、`createdAt+30d` 过期、退避 `now+30s` 等未来时刻，全部改为 SQL `DATE_ADD(NOW(), INTERVAL #{n} MINUTE/HOUR/SECOND/DAY)`，Java 只传数值（先例：ModerationMapper claimById 的 `lease_expire_at`、PostMapper submitDraft 的 `expire_at`）。
2. **读侧 Java 时钟保留**：扫描谓词（dueBefore、cutoff、召回窗口判断、sumTodayChange 日界）是查询条件不是时间写入，不动。同理 Redis TTL（验证码/防占单/滑窗）、WS 帧 ts、FileStoragePort 月份目录——非 DB 写入，不在范围内。

## 工作批次 A：PO 改名（机械，先行，独立编译闸门）

- 37 个 PO 类（`bs-infrastructure/.../dao/<域>/po/`）文件与类名去 PO 后缀；**删除两个零引用死类** `PostLikePO`、`ProductFavoritePO`（按 DirectRoomPairPO 先例）。包名不动。
- 引用面：bs-infrastructure 内 26 个 java 文件（14 个 Dao 接口 + 11 个仓储 + OutboxMessageStore/OutboxMessageSender）+ 13 个 mapper XML 约 105 处全限定名（无 typeAlias 配置，全是 FQN，sed 批量替换）。bs-domain/api/trigger 不 import 任何 PO，零波及。
- 闸门：mvn compile + test-compile。

## 工作批次 B：时间切 DB 时钟（按域推进）

### B1. SQL 语句改写（13 个 mapper XML）
- 所有 INSERT 的 `create_time/update_time`（及 `created_at/updated_at`，timeout 表）从 `#{...}` 改 `NOW(), NOW()`；INSERT-only 语句里相应 PO 字段引用消失。
- 纯「此刻」的业务时刻列改 `NOW()`：user `last_login_at`、moderation `entered_at`（insertIgnoreTask）、errand/trade 事件表时间、notification insert、outbox insert、chat 六条 insert。
- 未来时刻列改 `DATE_ADD(NOW(), INTERVAL #{n} ...)`：errand 三处超时 + `payById` 的 `deadline`（改传 timeLimitHours）、trade 下单 payDeadline、moderation 租约对应 timeout 行、timeout 表 `action_time/next_fire_time`（退避秒数参数化、resend 用 NOW()）、post/product `expire_at`、feed `feed_time` 已是 NOW() 不动。
- `recallMessage` 的 `recalled_at`、`updateUserRoomHiddenAt` 的 `hidden_at` 改 `NOW()`，参数退役。

### B2. 接口链路收窄（参数随列退役）
- `IChatDao/IChatRepository`：`recallMessage(roomId, seq, recalledAt, by)` 去 recalledAt；`hideRoom` 去 hiddenAt；`ChatRecallServiceImpl`/`ChatReadServiceImpl` 不再生成时间。
- timeout 仓储方法：`markRetry` 等改传退避秒数；`TimeoutTaskScanService` 只算秒数；errand/trade 的 `schedulePayTimeout` 改传分钟数。
- 各域 repository 的 toPO / 实体工厂（UserEntity.create、PostEntity.create、ProductEntity 等）停写时间字段，`expireAt=createdAt+30d` 之类的派生计算删除（SQL 侧算）。
- 写路径实体时间回填全删（`room.setCreatedAt(now)` 等）；死字段随批清理：`TimelineEntity.createdAt`、TimelinePO/UserPairRoomPO/OutboxPO 等 insert-only PO 的 createTime/updateTime 字段。

### B3. DB 时刻回读点（API 契约不变，insert 后点查回读）
| 消费点 | 回读方式 |
|---|---|
| chat 发送：WS 推送 payload.createdAt、HTTP 响应 createdAt、`last_msg_time` 排序键 | `deliverMessage` 内 `selectMessage(roomId, seq)` 点查回读 create_time，回填 message（uk_room_seq 点查原语复用） |
| post/comment/product/order/errand 新建响应 createdAt、errand deadline、登录响应 lastLoginAt | 各仓储 create 方法末尾按业务键回读对应行，回填实体后返回（errand pay 响应的 deadline 同理在 payById 后回读） |
| 审核池 FIFO 锚点 entered_at | SQL NOW() 写入；跨表同刻靠 DATETIME 秒级精度（同事务同秒），且 CommunityRepository 已有「事务内读回 DB entered_at」先例 |

### B4. 测试与文档（不起环境，翻新到位不实跑）
- 集成测试：`isBetween` 时间窗断言大多天然仍成立（DB NOW() ≈ Java now）；`isEqualTo Java 值` 的断言改 isBetween/isCloseTo（TimeoutShardingRouteIntegrationTest:82-88 revive、TimeoutCallbackFixture 等）；直插回拨时间夹具（传普通 ? 参数）不受影响；TimeoutTaskScanServiceTest 的 mock 断言随仓储签名翻新。
- docs：`docs/db/README.md:61` 总口径「不带 DB 默认值（应用写入）」→「SQL NOW() 显式写入，无 DB 默认值」；各域 docs/db/*.md「应用写入」注记逐条翻新；docs/api/* 复核 createdAt/deadline 字段语义（契约字段零变化）；CONTEXT.md 增补/对齐「时间口径」词条（Java 只产生时长、DB 产生时刻）。
- DDL（schema.sql）**不改**：NOW() 是显式写入，无需 DEFAULT CURRENT_TIMESTAMP。

## 验证

不起环境。每批次结束跑 `mvn compile` + `mvn test-compile`（bs-app -am）确认全绿；文档面改完 grep 复核无「应用写入」残留口径。行为等价说明：DATETIME 列秒级精度下同事务 NOW() 同秒，跨表一致性、排序语义、API 契约均不变；唯一可见差异是 DB 时钟成为唯一事实源（时钟偏移不再双写）。
