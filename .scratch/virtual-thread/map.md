# Map：虚拟线程采用规范（virtual-thread）

_Label: `wayfinder:map`_

## Destination

一份 spec：`.scratch/virtual-thread/spec.md`，定义本仓库 4 个 Spring Boot 工程**虚拟线程的采用规则与逐执行上下文裁决**——哪些执行上下文用虚拟线程、怎么用、并发上限与背压口径、需要的 pinning 改造、以及明确不采用者的清单与理由。**不含**代码改造步骤（spec 定稿后另拆落地票，与设计票同目录，照 timeout-center 惯例）。

## Notes

- **栈**（2026-09-19 侦察）：4 个互相独立的 Spring Boot 3.3.5 工程，全部 JDK 21（`JAVA_HOME=C:\Code\JDK21`，机器上**无 JDK 24**）——单体 `better-school` + `marketing-activity` + `marketing-asset` + `timeout-center`
- **已有先例（5 处手写虚拟线程，全在超时链路）**：`timeout-center` 扫描按槽位 fan-out（`TimeoutTaskScanCase.java:71`，嵌套到回调组间并行 `:102`）、注册逐行（`TimeoutTaskRegisterCase.java:40`）、单体 timeout 注册 outbox（`TimeoutRegisterOutboxSender.java:65`/`:90`/`:148`）。同目录 spec 已立判据：**否掉 CompletableFuture**（commonPool 会被阻塞 JDBC 饿死）、**Hikari 池 ≥ 并行度**
- **全仓缺席**：`spring.threads.virtual.enabled` 零命中；无 `@EnableAsync`/`@Async`/`@Scheduled`；无 `CompletableFuture`/`parallelStream`/`ForkJoinPool`（主源码）
- **选点规则（图绘期定稿 2026-09-19）**：某处**并发上限由平台线程数决定**、且工作主体是**阻塞 I/O**（DB / RPC / HTTP / 对象存储），换虚拟线程能抬高上限或消除扇出串行化 → **用**。否则（CPU 密集、并发度本就 ≤ 个位数、并发已被连接池或下游配额兜死）一律**不用**。「能把并发抬高」与「抬高了有用」是两件事
  - ⚠️ **判读精化（票 07，2026-09-21）—— 规则原文不改，只补判读**：① 「并发上限由平台线程数决定」看的是**上限由谁决定**，不是当前测到的量级——量级会被负载放大，开发机上的演示负载没有参考量；② 「并发已被连接池兜死 ⇒ 不用」**不适用于**「该处本就不该承担下游限流」的场合——DB 限流是连接池（+ `connection-timeout`）的事，不是 Dubbo provider 池、也不是 Web 层信号量的事，所以「拿掉这里的平台线程上限会把压力下沉到连接池」**构不成反对理由**
- **范围**：4 个工程全上（规则不该因工程而异），spec 按工程给出**适用性表**——单体是主战场（**21** 个消费者 + 全部 WS + 全部 MinIO 都在它里面；全仓 23 个消费者的另 2 个在两营销服，票 05 复核修正）
- **JDK 口径**：留 21，只修会被碰到的 pinning 点，spec 写明「JDK 24 / JEP 491 后这些改造可回收」
- **工作方式**：grilling 票每轮问 frontier、每题给推荐答案；调研先行，拍板票被调研票阻塞；调研报告落 `research/NN-*.md` 由票面 `## Answer` 链接
- 求职作品，真实产品标准；架构取向偏「更贵更能展示」，但代价要先讲清
- 术语沿用 `CONTEXT.md`；本 effort 新增词条只在 spec 收口时回填

## Decisions so far

- [调研：Dubbo 3.3.x 两侧线程模型与虚拟线程可行性](issues/01-research-dubbo-thread-model.md)：**两侧是两套模型，不能当一件事办**。Provider 走真业务池（默认 `fixed`/上限 200/队列 0/打满即抛，线程懒创建）；**Consumer 的同步 unary 根本不进池**（`ThreadlessExecutor` + `LockSupport.park`，VT 在该点卸载载体、不 pin）→ 「VT 化 consumer」在本仓库**没有可改的对象**，零 Dubbo 配置。**Dubbo 3.3.6 内置 `virtual` 线程池**（`dubbo.protocol.threadpool: virtual` 一行生效，已解包发布 jar 实证），且 3.3.5 起 `spring.threads.virtual.enabled=true` 会**自动**把它设为 `virtual`（可用显式配置压回）。**代价**：3.3.6 的 `virtual` = `newThreadPerTaskExecutor`——无界、忽略 `threads`/`queues`、**移除原有「200 打满即拒 + jstack」硬保护**，等于把并发上限整体转给下游；池化变体 `threads.virtual.core`（PR #16055）不在 3.3.6。Dubbo 全 jar 1856 类字节码扫描：热路径 **0 处 `synchronized`**。timeout-center spec 否掉原生 async 的三条论据**原样成立**
- [调研：JDK 21 pinning 雷区清单](issues/03-research-jdk21-pinning-inventory.md)：**全仓唯一需要为 pinning 动代码的地方，就是本仓库自己那处 `FileStoragePort.ensureBucket()`**（改法＝`ReentrantLock` + 双检），10 个依赖项逐个落到「不 pin」或「补偿型/微秒级」→ **票 05 的改造清单只剩这一项**。判据升级为「**pin 的类别 × 并发量 × 时长**」：JDK 21 只在两条情形真 pin（`synchronized` 块/方法内、native 帧内）；`Object.wait` / 文件 I/O / DNS 属**补偿型**（`Blocker.begin()` → ForkJoinPool 扩池），不拖吞吐只涨 OS 线程。载体池**全进程共用**，`parallelism = availableProcessors()`（本机 32）、`maxPoolSize = max(parallelism, 256)`。本机实测：64 条 VT 各 `synchronized{park(500ms)}` → 1047ms + 64 个 JFR 事件；换 `wait` / `ReentrantLock` / 纯 park → 均 ~505ms + 0 事件。**探测**：JFR `jdk.VirtualThreadPinned`（`default.jfc` 阈值 20ms，`threshold=0ms` 全收），但**它只是「park 时无法卸载」的子集，不能把「零事件」当「零 pin」**。**Boot 3.3.5 开关实测只做三件事**：Tomcat Connector `setExecutor(VirtualThreadExecutor)`、`applicationTaskExecutor`/`TaskScheduler` 换 VT builder、Reactor `defaultBoundedElasticOnVirtualThreads`——**NIO acceptor/poller 恒为平台线程**。**WS 发送路径不致命 pin**（Spring 装饰器全类零 monitor、Tomcat socket 写刻意移出 monitor），但**慢客户端阻塞写是补偿型**（`synchronized(writeLock){ writeLock.wait() }`）→ 每个卡住的会话占一个载体，池最多涨到 256。**ShardingSphere `HintManager` 是 TTL**（`extends InheritableThreadLocal`）→ hint 必须与执行 SQL **在同一虚拟线程内** `getInstance()`+`close()`，跨线程靠继承会炸
- [实测：翻框架开关的 pinning 与吞吐](issues/04-task-measure-framework-flip.md)：**翻开关换不来吞吐**——同机 A/B（10 op 混合负载、c=32/128/256、池 10 vs 64）on/off 差落在噪声内，而池 10→64 让吞吐翻倍（c=32: 179→452 rps）；JMX 探针显示池恒 100% 占满、**等连接线程峰值 280**、应用 CPU 仅 10–16% ⇒ **上限在池与 DB 延迟，不在线程数**（池开到 256、VT 组 `awaiting` 恒 0 时反而吞吐低 25%、p99 长 4.8×，单次跑仅供参）。JFR（threshold=0ms）59761 个 `jdk.VirtualThreadPinned` **全部来自 `com.mysql.cj.protocol.ReadAheadInputStream.fill()`**（JDBC socket 读，p50 1.28ms，超默认 20ms 阈值的仅 1.8%）⇒ pinning **无新增改造项**，但 0ms 阈值下「零事件 ≠ 零 pin」（已回填票 03）。环境侧两条坑：**数据量是最大混淆项**（同 op 同并发，帖子 500 行→1.7 万行，1756→190 rps）、同一用户并发的 `virtual_wallet` 死锁与 VT 无关且各臂都有
- [调研：RocketMQ 消费线程池能否虚拟线程化](issues/02-research-rocketmq-consumer-executor.md)：**换消费 thread pool 没有任何低成本官方口子**——starter 2.3.6 → client 5.3.2，executor 在 `ConsumeMessageConcurrentlyService` 构造器里 new（无界队列使 `consumeThreadMax=64` 永不生效，**实际并发 = 20**，460 条线程由此而来），容器侧只递 `consumeThreadMin/Max` 两个 int；可替换点仅 3 处（覆写 `RocketMQMessageListenerContainerRegistrar.registerContainer` / 自实现 `RocketMQListenerContainer` / `setConsumeMessageService` 自研整个服务）。官方 `setConsumeExecutor`（PR #11090，明示支持 JDK 21 VT）**只在 develop，未进 5.3.2/5.5.0/5.5.1**；专为 VT 的 #8062/#8063 未合并。**pinning 改造量 = 0**（并发消费路径 0 处 `synchronized`、`ProcessQueue` 用 RW 锁、`NioSocketImpl.park` 对 VT 走 `Poller.poll` → 120s 阻塞读不 pin）。ack/重试/DLQ 语义逐行不变。**线程一多天花板立刻转到 pull 流控**（`pullThresholdForQueue=1000` / 100MiB / span 2000）**与 Hikari 池**——必须与连接池口径同时定
- [决策：框架开关的落地面与承压口径](issues/05-grill-framework-flip-and-backpressure.md)：**四工程统一翻开关，但「实测无收益」原样入 spec**（理由只写「消除 Web 层 200 平台线程上限 + 口径统一」，不许包装成性能优化）。落地面实测**只有 Tomcat handler executor 一件真实生效** + 两条硬约束：翻后 `server.tomcat.threads.max` **静默失效**（JMX 读 `-1`）、不许混用 Tomcat 原生 `useVirtualThreads`。**Dubbo 连带：规则留、理由改**——3 个 provider 显式写 `dubbo.protocol.threadpool`（⚠️ **票 07 定为 `virtual`**：票 05 原文的「一律**压回**」那个**值**已被反转，规则「必须显式写、不许吃 3.3.5 的默认连带」保留；原理由「否则无界池会移掉『200 打满即拒 + jstack』、把压力下沉到 Hikari 的 30s 超时」已被票 07 否掉）。**背压口径 = 连接池是唯一真上限 + `connection-timeout: 3000`**（三个未配 Hikari 的工程显式化，池仍 10 / 24，不加 Web 层信号量）；pinning **本版只修 `FileStoragePort.ensureBucket()`**，其余按「补偿型不改 / 已证无害」两栏记账
- [决策：RocketMQ 消费线程模型](issues/06-grill-rocketmq-consumer-model.md)：**23 个消费者的消费池整体换虚拟线程**（4 工程统一，依据是**用户口径**「开发阶段、能上就上、架构展示面」——按选点规则本应判不换，这条必须原样入 spec，不许包装成性能优化）。落地**不等发布版**：同包子类（`org.apache.rocketmq.client.impl.consumer`）+ 覆写 public 的 `submitConsumeRequest` 改投 `newVirtualThreadPerTaskExecutor`，经覆写 `RocketMQMessageListenerContainerRegistrar` 接线 ⇒ ack/重试/DLQ 语义**逐行不变**、base 池懒创建故 460 条线程真归零。并发上限**不加信号量**，改由 `consumer.setPullThresholdForQueue(N)` 表达（`consumeThreadNumber` 记为**死参数**）。孤例（一个同步阻塞型消费者）**不再单列**（位点钉住 120s 是模型固有，不改善）；WS 扇出口径**整体归票 09**。两处前提修正见票面（WS 消费者实为 **3 个**、120s 是读超时上限而实际耗时无实测）
- [决策：Dubbo 两侧线程模型](issues/07-grill-dubbo-thread-model.md)：**provider 池换内置 `virtual`**（3 个 provider 工程显式写；与票 05 翻 Tomcat 同构：消平台线程上限 + 口径统一，无实测收益）。⚠️ 本票**反转了自己初稿的 `fixed` 推荐**——两条论据被用户否掉（「并发量级个位到数十」只是票 01 §7.2 的纸面推理、从未实测，判据应是**上限由谁决定**；DB 限流不该由 Dubbo 池承担，故「压力下沉连接池」不构成反对理由）。**consumer 侧无可改对象**（sync unary 走 `ThreadlessExecutor`，宿主是 VT 就免费 ⇒ 本仓「VT 化 consumer」无物可改）。**动态 `ReferenceConfig` 边零改造**（桶锁只裹纯构造、贵的 `.get()` 在锁外；`ReferenceConfig.init()` 3.3.6 用 `ReentrantLock` 非 `synchronized` ⇒ 不 pin——补上票 01 §5.3 未扫 `dubbo-config-api` 的盲）。代价 **5 项**记账（无界无背压 / `threads`+`queues` 成死参数 / 丢「拒绝 + jstack」/ `threadpool` 跨应用传播改 4 工程消费端 `streamExecutor`、今天零行为变化 / provider 层并入 pinning 适用面）；可回收触发条件 4 条，含「升到 #16055 换成有界 VT」
- [决策：调度侧与已有扇出链路](issues/08-grill-scheduling-and-existing-fanout.md)：**8 处扇出到虚拟线程**（单体的 7 个 job 入口 + 中心的回调批处理 `onTimeoutBatch`；全仓 17 个 `@XxlJob` + 1 个批处理入口逐条裁完），**依据是用户口径而非性能收益**（按选点规则本应判「不换」，照票 06 先例原样入 spec；助手初稿的「有用性 → 维持串行」推荐被否，原样留档不许再引用）。3 类不采用：已 `asyncSend` 的 outbox 扫描（5 个）、无循环的批量 SQL（2 个）、`lotteryDeductMerge`（整批一个事务，并发化会拆掉「绝不按 `status=0` 翻状态」的不变量）。**模板两变体**（单发一批 / 循环拉批到空）+ 四条硬规矩：**宽度 = 批大小、不加信号量**（与票 05/06/07 同一口径）、执行器即用即关（粒度 = 一个工作单元；VT 执行器不是池）、结果回主线程汇总、项内异常自吞记账；⚠️ `close()` 是**无限等待** ⇒ 项内必须自带超时。**两处无界查询必须补 `LIMIT` + 游标**：`selectUsersActiveOn` 不推进会**永远漏尾巴**（处理完仍满足查询条件），搜索重建的 4 处 `selectAllIds` 只重建前 N 行 = **静默不完整的索引**（第 5 个调用点 `PostDetailCache.initBloom()` 刻意不设限——布隆预热要全量 id、且不是循环，spec 记为唯一例外）。**既有 5 处 VT 复核全部一致**（三处记账：`expand()` 注册批宽度无界、⚠️ 票 05 的 `connection-timeout: 3000` **尚未落地**（单体/两营销服跑默认 30s、池 10）、池仍 10 不动）。**hint 契约完好**（hint 只在 timeout-center；仓储层每次 DAO 调用自设 hint ⇒ 对调用方透明）；⚠️ 修正票 03/05 两处事实：`HintManager` 持有者是 `com.alibaba.ttl.TransmittableThreadLocal`（**非** `InheritableThreadLocal`），且 VT **确实**继承 inheritable 值（本机实测）⇒ 真正的雷是**「扇出边界落在打开的 hint 作用域内」**（子 VT 再 `getInstance()` 直接抛）。**没有一处判出 Out of scope 第 5 条**（资金/信用余额更新全是原子 SQL ⇒ 跨行并发无丢失更新）；一处**新可达的既有竞态**进代价表：扇出让「同一用户多订单同时关单」可达，而 `virtual_wallet` 的同用户并发死锁**根因已定位**（RR 下流水插入是 `INSERT ... SELECT FROM virtual_wallet` ⇒ 取共享 next-key 锁，随后同事务的 `UPDATE` 要升级为排他锁 ⇒ 同用户两事务各持 S 各求 X 成环，解释「只在同用户并发、与 VT 无关」两个特征），**最小修法 = 删掉无读取者的 `wallet_id` 列改走 `INSERT ...
