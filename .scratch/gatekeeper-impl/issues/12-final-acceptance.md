三条走查口径（写进了 spec §8.5 与 README 坑 19–25）：

1. **"恢复 ≤ 1 个 `refresh_interval` 收敛"只能在中心侧量**（账本 `Σ份额` 从 0 爬回 `Σ需求`）。客户端在断租期走 fail-open、**按最后份额照跑**，放行率一秒都不掉——拿"客户端放行率恢复"当判据，任何一轮都读到 `0ms`，看着全绿其实一格都没量到（编排器第一版就是这么假通过的）。恢复起点也用**实测**的中心起来时刻，不用编排器排的时刻表（`stopCenter` 要等端口真不应答 + 中心启动几秒 ⇒ 配置 30s 的断租实测 36.5–37s）。
2. **场景 3 的"分区 ≠ 崩溃"要两条读数一起证明**：客户端侧整段空档 + 中心自己在原端口上一路 `200`（`directProbeFailures = 0`）。分区口径是 REJECT 风格（已建连接掐掉、新连接 accept 后立刻关），不是 DROP 风格的挂到超时。
3. **冷启动那一两笔首租失败不是异常信号**（50ms 预算在本机 loopback 上贴边过；实测那几条全在 `t=0~100ms`）。所以"某 pod 在窗口内不受影响"的判据锚**窗口内放行率 + 续租/降级计数**，不锚"首租失败计数 == 0"。

**本票量出并回修的两处"量具"缺陷**（都不是产品缺陷；改了 `measure/` 的两个脚本件）：

1. **中心端口不能从临时端口范围里挑**（长档场景 2 撞到）。`ServerSocket(0)` 分配的是**临时端口范围**（Windows 49152–65535），而我们的 HTTP 客户端／份额轮询器**出站连接也从同一范围取本地端口**；Windows 上一条出站 socket 占住本地端口 P 之后，`new ServerSocket(P)` 直接抛 `BindException`（现场用 `EphProbe2` 复现过这条语义，TIME_WAIT 已排除——监听关掉后立刻重绑是成功的）。症状是"**重启的中心起不来**"，而那一刻 `netstat` / `portAnswers` 都看不见占用者 ⇒ 排查方向被带偏。**修法**：`Procs.freePort()` 改扫 **18080–18299**（临时端口范围之外，仍保留"探测再放掉"以跳过孤儿进程），并给 `freePort(exclude)` 一个排除口（两个中心端口必须不同）。
2. **收敛判据的界要含客户端抖动**。各 pod 的续租节奏是 `interval + [0,10%)` 抖动（防惊群），界只写一个光秃秃的 `refresh_interval` 会让**完全正确**的实现偶尔判 FAIL——第一次长档实测恰好顶在 5500ms 上。**修法**：界 = `refreshInterval × 1.1 + 一次轮询`（与臂 A 那条"采样量化余量"同一条纪律）。同批修掉 `secondPort` 的死循环（`freePort()` 永远返回"从 18080 往上第一个空着的"，而主中心那时还没绑端口 ⇒ 同一个号一直还回来，JVM 在构造阶段空转十几分钟、一个文件都没写）。

### 5. 内存账 JOL 复核（票面第 3 条点名的那次）

`gatekeeper/measure/run-memprobe.sh`（JOL 0.17、64 位 HotSpot + 压缩指针、`-Djol.magicFieldOffset=true`——JDK 21 上 `Unsafe.objectFieldOffset` 对 **record** 类直接抛，`LeaseIdVO` 就是 record）对**真的实现类**灌数据、对整张图取 `GraphLayout.totalSize()` 减空容器基线 ÷ 条数：

| 容器 | 手算模型 | **JOL 实测** | 差的在哪 |
| --- | --- | --- | --- |
| 中心账本（两层 CHM） | 91 B/条 | **≈190 B/条**（合批 500 key/请求）／**≈285 B/条**（一次请求一个 key） | 模型漏了 `key` String + 其 backing `byte[]`（≈56）、`LeaseIdVO`（24）、**内层 map 的槽位**（每 key 只有 n_k 条、table 是 2 的幂 ⇒ ≈20，不是按大表负载因子摊的 11） |
| 幂等去重表 | 80–120 B/条 | **≈190 B/条** | 同类漏项 + 装箱时间戳 + 插入序队列结点 |
| 客户端桶表 | 92 B/条 | **≈239 B/条** | 同类漏项（键 String 及其数组 + 桶对象本体） |

零件浅尺寸实测与手算**逐位吻合**（`LeaseEntity` 48 / `LeaseIdVO` 24 / `String` 24 / `byte[]` 32），说明口径没跑偏。**结论：两个 10k 默认值复核结论不变、数字翻倍**——10k key × 200 实例 = 2M 条 ≈ **380 MB** → 8 分片 **47 MB/实例**（仍可行）；5000 实例 × 10k = 50M 条 ≈ **9.5 GB**（更明确地超配）；去重表 10 万条上限 ≈ 19 MB。已在 spec §3.5／§8.4／§11 与 research/12 §5 回填实测值。

**Standards 轴**（采纳三条 + 一处澄清）：

### 7. 已知波及 / 不在本票范围

- **规则错位窗**（`max(R_old,R_new) × 一个 refresh_interval`）仍是推演：IT 只验到"两端内容相同时不计数"（票 09 的判据用例），本票没给它加 chaos 场景。
- **分区脚本是 REJECT 风格**（拔线 = 掐连接），DROP 风格（挂到 2s 子批超时）那一档没有单独跑；子批超时路径由票 05/11 的 IT 覆盖。
- **内存账只复核了三个容器**（账本 / 去重表 / 桶表），`min_renew_interval` 的过频锚点表按"与账本同阶"估算、未单独 JOL。
- chaos 场景的"两分片"是**单机两进程**（不是两台机器）：localhost 上的进程级隔离不等价于真机架的网络/资源隔离。
