# 票 04 定稿：连接层方案（状态机 + 关键时序）

> 2026-09-09 grilling 定稿，基于[票 03 调研](03-ws-选型调研.md)的推荐参数。选型结论沿用票 03：**Spring 原生裸 WebSocket + 自定义 JSON 协议 + 自管连接注册表**（单机部署，内存注册表即终态）。

## 0. 决策记录（grilling 结论）

| # | 决策 | 结论 |
|---|---|---|
| Q1 | 上行通道 | **REST 发送 + WS 纯下行**。发送复用 moderation/事务/HTTP 错误语义；WS 协议面缩到「下行推 + 心跳 + 踢人」，不发明 ACK/去重/重发协议（阵营二：Discord/Slack/Matrix 形态） |
| Q2 | 推送触发点 | **outbox → MQ 消费者 → 推送**。与 agent-review 既有异步骨架同构，事务与推送解耦，漏推由补拉兜底 |
| Q3 | 推送载荷 | **全量内容**（文本/卡片完整体，图片只传 URL），客户端按 (roomId, seq) 判重 |
| Q4 | 事件类消息 | 动作走 REST、结果以**轻事件**推送（READ/RECALL 只带定位），离线成员靠拉取路径自然呈现 |
| Q5 | 重连对齐游标 | **全局投递序号 delivery_seq**（per-user 单调，扇出事务内从 user_seq 计数表取号；grilling 后的 code-review 否决了「timeline 自增主键当游标」——自增 id 无业务含义 + 并发提交乱序会漏拉）；room seq 只用于消息判重与未读计算，两个序号空间不混用 |
| Q6 | 参数包 | 心跳 25s/判死 60s、票据 60s 一次性、互踢 KICK+close(4001)、退避 1s×2 上限 30s——见 §5 |
| Q7 | 协议类型清单 | 见 §2，C→S 仅 PING |
| Q8 | MSG 推送范围 | **排除发送者本人**（发送方以 HTTP 响应为准；单设备无此场景） |
| Q9 | 重连可用性 | **连接即用、对齐并行**：不设 ALIGNED 阻塞态，补拉结果与实时推送靠 (roomId, seq) 判重合流 |
| Q10 | 边缘项归属 | WS 集成测试策略→票 07/spec；旧轮询降级→票 08；群系统消息→票 05 |

## 1. 组件与职责

```
服务端（单体内）                          客户端（手机 Web）
┌─────────────────────────┐            ┌──────────────────────┐
│ WsTicketService          │←─REST───│ 连接管理器（状态机 §3）│
│  签发/消费 60s 一次性票据  │            │  心跳循环             │
│ ChatWsHandshakeInterceptor│           │  退避重连             │
│  校验票据→身份入 attributes│           │  (roomId,seq) 判重   │
│ ChatConnectionRegistry   │            │  delivery_seq 游标    │
│  Map<userId, session>    │            └──────────┬───────────┘
│ ChatSessionRegistry(活跃) │                       │
│  lastInboundAt + 调度清扫 │                       │
│ ChatPushConsumer         │──WS MSG/READ/RECALL/KICK──→│
│  (outbox 消费者→查注册表推送)│                        │
│ ChatWsHandler            │←─WS PING────────────────│
│  afterEstablished/Closed │                          │
└─────────────────────────┘
```

- **发送路径不经过 WS**：`POST /api/chat/rooms/{id}/messages`（既有 Controller 模式 + moderation 初筛 + 事务）。
- **注册表互斥规则**：新连接先 `put(userId, newSession)` 占位；旧 session 的 close 回调用 `remove(userId, oldSession)` 两参语义，迟到的 close 不会误删新连接。
- **并发写保护**：session 以 `ConcurrentWebSocketSessionDecorator` 包装（JSR-356 不允许并发 send）。
- **推送线程模型**：outbox 消费者查注册表 → 对每个在线成员 session 投递；不在线直接跳过（漏推合法）。

## 2. 协议信封与消息类型

信封：`{type, roomId?, seq?, payload?, ts}`（JSON 文本帧）

| 方向 | type | 携带 | 用途 |
|---|---|---|---|
| C→S | `PING` | 无 | 应用层心跳（25s 一次，唯一上行） |
| S→C | `PONG` | 无 | 心跳应答 |
| S→C | `MSG` | roomId, seq, payload=完整消息体 | 新消息推送；按 (roomId, seq) 判重 |
| S→C | `READ` | roomId, userId, readSeq | 已读水位线变更（实时已读回执） |
| S→C | `RECALL` | roomId, seq | 撤回事件（只带定位，内容以拉取为准） |
| S→C | `KICK` | reason=SESSION_TAKEN_OVER | 互踢通知，随后 close(4001) |

注意清单里**没有 SEND/ACK**：发送走 REST 后 C→S 只剩心跳，服务端连接层无业务路由。

## 3. 连接生命周期状态机

### 3.1 客户端状态机

```
                 ┌─────────────────────────────────────────┐
                 │       （断线且非 4001 → 退避重连）         │
                 ▼                                         │
┌──────────┐ 要票+握手 ┌───────────┐ 收到KICK/close(4001) ┌────────┐
│DISCONNECT│─────────→│ CONNECTING│────────────────────→│ KICKED │
└──────────┘          └─────┬─────┘                     └───┬────┘
   ▲  ▲                     │ 握手 101                       │ 用户确认
   │  └─ 要票/握手失败 ──┘   ▼                              │（重登/回登录页）
   │     （退避重试，有上限）┌──────────┐                      │
   │                      │ CONNECTED │                     │
   │                      └──────────┘                      │
   └─────────────────────────────────────────────────────────┘
        进入即：① 启动心跳循环（25s PING）
               ② 并行触发 REST 增量补拉（delivery_seq 游标），不阻塞渲染
```

- `DISCONNECTED → CONNECTING`：app 启动 / 进入聊天页 / 退避到点 / `visibilitychange` 或网络恢复立即触发。
- `CONNECTING → CONNECTED`：握手 101 成功（票据已被消费，本次连接存续期内不再鉴权）。
- `CONNECTING → DISCONNECTED`：要票失败（重试有上限）或握手被拒（401，票据过期/非法）→ 计入退避；**退避到上限仍失败 → 停在 DISCONNECTED 并提示重新登录**（JWT 已过期的典型场景，重登换新 JWT 后再走要票+握手）。
- `CONNECTED → CONNECTING`：onclose 且非 4001（网络断/服务端判死清理）→ 指数退避重连。
- `CONNECTED → KICKED`：收到 `KICK` 消息或 close code 4001 → **停止自动重连**（防止两设备互踢死循环），提示「账号已在别处登录」。
- `KICKED → DISCONNECTED`：用户操作（重新登录）后重新建连，反向踢掉对方。

### 3.2 服务端会话状态（无显式状态机，两条不变式）

- **登记不变式**：注册表中的 `(userId → session)` 与活跃时间戳 `lastInboundAt` 成对存在；任何入站帧（含 PING）刷新 `lastInboundAt`。
- **判死不变式**：调度器每周期扫描，`now − lastInboundAt > 60s` → 主动 close + `remove(userId, session)` 两参注销。容器层 Tomcat `READ_IDLE_TIMEOUT_MS` 作兜底。

## 4. 关键时序

### 4.1 登录建连

```
客户端                          服务端
  │ POST /api/auth/login ────────→ 签发 JWT
  │ POST /api/chat/ws-ticket ────→ 校验 JWT，签发 60s 一次性 ticket
  │ GET /ws/chat?ticket=… ───────→ Interceptor 原子取删+校验
  │   （失败→HTTP 401，客户端重新要票）
  │ ←──────── 101 Switching Protocols
  │                    afterConnectionEstablished:
  │                      registry.put(userId, session)
  │                      若已有旧 session → 发 KICK + close(4001)（见 4.2）
  │ {PING} 25s 周期 ─────────────→ {PONG}；并行触发 REST 增量补拉
```

### 4.2 互踢（旧连接视角）

```
新设备                      服务端                         旧设备
  │ 握手成功                  │                              │
  │        registry.put(user, new) 占位                     │
  │                          │──{KICK,SESSION_TAKEN_OVER}──→│
  │                          │──close(4001)──────────────→│
  │                          │   （旧连接 close 回调          │
  │                          │    remove(user, old) 两参，   │
  │                          │    不影响新连接）              │
  │                          │              停止自动重连，     │
  │                          │              提示→回登录页     │
```

多 tab 同语义（第二个 tab 踢掉第一个），KICK reason 注明，避免用户误以为被盗号。

### 4.3 断线重连

```
  │ ✕ 网络断（onclose，非 4001）
  │   退避：1s → 2s → 4s → … 上限 30s，抖动 0.3~0.5
  │   visibilitychange / 网络恢复 → 立即重试一次
  │   重新要票 → 完整重新握手（票据不重用）
  │ ←── 101，CONNECTED，心跳恢复
  │ GET timeline?afterDeliverySeq=N ──→ 返回 delivery_seq>N 的收件箱行
  │   （含期间被撤回的终态；缺口超出服务端保留窗口 → 降级全量拉取）
  │   补拉结果与期间实时到达的推送按 (roomId, seq) 判重合流
  │   游标只被补拉推进（实时推送不推进游标，重复段由判重吸收）
```

### 4.4 收发一条消息（完整链路）

```
A（发送方）                服务端                             B（接收方，在线）
  │ POST …/messages ──────→ moderation 初筛
  │   事务内：room 取 seq → message INSERT →
  │   user_seq 计数器批量 +1 读回（各接收者得 delivery_seq）→
  │   timeline 多值 INSERT 扇出（含 delivery_seq）→ outbox 事件
  │ ←── 200（roomId+seq+完整消息体）→ A 上屏
  │                         MQ 消费者消费 outbox：
  │                         查注册表 → B 在线
  │                         （A 排除，HTTP 响应已覆盖）
  │                         ──{MSG, roomId, seq, 全量payload}──→
  │                                            (roomId,seq) 判重 → 渲染
  │                                            未读数 = last_seq − 水位线（本地算）
  │ B 打开会话：REST 推水位线 ─→ 提交后推 {READ} 给其他在线成员（实时已读回执）
```

- **B 离线**：无推送，消费者跳过；B 下次启动/重连走 4.3 补拉，消息从 timeline 按 seq 到位。
- **撤回**：A 走 REST 改 message 终态 → 推 `{RECALL, roomId, seq}` 轻事件给在线成员；离线成员拉取时 message 状态字段自然呈现。
- **群聊**：同链路，扇出目标为全部成员的 timeline 行 + 在线成员的 MSG 推送（排除发送者）。

## 5. 参数汇总

| 参数 | 值 | 依据 |
|---|---|---|
| 心跳间隔（客户端 PING） | 25s | < nginx/云 LB 默认 60s 读超时（票 03 §2.1） |
| 服务端判死阈值 | 60s 无入站 | ≈2.4 个心跳周期，容忍丢一次心跳 |
| 票据有效期 / 次数 | 60s / 一次性 | RFC 6819 §4.6.7：短时 token 进 query 的泄漏面（票 03 §4.2） |
| 重连退避 | 1s 起 ×2，上限 30s，抖动 0.3~0.5 | Socket.IO 惯例；上限放宽适配后台页面（票 03 §2.2） |
| 互踢关闭码 | KICK 消息 + close(4001) | RFC 6455 私有段 4000~4999；MQTT 0x8E 同构（票 03 §3） |
| 被踢客户端 | 不自动重连 | 防两设备互踢死循环（票 03 §3.4） |
| 对齐游标 | delivery_seq（per-user 投递序号，user_seq 计数器扇出事务内取号） | per-user 单调 = 提交序，杜绝并发乱序漏拉（微信 SyncKey 同款设计） |

## 6. 推/拉分工边界（票面问题收口）

| 走推（加速路径，丢了不出错） | 永远靠拉（真相路径） |
|---|---|
| MSG 全量新消息 | 会话列表、未读数初值 |
| READ 水位线变更 | 历史消息、timeline 对齐/增量补拉 |
| RECALL 撤回事件 | 离线期间的一切 |
| KICK 互踢通知 | 成员水位线（离线成员的已读回执） |

原则：**推丢了不出错，拉才是真相**。推送只服务「在线成员的实时感」，任何一致性都由 REST 读路径 + (roomId, seq) 判重 + timeline 游标兜底。

## 7. 何时重估
