> 2026-09-09 grilling 定稿（一轮 + 收尾三小项）。审核口径沿用[票 05](../issues/05-group-rules.md)：chat 全路径零审核 + 举报兜底，本票不涉及审核。四表 DDL 归[票 02](../issues/02-ddl-prototype.md)，本文的字段设计是票 02 的输入。

## 1. 消息类型清单

| type | content 载荷 | ref 列 | 发送者 | 说明 |
|---|---|---|---|---|
| `TEXT` | 纯文本原文，≤500 字符 | — | 会话成员 | 默认类型，占绝对多数 |
| `IMAGE` | JSON `{"url","width","height"}` | — | 会话成员 | url 须本站上传域前缀；width/height 客户端上报、可缺省（前端兜底固定比例防布局抖动） |
| `CARD` | **空**（不做任何快照） | `ref_type` + `ref_id` 非空 | 会话成员 | 引用站内对象，实时渲染（§3） |
| `SYSTEM` | JSON `{"event",...}` + 服务端渲染好的文案 | — | 仅系统侧 | 票 05 四事件，见 §5 |

不在清单里的东西：撤回（message 行状态）、已读（room_user 水位线 + READ 事件）、踢人（KICK 事件）——全部不是消息类型。

## 2. 消息体结构（message 表口径，DDL 归票 02）

- `msg_type`：枚举列（TEXT/IMAGE/CARD/SYSTEM）。
- `content`：载荷列，语义按类型分（§1）；TEXT 保持裸文本可读可搜，不包 JSON 壳。
- `ref_type` / `ref_id`：独立可空列，仅 CARD 非空。ref 提列是因为它是结构化外键而非内容——跳转语义显式、可索引反查。
- 撤回三件套：`status`（NORMAL/RECALLED）+ `recalled_at` + `recalled_by`（§6）。
- **room.last_msg 列表预览文案规则**（发送时生成）：TEXT→原文；IMAGE→`[图片]`；CARD→类型标签 `[商品]`/`[帖子]`/`[跑腿卡片]`（不查标题，与实时渲染口径一致）；SYSTEM→渲染文案；消息被撤回后显示 `[已撤回]`。

## 3. 业务卡片（CARD）

- `ref_type`：`PRODUCT` / `POST` / `ERRAND`；`ref_id` 指向对应实体主键。
- **纯实时渲染**：客户端渲染时按 ref 实时取对象；对象已软删/下架/被拒 → 显示「该内容已失效或不可见」。消息表不冗余任何快照字段（价格改了显示新价，删了显示失效，无陈旧快照问题）。
- **发送时校验**：对象存在且未被删除/拒绝——
  - post：非 `DELETED`/`REJECTED`/`DRAFT`（PENDING_REVIEW 可发）；
  - product：非 `DELETED`/`REJECTED`（PENDING_REVIEW、ON_SALE、SOLD、LOCKED、草稿均可发——会话里发已售商品是正常场景）；
  - errand：非 `REJECTED`/`CANCELLED`（无删除态，终态 COMPLETED 可发）。
- 点击跳转时实时校验可见性，失效则提示，不跳转。
- 卡片实时渲染意味着举报快照与 last_msg 都拿不到卡片内容——分别以 ref 标识与类型标签代替（§7、§2）。

## 4. 图片（IMAGE）

- 上传复用既有 `POST /api/files/upload`（FileController → jpg/png/webp 白名单 + Content-Type 一致性 + 5MB → MinIO，URL 公开读），**链路一行不动**；chat 图片零审核（票 05）。
- **单条消息单张图**，多图拆多条消息发送（IM 惯例，避免 IMAGE 载荷发明数组结构）。
- 发送时校验 `url` 前缀必须为本站上传域（复用 FileStoragePort 的 publicUrl 配置），防塞外链。

## 5. 系统消息（SYSTEM）的载荷

event 枚举与票 05 四事件一一对应：

| event | JSON 附加字段 | 说明 |
|---|---|---|
| `GROUP_CREATED` | 群名 | 建群 |
| `MEMBER_JOINED` | 成员 userId | 成员加入 |
| `MEMBER_REMOVED` | 被移除成员 userId | 成员移除（被移除者不收此消息，票 05） |
| `SEALED` | — | 封盘 |

文案由服务端按 event 渲染成纯文本一并落 content（快照式，客户端零渲染逻辑）；event 枚举保留下发，供未来换文案不改历史。

## 6. 撤回机制

- **发送者自行撤回**：发送后 **2 分钟窗口**内可撤回（常量），1v1 与群一致；仅本人可撤自己的消息。
- **message 行状态**：`status`（NORMAL/RECALLED）+ `recalled_at`（撤回时间）+ `recalled_by`（`USER` 自行撤回 / `AUDITOR` 强制撤回，审计区分）。
- **语义（票 01 已定，落地口径）**：撤回占 seq 不回退、不动已读水位线、计入未读；RECALL 事件轻推 `(roomId, seq)` 定位（票 04 协议）。
- **content 库内保留**：撤回只改状态不删内容——强制撤回复用同一机制，取证直接查行；读路径（历史拉取、MSG 载荷、last_msg）一律按状态脱敏为「已撤回」空壳，content 不出服务端。

## 7. 举报与强制撤回落地

- **content_report 扩 `target_type=MESSAGE`**，其余一行不动：
  - 一人一消息一单：复用现有 `uk_reporter_target(reporter_id, target_type, target_id)`；
  - 举报者须为该会话成员（room_user 存在校验）；
  - **已撤回消息可举报**（追责留痕），处理时幂等；
  - `content_snapshot` 存消息 content（TEXT ≤500 字符、IMAGE/SYSTEM 为 JSON，均在 VARCHAR(1000) 内）；CARD 消息 content 为空，snapshot 存 ref 标识（如 `CARD:PRODUCT#123`）。
- **处理链路**：`ReportCase` 按 target_type 分支——MESSAGE 分支调 **chat 系统侧内部撤回 API**（chat 领域暴露的无归属校验撤回入口，`recalled_by=AUDITOR`，不受 2 分钟窗口限制），消息已 `RECALLED`（含发送者自行撤回）则跳过撤回、只落处理结论（票 05 幂等口径）；落 `PROCESSED`/`IGNORED` 同现有状态机；**不走扣分流水**（票 05：chat 消息无下架概念）；举报人/被举报人通知沿用既有 `REPORT_RESULT`。
