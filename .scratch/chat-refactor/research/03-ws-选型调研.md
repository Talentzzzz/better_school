## 1. 三种长连接方案的适用边界与取舍

### 1.1 裸 WebSocket（Spring 原生）

**协议事实（RFC 6455）**

- WebSocket 是在单条 TCP 连接上建立全双工双向通道，从 HTTP Upgrade 握手切换协议（101 Switching Protocols），此后同一 TCP 连接持续双向收发。
  来源：[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)、[Spring – WebSockets](https://docs.spring.io/spring-framework/reference/web/websocket.html)

**Spring 官方对「什么时候该用 WebSocket」的定位**

> "It is the combination of low latency, high frequency, and high volume that make the best case for the use of WebSocket."

即：**低延迟 + 高频 + 双向**是 WebSocket 的最佳情形；反之若只是低频刷新，官方建议轮询 / long polling 即可。IM 私信属于典型的低延迟+双向场景，命中 WebSocket 最佳情形。
来源：[Spring – WebSockets（When to Use WebSockets）](https://docs.spring.io/spring-framework/reference/web/websocket.html)

**Spring 同时明确：裸 WebSocket 只定义传输、不定义消息语义**

> "WebSocket is also a low-level transport protocol, which, unlike HTTP, does not prescribe any semantics to the content of messages. That means that there is no way to route or process a message unless the client and the server agree on message semantics."

这条"过于底层"的批评，对 IM 恰好不构成否决——IM 本来就要自定义消息协议（消息类型、业务卡片、ACK/序号、踢下线通知），无论选哪个方案这层协议都省不掉。
来源：同上

**Spring 提供的裸 WebSocket 服务端 API（覆盖自管注册表/互踢所需的一切钩子）**

- 服务端实现 `TextWebSocketHandler` / `BinaryWebSocketHandler`，通过 `@EnableWebSocket` + `WebSocketConfigurer` 映射到 URL；生命周期回调 `afterConnectionEstablished` / `afterConnectionClosed` 是天然的建连登记/断连注销钩子。
- `HandshakeInterceptor` 提供 handshake 前后拦截，"可阻止握手（preclude the handshake）"或向 `WebSocketSession` 的 attributes 塞入（认证后的）身份信息——这是握手鉴权的官方扩展点。
- 关键线程安全约束：**JSR-356 底层 session 不允许并发发送**，官方建议用 `ConcurrentWebSocketSessionDecorator` 包装 `WebSocketSession`（自管注册表向单用户推送时必须处理，否则并发写会抛异常）。
- 安全默认值：自 Spring Framework 4.1.5 起，WebSocket/SockJS **默认只接受同源（same-origin）请求**，可用 `setAllowedOrigins` 放开。
- 部署形态：与 Spring MVC 同进程，DispatcherServlet 同时服务 HTTP 握手与其它 HTTP 请求（跑在 Servlet 容器 Tomcat 上，容器自带 NIO 与连接管理）。
  来源：[Spring – WebSocket API（server）](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)

**容器层的兜底能力（Tomcat 10.1 实测文档）**

- Tomcat 默认整条消息缓冲 8192 字节（binary），可通过 `org.apache.tomcat.websocket.binaryBufferSize` / `textBufferSize` 调整 → **大图不适合走 WS 文本帧裸传，应 HTTP 上传对象存储后只传 URL**。
- Tomcat 支持按 session 设置读空闲超时（`org.apache.tomcat.websocket.READ_IDLE_TIMEOUT_MS`、`Session.setMaxIdleTimeout`）→ 服务端清理死连接有容器级钩子。
- 阻塞发送超时默认 20s（`BLOCKING_SEND_TIMEOUT`）。
  来源：[Tomcat 10.1 – WebSocket How-To](https://tomcat.apache.org/tomcat-10.1-doc/web-socket-howto.html)

### 1.2 STOMP over WebSocket

STOMP 是 Spring 官方推荐的 WebSocket 子协议（RFC 6455 的 `Sec-WebSocket-Protocol` 机制协商），帧结构仿 HTTP，核心语义是 **SEND / SUBSCRIBE / destination 的发布-订阅**。

Spring 列出的 STOMP 收益：无需发明自定义消息协议；@Controller 注解式路由；可接外部 broker（RabbitMQ/ActiveMQ）；可用 Spring Security 按 destination 保护消息。
来源：[Spring – STOMP Benefits](https://docs.spring.io/spring-framework/reference/web/websocket/stomp/benefits.html)

**但 STOMP 对 IM 有一个结构性错配——服务器不能主动发消息：**

> "A server cannot send unsolicited messages. All messages from a server must be in response to a specific client subscription, and the subscription header of the server message must match the id header of the client subscription."

IM 的控制面需求（单设备互踢通知、系统通知、按 seq 对齐的推送）本质是"服务器主导的点对点推送"，不是 pub/sub 订阅模型；强行套 STOMP 需要先建订阅、维护 user destination 与 session 映射，再叠加 Spring Security 的 CONNECT CSRF（"Any inbound CONNECT message requires a valid CSRF token"）与 destination 授权规则——**为省掉一个自定义 JSON 协议，引入一整层消息代理抽象**。
来源：[Spring – STOMP Overview](https://docs.spring.io/spring-framework/reference/web/websocket/stomp/overview.html)、[Spring Security – WebSocket Security](https://docs.spring.io/spring-security/reference/servlet/integrations/websocket.html)

### 1.3 Netty

Netty 的自我定位：

> "Netty is an asynchronous event-driven network application framework for rapid development of maintainable high performance protocol servers & clients."

Netty 解决的是"自定义传输层协议 + 超大并发连接"级别的问题（官方举例：FTP/SMTP 类协议服务器）。而 Spring WebSocket 本身已跑在 Servlet 容器上，容器已经处理了 NIO、连接升级与线程模型；引入 Netty 意味着在 Spring Boot 单体里**另起一套脱离 Servlet 栈的传输层**（独立端口/事件循环/自管生命周期），Spring Security 过滤器链、事务、`DispatcherServlet` 生态全部要手工桥接。对校园规模的单体应用，这些复杂度换不来收益。
来源：[netty.io](https://netty.io/)、[Spring – WebSocket API（Deployment）](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)

### 1.4 SSE（Server-Sent Events）

- SSE 是**服务器到客户端的单向**事件流：响应 MIME 类型为 `text/event-stream`，事件以文本块发送；浏览器端用 `EventSource` 接收。
- 内建断线重连：事件可带 `retry` 字段指定重连间隔，"If the connection to the server is lost, the browser will wait for the specified time before attempting to reconnect"；`id` 字段配合 `Last-Event-ID` 请求头可做断点续传。
- 连接数限制：HTTP/1.1 下浏览器对同域连接数有限制（经典为 6），HTTP/2 下由服务端协商（默认 100 streams）。
  来源：[MDN – Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

**结构性缺失**：SSE 无法承载 客户端→服务器 方向的任何消息（上行要走另一条 HTTP 通道，自行拼装"下行 SSE + 上行 REST"的双通道架构），也没有连接级双向心跳与互踢语义；适合做轻量单向通知（如审核结果推送），**不适合做 IM 主通道**。

### 1.5 取舍对照表

| 维度 | 裸 WebSocket | STOMP over WS | Netty | SSE |
|---|---|---|---|---|
| 双向通信 | 是 | 是 | 是 | 否（仅下行） |
| 消息协议 | 自定义（IM 本就需要） | STOMP pub/sub | 全自定义 | 事件流 |
| 服务器主动推送/踢人 | 直接（注册表直查） | 须先有订阅，绕 | 直接 | 直接（单向） |
| Spring 生态集成 | 完整（同进程/同过滤器链） | 完整但配置多（CSRF/destination 授权） | 全部手工桥接 | 完整（SseEmitter） |
| 运维/代码复杂度 | 低 | 中 | 高 | 低 |
| 适合规模 | 小~中单体 | 中大型 + 需要 broker | 超大并发/自定义传输 | 单向通知 |

## 2. 移动端 Web 的心跳与断线重连惯例

### 2.1 心跳

**协议层 Ping/Pong（RFC 6455）**

- Ping 帧 opcode 0x9、Pong 帧 0xA；"Upon receipt of a Ping frame, an endpoint MUST send a Pong frame in response"；"A Ping frame may serve either as a keepalive or as a means to verify that the remote endpoint is still responsive"；Pong 可主动发送，"serves as a unidirectional heartbeat"。
- **浏览器侧约束**：浏览器 JS 的 WebSocket 构造器只有 URL 与子协议两个参数（见 §4），不提供发送协议层控制帧的接口——所以**客户端主动心跳的通行做法是应用层心跳**（MDN 官方 WebSocket 客户端指南的示例即是应用层 ping：客户端每秒发一条 `"ping"` 文本消息、服务器回 `"pong"`；该 1 秒仅为演示值，非建议间隔）。
  来源：[RFC 6455 §5.5.2/§5.5.3](https://www.rfc-editor.org/rfc/rfc6455#section-5.5.2)、[MDN – WebSocket() constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)、[MDN – Writing WebSocket client applications](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_client_applications)、[MDN – Writing WebSocket servers（Pings and Pongs）](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers)

**间隔取值的现实下限：中间层静默超时**

- nginx 反向代理 `proxy_read_timeout` **默认 60s**："If the proxied server does not transmit anything within this time, the connection is closed." —— 空闲连接会被中间层静默掐断，这是心跳间隔必须显著小于 60s 的最常见原因（自建 nginx、云 LB 均同构）。
- 业界事实标准参考：Socket.IO（v4 官方文档）默认引擎层心跳 `pingInterval = 25000ms`、`pingTimeout = 20000ms`——服务器每 25s ping 一次，20s 内未收到 pong 判定连接死亡。
  来源：[nginx – ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)、[Socket.IO – Server Options](https://socket.io/docs/v4/server-options/)

**惯例结论**：客户端应用层心跳 25~30s（落在常见代理 60s 读超时之内）；服务器以 2 个心跳周期（约 60s）未收到任何消息判死并清理；服务端可叠加 Tomcat `READ_IDLE_TIMEOUT_MS` 兜底（见 §1.1）。

### 2.2 重连退避

Socket.IO 官方客户端默认值是业界最广泛引用的重连惯例：

- `reconnectionDelay = 1000ms`（初始延迟）、每次尝试 **×2**、`reconnectionDelayMax = 5000ms`（上限）；
- `randomizationFactor = 0.5`（抖动因子）——官方说明其目的："so that the clients do not reconnect at the exact same time after a server crash"（**防服务端恢复瞬间的重连惊群**）。
  来源：[Socket.IO – Client Options](https://socket.io/docs/v4/client-options/)

**惯例结论**：指数退避 1s 起步、×2 增长、上限 30~60s（Socket.IO 的 5s 上限偏激进，适合常驻页面；IM 页面常在后台，放宽上限更省电省连接），叠加 0.3~0.5 随机抖动；页面 `visibilitychange`/网络恢复时立即触发一次重连是常见补充。

### 2.3 重连后的对齐动作

Socket.IO 官方的「Connection state recovery」章节给出了工程边界（值得整段引用）：

> "Under real conditions, a Socket.IO client will inevitably experience temporary disconnections… please be aware that the recovery will not always be successful. That's why you will still need to handle the case where the states of the client and the server must be synchronized."

即：服务器在断线窗口内暂存会话状态与错过的包，重连时尝试恢复（`maxDisconnectionDuration` 有上限且官方明确"不要设成 Infinity"），**恢复失败时客户端仍必须做全量状态对齐**。
来源：[Socket.IO – Connection state recovery](https://socket.io/docs/v4/connection-state-recovery)

**惯例结论**：重连成功后客户端携带本地已收位点（每会话 lastSeq）请求增量补齐；位点超出服务器保留窗口/时间线被截断时，降级为全量拉取（会话列表 + 未读 + 最近消息）。这与本项目票 01/票 07 的时间线模型与可靠性设计正好对接——WS 层只管"在线推"，对齐走"离线拉"的既有 HTTP 读路径。

## 3. 同账号单设备互踢的常见实现

### 3.1 协议层先例：MQTT 的「Session taken over」

同身份只允许一条连接、新连接踢旧连接，在 IoT 领域是被协议规范化的，MQTT 5.0 §3.1.4 原文：

> "If the ClientID represents a Client already connected to the Server, the Server sends a DISCONNECT packet to the existing Client with Reason Code of 0x8E (Session taken over) … and MUST close the Network Connection of the existing Client. [MQTT-3.1.4-3]"

规范化的互踢三步：**① 以身份为键唯一登记 → ② 给旧连接发一个"会话被接管"的通知（0x8E 专用码）→ ③ 关闭旧连接**。这是"踢下线消息协议"的行业标准形态。
来源：[OASIS MQTT 5.0 spec §3.1.4](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)（Reason Code 0x8E 见 §2.4.1 表格，仅可用于 DISCONNECT）

### 3.2 服务端连接注册表

- 单机部署的标准结构：`ConcurrentHashMap<userId, WebSocketSession>`（并发建连/断连/推送同键操作，必须线程安全容器）；`afterConnectionEstablished` 登记、`afterConnectionClosed` 注销；单机即完整，只有集群部署才需要把 userId→节点 路由外置（Redis pub/sub 等）——**本项目单机运行，内存注册表即终态**。
- 竞态要点（工程惯例）：新连接**先占位注册**，再异步关闭旧会话；旧会话的 `afterConnectionClosed` 回调里必须校验"待注销的 session 是否仍是注册表当前值"（`map.remove(userId, oldSession)` 语义），否则旧连接的迟到的 close 事件会把新连接误删。
- 推送侧配合 `ConcurrentWebSocketSessionDecorator` 串行化对同一 session 的并发写（JSR-356 不允许并发 send，见 §1.1）。
  来源：[Spring – WebSocket API](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)；注册表形态另见社区通行实现（如 [RuoYi-Plus WebSocket 会话管理](https://plus-doc.dromara.org/#/practices/features/message-push)）

### 3.3 踢下线消息协议

- **先发应用层 KICK 消息，再关连接**——不能指望 Close 帧的 reason 字段承载 UI 信息：RFC 6455 §5.5.1 明确 "clients MUST NOT show it to end users"（且 reason 不保证可靠送达）。
- **Close code 用 4000~4999 私有段**：RFC 6455 §7.4.2 "4000-4999 … are reserved for private use … can be used by prior agreements between WebSocket applications"（如自定义 4001=KICKED）。1008（policy violation）是通用兜底。
  来源：[RFC 6455 §5.5.1](https://www.rfc-editor.org/rfc/rfc6455#section-5.5.1)、[RFC 6455 §7.4.2](https://www.rfc-editor.org/rfc/rfc6455#section-7.4.2)
- 消息形态参照 MQTT：`{type:"KICK", reason:"SESSION_TAKEN_OVER"}` + `close(4001)`，与 0x8E (Session taken over) 同构。

### 3.4 客户端被踢后的处理

商业 IM SDK 的官方惯例（两家头部厂商口径一致）：

- **腾讯云 IM**：Web 端默认不支持多实例登录，同账号在他处登录会触发 `KICKED_OUT` 事件（细分 `KICKED_OUT_MULT_ACCOUNT` / `KICKED_OUT_MULT_DEVICE` / `KICKED_OUT_USERSIG_EXPIRED` / `KICKED_OUT_REST_API`）；官方建议监听该事件后**提示用户并跳转登录页**，重新 login 会反过来踢掉对方。离线互踢无感知，下次登录返回错误码 **6208**（ERR_IMSDK_KICKED_BY_OTHERS），由用户确认是否踢回。
- **融云**：连接状态监听暴露 `KICKED_OFFLINE_BY_OTHER_CLIENT`（"用户账号在其它设备登录，此设备被踢下线"），客户端据此提示。
  来源：[腾讯云 IM Web SDK – EVENT](https://web.sdk.qcloud.com/im/doc/v3/zh-cn/SDK.html)、[腾讯云 IM – 状态变更回调](https://cloud.tencent.com/document/product/269/2570)、[融云 – 连接状态](https://docs.rongcloud.cn/android-imlib/connection/monitor-status)

**惯例结论**：客户端收到 KICK/4xxx 踢码后**必须停止自动重连**（否则两台设备互踢死循环），展示"账号已在别处登录"UI，由用户操作（重新登录/回登录页）后再次建连。这与 §2.2 的自动重连互斥：自动重连只服务"网络断"，不服务"被踢"。

### 3.5 Web 多 tab 的特有边界

浏览器同一账号开多个 tab = 多条并发连接。单设备策略下，打开第二个 tab 会踢掉第一个 tab。腾讯 IM 将「Web 端可同时在线个数」做成控制台配置项正是为此。本项目需在产品层明确：接受"Web 内多 tab 互踢"，并在 KICK 消息 reason 中注明，避免用户误以为被盗号。
来源：[腾讯云 IM Web SDK – 登录设置说明](https://web.sdk.qcloud.com/im/doc/v3/zh-cn/SDK.html)

## 4. 握手阶段认证：query string vs header vs Sec-WebSocket-Protocol

### 4.1 三个硬事实

1. **浏览器 WebSocket 无法携带自定义 header**：`new WebSocket(url, protocols)` 仅接受 URL 与子协议两个参数（MDN）→ "JWT 放 Authorization header" 这条 REST 惯例在浏览器 WS 握手上**根本做不到**。本项目 REST 现行 `Authorization: Bearer` 机制无法直接复用于 WS 握手。
   来源：[MDN – WebSocket() constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)；本项目现状见 `backend/bs-infrastructure/.../JwtAuthenticationFilter.java`
2. **协议本身不规定握手认证方式**：RFC 6455 §10.5 "This protocol doesn't prescribe any particular way that servers can authenticate clients during the WebSocket handshake. The WebSocket server can use any client authentication mechanism available to a generic HTTP server, such as cookies, HTTP authentication, or TLS authentication."
   来源：[RFC 6455 §10.5](https://www.rfc-editor.org/rfc/rfc6455#section-10.5)
3. **WS 握手就是 HTTP 请求，认证信息可从 HTTP 层移交**：Spring Security "WebSockets reuse the same authentication information that is found in the HTTP request when the WebSocket connection was made. This means that the Principal on the HttpServletRequest will be handed off to WebSockets." Spring 侧扩展点是 `HandshakeInterceptor`（可拒绝握手、注入身份到 session attributes，见 §1.1）。
   来源：[Spring Security – WebSocket Security](https://docs.spring.io/spring-security/reference/servlet/integrations/websocket.html)、[Spring – WebSocket API](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)

### 4.2 三种方式的惯例与安全坑

| 方式 | 惯例 | 安全坑 | 缓解 |
|---|---|---|---|
| **Query string**（`/ws?token=…`） | 浏览器下最普遍的现实做法 | RFC 6819 §4.6.7 原文："If access tokens are sent via URI query parameters, such tokens may leak to log files and the HTTP referer."（服务器访问日志、代理日志、浏览器历史、Referer） | **只放短时效一次性票据，不放长效 JWT**；websocket.org 官方指南建议 query 参数中只用 5~15 分钟短时 token |
| **Sec-WebSocket-Protocol** | 把 token 当"伪子协议"塞进候选列表，服务端识别后剔除再协商 | 该头语义是子协议协商：服务端必须回显所选子协议、浏览器校验返回值必须来自请求列表（RFC 6455 §11.3.4）；塞 token 属于 hack，需自定义协商逻辑，且部分中间代理对多值子协议头处理不佳 | 一般不推荐；仅在既不能用 cookie 又要避开 URL 泄漏时考虑 |
| **Cookie / Session** | 同源部署下的 Spring 默认模型（握手自动带 cookie，Principal 自动移交） | CSRF 面（STOMP 场景 Spring Security 强制 CONNECT 带 CSRF token）；本项目 REST 为无 cookie 的 JWT，需引入 cookie 通道 | 同源 + SameSite + Origin 校验（Spring 默认同源） |

另：**首消息认证**（连接建立后第一条消息带 token）无泄漏面，但认证前连接已占用、失败连接都消耗一次 HTTP 升级，通常作为 fallback。
来源：[RFC 6819 §4.6.7](https://www.rfc-editor.org/rfc/rfc6819#section-4.6.7)、[websocket.org – WebSocket Authentication](https://websocket.org/guides/authentication/)、[RFC 6455 §11.3.4](https://www.rfc-editor.org/rfc/rfc6455#section-11.3.4)

### 4.3 JWT 与长连接生命周期

握手时认证一次、连接存续期内持续有效，是 Spring 的默认模型（STOMP 认证文档："The user is authenticated at the HTTP request level … and results in a user header being stamped on every Message"）——**连接的有效期不随 JWT 过期自动续期**。通行做法：握手票据换取"会话级"信任，token 过期问题交由连接本身的生命周期管理（服务端心跳判死 + 客户端重连时重新走握手认证）。
来源：[Spring – STOMP Authentication](https://docs.spring.io/spring-framework/reference/web/websocket/stomp/authentication.html)

## 5. 对本项目的推荐

**选 Spring 原生裸 WebSocket + 自定义 JSON 信封协议 + 自管连接注册表**；不选 STOMP、Netty、SSE 作为 IM 主通道。

理由：

1. **需求形态命中**：1v1+群聊、在线推送、单设备在线是"低延迟 + 双向 + 服务端主导推送"，官方口径下的 WebSocket 最佳情形；且单机部署使内存注册表成立——这是一般 IM 架构里"连接路由层"被整个消掉的最大简化红利。
2. **STOMP 的收益用不上、成本绕不开**：IM 协议（文本/图片/卡片、ACK/seq、KICK）本就自定义，STOMP 的 destination pub-sub 帮不上；而"服务器不能未经订阅主动发消息"、CONNECT CSRF、destination 授权、（可选的）外部 broker 都是纯增量复杂度。自管注册表 + 互踢在裸 WebSocket 上只是 `ConcurrentHashMap` + 建连/断连两个钩子 + 一条 KICK 消息——**"裸 WebSocket 对自管连接注册表/互踢更直接"这一判断成立**。
3. **Netty 越界**：解决的是超大并发/自定义传输层，单体校园应用无此规模，且脱离 Servlet 栈损失 Spring 集成。
4. **SSE 单向**：承载不了上行与互踢，只能做未来单向通知的备选。

**连接层参数落点（供票 04 定稿）**：

- 协议：JSON 信封 `{type, seq, roomId, payload}`；图片/卡片走 HTTP 上传对象存储，WS 只传 URL/结构化卡片（Tomcat 默认 8KB 消息缓冲）。
- 心跳：客户端应用层 PING 25~30s（< nginx 默认 60s 读超时）；服务器 2 周期无消息判死清理（可叠加 Tomcat `READ_IDLE_TIMEOUT_MS`）。
- 踢人：新连接先占位 `map.put(userId, newSession)` → 旧 session 发 `{type:"KICK"}` → `close(4001)`；close 回调用 `remove(userId, oldSession)` 防误删；客户端见 4xxx 踢码**不自动重连**。
- 重连：1s 起指数退避 ×2、上限 30~60s、抖动 0.3~0.5；`visibilitychange`/网络恢复立即重试。
- 对齐：重连后按每会话 lastSeq 增量拉缺口，超窗口走全量 REST（对接票 07 可靠性设计）。
- 认证：新增 `POST /api/chat/ws-ticket`（鉴权后签发 60s 一次性 ticket）→ WS `?ticket=…` 握手 → `HandshakeInterceptor` 校验并消费（一次性）→ 身份写入 session attributes；失败拒绝握手。避免长效 JWT 进 URL 日志。
- 多 tab：明确 Web 同账号多 tab 互踢语义并写入 KICK reason。

**何时需要重估本结论**：未来真要水平扩容（注册表需外置为 userId→节点路由 + 跨节点推送），或出现数万级长连接与定制传输需求 → 再评估 Netty/独立网关；产品升级为大规模多端订阅广播（在线状态广播给大量联系人）→ STOMP + broker 才开始有意义。
