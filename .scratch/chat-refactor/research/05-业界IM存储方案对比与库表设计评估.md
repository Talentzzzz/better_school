# 票 05 调研：业界 IM 存储方案对比与本项目 chat 库表设计评估

> 2026-10-31 调研定稿。调研对象：OpenIM、微信（公开分享）、WhatsApp、Signal-Server、野火 IM、Turms、腾讯云 IM 产品文档、阿里云 Tablestore Timeline（IM 存储的经典工程论述）、52im 经典文章。每个论断尽量回溯一手来源（源码/官方文档），拿不准的标「二手来源」。评估对象是本项目 1v1-only 的六张表（room / direct_room_pair / room_member / message / timeline / user_seq）。

## 0. 结论速览（针对三个争议点）

| # | 争议点 | 结论 |
|---|---|---|
| ① | timeline 写扩散（每消息 2 行）对 1v1-only 是否过度设计 | **没问题，有取舍但合理**。业界两条路线并存（OpenIM/Turms 读扩散 vs 野火/Signal/Tablestore 写扩散），本项目「内容一份 + 收件人一行索引」的形态与野火 `t_messages`+`t_user_messages`、Tablestore「存储库+同步库」**同构**，且是 delivery_seq 单游标断线补拉的物质基础 |
| ② | 分库后发消息事务跨 3 片 | **当前单库没问题；分库预案必须改写为最终一致**。业界无一例跨片强一致事务：OpenIM 是异步流水线、微信靠 seqsvr+同步协议、Signal 逐条 Put、Tablestore 1+N 分库写。现有表结构（timeline 只插不改、uk 判重、delivery_seq 游标）恰好是最终一致化所需的全部材料 |
| ③ | 会话列表排序键 last_msg_at 在 room 行（会话维度） | **有偏离，算问题，建议修**。主流做法是用户维度维护会话列表（OpenIM Conversation(OwnerUserID,…)、野火 user_messages 会话索引、腾讯云 recentcontact、Tablestore per-user 同步队列）。低成本修法：把 last_msg_at/preview 冗余进 room_member（与 room 同片，分库后仍可同事务更新） |

## 1. OpenIM（github.com/OpenIMSDK/Open-IM-Server）

**核心设计：读扩散（消息按会话存一份）+ 用户维度水位线（userMinSeq/userMaxSeq/hasReadSeq）。**

1. **读写扩散**：消息表以会话为单位存一份，不做收件箱扩散；用户侧只有「序号水位线」（`seqUser`：每 (conversationID, userID) 的 max/min/read seq，存 Redis + Mongo 落盘）。1v1 与群聊同一套模型（群聊多一个 userMinSeq 用于新成员/被踢成员的可见范围截断）。
   - 来源（一手，源码）：`pkg/common/storage/controller/msg.go`（`GetMsgBySeqsRange`/`GetMsgBySeqs` 中 minSeq = max(会话 minSeq, userMinSeq) 的收敛逻辑）。
2. **消息表模型**（MongoDB）：`MsgDataModel`（表名 `msg`）字段含 SendID/RecvID/GroupID/ClientMsgID/ServerMsgID/**Seq**/Content/Status/IsRead 等；以 `MsgDocModel`（`doc_id` = `conversationID:seqSuffix`，`seqSuffix = (seq-1)/100`）**每 100 条 seq 聚成一个文档**存储，读时按 index 定位。
   - 来源（一手，源码）：`pkg/common/storage/model/msg.go`（`GetDocID`、`singleGocMsgNum = 100`、`MsgTableName = "msg"`）。
3. **seq 生成**：**per-conversation seq，Redis 号段批量分配**。msgtransfer 落库前调 `seqConversation.Malloc(conversationID, n)`；Redis 内实现 `malloc()`（批量预留、CAS setSeq 重试），Redis 缺席时回落到 Mongo `Malloc`（原子 `$inc`）按步长取段；消息序号 = 分配到的段起点+i。
   - 来源（一手，源码）：`pkg/common/storage/controller/msg_transfer.go`（`BatchInsertChat2Cache`：`Malloc` 后 `m.Seq = currentMaxSeq++`）；`pkg/common/storage/cache/redis/seq_conversation.go`（`malloc`/`setSeqRetry`/`mallocTime` 回落 Mongo）。
4. **1v1 会话 ID 生成**：`GenConversationIDForSingle(sendID, recvID) = "si_" + sort(sendID, recvID).join("_")`——**与本项目 direct_room_pair 的 user_min/user_max 完全同构**；另有 `GenConversationUniqueKeyForSingle` 返回排序后的纯键用于查重。
   - 来源（一手，源码）：`pkg/util/conversationutil/conversationutil.go`。
5. **会话列表**：**用户维度表**。`Conversation{OwnerUserID, ConversationID, ConversationType, RecvMsgOpt, IsPinned, MaxSeq, MinSeq, …}`——每个用户每个会话一行（没有 last_msg 预览字段，最后一条消息由 `GetLastMessage` 按会话现查）；已读水位 `hasReadSeq` 存 `seqUser`（Redis 优先、落 Mongo）。
   - 来源（一手，源码）：`pkg/common/storage/model/conversation.go`；`pkg/common/storage/controller/msg.go`（`GetLastMessage`/`SetHasReadSeq`）。
6. **分库分表/跨片事务**：MongoDB 分片集群，消息按 docID 前缀（会话）天然分片；**发送链路不是单事务**——msggateway 收消息 → msgtransfer `BatchInsertChat2Cache`（Redis 取号+缓存）→ MQ → `BatchInsertChat2DB`（Mongo 插入）→ push，每段独立，失败靠客户端按 seq 补拉对账。
   - 来源（一手，源码 + 架构文章）：上述源码文件；[开源OpenIM：高性能、可伸缩、易扩展的即时通讯架构（腾讯云社区）](https://cloud.tencent.com/developer/article/1853605)、[OpenIM 客户端SDK架构剖析——确保消息的有序性（知乎）](https://zhuanlan.zhihu.com/p/469590316)（seq 连续性判定 + 缺口触发拉取）。

## 2. 微信（公开技术分享）

**核心设计：per-user 单调 seq（seqsvr）+ 按用户分库的消息索引 + 「带本地最大版本号增量拉取」的同步协议。服务端无跨用户强一致事务。**

1. **读写扩散**：公开一手资料不直接给出消息表扩散方式。52im 转述微信后台团队分享认为**群聊是写扩散**；单聊按「收发双方各自的用户索引」组织（索引写扩散、内容一份）。**此条为二手来源/传闻**（[52im thread-1616](https://www.52im.net/thread-1616-1-1.html)）。
2. **索引表/分片**：广泛流传的描述是 msgInfo 索引表（uid、seq、msgId、时间、内容指针）**以 uin 为 sharding key 按用户分库分表**，消息正文与索引分离存 KV。**二手来源**（源自《微信后台存储架构》分享的转述，未找到公开原始 PPT）。
3. **seq 生成**：**per-user 64 位 seq，不要求连续只要求递增不回退**。seqsvr 内核是「每用户一格的巨大数组」：内存 `cur_seq++`，超过 `max_seq` 就把上限按**步长 10000** 提升并持久化（号段模式，把磁盘 IO 从 ~10^7 QPS 降到 ~10^3）；相邻 10 万 uid 共享一个 Section 的 max_seq；AllocSvr 按号段分 Set，容灾切换用租约保证新旧不重叠（否则「消息消失/数据错乱」）。同步时客户端带「已同步的最大版本号」，后台对比出增量。
   - 来源（一手，官方技术文章）：[微信序列号生成器架构设计及演变（InfoQ）](https://www.infoq.cn/article/wechat-serial-number-generator-architecture)。
4. **会话列表/未读**：靠客户端本地（聊天记录与列表在终端 SQLite/本地库），服务端只保证 seq 同步。**二手来源**（多篇架构综述一致）。
5. **分库与跨片**：存储按 set 单元化、按 uid 分片；收发双方索引在不同分片意味着**发消息天生不可能单事务**，正确性由「seq 单调 + 异步可靠投递 + 客户端增量同步兜底」保证。
   - 来源：[从无到有：微信后台系统的演进之路（InfoQ，2016）](https://www.infoq.cn/article/yaogongzian-from-scratch-the-evolution-of-wechat)（二手转述）；seqsvr 一手文章同上。

## 3. WhatsApp（公开架构资料）

**核心设计：服务器只做「待投递队列」，不存历史。**

1. **读写扩散**：写扩散的极端形态——消息以**收件人队列**形式暂存，**送达即删**；历史记录全在客户端 SQLite。
2. **存储**：Erlang/OTP + **Mnesia 内存库**（~2TB 内存、16 分片、~180 亿条记录，存会话/路由/离线队列）；服务端不持久化聊天内容。
3. **seq**：无公开的类 seq 机制；离线投递靠队列 + ack。
4. **会话列表/未读**：服务端不管，客户端本地。
5. **分库**：Mnesia 按节点分片；无跨片事务（送达即删的队列语义不需要）。
   - 来源（二手，但为公认最接近一手的公开整理）：[How WhatsApp Grew to Nearly 500 Million Users, 11,000 Cores, 2 Million Connections, and 50 Engineers on One System (High Scalability, 2014)](https://highscalability.com/how-whatsapp-grew-to-nearly-500-million-users-11000-cores-an)。

## 4. Signal-Server（github.com/signalapp/Signal-Server）

**核心设计：DynamoDB per-device 收件箱队列，纯投递语义，无服务端会话历史。**

1. **读写扩散**：**写扩散，且扩散到设备级**——每个收件人的每台设备一份 Envelope（partition key = 目标账号 UUID + 设备 ID），客户端 ACK 后逐条删除；消息 TTL 到期自动清（时长由配置注入，社区默认 30 天）。**没有 seq**：排序键 = `serverTimestamp + messageUuid` 拼接的 24 字节；拉取 = 整队列 Query（强一致读），删除按 key 逐条。
   - 来源（一手，源码）：`service/src/main/java/org/whispersystems/textsecuregcm/storage/MessagesDynamoDb.java`（`KEY_PARTITION="H"`、`KEY_SORT="S"`、`convertPartitionKey(accountUuid, device)`、`getTtlForMessage`、`deleteMessage`）。
2. **会话列表/未读**：服务端不存（客户端本地）。`mayHaveMessages` 只判「队列是否还有未取消息」。
3. **分库/跨片事务**：每条消息一次独立 `PutRequest` 批量写，**不存在跨片事务问题**；发送方侧无持久化（TLS 终止即忘）。
4. **对本项目的镜像意义**：Signal 证明「每收件人一行 + 游标/队列拉取 + 到期清理」是自洽的收件箱设计，代价是没有漫游历史（历史靠端上备份）。本项目 timeline 的 uk_user_delivery + delivery_seq 补拉上限（200/500）本质是同一语义的 MySQL 版。

## 5. 野火 IM（github.com/wildfirechat/server，wildfirechat 分支）

**核心设计：内容一份 + 每收件人一行索引（索引写扩散），外置 MySQL 时索引表按用户哈希分 128 张表。与本项目结构最接近的系统。**

1. **表模型**（一手，flyway 迁移脚本 `broker/migrate/h2/V3__create_sharding_table.sql` 及后续）：
   ```sql
   CREATE TABLE t_messages (            -- 内容，一份
     id AUTO_INCREMENT PK,
     _mid bigint NOT NULL,              -- 消息 ID（唯一索引 message_uid_index）
     _from, _type, _target, _line, _data BLOB, _dt,
     -- V43: INDEX messages_conv_index (_type, _target, _line)  会话维度取历史
   );
   CREATE TABLE t_user_messages (       -- 索引，每收件人一行（写扩散）
     id AUTO_INCREMENT PK,
     _mid bigint, _uid, _seq bigint, _dt,
     UNIQUE INDEX message_seq_uid_index (_uid DESC, _seq DESC),
     -- V26: +_line, INDEX (_uid,_line,_mid)
     -- V38: +_type/_target/_directing, INDEX user_messages_conv_index (_uid,_type,_target,_line,_mid desc)
   );
   ```
   - 消息实体不复制，**扩散的只是 (uid, seq, mid, 会话定位) 索引行**——正是 52im 经典文里「消息实体存一份，用户只冗余消息 ID」的方案（见 §8）。
2. **seq**：`t_user_messages._seq`，唯一键 (uid, seq)，即**用户维度唯一递增**；消息 ID `_mid` 由 `t_id_generator` 表生成（`V2__create_table.sql`）。
3. **会话列表**：从 `user_messages_conv_index (_uid, _type, _target, _line, _mid desc)` 直接可查「某用户的某会话最新消息」——**用户维度的会话列表由索引表派生**，不需要单独冗余 room 行。
4. **分库分表**（一手，源码 `broker/src/main/java/io/moquette/persistence/DatabaseStore.java`）：
   ```java
   private String getUserMessageTable(String uid) {
       if (DBUtil.IsEmbedDB) return "t_user_messages";
       int hashId = Math.abs(uid.hashCode()) % 128;
       return "t_user_messages_" + hashId;   // 外置 MySQL：按 uid 哈希分 128 张表
   }
   ```
   内容表 `t_messages` 不分片（mid 全局唯一即可查）。写入 = 内容表 1 行 + 各收件人索引表各 1 行，靠同库事务（或接受短暂不一致 + 客户端拉取）。
5. **清理**：用户消息队列有上限语义（`select … order by _seq desc limit MAX_MESSAGE_QUEUE`，DatabaseStore.java:76）。

## 6. Turms（github.com/turms-im/turms）

**核心设计：官方明确「基于读扩散（fanout read）」建模，MongoDB 分片集群，默认按时间冷热分离。**

1. **读写扩散**：官方 README/文档明示 fanout-read inbox + push/pull/push-pull 感知。
   - 来源（一手）：[turms-im/docs](https://github.com/turms-im/turms)、[Turms Documentation](https://turms-im.github.io/docs/)。
2. **消息 schema 与分片**：message 是唯一支持冷热分离的模型——默认索引「发送时间+收件人 ID」、**shard key = 发送时间**（不同时间段 Zone 分到不同 Shard）；不需要冷热分离时反过来：索引「收件人 ID+发送时间」、**shard key = 收件人 ID**（同一收件人的消息尽量同 Chunk）。私聊不索引发送者（可选索引 `turms.service.mongo.message.optional-index.message.sender-id` 因要两次查询被官方认为太低效）。
   - 来源（一手，官方文档）：[Collection Schema Design](https://turms-im.github.io/docs/design/schema.html)。
3. **会话 ID**：私聊 conversation id = 16 字节（发送者 ID+接收者 ID 拼接），群聊 = 群 ID。同 OpenIM 一样是「对端拼接」而非随机业务键。
4. **seq**：没有暴露 OpenIM 式连续 seq；同步靠「客户端按时间区间拉取、服务端补默认区间」避免重复拉取（同文档）。分片方案详见 [架构设计](https://turms-im.github.io/docs/design/architecture.html)（依赖 mongos 路由）。

## 7. 腾讯云 IM（产品文档，一手）

**核心设计：服务端按会话存历史（可付费延长），群 seq 服务端按群严格递增，单聊 msgSeq 客户端域。**

1. **消息标识**（[消息相关问题 FAQ](https://cloud.tencent.com/document/product/269/32486)）：客户端 `msg_id = tinyid-clientTime-random`；服务端单聊 `msgKey = clientSeq_random_serverTime`；**服务端群聊 = 群 ID + msgSeq 唯一标识**。发送幂等靠去重 Key（有效期 120 秒）——与本项目 `uk_room_client(room_id, client_msg_id)` 同语义。
2. **seq**（[单发单聊消息 REST API](https://cloud.tencent.com/document/product/269/2282)）：**群聊 MsgSeq 由后台按群生成、从 1 起严格递增**；**单聊 MsgSeq 由调用方填**（不填填随机数，禁止 0，建议递增），「单聊历史先按时间排序、同秒内按 MsgSeq 排序」——即**单聊并不保证会话内严格连续 seq**，排序 = 时间 + msgSeq。
3. **存储与清理**：云端历史消息体验/专业版默认 7 天、旗舰版 30 天，可付费延长至 360 天；未读消息每用户最多保存 250 个单聊会话。
4. **会话列表**：服务端 per-user 的 recentcontact（`v4/recentcontact/get_list`），会话对象携带 lastMessage 与已读 Sequence/时间戳，未读 = 比较 lastMessage seq 与已读 seq。
5. **分库**：闭源无公开资料（标注：未查到）。

## 8. 国内工程实践经典论述

- **52im/沈剑（58 同城）**《IM 群聊消息究竟是存 1 份（扩散读）还是存多份（扩散写）？》：给出四步演进——①只存离线（丢消息，否决）→ ②所有收件人各存一份 → ③**内容一份 + 用户只冗余消息 ID**（`group_msgs(msgid,…)` + `user_msgs(uid, msgid)`）→ ④终极方案：**利用消息偏序性，用户只存 last_ack_msgid 水位线，索引行都省掉**（读扩散）。文中并转述微信后台分享认为微信群聊实际是②式写扩散。
  - 来源：[52im thread-1616](https://www.52im.net/thread-1616-1-1.html)（2018）。
- **阿里云 Tablestore Timeline（IM 存储的标准参考架构）**：**「存储库 + 同步库」双库写扩散**——每条消息写 **1+N 份**：存储库按会话 ID 持久存完整历史（无 TTL），同步库**每用户一个同步队列**（写扩散），TTL 示例 7 天；客户端持 checkpoint（sequenceId 位点）增量拉同步库，**未读数 = checkpoint 之后按会话分组的消息计数**。
  - 来源（一手，官方文档）：[基于 Tablestore Timeline SDK 搭建 IM 消息系统](https://help.aliyun.com/zh/tablestore/use-cases/build-im-messaging-system)；架构论述见《现代 IM 系统中的消息系统架构——架构篇》（[知乎转载](https://zhuanlan.zhihu.com/p/65119683)，403 需登录，观点已由官方帮助文档一手佐证）。

## 9. 横向对比表

| 系统 | 读/写扩散 | 消息存储 | 分片键 | seq 方案 | 会话列表维度 | 服务端历史/清理 |
|---|---|---|---|---|---|---|
| OpenIM v3 | **读扩散**（会话一份）+ 用户水位线 | Mongo `msg` 文档，100 seq/文档，docID=conversationID:seqSuffix | 会话（docID 前缀）/ Mongo sharded cluster | per-conversation，Redis 号段 `Malloc`（批量大段），Mongo `$inc` 兜底 | **用户维度表** Conversation(OwnerUserID, ConversationID)，无预览字段现查 last msg | 默认 7 天/可配 msg_destruct（README/旧版） |
| 微信 | 单聊索引写扩散+内容一份；群聊写扩散（二手/传闻） | msgInfo 索引（uid,seq）+ 正文 KV（二手） | **uid**（按用户分库，set 单元化） | **per-user**，seqsvr 号段（步长 1 万）+ Section，不要求连续 | 客户端本地 | 服务端仅同步面，历史在端 |
| WhatsApp | 写扩散（收件人队列，送达即删） | Mnesia 内存队列 | 节点分片 | 无公开（队列+ack） | 客户端本地 | 送达即删（最激进） |
| Signal | **写扩散到设备级** | DynamoDB Envelope 队列，partition=账号+设备，sort=serverTimestamp+UUID | **账号+设备**（DynamoDB 分区） | **无 seq**（时间戳+UUID 排序，整队列拉取后逐条删） | 无服务端 | TTL（默认 30 天，配置注入）+ ACK 删除 |
| 野火 IM | **索引写扩散 + 内容一份** | `t_messages` 内容 + `t_user_messages(uid,seq,mid)` 索引 | 索引表按 **uid.hashCode()%128** 分 128 表；内容表不分片 | per-user（唯一键 uid+seq），mid 由 id 生成器表 | **用户维度**（user_messages 会话索引派生） | 队列上限 MAX_MESSAGE_QUEUE |
| Turms | **读扩散**（官方明示） | Mongo message 集合，冷热分离 | 默认**发送时间**，否则**收件人 ID** | 无连续 seq，按时间区间拉取 | 客户端为主（服务端 conversation id 仅查询辅助） | 冷热分离+逻辑删除字段 |
| 腾讯云 IM | 未公开（产品化：历史按会话查） | 按会话存历史 | 未公开 | **群：per-群服务端严格递增**；**单聊：时间+客户端 msgSeq** | **服务端 per-user** recentcontact | 7/30 天起，可延至 360 天 |
| Tablestore Timeline | **写扩散 1+N**（存储库+同步库双库） | 存储库（会话，永久）+ 同步库（用户队列，TTL 7 天） | 会话 ID / 用户 ID 分属两库 | 同步队列单调 sequenceId + checkpoint | **用户维度**（同步队列派生） | 同步库 TTL，存储库永久 |

**规律总结**：
1. 「内容一份」是所有系统的共识（包括写扩散派：扩散的是索引/信封，不复制正文）。
2. 「要不要每收件人一行」分化为两派，且**与 seq 粒度绑定**：读扩散派（OpenIM/Turms/腾讯云单聊）seq 挂在**会话**上，用户侧只留水位线；写扩散派（野火/Signal/Tablestore/微信索引）seq/游标挂在**用户（或设备）**上，换来单游标断线补拉。
3. 会话列表凡服务端管的，几乎清一色**用户维度**（OpenIM Conversation 行、野火 user_messages、腾讯云 recentcontact、Tablestore 同步队列）。
4. 收件箱/Timeline 表普遍有**上限或 TTL**（Signal 30 天、Tablestore 同步库 7 天、野火队列上限、本项目 200/500）。

## 10. 对本项目 chat 库表设计的评估结论

### 争议点①：timeline 写扩散（每消息 2 行）对 1v1-only 是否过度设计？

**结论：没问题，有取舍但合理。不算过度设计，不建议砍。**

- **业界主流做法**：两派并存且都有头部用户（读扩散：OpenIM、Turms；写扩散：野火、Signal、Tablestore、微信单聊索引）。关键分歧从来不是「1v1 要不要」，而是**seq 挂在会话还是用户**：
  - 选读扩散（本项目砍掉 timeline）→ 必须把每用户的**断线补拉游标**改成「遍历该用户全部活跃会话，按各会话 last_seq 收敛」——OpenIM 就是这么做的（`GetMsgBySeqsRange` 对每个 conversation 算 userMinSeq/conMinSeq），代价是补拉路径从 1 个游标变成 N 个会话各查一次，且需要 OpenIM 式的 per-(user, conversation) 水位线表，复杂度并没有消失，只是从 timeline 挪到了水位线表。
  - 选写扩散（现状）→ timeline 每消息 2 行索引，换来 delivery_seq 单游标 O(1) 补拉，与票 04 定稿的「并行补拉 + (roomId, seq) 判重合流」严格配套。
- **本项目是否偏离**：没有。形态上与野火 `t_messages + t_user_messages`（内容一份、每收件人一行索引、唯一键 uid+seq）和 Tablestore「存储库 + per-user 同步库（1+N）」**逐字段同构**；timeline 只存索引不复制正文，符合所有写扩散系统的共同底线（52im 方案③）。
- **唯一要守住的条件**：timeline 行必须是纯索引（user_id, delivery_seq, room_id, seq），不落内容、只插不改——现状已满足；若有删改需求，走 user_min_seq/隐藏过滤而非 UPDATE timeline。
- **附带成本核算**：1v1 场景写放大恒为 ×2（群聊才是 ×N，那才是写扩散的痛点，也是 52im 那篇「千人群要不要写扩散」的争议所在）。本项目明确不做群聊，等于把写扩散的缺点自动排除了。

### 争议点②：若分库，room 按 room_id 片、timeline/user_seq 按 user_id 片，发消息事务跨 3 片

**结论：当前单库没问题；分库预案若保留「单事务」假设则是问题——业界没有跨片强一致事务的先例，预案应明确改写为最终一致。**

- **业界主流做法**：
  - OpenIM：发送链路是**异步流水线**（gateway → Redis 取号 → MQ → Mongo 落库 → push），各环节独立，无跨存储事务；
  - 微信：收发双方索引按 uid 分片，**结构上就不可能单事务**，正确性 = seqsvr 单调号 + 异步投递 + 客户端带本地最大 seq 的增量同步兜底（InfoQ seqsvr 一手文章）；
  - Signal：每条消息独立 DynamoDB Put，无事务；Tablestore：存储库与同步库本就是两个库两次写。
  - 换言之，**分库后发消息的业界标准形态 = 会话片本地事务（message + room.last_seq 取号）→ outbox/可靠队列异步扩散（timeline×2 + user_seq×2 + 推送）→ 游标对账兜底**。
- **本项目是否偏离**：表结构本身**不偏离**，反而是按最终一致路线预制的：timeline 只插不改 + `uk_user_delivery` 幂等、`uk_room_seq` 推送判重、delivery_seq 游标补拉、outbox→RocketMQ 骨架（票 04 Q2）——这些正是 OpenIM/微信用来替代跨片事务的四件套。真正的问题在**预案的措辞**：如果预案里写着「分库后仍保持发消息大事务」，那这条预案本身就是不可实现的，应改写为「room 片本地事务提交为准，timeline/user_seq 异步最终一致，漏写由 delivery_seq 对账补齐」。
- **两个分库路线的细节提醒**（业界佐证）：room.last_seq 行锁取号随 room_id 分片天然无跨片竞争（1v1 单会话并发低，行锁够用；微信/OpenIM 上号段/Redis 是因为单会话或全局成为热点时才需要）；timeline/user_seq 按 user_id 分片与野火 `t_user_messages_0..127` 的分表方式一致，是成熟路线。

### 争议点③：会话列表排序键 last_msg_at 在 room 行（会话维度）

**结论：有偏离，算问题，建议修（把列表副本冗余进 room_member）。**

- **业界主流做法**：凡是服务端维护会话列表的系统，全部是**用户维度**——OpenIM `Conversation{OwnerUserID, ConversationID, …}` 每用户每会话一行；野火直接用 `t_user_messages` 的 `(uid, type, target, line, mid desc)` 索引从用户侧派生会话列表；腾讯云 IM 服务端 recentcontact 按 user 提供 list 且会话对象带 lastMessage/已读 seq；Tablestore 干脆把「每用户同步队列」本身当列表数据源。**没有主流系统把会话列表排序键只放在会话行上**。
- **本项目是否偏离**：偏离。last_msg_type/preview/at 全在 room 行，用户维度列表 = 「先查 room_member 拿房间集合 → 再查 room 排序」两段式，且排序必须在应用层内存做（或再给 room_member 加排序冗余，等于回到建议方案）。校园规模（单用户会话数几十）两段式能用，但它是**增长会痛的方向**：列表页一次打开 = 1 + N 次查询 + 应用层排序，且未来任何「按时间倒序的服务端分页」都要重建。
- **修法与代价**：把 `last_msg_at`（需要的话连 preview）冗余进 `room_member`——发消息事务里本来就要写 timeline×2，顺手 `UPDATE room_member SET last_msg_at=… WHERE room_id=? AND user_id IN (…)` 两行，**单库下零新增事务、分库后 room_member 跟 room 同片（按 room_id 分）也零跨片**；列表查询变成 `SELECT … FROM room_member WHERE user_id=? ORDER BY last_msg_at DESC`（需加 `uk(user_id, last_msg_at)` 类索引）。room_member 是收件人视角的行、恒两行，语义上正是「用户维度会话列表行」，OpenIM 的 Conversation 行与其同构；hidden_at 软删已在同表，列表过滤零成本。
- **注意分库下的反向问题**：room_member 若按 room_id 分片，则 `WHERE user_id=?` 会扫全片。两种业界处理：① 1v1 会话数少，接受「按 user_id 广播/二级索引」；② 学野火把索引表按 user_id 分片（本项目 timeline 已按 user_id 分片，**会话列表也可以直接从 timeline 派生**：给 timeline 加 `(user_id, room_id, delivery_seq desc)` 查询取每会话最新一条，等于野火从 user_messages 派生列表的方式）。无论哪种，排序键的**权威副本应落在用户维度的行上**，room 行的 last_msg_* 降级为纯缓存。这是本报告唯一建议动手改的点。

### 其他对照项（顺带校验，均无问题）

| 本项目设计 | 业界对照 | 结论 |
|---|---|---|
| `direct_room_pair` user_min/user_max 唯一键查重 | OpenIM `GenConversationIDForSingle = "si_" + sort(sendID, recvID)` 排序拼接，同构 | 没问题，业界标准做法 |
| `uk_room_client(room_id, client_msg_id)` 发送幂等 | 腾讯云 msgID 去重 Key（120s）、OpenIM ClientMsgID | 没问题，主流 |
| room.last_seq 事务内行锁取号 | OpenIM Redis 号段/Mongo $inc、微信 seqsvr 号段——都是** hotter 场景才上号段**；行锁是正确且最简的单库实现，1v1 单会话并发低无热点 | 没问题；分库后随 room_id 分片依旧成立，预案里不用预留发号器 |
| delivery_seq 默认 200/上限 500 补拉 | Signal 队列 TTL+ack 删除、Tablestore 同步库 TTL 7 天、野火 MAX_MESSAGE_QUEUE 队列上限 | 没问题，收件箱容量上限是主流做法 |
| 未读数 = room.last_seq − room_member.last_read_seq | 腾讯云「比较 lastMessage seq 与已读 seq」、OpenIM hasReadSeq vs maxSeq，同为水位线差值 O(1) | 没问题，主流 |
