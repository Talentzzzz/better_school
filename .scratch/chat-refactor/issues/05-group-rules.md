# 票 05：群聊产品规则

## Question

群聊（上限 500 人）的产品规则，尽量用最小规则集覆盖「未来跑腿多人接单」的通用形态：

- 谁能建群（全员可建？人数门槛？）
- 加入方式：邀请链接/搜索群号/成员拉人，选哪几种
- 角色模型：群主/普通成员够不够，要不要管理员
- 500 上限语义：满员时加入被拒的提示与处理
- 退群与解散语义：群主退群怎么办，解散是软删还是硬删
- 群信息（名称/头像）谁可编辑

➡️ 产出：一组可写进 spec 的规则，边界情形用具体场景磨清。

## Answer

（2026-09-09 grilling 结论，两轮定稿）

### 定向：群聊是系统群，不是用户群

**群聊为跑腿而建**：未来一个跑腿单需要多人接单时，订单生效后由系统自动创建「发布方 + 接单者们」的群。因此**用户没有任何群管理入口**——不建群、不拉人、不踢人、不解散、不改群信息；无群主、无管理员、无禁言。跑腿绑定本身是未来 effort（跑腿当前一人一单不扩展），本次先把群聊通用能力做出来，后续合并。

### 规则集

1. **群的形态**：群是系统群，由系统按宿主业务创建。落地形态为**纯领域层**：room 支持 GROUP 类型 + 系统侧 service API（建群[名称+初始成员]、成员进出、封盘），集成测试当调用方，无 HTTP 端点、无前端入口。
2. **群名**：建群时系统传入，创建后任何人不可改（没有群主，自然没人有编辑权）。群成员上限 **500、可配置**。
3. **1v1 与群**统一 room 模型，类型创建即定死，不可互转/升级。
4. **封盘**（原「解散」问题的答案）：宿主业务到达终态（未来跑腿的 COMPLETED 与 CANCELLED 均算）→ 封盘，**软删**（room 状态位），**不可逆**（重开意味着水位线/扇出/seq 全要复活，无场景值得）；禁发言、禁成员变更，**历史消息全员只读可见**（含封盘前已退出的成员此前消息）；封盘瞬间投一条系统消息。
5. **成员移除**：被系统移除后停止收新消息（扇出排除），此前消息仍可见（room_user 留痕不删行，追溯跑腿纠纷）。
6. **系统消息**：建群/成员加入/成员移除/封盘走**会话内系统消息**（SYSTEM 类型、占 seq、计未读、走正常 room/message/timeline 链路）；投递对象 = 事件时刻的成员集合（被移除者不收移除消息、退出的不收后续）；notification 域一行不动。
7. **审核：chat 全路径为零审核**——私信与群聊想去掉敏感词初筛（只拆 `MessageSendCase` 一处调用），图片也不过审；想发什么发什么。帖/评/商品/跑腿的审核与 agent-review 全部不动。
8. **兜底是举报**：沿用 `content_report` 链路——target_type 加 MESSAGE；一人一消息一单；理由自由文本；举报者须为该会话成员。AUDITOR 处理动作 = **强制撤回**（复用撤回机制：消息标记已撤回、占 seq 不动水位线），若消息已被发送者自行撤回则只落处理结论；举报人/被举报人通知沿用既有 `REPORT_RESULT`。不做扣分（信用分挂在内容下架上，chat 消息无「下架」概念）。

### 被否决的选项（记档防复发）

- 用户建群/成员拉人/邀请链接（全库无 invite 基建，校园实名场景无审批需求）——整条「谁能建群/加入方式/角色模型」分支因系统群定向而作废
- 解散硬删：要清理 message+timeline 数千行且丢追溯，零收益
- 群系统消息走 notification 域：两套展示逻辑，消息链路统一后 SYSTEM 类型免费获得未读/同步/撤回
- 举报处理绑扣分：发明规则，无场景驱动
