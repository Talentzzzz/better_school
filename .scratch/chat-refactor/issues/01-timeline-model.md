# 票 01：时间线读写模型与消息记录表必要性

## Question

UserTimeLine 的读写模型怎么选？1v1 与群聊（≤500 人）各自用写扩散（每个成员一行时间线）、读扩散（按 room 聚合拉取）还是推拉结合？核心权衡点：

- 会话列表的「最后一条消息 + 会话精确未读数」在每种模型下分别怎么高效取（单机 MySQL）
- 500 人群写扩散意味着每条消息最多 500 行的写放大，单机是否可接受；群聊读扩散时「成员已读位」「成员删除（会话隐藏）」又挂在哪
- 用户构想中的「消息记录表（消息id、用户id、状态）」到底是什么角色：写扩散时间线本体？还是读扩散下的收件箱/回执辅助？它与 UserTimeLine 是二选一还是并存——**它是否必须**

➡️ 产出：模型结论（1v1 与群聊可不同）+ 每张表的读写路径论证 + 消息记录表去留。主考场景：手机端单设备在线、会话列表按更新时间排序、未读数精确到会话。

## Answer

（2026-09-09 grilling 结论，1v1 与群聊统一模型）

### 模型结论：统一写扩散（内容中心表 + 瘦时间线 + 水位线）

- **1v1 与群聊（≤500 人）统一为同一套模型**，不分裂路径。论证口径：读写比约 10:1 偏读，写扩散把扇出成本从「每次读」挪到「一次写」，读路径变成纯「扫自己的收件箱」；这是写扩散的经典适用条件（读多写少）。注意正确论证是「扇出成本的路径选择」，不是「读扩散把读次数乘上去」——N 个成员读同一条群消息，两种模型下都是 N 次读发生，面试别讲错。
- **不做推拉结合**：500 人封顶 + 校园量级，纯写扩散即可；spec 固化容量估算与演进口（见下）。

### 四表分工与读写路径

| 表 | 角色 | 写路径 | 读路径 |
|---|---|---|---|
| `room` | 会话本体：last_seq（会话内单调递增）、last_msg 冗余（列表展示） | 发消息事务内 `UPDATE last_seq = last_seq + 1` 原子取号（按会话串行化并发发送），冗余 last_msg | 会话列表按 last_msg_at 排序 |
| `room_user` | 成员状态（唯一会被更新的成员维度行）：`last_read_seq` 已读水位线、`hidden_at` 会话隐藏 | 打开会话推高水位线到 room.last_seq；新消息清空 hidden_at（删除的会话弹回，微信行为） | 未读数 = `room.last_seq - last_read_seq`（O(1)，一次 JOIN 全算完）；已读回执 = 对方的 last_read_seq |
| `message` | 内容中心表：内容只写一份 | 随发消息事务插入一次 | 按 room + seq 分页拉取；撤回/审核只改这里 |
| `timeline` | 写扩散收件箱（瘦行：user_id, room_id, seq, msg_id），**只插不改** | 单条多值 INSERT 扇出（一条 SQL N 个 value，非 N 次往返） | 增量同步游标：`user_id = ? AND seq > last_seq`（票 07 重连对齐用） |

### 水位线机制（已读/未读语义）

- `last_read_seq` 是 Kafka 消费者位点同思想的高水位：水位以下全已读，以上全未读；时间线行不可变，已读动作 O(1)。
- **已读粒度是会话不是单条消息**（微信/WhatsApp 标准行为）：打开会话推水位线到最新，旧消息随之全读——这是语义而非副作用；不做滚动位置细化。
- **撤回的消息占未读数**：撤回不回退 seq、不动水位线，点开后显示「已撤回」；保住水位线简洁性。
- seq 在发消息事务内原子分配，失败回滚无空洞，`last_seq - last_read_seq` 即精确未读数。

### 消息记录表：否决

用户构想的「消息记录表（消息id、用户id、状态）」在读扩散/写扩散下都没有独立角色：它长得像写扩散时间线本体，而 `timeline` 瘦行就是它；status 列被 `room_user.last_read_seq` 水位线取代。**不建**，显式记档防复发。

### 写放大量化（单机可接受性）

总量 = 消息数 × 平均会话人数（上限 500 只限单条倍数）。按 1 万用户、人均日发 100 条、平均会话 8 人：约 800 万行/天 ≈ 均值 92 写/秒、峰值 ~900 写/秒，InnoDB 单机扛得住；瘦行+索引 ~100B → ~0.8GB/天。落地要求：① 多值 INSERT 扇出；② spec 固化该估算 + 演进口（数据归档 / 群聊扇出转异步，票 07 已有 MQ）；③ 平均扇出按校园真实分布（多数会话 2~10 人）而非 500 顶格。

AND seq > last_seq` 不成立——seq 是 room 内序号副本（每会话从 1 起），跨会话不可比；timeline 自增主键当游标也被否决（无业务含义 + id 分配序 ≠ 提交序，并发下漏拉）。更正为 **per-user 投递序号 delivery_seq**：timeline 瘦行增加 `delivery_seq` 列，新表 `user_seq(user_id, seq)` 计数器在扇出事务内批量 +1 读回取号，游标谓词 `user_id = ? AND delivery_seq > ?`。计数器行锁到提交，保证同一用户 delivery_seq 单调 = 提交序（微信 SyncKey 同款）。扇出由单条多值 INSERT 变为「计数器 UPDATE + 读回 + INSERT」三步：1v1 仅 +2 行更新；500 人群 +500 行/条，写放大翻倍——归入本票既有演进口（spec 固化估算时一并量化）。详见[票 04 设计文档](../research/04-连接层设计.md) §5。
