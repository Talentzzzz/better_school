# 平台代收：买家先付给平台，完成/取消时平台出账

## Problem Statement

现在的「支付」只是把买家的 `frozen_amount` 抬高，钱没有真正离开买家账户——平台没有任何收款账户，用户付完款后自己的余额仍然是满的。这带来三个只有使用者能感知的问题：

- **钱在谁手里说不清**：平台侧没有一条账能回答「这笔货款现在由谁持有」。运营想看「平台代收了多少、还没结算多少」，没有数据源。
- **账不平**：按文档口径「可用余额 = `balance − frozen_amount`」，支付只加冻结不减余额；确认收货时又是「解冻买家 + 给卖家入账」。这等于买家锁定的钱被释放、卖家又凭空收到一笔，同一笔货款被记了两次。
- **语义与产品对不上**：产品要的是「买家先把钱付给平台，平台托管，订单完成后平台再付给卖家」。现在的模型是「钱冻在买家自己账上」，既不是代收，也不是代付，退款路径也只能表达成「解冻」而不是「平台退款」。

用户明确要的模型是：**平台就是 `virtual_wallet` 里的一行**，买家支付时钱进这一行，订单完成时从这一行付给卖家，取消/超时从这一行退回买家；不新增账户表、不改支付单与订单表。

## Solution

给平台建一个保留账户（`virtual_wallet` 的一行，`user_id` 用保留常量，余额从 0 起），把商品订单的三笔资金动作改成平台过账：

| 时点 | 买家 | 平台 | 卖家 |
|---|---|---|---|
| 支付（收银台确认） | `balance − 金额` | `balance + 金额` | — |
| 完成（买家确认收货） | — | `balance − 金额` | `balance + 金额` |
| 取消 / 支付超时 | `balance + 金额` | `balance − 金额` | — |

每笔动作仍是一个钱包域仓储事务，双边各落一条流水；`frozen_amount` 在商品链路退役（列保留、不再写入）；支付单、收银台、回调、订单状态机全部不变。资金孤儿扫描的判据从「有 `PRODUCT_FROZEN` 无 `PRODUCT_UNFROZEN`」换成「平台有入账无出账」。

## User Stories

1. 作为买家，我在收银台支付时希望钱从我的余额里真正扣掉，这样我付过的钱不会还显示在自己的账户上。
2. 作为买家，我希望余额不足时支付直接失败、订单停在待支付，这样不会出现「已支付但没扣钱」。
3. 作为买家，我重复支付同一订单时希望只扣一次钱，这样重试不会重复出账。
4. 作为买家，我取消已支付订单时希望钱由平台退回我的余额，这样退款的资金来源是明确的。
5. 作为买家，我的订单因支付超时被关闭时希望钱同样由平台退回，这样超时退款不会悬空。
6. 作为买家，我确认收货后希望自己的余额不再变化，这样我对账时能看懂「钱是支付时扣的」。
7. 作为卖家，买家确认收货时我希望钱从平台结算到我的余额，这样我的收入有明确来源。
8. 作为卖家，我希望同一订单只结算一次，重复确认或重放不会重复入账。
9. 作为卖家，我希望被取消的订单永远不会结算给我，这样我不会拿到不该拿的钱。
10. 作为平台运营，我希望平台账户就是 `virtual_wallet` 的一行、余额从 0 开始，这样不需要新建账户表或账户体系。
11. 作为平台运营，我希望平台余额恒等于「已收款但尚未结算/退款的订单金额之和」，这样我能用一条 SQL 对账。
12. 作为平台运营，我希望平台出账前校验余额充足，不足时整笔回滚并留下 ERROR 日志，这样不会把平台余额扣成负数还静默通过。
13. 作为平台运营，我希望支付单与订单表结构不变，这样收银台、订单详情、回调链路都不受影响。
14. 作为平台运营，我希望平台账户不出现在任何用户可见接口里，这样「钱包对用户隐藏」的产品口径不变。
15. 作为审计，我希望每笔资金动作都落双边流水（买家/平台、平台/卖家、平台/买家），这样钱的来路与去向都能追。
16. 作为审计，我希望流水类型名与真实语义一致（不再叫「冻结/解冻」），这样对账时不需要二次解释。
17. 作为审计，我希望历史流水能通过一次确定的映射迁移保留可读性，这样旧数据不会变成孤儿。
18. 作为运维，我希望资金孤儿扫描改成「平台已入账但未出账」的判据，这样宕机窗口仍能收敛。
19. 作为运维，我希望孤儿扫描对未终态订单不动钱（宁可长款），这样不会出现「订单还没完成就退了款」。
20. 作为运维，我希望平台账户行在首次使用时懒创建（`INSERT IGNORE`），这样不依赖启动顺序或初始化脚本。
21. 作为开发者，我希望三笔资金动作各自是钱包域的单仓储事务，跨域顺序由用例层编排，这样不违反 ADR-0016 的事务边界。
22. 作为开发者，我希望用例层不互相注入、钱包域只暴露「结算/退款」两个原子方法，这样上一轮 case 解耦的成果不被破坏。
23. 作为开发者，我希望交付口径是「实现完成后不跑测试」，由维护者自行验证，这样与仓库既有约定一致。
24. 作为维护者，我希望领域文档、DB 文档与 ADR 同步更新资金归属口径，这样下一个人不会按「冻结」去理解代码。

## Implementation Decisions

- **平台账户**：新增保留常量 `PLATFORM_USER_ID`（与通知助手 `SYSTEM_USER_ID` 区分，避免一个账号两种角色），平台账户就是 `virtual_wallet` 的一行，`balance` 初始 0、`frozen_amount` 0。播种走懒创建：`ensureWallet(userId, initialBalance)` 增加带初始余额的重载，注册路径仍用注册赠送额，平台路径用 0；`INSERT IGNORE` 撞 `uk_user` 幂等。
- **三笔原子动作**：钱包仓储新增两个事务方法——`settleProductOrder(orderId, sellerId, amount)`（平台出账 + 卖家入账）与 `refundProductOrder(orderId, buyerId, amount)`（平台出账 + 买家入账）；`pay(payNo, userId)` 内部改为买家出账 + 平台入账。每笔都在一个 `TransactionTemplate`（REQUIRED）里完成「双边流水 + 双边余额更新」，任一步失败整笔回滚。
- **余额守卫**：买家出账用 `balance − frozen_amount >= amount`（保留对历史冻结额的尊重）；平台出账用 `balance >= amount`，不足视为不变量破坏，抛异常整笔回滚并留 ERROR 日志，不静默跳过；卖家/买家入账只加余额。
- **幂等**：沿用 `wallet_detail.uk_order_type(order_id, type, biz_round, user_id)`。每笔腿以业务侧那一行为锚（买家支付行、卖家结算行、买家退款行），`INSERT IGNORE` 影响 0 行即整笔视为已处理、直接返回；平台侧那行同事务写入。
- **流水类型**：商品链路改为双边语义——`PRODUCT_PAY`（买家支付出账，承接原 `PRODUCT_FROZEN`）、`PRODUCT_REFUND`（买家退款入账，承接原 `PRODUCT_UNFROZEN`）、`PRODUCT_INCOME`（卖家入账，保留）、新增 `PLATFORM_IN` / `PLATFORM_OUT`（平台收/付；结算与退款都走 `PLATFORM_OUT`，方向由订单状态与配对行判定）。`RECHARGE` / `FROZEN` / `UNFROZEN` / `INCOME` 保留但商品链路不再产生。历史行做一次性映射：`PRODUCT_FROZEN → PRODUCT_PAY`、`PRODUCT_UNFROZEN → PRODUCT_REFUND`。
- **`frozen_amount` 退役（商品链路）**：不再冻结、不再解冻；列与历史值保留，只作为余额守卫的减项。其他历史流程若仍写它，行为不变。
- **用例编排**：`IdleCase` 的确认收货改为调 `settleProductOrder`；取消、支付超时、资金孤儿扫描改为调 `refundProductOrder`；不再直接调 `unfreeze` / `income`。`IdleCase` 仍只注入各域 service，不注入其他 case。
- **资金孤儿扫描**：扫描判据改为「平台有 `PLATFORM_IN`、同订单无 `PLATFORM_OUT`、且超过阈值（沿用 10 分钟）」，单轮上限沿用；裁决口径保持「宁可长款」——订单 `COMPLETED` 补结算、`CANCELLED` 补退款、其余状态不动钱；退款目标从流水行的 `user_id`（现在是平台）改为订单的买家/卖家。
- **对账不变量**：平台 `balance` = Σ(有 `PLATFORM_IN` 无 `PLATFORM_OUT` 的订单金额)。本期只把口径写进文档，不新增定时对账 job。
- **接口收敛**：钱包域对外只暴露 `settleProductOrder` / `refundProductOrder` 两个新方法；`freeze` / `unfreeze` / `income` 若商品链路之外不再有调用方则一并删除，避免留下两套并行的资金口径。
- **文档**：`CONTEXT.md` 的「支付」词条补「平台代收账户」与三笔资金归属；DB 文档的钱包段更新流水类型与平台账户；`docs/adr/0018` 增补或新开一条 ADR 记录「资金模型从冻结改为平台代收」。
- **交付口径**：按用户指示，**实现完成后不运行测试套件**（不执行 mvn），由维护者自行验证；测试代码如需同步修改则随实现交付但不执行。

## Testing Decisions

- **好的测试只测外显行为**：断言订单状态、买家/平台/卖家三方余额、`wallet_detail` 的流水行（类型 + 金额 + 订单号）、重复调用不重复动钱；不断言事务内部顺序与调用次数。
- **主缝 = 用例编排层**：`IdleCase` 的公开方法（下单/支付/确认收货/取消/超时回调/孤儿扫描）是本次改动的最高缝，失败注入点放在钱包动作边界（余额不足、平台余额不足）。理想缝数量为 1，全部复用现有缝，不新开。
- **第二缝 = 钱包仓储事务**：仅在需要验证「双边流水 + 双边余额同生共死」时使用，断言「任一步失败后三方余额与流水一起回滚」。
- **先例**：现有商品支付、商品取消两个集成测试的外显断言形状（订单状态 + 流水条数 + 余额/冻结额）直接沿用，只是把「冻结/解冻」换成「出账/入账」，并补上平台余额断言。
- **需要同步修改的既有测试**：现有两个集成测试对买家 `balance` 的断言在现有 SQL 下无法同时成立（支付后断言 960.20、取消后断言 1000），本次以「支付扣减余额、取消由平台退回」为新口径统一，测试代码随实现更新。
- **交付口径**：按用户指示，**实现完成后不运行任何测试**，测试的正确性由维护者在本地自行验证。

## Out of Scope

- 多商户 / 服务商模式（`mchid`、`sub_mchid`、按收款方分账）。
- `payment_order` 结构改动（`subject` 保留、不加商户列）。
- 平台账户的提现、充值、对外查询或管理接口。
- 定时对账 job（本期只定不变量与口径，不建任务）。
- 真实微信/支付宝接入（签名、验签、主动查单、HTTP 通知）。
- 历史 `wallet_detail` 行之外的存量数据修复（开发/测试库可直接重建）。
- 抽奖、返利等其他域的资金动作（它们不经过商品订单链路）。

## Further Notes

- **为什么平台用 `virtual_wallet` 的一行**：账户模型同构（余额 + 流水 + 幂等键），零新表、零新迁移；用户明确要求「这么模拟就行」。
- **为什么三笔必须一起改**：只改支付这一笔，平台会只进不出——确认收货后卖家拿到钱、平台余额却永远不减，总账凭空多钱。完成与取消不是「其他」，是同一笔货款的后半段。
- **与 ADR-0016 的关系**：三笔动作各自是单仓储事务，跨域顺序由 case 保证；平台行属于钱包域，不引入跨域事务。
- **与 ADR-0018 的关系**：支付单、收银台、进程内回调、支付单状态机全部不变，只改资金的最终归宿与流水口径。
- **已知的现状矛盾**：当前 `updateFreeze` 只加冻结不减余额、`updateUnfreeze` 只减冻结不加余额，而确认收货走的是「解冻 + 入账」，按文档口径账是不平的；本次改造顺带把这个口径统一掉，历史冻结额只在余额守卫里作为减项保留。
- **风险**：平台账户是一个全局热点行，所有支付/结算/退款都会更新同一行；课程项目量级可接受，若未来量大需要拆分或改为记账式汇总，另立规格。
