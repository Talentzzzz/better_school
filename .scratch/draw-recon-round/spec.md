# 抽奖库存全量对账轮（drawReconScan）：逐笔孤儿收敛之上的总量兜底

## Problem Statement

抽奖主链路是三个独立事务：扣抽奖次数 → 库存域预扣（合并器批量落库）→ 中奖记录 + outbox 事件落库。跨事务一致性目前只靠两层机制：

- **幂等键**（record_id = hash(userId, token)、库存明细唯一键、次数桶唯一键）——防重复，但不防缺失；
- **孤儿预扣收敛 job**（`orphanPrereserveScan`，0/30 cron）——逐笔收敛「预扣已提交、记录未落库」的漏结。

孤儿收敛 job 是主链路的一环，它自己坏掉时**没有任何机制能发现**：

- xxl-job 调度中断 → 种单不再发生，孤儿预扣无限期占用库存，无人知晓；
- 对账单重试耗尽进死信（DEAD）后 → 只有当次 ERROR 日志，没有周期性复查；
- 库存回补守卫不过（`restitutePrereserve` 返回 false）→ 只留 ERROR，无复核机制；
- 数据破坏类（孤儿预扣查不到扣次明细）→ ERROR 跳过，永久悬置。

这些静默失败对用户的后果是累积性的：库存台账与真实可用量漂移（虚低 → 抢得到却发不出；虚高 → 超发），抽奖次数被幽灵占用，且没有任何告警。对维护者而言，当前只有"逐笔补课"，没有"期末大考"——没有任何一个机制能独立于逐笔链路回答「账到底平不平」。

社区调研（`docs/wayfinder/research/002-库存扣减与记录落库一致性-社区调研.md`）确认这是行业标准缺口的标准解法：美团式**周期性全量对账轮**——总数对账为辅（复核兜底）、明细对账为主（定位到单）、差错二次核对（防日切误报）、平账自动修 + 人工兜底。

## Solution

新增一个**纯旁路**的每日全量对账轮（xxl-job `drawReconScan`，03:00 低峰）：

1. **轧账**：对营销库存四条不变量各跑一条只读聚合 SQL——两条台账守恒公式（按 award_id 分组）+ 正向配对（库存明细 ↔ 中奖记录/孤儿单）+ 反向配对（中奖记录 ↔ 预扣明细）。
2. **差错登记**：本轮发现的不一致写入新差错表，一律 `PENDING`，不立即处理；**下一轮复查仍在**才转 `CONFIRMED`（即美团的"二次核对"，天然消化日切边界的假差错）。
3. **平账分流**：`CONFIRMED` 后——正向漏结且无对账单 → 复用现有孤儿种单逻辑自动补种；孤儿单已 DEAD → 告警人工；守恒破坏 / 反向缺失（数据破坏级）→ 只告警人工，绝不自动修。
4. **告警**：走现有营销通知链路，不新接通道。

不变量公式全部来自现有代码已声明的守恒判据（库存 flush 落库注释中的 B3 等），对账轮只是把它们变成每天真跑一遍的 SQL。不引入 Redis 前置库存、MQ 事务消息、fence 表（调研结论：现有组件已以更少组件覆盖同构防御）；不动主链路、不动合并器。

## User Stories

1. 作为抽奖用户，当孤儿收敛 job 调度中断期间我的抽奖落在「预扣成功但记录未落」的窗口时，我希望全量对账轮最终发现并补种收敛，这样我的抽奖结果最终能补出来或库存/次数被退还。
2. 作为抽奖用户，当库存台账与明细出现系统性漂移导致可发库存虚低时，我希望对账轮及时发现并告警，这样活动期间我能抢到的奖品与真实库存一致。
3. 作为抽奖用户，当出现守卫失败类的静默失败导致我抽中的奖品没落库时，我希望差异被周期性复查兜住，这样我不需要反复投诉才能拿到结果。
4. 作为维护者，我希望每天凌晨自动跑一轮全量对账（两条台账守恒公式 + 正反双向配对），这样我不需要手工写 SQL 巡检。
5. 作为维护者，当某个奖品账户的守恒公式（限量户 `surplus + waiting + issued = Σ分配转入量`、`waiting + issued = Σ预扣明细量`）被破坏时，我希望收到按 award_id 定位的告警并附期望/实际值快照，这样我能立刻知道哪个账户坏了、坏在哪一侧。
6. 作为维护者，当库存明细的 biz_id 既查不到中奖记录也查不到孤儿对账单时（说明种单环节漏了），我希望对账轮自动补种孤儿对账单并标记为已自动修复，这样逐笔链路的遗漏被自动闭环。
7. 作为维护者，当出现「中奖记录在、预扣明细丢」的反向不一致时，我希望只收到告警而不被自动修复，这样不会被错误的自动动作放大数据破坏事故。
8. 作为维护者，我希望日切边界的假差错（取数时刻两侧快照不一致造成）不会打扰我——差错必须经过下一轮复查确认才触发告警/修复，这样我信任每一条告警。
9. 作为维护者，我希望对账轮对同一（轮次、检查类型、业务单号）幂等，调度重复触发不产生重复差错行，这样重跑永远无害。
10. 作为维护者，我希望差错行记录轮次、检查类型、定位键与期望/实际值快照，这样人工核对时有全部上下文，不需要重新推导。
11. 作为维护者，当孤儿对账单已进死信（DEAD）时，我希望对账轮周期性再次点名告警，这样死信不会被"当次 ERROR 之后被遗忘"。
12. 作为维护者，我希望对账告警走现有营销通知渠道，这样不需要对接新的告警系统。
13. 作为维护者，我希望对账轮是纯旁路（只读业务表、只写差错表），这样对账轮自身故障完全不影响主链路。
14. 作为维护者，我希望对账轮按 award_id 分批扫描并在低峰调度，这样不与高峰业务争抢连接与锁。
15. 作为维护者，我希望孤儿收敛 job 与对账轮保持完全独立（互不依赖代码路径），这样两层机制不可能共享同一个 bug。
16. 作为运营/客服，当用户投诉「抽中了但查不到记录 / 奖品没到」时，我希望按 record_id 查差错表就能得到结论（在修 / 已修 / 无差异），这样能快速给用户确定答复。
17. 作为维护者，我希望对账框架的检查清单可扩展（二期加池侧守恒、次数桶、积分桶），这样新账本接入不需要重写编排与差错状态机。

## Implementation Decisions

- **模块与分层**（照孤儿收敛的既有分层纪律）：编排与口径判断归抽奖域一个对账服务（参照 `RaffleOrphanPrereserveServiceImpl` 的形态——不注入事务模板，每一步都是仓储/端口自带的原子用例）；四条不变量检查以只读聚合查询落基础设施层 mapper；调度触发归 trigger 层 xxl-job。差错写与检查同为独立原子写。
- **新表：差错表** `draw_recon_variance`：轮次号 + 检查类型 + 定位键（scope_key=award_id 或 record_id + biz_id）+ 期望/实际值快照 + 状态机（`PENDING → CONFIRMED → AUTO_FIXED / RESOLVED_MANUAL / FALSE_ALARM`）；唯一键（轮次, 检查类型, biz_id）保证幂等。可选配套一张轮次表记录每轮起止与计数（纯观测用，最小列）。
- **四条不变量**（全部只读，基于现有表 `draw_strategy_award_inventory` / `draw_strategy_award_inventory_detail` / `draw_record` / `draw_orphan_prereserve_order`，公式出处是库存 flush 落库注释已声明的守恒判据 B3 与分配/预扣/回补口径）：
  - B1 台账守恒：限量户（`surplus_qty ≠ -1`）`surplus_qty + waiting_qty + issued_qty = Σ(flow_type=0 分配转入明细 quantity)`，按 award_id 分组；不限量户跳过 surplus 项。
  - B3 预扣守恒：`waiting_qty + issued_qty = Σ(flow_type=1 预扣明细 quantity)`，按 award_id 分组（回补是「台账转回 + 删明细」同事务，公式天然平衡）。
  - 正向配对：每条 `flow_type=1 AND biz_type=LOTTERY_DRAW` 的明细 biz_id（= record_id）必须命中 `draw_record.record_id` 或 `draw_orphan_prereserve_order.record_id`，否则为漏结（孤儿种单环节失效）。
  - 反向配对：每条 `draw_record`（`inv_id IS NOT NULL AND award_type ≠ 'THANKS'`）必须存在对应预扣明细（`award_id = inv_id` 快照、`biz_id = record_id`），否则为数据破坏级缺失。
- **数据窗口与日切**：对账数据集只取 `update_time < now - 10min` 的行（与孤儿种单阈值对齐，避开主链路在途窗口）；所有差错先 `PENDING`，下一轮复查同键仍在才 `CONFIRMED`——即二次核对，消化取数时刻两侧快照不一致的假差错。
- **平账分流**（CONFIRMED 后）：正向漏结且无对账单 → 复用现有孤儿种单入口补种，置 `AUTO_FIXED`；孤儿单已 DEAD → 告警人工；守恒破坏 / 反向缺失 → 只告警人工，人工核对后置 `RESOLVED_MANUAL`；复查消失 → 置 `FALSE_ALARM`。
- **告警**：复用现有营销通知链路（对账轮发现 CONFIRMED 差错 / DEAD 孤儿单时发通知），消息内容带轮次、类型、定位键、快照。
- **调度**：xxl-job handler `drawReconScan`，每日 03:00；照 `OrphanPrereserveScanJob` 口径——trigger 层薄壳，无 xxl 上下文可直调；按 award_id 分页/分批扫。
- **幂等与并发**：差错表唯一键 + 轮次号保证重跑零副作用；无跨表条件更新需求（纯追加 + 状态推进按唯一键条件更新）。
- **不动的部分**：主链路三事务、合并器、孤儿收敛 job、幂等键口径一律不改；对账轮与其零代码共享（只读其产物表）。

## Testing Decisions

- **开发者明确决定：本期实现完成后不跑自动化测试**（含既有集成测试基线也不用回归执行）。该决定覆盖实现 agent 的收尾行为：改完直接交付，不执行测试套件。
- 本期不编写任何新测试。若未来补测试，最高可用 seam 是抽奖域对账服务的集成测试层（直接调服务方法、真实 DB，先例是营销模块既有集成测试的形态），不测 mapper SQL 细节、不为差错状态机单开低层 seam。
- 人工验证口径（替代测试）：对开发库手工执行四条不变量 SQL 与预期空结果比对；触发一次 job，确认差错表落行/状态推进/通知发送符合分流表。

## Out of Scope

- 池侧守恒对账（`virtual_inventory_quota` / `physical_marketing_quota` / `inventory_allocation_flow` 的「池转出量 = Σ分配流水」）——二期，公式形状与本轮一致。
- 次数桶、积分桶的对账扩展——二期（检查清单可扩展是本期唯一预留）。
- 实时 / 准实时对账（Binlog 哨兵式）——现有孤儿种单 + 轮询已承担该角色。
- Redis 前置库存、MQ 事务消息、独立 fence 表——调研明确不引入（现有幂等键 + 状态守卫 + outbox 已同构覆盖）。
- 守恒破坏 / 反向缺失的自动修复——数据破坏级只告警人工。
- 对账报表 / 仪表盘——轮次表已含最小观测数据，不做 UI。
- 词典外的新通知渠道。
