# 12 调研：速率租约口径下的突发上界与中心容量账（重推票 03 §4）

Type: research
Status: resolved
Blocked by: 04

## Question

[票 04](04-grill-lease-model.md) 选定**速率租约**（中心下发份额速率 + 有效期，客户端本地桶按份额自补），因此 [票 03](03-research-algorithm-pitfalls.md) 的 §4 整节（在飞量上界推导）**前提失效、整节作废**——它假设"中心真的在扣账、发放即扣令牌"，而票 04 已把这个前提换掉（[research/03](../research/03-algorithm-pitfalls.md) 的 ⚠️ 未核实项第 11 条自己点名了这条依赖）。

本票把 §4 **按速率口径重推一遍**，产出仍是"事实 + 推导"，供票 05 / 06 / 09 / 11 引用。

要重推的（沿用票 03 §4 的记号：`R` 全局速率、`T` 租约/续租周期、`N` 实例数、`burstSeconds` = 规则里"允许几秒的量"、`f` 瞬时活跃实例比例）：

1. **瞬时突发上界**：票 04 的 Answer 给的形状是 `瞬时突发 ≤ R × burstSeconds`，依据是"Σ份额 ≤ R，每实例本地桶容量 = 份额 × burstSeconds"。这个构造上界要形式化：**份额分配有延迟（一个续租周期）时**，一个实例手里可能同时握有"上一轮的高份额"与"本轮的新份额"，上界会不会被放大到 `R × burstSeconds × (1 + T/…)`？请给出**带收敛项的形式**（Doorman 自己的仿真超调读数是 `106.05%`，即稳态超调约 6%，但那是 Doorman 的分配算法 + 参数，不是我们的）
2. **任意窗口 Δ 的放行量上界**：票 03 §4.9 给的 `R·(Δ+T)+2K` 形态在速率口径下换成什么；由此推出"要让窗口 Δ 的平均放行率落在 R 的 ε 以内，Δ 至少要多大"——**票 09 的准确度验收口径要直接引用这条**（票 03 的结论是"长期"是分钟量级，不是"一秒一秒地准"）
3. **中心租约 QPS 与处理成本**：票 04 已定"按实例聚合的批量续租"，全中心 QPS ≈ `实例总数 / T`、**与 key 数无关**；但**每 key 的每次续租要重算一遍分配**，所以 CPU 成本是 `Σ_k (该 key 在册实例数) / T`。请给出这个成本的形式与算例（`R`、`N`、`T`、key 数各取几组）
4. **分配算法的收敛速度**：票 04 选的是 PROPORTIONAL_SHARE（O(n)）+ `minF(gets, unusedCapacity)`。从"流量突变"到"份额收敛到新 equilibrium"要几个续租周期？有没有震荡（票 04 现场追问过"会不会无限放大"，答案是不会——但**收敛速度与超调幅度**需要定量）
5. **中心账本的内存账**：票 03 §6.2 算的是"每 key 一个桶 / 时间环"（O(key)）；速率口径下是 **O(key × 该 key 的在册实例数)**——**这正是 §6.2 判为"不可行"的"设计①（按租约条目记）"形状，选速率租约等于认下这笔代价，本票要把这笔账算实**。请按同一套估算方法给出每 `(key, 实例)` 一条记录的成本（票 03 估 99 B/条 是 `HashMap<LeaseId, Lease>` 形状，Doorman 用 `map[string]Lease` 装两个 float64 + 一个 `time.Time`，**可以更紧凑**），以及分片后的量级
6. **大 N 行为**：票 03 §4.8 的"好的一半 / 坏的一半"在速率口径下逐条复核——哪些失效模式消失了（批量过期浪费、B<1）、哪些仍在（中心 QPS 随实例数涨）

**方法要求**：票 03 的 ⚠️ 未核实项第 1 条自己建议"用一个小仿真（离散事件，几十分钟能写）复核三个算例"。本票**优先做仿真**（`N` 个客户端 + 一个中心 + 可配流量抖动，观察瞬时突发、窗口平均、收敛周期），而不是再写一版纸面推导；仿真脚本与读数落 `.scratch/gatekeeper/measure/`（照本仓 `.scratch/*/measure/` 惯例，产物不入库）。

产出：`research/12-rate-lease-bounds.md`。

## Answer

报告：[research/12-rate-lease-bounds.md](../research/12-rate-lease-bounds.md)。仿真器与读数：`.scratch/gatekeeper/measure/`（`sim_rate_lease.py` 可重跑、`results/r-*.json` 为读数，照惯例产物不入库）。方法 = 纸面推导（证明）+ 离散事件仿真（复核），票面方法要求的"优先仿真"已执行。

**事实自核带来的新事实（比票面预期多做的核对）**：本次拉取 Doorman `go/server/doorman/algorithm.go`（master 快照）逐字核对，`unusedCapacity := capacity - store.SumHas() + old.Has`——**minF 的"未用量"必须排除请求者自身已持有的份额**。这个 `+ old.Has` 是"Σ租约 ≤ R"不变量成立的全部（报告 §1.1 有证明）；票 04 Q13 当时引的注释（`We cannot give out more than the currently unused capacity`）没带这个细节，**spec 落实现时必须逐字写对，否则续租会把已有份额清零**。

### 逐条结论（编号 = 票面 `## Question` 1–6）

**Q1 瞬时突发上界（带收敛项）** → **票面担心的放大（`R × burstSeconds × (1 + T/…)`）不发生，机制上不可能**：份额落地是对本地桶的**覆盖式改写**（速率变 → 容量变 → 存量按比例缩放，票 04 Q9 的 rescale），不存在"两轮份额相加"的时刻；中心侧 Σ租约 ≤ R 是硬不变量（仿真 s1/s2/s3/s3b 四场景全程贴 1.0000000×R）。最终形式：**正常路径系数 1（`≤ R × burstSeconds`）、降级期系数 ≤ 2**——唯一超发通道是 fail-open 陈旧份额（断租客户端继续按最后份额 + 账本过期后份额被再分配，s4 实测 1.1R、与手算逐位吻合）。⚠️ **乙案裁决后（见下）公式改写为 `Σ max(份额 × burstSeconds, 1)`**。Doorman 的 106.05% 超发出自**层级部署**（其文档自述成因），本设计单层、无此通道。

**Q2 任意窗口 Δ 的放行量上界 + ε 窗口** → `放行量(Δ) ≤ Σ生效份额 × (burstSeconds + Δ)`（正常 = `R(Δ+burstSeconds)`，降级 ≤ `2R(Δ+burstSeconds)`）；超额是固定一项 `R × burstSeconds`，不随 Δ 增长。**要 ε=2% 则 Δ ≥ burstSeconds/ε = 50s，拍定 Δ = 60s**——票 09 Q2 接口已回填（其 Answer §3 两处加注；⚠️ Δ 随规则的 burstSeconds 走、spec 写公式不写常数）。降级窗口不进稳态准确度验收（归故障验收）。

**Q3 中心租约 QPS 与处理成本** → QPS 沿用票 06（≤ 实例数 × min(订阅 key 数, 分片数)/T，与 key 数无关）。**CPU 账（本票新算）：`Σ_k n_k²/T` 次条目扫描/秒**（重算总是的上界），仿真实测 4.69M/s vs 理论 5M/s（单 key N=5000）吻合；满配算例 ≈ 每分片 10M 次/s ≈ 2% 核（T=2s 时 ×2.5）——**CPU 不是瓶颈**，R（速率值）完全不进该式。优化空间留档：票 04 Q9 的"份额未变只延有效期"可做 O(1) 判定，代价是再分配延迟一轮，v1 不依赖。

**Q4 分配算法的收敛速度** → **收敛 = 1 个续租周期**（请求者自己的份额自己下轮续租即到位），热实例 ≤ 2 轮（等释放方续租腾出 unused）；**无震荡**（每轮零基重算 + minF 封顶，无正反馈回路）。s2 实测：翻转后 5.01s 达终值 95%、全局放行率 3.77s 回到 R±2%。票 04 留的"收敛速度与超调幅度需要定量"至此回填。

**Q5 中心账本的内存账** → **每条 ≈ 91 B**（Java 64 位 + 压缩指针：Lease 48 + HashMap.Node 32 + 槽位 11；含 share/wants/lastRenew/expiry 四字段，手算 ±20% 未 JOL——与当年 99 B 估算同量级，"Doorman 更紧凑"只在 Go 成立、Java 侧 wants 是分配必需输入省不动）。满配 10k key × 200 实例 = 2M 条 ≈ 200 MB → 8 分片 **25 MB/实例，可行**。**两个 10k 默认值复核通过**（票 09 移交）：本地桶表 10k ≈ 0.92 MB/实例；每实例订阅 10k ⇒ 单实例贡献 1 MB，全局按 `Σ n_k` 记账、5000 实例 × 10k = 5 GB 属超配（spec 带警示）。**map 指名的"§5 内存账"= 报告 §5，两处 Not yet specified 已回填。**

**Q6 大 N 行为逐条复核** → 票 03 §4.8 三条坏失效模式**全部消失**：批量过期浪费（90% 作废）消失（无囤积）；`N/(C·W)` QPS 爆炸消失（机制撤销，现行 `N/T` 封顶分片）；`B<1` 机制失效消失（无 B）。仍在的账全部多项式且已算实：QPS 随实例数（封顶分片）、CPU `Σ n_k²/T`、内存 `Σ n_k`。AVG_LOCAL 饿死复核：**仿真实测证实**（s2b：静态 R/N 下热实例钉死 5/s、45% 的 R 闲置）——票 04 Q13 选 PROPORTIONAL_SHARE 被仿真背书。

### ⚠️ 新发现一：微份额区间（票面没预料的，已由用户裁决）

**份额 × burstSeconds < 1 个请求时，本地桶永远装不满 1 个请求 → `tryAcquire` 恒拒**（票 05 Q6 的微令牌整数域 + 容量无下限的直接后果）。s5 实测（R=1000/N=5000）：99.98% 实例恒拒、**翻转前全网放行 = 0**；触发条件 = 该 key 实例数 > R × burstSeconds（票 09 harness 4 JVM 配 rate ≤ 4/s 即触发）。**用户裁决（2026-09-22，选乙案）：本地桶容量下限 1 个请求**——`容量 = max(份额 × burstSeconds, 1 请求)`；微份额行为 = 每 `1/份额` 秒放 1 个、无囤积；代价 = 上界改写 `Σ max(份额×burst, 1)`（对照臂 s5b 实测最坏 3.6×R×burst；正常区间与原式逐字相同）。实现易错点三条在报告 §7.4（下限只作用容量不作用速率；rescale 用新旧容量算；share=0 不凭空多放）。

### ⚠️ 新发现二：闲置清零（无需决策，spec 写使用建议）

客户端一个上报窗口零到达 ⇒ wants=0 ⇒ 份额清零 + 存量令牌 ×0 ⇒ 恢复期 ≤ 1 轮拒绝。这是"分配吃实测 wants"的固有性质（Doorman 同款，s5 里 37.2% 实例间歇清零、账本其余实例塌缩到 712.6 即其放大形态）。缓解钩子票 04 Q4 已有（**配置基线**：分配取实测与基线的较大值）——spec 在"参考接入器"节写一句"突发型 key 应声明基线"，不新增机制、不改裁决。
