# 03 调研：算法细节与陷阱清单

Type: research
Status: resolved
Blocked by:

## Question

把"令牌桶 + 分布式配额"这条路上会踩的算法与数值坑列清楚，供 [票 04](04-grill-lease-model.md)（在飞量上界）与 [票 05](05-grill-local-bucket-and-admission.md)（本地桶 / 时间源）拍板时依据。

只收事实与推导，选型判断留给 04 / 05。

1. **数值精度**：令牌桶惰性补令牌用浮点（double）还是定点（long/纳秒整数）的取舍；长时间运行（天/周）后的累积漂移量级；`nextFreeTicketMicros` 这类单调递增时间戳的溢出边界
2. **时间源**：单调时钟（`System.nanoTime`）vs 墙钟（`System.currentTimeMillis`）在限流里的作用；**时钟回拨 / NTP 跳变**的后果与常见防护（Guava 怎么处理的，`nanoTime` 会不会回退）；客户端与服务端**时间不同源**时租约怎么算（用谁的时间）
3. **突发语义**：`capacity` 与 `rate` 的配比怎么选；"冷启动突发"是不是我们想要的（一个空闲很久的客户端是否该被允许瞬间打满桶）；Guava `SmoothWarmingUp` 的预热解决的是什么场景
4. **在飞量的上界推导**（本票的核心）：给定 rate=R、租约时长=T、客户端实例数=N、单次 batch=B，**全局瞬时放行量的上界是什么**；"在飞量上限 = C×配额"这个约束能不能真的兜住突发、该怎么设才有效；N 很大（几千实例）时这套还成立吗
5. **HTTP 层的原子性与重试**：租约请求超时后客户端重试会不会**重复领**（幂等键的必要性与形状）；服务端如何识别同一客户端的重复请求；网络分区期间两边各自的状态会怎样漂移
6. **中心的容量账**：每个 key 的权威桶状态最少要存什么、占多少字节；10k / 1M key 各占多少内存；心跳与续租带来的请求 QPS 怎么估

产出：`research/03-algorithm-pitfalls.md`。推导类结论要给过程（公式 + 代入算例），不要只给结论。

## Answer

报告：[research/03-algorithm-pitfalls.md](../research/03-algorithm-pitfalls.md)。**§4 全部为纸面推导，未实测**，票 04 定完租约口径后建议用小仿真正式复核三个算例。

**4. 在飞量上界（核心）。** 记 R=速率、K=规则桶容量、T=租约时长、N=实例数、B=批量、f=瞬时活跃实例比例。主公式（推导）：**瞬时突发 ≤ min{ K + f·N·B , R·T + 2K }**，且任意窗口 Δ 的放行量 ≤ R·(Δ+T)+2K。两条在飞界：① 每客户端囤积 ≤ B ⇒ 在飞 ≤ f·N·B；② **在飞 ≤ R·T + K，与 N、B 无关**（中心按 R 发放，T 秒内发不出更多）。**N 只在界①里** —— 算例：R=1000/s、K=1000、T=10s、B=20、f=1，N=200 时突发 ≤ 5000（5×K，界①主导）；N=5000（25 倍）时突发只涨到 12000（12×K，界②封顶）。**所以"实例多了就雪崩"在上界维度上不成立。**

**「在飞 ≤ C×配额」能不能兜住，全看"配额"锚在哪。** 锚 K 时 C 直接就是"允许多超几倍"：C=1 ⇒ 突发 ≤ 2K，有效。锚 R·T 时默认 C=2 ⇒ 在飞上限 2RT，代入 T=10s 等于**放行 20 秒流量**——算例 A 里 `C·2RT=20000` 落在 min 的最大项上，**约束完全没生效**；要压到 2 倍突发需 **C ≤ (λ−1)·W/T = 0.1**，默认的 2 大了 20 倍。

**C 的有效区间与可行条件（式 8）：** `f·N·B ≤ (λ−1)·K` 即 `B ≤ (λ−1)·K/(f·N)`。代 λ=2：算例 A 得 B≤5（**"一次领 20 个"与"突发 ≤2 倍"在 N=200 下不能共存**）；算例 B 得 **B≤0.2，即 B<1，机制直接失效**；算例 C（N=4）B≤25，是舒服区间。另得中心租约 QPS 下界 **≥ N/(C·W)（与 R 无关！）**：N=5000、C=1 时 **5000 QPS/key**，哪怕该 key 只有 1 QPS 流量。**大 N 下"上界"没问题但"收益"没了**，且 90% 批量过期作废（r_i·T=2 用不满 B=20）——**"过期作废的发放量退不退回中心账"必须在票 04 裁决，它在大 N 下放大成 10 倍量级服务偏差**。

**其余五项。** ①精度：时间轴用 long 纳秒（微秒的硬顶是 R≈10⁶/s，Guava 源码 TODO 明说）；数量用 double 或定点都行（误差 1e-16 vs 1e-6，都远够），**漂移不是主要风险**；long 纳秒差值 292 年不会溢出，绝对形式 `nanoTime()+T` 才有风险（epoch 纳秒是 2262 年）。②时间源：`nanoTime` **规范未承诺单调**，但 HotSpot 在 Linux 上显式声明 `may_skip_backward = false`（macOS/AIX 是平台特定实现，未覆盖）；**租约必须传"时长"不传绝对时刻**，两端各用各自单调时钟——δ=1s 钟差就能多出 R 个令牌的在飞量。Doorman 用墙钟 `expiry_time` 是先例，靠"内网 NTP + 5 分钟租约"成立。③突发：Guava 默认 `maxBurstSeconds=1.0`（K=R×1s），桶存在的**首要理由是吸收调度抖动、不是奖励突发**；`SmoothWarmingUp` 保护的是**下游**（冷缓存需预热），冷因子硬编码 3.0——注意它在分布式下的语义错配：Guava 的"空闲"是单进程空闲，gatekeeper 的"空闲"是全局键空闲，不是一回事。⑤幂等：POST 非幂等（RFC 9110 §9.2.2），超时重试**必然**重复领；幂等键须**客户端生成、每批一个新 UUID、重试复用**（Stripe 形状），服务端缓存首次响应体回放并设保留期；**`clientId` 必须是"实例身份+世代号"**（Kafka producer epoch 形状），否则崩溃重启的实例会让在飞量翻倍。fail-open 的本地速率必须是 **R/N 而非 R**（Doorman `safe_capacity` 形状），否则分区期间 N 倍超发。⑥容量：每 key 最少三字段（令牌/上次补充时刻/规则引用）≈ **64 B**，10k key 不到 1 MB；要"在飞上限"就加时间环，**每 key 76+8T 字节**（T=10s → 1M keys 约 156 MB）；**绝不按租约条目记账**（99 B/条 × N 条/key，10k key 就 200 MB 起）；**心跳必须按客户端聚合**——按 (key, 实例) 打点在 10k key×200 实例下是 **200,000 QPS**，聚合后 20 QPS，**所以协议的批量接口是硬要求不是优化**。
