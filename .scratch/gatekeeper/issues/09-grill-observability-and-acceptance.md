## Question

怎么证明这个限流器**是准的**，以及它**坏的时候能被看见**。这是新起的独立工程，没有本仓既有的可观测设施可继承（单体只有一个 `JwtAuthenticationFilter`，全仓无 actuator / micrometer）。

要裁决：

1. **指标集**：中心侧（发放量、在飞量 / 悬浮量、拒绝率、各分片负载、租约回收量、规则版本分布）与客户端侧（本地桶水位、领额度延迟与其失败率、降级次数、被限流次数）。**每个指标要能回答哪个问题**，不列没用的
2. **设施选型**：引 micrometer + Prometheus（通用件的常规姿势，但要评估"给一个库引一整套观测依赖"是否合适）；还是照 virtual-thread effort 的先例走"**命名规范 + JMX + JFR / 轻量日志**"；两者对"通用中间件"这个定位各意味着什么（下游接入方的成本）
3. **准确度验收**：稳态放行 ≤ `rate × (1+ε)` 怎么测——什么压测形态（并发数、客户端实例数、时长）、用什么观测点（中心的发放计数？客户端的放行计数？）、ε 取多少算通过；**瞬时突发 ≤ 在飞量上限**怎么测（需要一个能制造同步突发的 harness）
4. **故障验收**：逐场景给出期望行为与验证方法——中心宕机（fail-open 是否真的放行、本地是否按规则自跑）、单分片宕机、规则热更新（在飞额度是否按预期处置）、客户端重启、网络分区恢复后的收敛
5. **验收资产落哪**：脚本与报告目录（照本仓 `.scratch/*/measure/` 惯例，产物不入库），以及**验收要不要常态化**（virtual-thread effort 的结论是 JFR 常态化 + 人工手册）

### 1. 观测设施（Q1 + Q9 + Q10 + Q11）：分裂式——center 带 micrometer，SDK 零依赖

- **`gatekeeper-center` 引 `micrometer-registry-prometheus`**，`/metrics` 端点常开。中心是新起的独立服务，观测是它自己的事；与本仓四工程「零 metrics」先例（virtual-thread 票 10）的**差异是有意为之**——那是对既有单体 retrofit、引设施不成比例，这里是新服务且观测本身就是交付物的一部分
- **`gatekeeper-client` SDK 零观测依赖，三件套**：内置原子计数器（指标全挂这）+ **默认 MXBean**（接入方零成本拿到 JMX 读数）+ **`GatekeeperObserver` SPI 回调**（放行/拒绝/降级/续租结果/逐出事件；桥接 micrometer 或自埋点走这里）。MXBean 是「开箱能看」，SPI 是「能接走」，计数器是共同底座
- **验收不起 Prometheus**：取数 = 窗口起止各抓一次 `/metrics` 文本（client 侧读 MXBean），harness 自行算差值；Prometheus/Grafana 是部署/展示面，spec 不把验收绑在它上。指标端点常开保证「上真 Prometheus 即插即用」
- **key 维度不进指标**（10k key 做 tag 是基数爆炸，MXBean per-key 注册同样不可运维）：指标只回答系统健康问题；key 级排查（"这个 key 为什么被限"）走**日志采样**（续租/拒绝事件带 key）+ 一个**管理端点**（`GET /admin/keys?top=N`，按水位/份额排序的实时快照，中心从账本直读、SDK 侧经 MXBean 同理）。指标 tag 维度**只允许 `rule`**（规则数是人工管理的个位～两位数，基数安全）

### 2. 指标清单定稿（票面 Q1）：每个指标回答哪个问题

**中心侧**（micrometer，命名 `gatekeeper.<域>.<名>`）：

| 指标 | 回答哪个问题 |
| --- | --- |
| 份额发放合计（tag=rule） | 中心发了多少额度——与客户端放行合计对照，两者偏差暴露幽灵条目/逐出异常 |
| 首租结果计数 `{result=granted\|throttled\|fail}` | 首租失败率（票 06 ②）；`throttled` 命中数（票 08 ②）——绝不能被读成 share=0 或 unmatched |
| 在册条目数 / 在册实例数（gauge，分片维度） | 每分片负载（票 06 ②）+ 账本是否在收敛 |
| 冷驱逐 / ttl 过期 / return 回收计数（按 cause 分） | 租约回收量（票面 Q1 原列）——幽灵条目是否按期消失（票 08 ③ 验收看这里） |
| `421` 重定向计数 | 路由错发频率（票 06 ②）——持续非零 = 拓扑不同步 |
| 幂等去重命中计数 | 重试/重复量（票 08 ②） |
| `400` key 超限计数 | 契约违约量（票 08 ②） |
| 规则版本错位计数 + 配置整份拒收计数 | 规则热更新的观测面（票 07 ①，错位窗口 = 一个 `refresh_interval`、只观测不阻断）；死规则/易误配前缀 = 加载期告警日志，不进指标 |
| 续租请求处理时延（timer） | 标定复核 ③ 的观测点（§5） |

**客户端侧**（counter + MXBean，实例级聚合；SPI 事件 = 同一清单的回调版）：

| 指标 | 回答哪个问题 |
| --- | --- |
| 放行计数 | **准确度验收的主观测点**（§3） |
| 被拒计数 | 限流是不是在真的拦（票 05 ①） |

| `acquire` 等待分布 | 放行延迟体验（票 05 ①） |

### 3. 准确度验收（票面 Q3 + Q2 时序）：长窗口平均，不按秒断言

- **判据形状**：稳态窗口 Δ 内平均放行率 ∈ `[R, R×(1+ε)]`；**不按秒断言**（速率口径的"一秒一秒准"已被票 03 否过）。**ε 临时取 2%**（Doorman 实测稳态超调 6% 是它的分配算法；我们是 O(n) 比例份额、理论收敛无系统性偏差，2% 留余量又不松到测不出问题）、**Δ 引票 12**（票 03 的结论是分钟量级，不是一秒一秒）——两者票 11 落稿前以票 12 产出定稿。⚠️ **2026-09-22 [票 12](12-research-rate-lease-bounds.md) 已回填（Q2 接口交付）**：**Δ = 60s、ε = 2% 定稿**（推导：窗口超额 ≤ `R × burstSeconds` 固定一项 ⇒ Δ ≥ burstSeconds/ε = 50s，Δ=60s 留 1.7% 余量；⚠️ **Δ 随规则的 burstSeconds 走**：Δ ≥ burstSeconds/ε，burstSeconds 配 10 时要 500s——spec 写公式不写常数）；降级窗口不进本验收（归故障验收，恢复口径 ≤ 1 个 refresh_interval）
- **观测点**：各客户端实例放行计数**合计**为主（用户感知口径）+ 中心份额发放为**对照**（偏差本身就是诊断信号）
- **瞬时突发 ≤ `R × burstSeconds`**：栅栏同步起跳后 1s 窗口的放行增量（harness 见 §4；构造上界由"每实例桶容量 = 份额 × burstSeconds"保证，测的是实现没把它做穿）。⚠️ **2026-09-22 [票 12](12-research-rate-lease-bounds.md) 乙案（容量下限 1 请求）后改写为 `≤ Σ max(份额 × burstSeconds, 1)`**——harness 的 rate 配置要让每实例份额 ≥ 1/burstSeconds（4 JVM 时 rate ≥ 4/s），否则微份额区间读数对不上这个式子（[research/12](../research/12-rate-lease-bounds.md) §7）
- **过渡窗超发 ≤ `2R`**：中心重启后**一个 `refresh_interval` 内**的放行总量（票 06 的纸面账，本票**实测**——这是可测验收项，不是纯推导）。⚠️ **2026-09-22 [票 12](12-research-rate-lease-bounds.md) 已复核**：2R = 速率上界（s4 实测降级段稳定 1.1R、恢复即收敛）；"一个 refresh_interval"读作收敛时间，分区情形持续到恢复
- **世代交替**（票 08 ③）：崩溃重启后稀释窗口内**不超发**、幽灵条目过期（≤ 2 个 `refresh_interval`）后一个 `refresh_interval` 内份额恢复（读 §2 的回收计数与份额发放对照）

### 4. harness 形态（Q4）

- **单机多进程**：1 个 center 进程（单分片起步）+ **4 个** SDK 客户端 JVM（可调档 2–8——足够证份额分配与收敛，不让单机噪声盖过读数；大 N 留给票 12 仿真），实例身份用 `POD_NAME` 环境变量显式区分（不靠 HOSTNAME 巧合）
- **流量形态**：`CountDownLatch` 栅栏同步起跳的闭环突发 + 固定速率吸入的稳态段，**每臂稳态 ≥ 5 分钟**（≥ 60 个 `refresh_interval`）
- **一个 harness 覆盖四个验收项**：突发 ≤ `R×burstSeconds`、过渡窗 ≤ `2R`、`ttl=0` 主动停 vs 断租被动继续跑（票 05 ③ 的可区分行为对）、分区 fail-open

### 5. 故障验收（票面 Q4 + Q5）：两档执行形态

场景清单已由 04–08 转齐，按"能否嵌进 IT"分档——**能进 IT 的进 IT 才有回归防线**（virtual-thread 票 10 的教训：断言进 seam 才防悄悄退化）；真进程级故障脚本化 + 人工走查，读数留票面。

| 场景 | 执行形态 | 期望行为 |
| --- | --- | --- |
| 同步首租拦截（冷启动第一个请求） | 自动化 IT | 有规则但首租失败 ⇒ 拒（票 05 ②） |
| 规则热更新 | 自动化 IT | 份额变立即生效 + 桶按容量比例缩放 + 回调触发立即续租（带抖动） |
| 规则删除 | 自动化 IT | 该 key 一个 `refresh_interval` 内收敛为放行、**无拒绝窗口**（票 07 ②） |
| `ttl=0` 主动停 vs 被动到期继续 | 自动化 IT | 两行为可区分（票 05 ③） |
| 世代交替（崩溃重启） | 自动化 IT | §3 末条口径 |
| 客户端重启 / 桶表逐出后重遇 | 自动化 IT | 重遇走冷启动首租路径（Q12） |
| 杀 center（fail-open 真的放行、本地按规则自跑） | chaos 脚本 + 人工走查 | 按最后份额继续；center 回来 ≤ 1 个 `refresh_interval` 收敛 |
| 双 center 起两分片再杀一个 | chaos 脚本 + 人工走查 | **存量 pod** 按最后份额 fail-open；**新起 pod 首租失败 ⇒ 拒**（票 06 Q3/Q9 已知限制）；恢复 = 实例回来后 ≤ 1 个 `refresh_interval` 收敛 |
| 网络分区 + 恢复 | chaos 脚本 + 人工走查 | 分区期间按最后份额跑（fail-open）；恢复后一轮内收敛 |

### 6. 标定复核（票 08 ① 交接）：性能值实测、策略值走场景语义

- **实测复核三项**（gatekeeper/measure/ 下微基准）：① **首租端到端 p99 ≤ 50ms**（合批窗 10ms 下，空载 + 带载各一档）；② **满配 500 key/请求的续租批**编解码+网络端到端 ≪ 2s 子批超时；③ **中心单分片续租吞吐 ≥ 200 QPS**（1000 实例 ÷ 5s 算例，照票 06 Q6 形状）
- **语义复核四项**（不另立基准，由 §5 场景验收本身复核窗口语义）：`refresh_interval` 5s、`min_renew_interval` 5s、`ttl = 2×`、去重窗 = 一个 `refresh_interval`——判据即"规则删除一个 refresh_interval 收敛 / 幽灵条目 2 个 refresh_interval 内过期 / 重试退避不惊群"这些场景行为成立

### 7. 容量默认值（Q7 + Q12；map 交接两条落定）

- **每实例订阅 key 数上限 = 10k**（确认票 06 Q6 建议值；触发 = 显式拒绝 + 指标可见，不是静默坏）——⚠️ 以票 12 §5 内存账复核
- **本地桶表上限 = 10k**（与订阅上限**同值、一个旋钮两处引用**）；超限**逐出最冷条目**（LRU 序，复用票 05 冷 key 逐出的同一机制），逐出后重遇 = 冷启动首租路径（50ms 预算 + 合批兜底）；**绝不因表满拒绝请求**——拒绝是限流语义的输出，不该被内部容量误触发。配套观测：桶表条目数 + 逐出计数（§2）

### 8. 验收资产与常态化（票面 Q5 + Q6）

- **落点**：脚本 + README（坑清单）落 `gatekeeper/measure/`（随 subtree split 走），产物不入库——照本仓惯例
- **验收不常态化**：一次性跑、读数留票面、脚本保留可重跑（virtual-thread 票 10 同构结论：验收是仪式化的会重复，观测才值得常开）
