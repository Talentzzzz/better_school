# 06 grilling：中心的分片与高可用

Type: grilling
Status: resolved
Blocked by: 01

## Question

中心从"单实例 + 内存"走向图绘期已定的"**多实例 + 按 key 分片**"（见 [map](../map.md) 的 Notes：中心之间不共享状态，Redis 只做规则存储/快照、不做令牌账本）之后，拓扑与故障面怎么定。

要裁决：

1. **分片算法与拓扑**：`hash(key) % N` 还是 一致性哈希；客户端怎么知道有哪些实例（静态配置 / Nacos 注册 / 中心自己广播拓扑）；分片数 N 是固定还是可动态调整
2. **路由错了怎么办**：同一个 key 被两个实例同时当成权威 → 额度被发两份、限流失效。**防到什么程度**——中心侧拒绝非本分片的请求（客户端必须路由正确）？还是容忍并靠"在飞量上限"兜？这是本票最关键的一问
3. **单个分片挂掉**：那部分 key 的客户端怎么办（fail-open 本地自跑 / 客户端重路由到别的分片 / 中心副本接管）；与"默认 fail-open"口径怎么对齐；**挂掉期间恢复后的状态怎么收敛**
4. **扩缩容**：加/减一个实例时额度状态怎么迁（整块重建？按迁移比例缩水？短暂双发？）；客户端拓扑感知的更新时间窗
5. **中心重启**：内存里的权威桶状态丢不丢？要不要持久化 / 预热？丢了 = 全部 key 重置为满桶 → 是**短暂超发**还是可接受（这笔账要算出来）
6. **中心自己的保护**：中心被限流请求打爆时怎么办（它自己需要一个限流器吗？还是靠连接数/队列兜）；租约请求的峰值 QPS 怎么估（依赖票 03 的容量账）

## Answer

**裁决：中心 = 多实例 + 固定槽位分片（M = 1024，`slot = murmur3(key) % M`，显式「槽→实例」映射表带拓扑版本号）+ 中心侧权威校验与重定向（绝不替别的分片发份额）+ 客户端按分片拆批续租 + 单槽无副本（挂掉的槽靠客户端 fail-open 兜、实例回来走冷启动收敛）+ 中心自身只做过载保护（不内建限流器）。**

> **编号约定**（供 [票 11](11-task-write-spec.md) 逐条汇总）：**Q1–Q9 照票面 `## Question` 的编号**；**Q10（拓扑版本错位 / redirect 往返）、Q11（槽→实例映射表的生成与迁移）、Q12（批量续租怎么跨分片）、Q13（上报幂等）是票面没列、本轮 grilling 新暴露的四条**。另：**Q5 / Q7 由 [票 04](04-grill-lease-model.md) 已裁、Q9 的客户端一半由 [票 05](05-grill-local-bucket-and-admission.md) 已裁**——本票只收口、不重开。

### 决策依据

**1. 根决策「中心之间不共享状态」把分片归属逼成一个纯函数。** 同一份拓扑，所有参与方必须算出同一个答案；一旦要靠中心之间协商（选主、广播、转发），"不共享状态"就被悄悄破掉了。这一条直接排掉三个选项：中心自己广播拓扑（中心挂了就没人能广播）、中心间转发（Q12 的乙）、机械 `slot % 实例数`（把实例数塞回函数，6→8 时约 3/4 的槽换家）。

**2. [票 04](04-grill-lease-model.md) 撤销在飞量上限 ⇒ "容忍双发"这条路没了。** 速率口径下"两个分片都以为自己是权威"的后果是**份额被重复计入**（该 key 的全局上限按 2 倍算），而没有任何机制兜它。所以路由正确性**必须**由中心侧强校验兜住——这是 Q2 的直接依据，也是本票最关键的一问。

**3. 票 04 Q4「上报就是算法输入」⇒ 账本状态是「可在 ≤ 1 个 `refresh_interval` 内从续租请求重建的派生状态」。** 由此：扩缩容与重启**都不需要状态迁移**，只需换拓扑 + 短租约（Q4 / Q5）。这也是本票能不落盘、不复制还不塌的根本原因。

**4. Doorman 有两条可引的先例（其中一条只是文档声明）。** ①**非 master 回 master 地址**——`doc/design.md:208-216`（[research/01](../research/01-prior-art.md) §1.5）逐字：`If a non-master task gets a request if will respond with the address of the master, so that the client knows who to talk to.` ⚠️ **该条只见于 `doc/design.md`**，**本 effort 未在 `server.go` 中核实**（[research/02](../research/02-open-source-impls.md) 没有读这条路径；它核实的是"5s 内静默忽略"那条**同为文档声明**，见其 ⚠️ 未核实项 9），引用时要带上这条。②**分片归属依赖外部 LB、中心不持久化不复制**——`doc/design.md` 的 "Handling cluster unavailability" 节首注（[research/01](../research/01-prior-art.md) §1.5）逐字：`***Note***: The strategies described in this chapter are dependent on the availability of a global load balancing infrastructure that directs clients to the closest available server with capacity.`；`doc/design.md:538`、`:540` 逐字：`The server does not store its internal state on a durable medium and also does not replicate it to the runners-up in the election process.`

**5. ⚠️ 本票的核心机制没有一手参照可抄（Q8 的正面回答）。** 见下面 Q8——**槽位表 / 拓扑版本号 / 中心侧权威校验与重定向 / 冷启动收敛**这一套是我们自研的，spec 里**不得**写成"业界通行做法"。

### 逐条结论

**Q1 分片算法与拓扑** → **固定槽位数 M（默认 1024）+ `slot = murmur3(key) % M` + 显式「槽→实例」映射表**（Redis Cluster 形状）；**拓扑 = 与规则源同一套抽象的配置**（v1 静态文件优先，可换 Nacos），**中心与客户端读同一份**；**全链路带拓扑版本号**（客户端请求带上、中心响应回带）。**槽位数固定 1024；分片数 = 中心实例数 S，动态**（一个实例就是一个分片）——两者解耦正是选它而不选另外两条的理由：`hash(key) % N` 在 N 变化时**全量重排**（**手算**：6→8 时 key 不换家要求 `hash % 6 == hash % 8`，在模 24 的一个周期里只有 `0..5` 这 6 个值命中 = **1/4 不动、3/4 换家**；而理想的分片迁移面只是新实例分到的份额，6→8 时约 `2/8 = 1/4`），一致性哈希环要自己写 vnodes 与再平衡却买不到映射表之外的任何东西。**否掉"中心自己广播拓扑"**：拓扑是部署事实、应由配置源承担，而且中心挂了就更没人能广播。
> v1 **一个实例就是一个分片**（槽→实例直连，**不引入"逻辑分片 id"这层间接**——它是 Q9 被否掉的乙方案的前提）。下面各条里的 **S = 分片数 = 中心实例数**，**槽数 M 恒为 1024、与 S 无关**。

**Q2 路由错了怎么办** → **中心侧权威校验 + 重定向**：中心先算 `slot(key)` 是否归自己，**不是就绝不接**，回 `421 redirect{ authority, topo_version }`；客户端收到立刻改道并刷新拓扑。**两道保险**：拓扑版本号（见 Q10）+ `clientId` 世代号（票 04 Q11）。**不能容忍双发**，理由见"决策依据 2"。先例为 Doorman `doc/design.md:208-216`（⚠️ 文档声明，见"决策依据 4"）。

**Q3 单个分片挂掉** → **客户端不重路由**：按最后已知份额继续跑（= 票 05 Q3 的 fail-open），续租失败就退避重试；**分片回来或新权威接管时按冷启动语义重建**——因为客户端上报**本来就是分配算法的输入**（票 04 Q4），新权威一个 `refresh_interval` 内即可收敛。**不做副本、不做接管**（见 Q9）。
> 挂掉期间会看到什么（如实记）：那部分 key 的**份额不再重新分配**，且**新起的 pod 拿不到份额**（首租失败 → 拒绝，票 05 Q10 第②格）——这是 [票 05](05-grill-local-bucket-and-admission.md) 那一格的一个具体触发面。

**Q4 扩缩容** → **改拓扑、不搬状态**。迁移 = 发布新拓扑（槽整块或分批换家、可灰度），新权威**空账本**起步、按客户端上报在一个 `refresh_interval` 内收敛。与根决策"中心之间不共享状态"一致，也与 Doorman 一致（它同样不复制，靠外部 LB + 重新选举）。

> **题面 Q5 要求"算出来"的那笔账（超发上界；它落在 Q4 的重启 / 迁移路径上）**：取 `R = 1000/s`、该 key 在册 20 个实例、每实例份额 50/s。重启 / 迁移后，**已续租的客户端拿到新份额（Σ ≤ R）、尚未续租的仍在跑旧份额（Σ ≤ R）** ⇒ 过渡窗口内全局放行 ≤ `R + R = 2R`，窗口长度 W = 拓扑/租约收敛时间 ⇒ **超发绝对量 ≤ `R × W`**。把 W 压到一个 `refresh_interval`（默认 5s）⇒ **≤ 5000 个请求**（≈ 满速 5 秒的量）。**结论：可接受，但前提是"把窗口压住"**——拓扑版本号 + redirect 立即改道 + 新权威首轮只发短 TTL 的保守份额，三者缺一不可。
> 可选旋钮（谨慎用）：首轮发放总额封顶 `α·R`（α 默认 1.0，可配 0.5）⇒ 上界收紧到 `(1+α)·R`，代价是恢复期整体**偏保守（少发）**。默认**不开**。
> ⚠️ 这是纸面推导、**未实测**；"带收敛项的形式"与仿真正是 **[票 12](12-research-rate-lease-bounds.md) Q1** 要的东西。**这不是我们的独有风险**：Doorman 自己仿真的 `shortfall` 读数逐字是 `The maximum capacity handed out was 530.24 (106.05%)`，而它给出的成因与我们这个窗口**是同一个机制**（上游重分配后，下层手里仍握着旧租约），文档还明说该状态 `will have corrected itself in a single refresh interval`（`doc/design.md` 的 "Convergence and shortfall" / "Shortfall" 两节，[research/01](../research/01-prior-art.md) §1.3）⇒ **我们的 `2R` 与 Doorman 实测的 `shortfall` 是同一个成因、同一个自愈窗口**（它是实测峰值 106%、我们是只在重启 / 迁移瞬间出现的推导上界 200%），**不是本设计独有的新风险**；且 Doorman 明确认定不值得治：逐字 `Combatting shortfall would mean changing the system in a way which also slows down convergence.`
>
> ⚠️ **2026-09-22 [票 12](12-research-rate-lease-bounds.md) 已交付形式化与仿真（细化非反转）**：① `2R` 指**速率**上界，实测形态见 [research/12](../research/12-rate-lease-bounds.md) §1.3（s4 分区情景：降级段稳定 1.1R、恢复即收敛；本条的重启 / 迁移情景同构）；② **本条"窗口 = 一个 refresh_interval"应读作拓扑 / 租约的收敛时间**——分区情形的 2R 形态持续到分区恢复为止，不是只超发一个窗口；③ Doorman 的 106.05% 成因是其**层级部署**（中间层"上游新额度 < 已发下游的在租额度"），本设计单层、等价通道只有 fail-open 陈旧份额（≤ 2R 封顶，[research/12](../research/12-rate-lease-bounds.md) §1.1 断言 A 证明正常路径 Σ份额 ≤ R 硬成立）。

**Q5 中心重启** → **按票 04 Q5 收口，本票不重开**：v1 **不落盘**；重启后第一轮保守发放 + 短有效期；重启前给在册客户端下发 `ttl = 0` 预告降级；**不抄 Doorman 的 learning mode**。⚠️ 票面原问法"丢了 = 全部 key 重置为满桶"**已不适用**——速率口径下没有"满桶"这个量（客户端桶里的余量是它自己的，不是中心的资产）。**本票的补充**：**重启与单分片挂掉是同一条路径**（都走冷启动收敛），区别只在触发面（全部分片 vs 一个分片）与是否提前预告（重启可预告，宕机不能）。

**Q6 中心自己的保护** → **只做过载保护，不内建限流器**：①有界队列 + 快速失败（503 ⇒ 客户端据此 fail-open）；②**每请求 key 数上限**（建议 500，可配）；③**每实例订阅 key 数上限**（建议 10k，可配）。依据：中心的 QPS ≈ `实例数 / T`、**与 key 数无关**（票 04 Q8；5000 实例 / 5s = 1000 QPS 全中心——⚠️ **该数被 Q12 的"按分片拆批"细化为 ≤ 8000 QPS，量级结论不变**），量级不足以需要一个自举限流器；真正的成本是**每 key 每次续租要重跑一遍分配**的 CPU（`Σ_k 该 key 在册实例数 / T`），靠**分片摊 + 批量上限**挡。⚠️ "一批塞 10 万个 key"才是能打爆中心的写法——所以②③比对症得多。

**Q7 中心重启后的状态（业界两条对立路线选哪条）** → **选 Doorman 路线（不持久化、不复制）**，不选 DFMF 的"主从 + 快照"。
- **对 DFMF 数据点的正面回应**：它图 6 的优势有两项来源——主从快照，以及**作者自认的"让节点尽量持有闲置配额"**（[research/01](../research/01-prior-art.md) §5「DFMF」引论文 §4.5 末逐字：`考虑公平性最大值为 1,实际上掩盖了 DFMF 的另外一个优势,即让节点尽量持有闲置配额以应对突发流量,从而弥补流量预测不够精确的缺点.`）；实验规模仅 **4 台云主机**、无方差/显著性，且对照臂是否上游 Doorman 原版**未确认**（[research/01](../research/01-prior-art.md) ⚠️ 未核实项⑥）。
- **最本质的一条**：**Doorman 非有 learning mode 不可，是因为它的客户端在中心不知道 `has` 时只能拿 0**；**我们的客户端根本不需要中心知道 `has`**（它按自己最后份额跑，票 05 Q3）⇒ 中心空着重建**不影响对外分发**。"崩溃后对外分发骤降"这个 DFMF 要补的洞，在我们这里由客户端侧补齐了。
- 代价：中心不掌握"在飞份额"⇒ 过渡窗口的双发上界 `2R`（见 Q4 的账）。

**Q8 这一块没有一手参照（如实标注，不是问题）** → **本票的分片与迁移设计基本是自研**，spec 里必须如实标注、**不得暗示"业界通行做法"**。三条依据：① **Envoy RLQS 无开源服务端实现**（[research/01](../research/01-prior-art.md) 未核实项②逐字：`Open source reference implementation of the rate limiting service is currently unavailable`），其分片 / 选主 / 持久化 / 重启重建**全部无从以一手材料回答**；② **Sentinel 集群流控的状态全在堆内存**（`ClusterMetricStatistics.java:32` 的 `METRIC_MAP`，重启即清空、无学习模式），且其 wiki 把多 server 的分片与故障转移**明确推给使用方**——逐字：`若在生产环境使用集群限流,管控端还需要关注以下的问题：` / `- Token Server 自动管理、调度（分配/选举 Token Server）` / `- Token Server 高可用,在某个 server 不可用时自动 failover 到其它机器`；③ **Doorman 不持久化不复制、分片归属依赖外部 LB**（见"决策依据 4"）。
> 唯一真正可引的两条都是 **Doorman 的文档声明**（重定向、外部 LB），且都已标明"未在源码中找到实现"。

**Q9 降级档位** → **客户端一半已由票 05 Q3 定**（被动到期 ⇒ 继续最后份额即 fail-open；主动 `ttl = 0` ⇒ 停止自补、存量花完；票 03 §5.4 的 `R/N` 约束在速率口径下自动满足）。**中心一半（本票定）**：① 分片挂掉时**不重路由**（Q3 / Q4）；② **不做槽级主备/接管**（见下）；③ "档位"由**规则级配置**提供（与 map 的"规则级可配、默认 fail-open"对齐），可配 fail-closed（拒绝）——⚠️ **2026-09-22 [票 07](07-grill-rule-model-and-hot-reload.md) Q7 落点**：该「规则级配置」= 规则字段 `fallback: fail-open | fail-closed`，语义 = fail-closed ⇒ **停止自补、存量花完**（复用票 05 Q3 表第二行）；**首租失败不分档一律拒**（票 05 Q10 ②格不动）；**不做** Doorman `safe_capacity` 那种显式 `safeShare` 字段（票 05 Q3 已否）；④ **残余风险如实记**：分区前份额远大于 `R/N` 的实例（它是唯一活跃者）在 fail-open 期间会按那个大份额跑。

> **单槽要不要主备（票面 Q3 列的第三个选项，本轮正面裁掉）**：**v1 不做副本、不做接管**。接管的三条路都被上游堵死——状态迁移与"中心之间不共享状态"的根决策冲突；learning mode 票 04 已明确否掉；客户端可见的拓扑变更就是本轮否掉的"重路由"。**已知限制**（写进 spec）：单槽无副本，挂掉的槽在实例回来前不重新分配份额。**将来可扩展的形状**（留档，不在 v1）：把"槽→实例"改成"槽→**逻辑分片**→实例"两层绑定，实例挂了改第二层——客户端仍只是"改道"，但**分区（非宕机）时旧实例还活着 ⇒ 仍然双发**，要配世代号 fencing 才干净。

### 本轮新增（票面未列）

**Q10 拓扑版本错位的防护（redirect 往返）** → **redirect 回带目标版本 + 客户端单轮只跟一跳**：只在 `目标版本 ≥ 自己版本` 时跟随；同一 key 一轮内最多跟一次；第二次直接**放弃本轮**（fail-open 跑最后份额）+ 后台强制刷拓扑。封死 `A → B → A` 的环。
> 场景：配置源发布 v8，**客户端先拿到、中心还是 v7** ⇒ A（v7）把 slot=130 重定向给 B，B（v7）又重定向回 A，续租永远失败、规则更新永远拉不到。**否掉"只靠部署纪律"**：一次发布顺序搞错就是"该区间限流静默失效到收敛为止"。**退化路径 = 已定好的 fail-open**，所以护栏的代价为零。

**Q11 槽→实例映射表的生成与迁移** → **显式表 = 自动均分生成 + 手工覆盖**：槽按实例数等分自动生成成表（1024 / 8 = 每实例 128 槽），机器规格不齐时可手工调；迁移**逐槽搬、可分批灰度**（一次搬 32 槽这种粒度）。
> ⚠️ **否掉 `slot % 实例数` 机械派生**：它把"实例数"又塞回公式，6→8 时约 3/4 的槽换家，**固定槽位白设了**——这正是 Q1 里被否掉的甲换了个粒度。机械派生**不等于**"自动均分生成显式表"，差别就在公式里有没有那个 N。

**Q12 批量续租怎么跨分片** → **客户端按分片拆批**：一个 pod 的 key 散在 S 个分片里，就拆成 ≤ S 个子请求**并发**发出，每个只带该分片的 key。中心之间**零耦合**。
> **这修正了票 04 Q8 ① 的数字（细化，不是反转）**：全中心 QPS 从 `实例数 / T` 变为 ≤ `实例数 × min(该实例订阅 key 数, 分片数) / T`（5000 实例 × 8 分片 / 5s = **8000 QPS**）。**"与 key 数无关"仍然成立**（封顶于分片数，不是 key 数）；批量接口"是硬要求不是优化"的结论也不变。**否掉中心间转发**：会让中心之间出现横向 RPC 依赖（N² 耦合、转发风暴、超时叠加、内部地址发现），"中心之间不共享状态"这条根决策被悄悄破掉。

**Q13 用量上报的幂等** → ⚠️ **用户在此处否掉了助手的推荐，选了 RLQS 逐字那条**：**上报增量值（本轮 `allowed / denied / elapsed`）+ 客户端生成幂等键、重试复用 + 中心侧短窗口去重表**（[票 03](03-research-algorithm-pitfalls.md) §5.2 的形状）。**不去重**被否（偶发重复计数会让分配算法看到翻倍的需求）；助手推荐的"上报累计值（重试天然幂等、不新增结构）"被否，理由是**保持 RLQS 的字段语义**。
> **去重表的账（[research/03](../research/03-algorithm-pitfalls.md) §5.2 点名"要进票 06 的分片容量规划"，此处交付）**：条目 ≈ 80–120 B（[research/03](../research/03-algorithm-pitfalls.md) §5.2 手算估算，未做 JOL/heap dump 验证，±20%）；**保留期 = 一个 `refresh_interval`**（只服务"超时重试"这个窗口，不做长保留）。Q12 拆批后，**每个子批一个幂等键，收在接收分片的本地**，因此**不引入新的分片维度**。量级：全中心 `实例数 × min(订阅 key 数, 分片数) / T` ≈ 8000 QPS × 5s = **4 万条 ≈ 4 MB**；分片后每实例更小。**另设硬上限**（超限逐出最旧）+ 该表**不参与分配决策**（它不是票 04 Q10 说的那种"派生计数器"，而是一张请求级缓存——这句要写进 spec，否则会被读成与 Q10 矛盾）。
> ⚠️ **2026-09-22 [票 08](08-grill-protocol-contract.md) 收口确认**：①窗长**沿用本条**（= 一个 `refresh_interval`）——grilling 现场初版曾推荐 60s，与本条冲突，已按上游修正（60s 会把"4 万条 ≈ 4 MB"的账放大 12 倍；重试跨度上界 ≈ 3s = 续租超时 2s + 退避 1s，一个 `refresh_interval` 足盖）；②**重复到达的行为落定**：只存 `幂等键 → 时间戳` 不存响应（存响应可达 500 key/批、内存爆炸），重复 ⇒ **跳过用量增量记账、其余照常走**（重算份额 + 返回当前租约状态——份额重算天然幂等）；③硬上限默认 10 万条、逐出最旧；④去重表在收到请求时插入、不区分处理成败（漏记增量的方向是"中心低估需求 ⇒ 少发"，安全侧）。
