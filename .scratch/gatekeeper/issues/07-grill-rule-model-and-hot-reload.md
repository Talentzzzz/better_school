# 07 grilling：规则模型与热更新

Type: grilling
Status: resolved
Blocked by: 04

## Question

规则长什么样、存哪、怎么下发、"限谁多少"与"限流器本身"怎么分离。图绘期已定：**规则源 = 抽象 + 双实现（Nacos / 本地文件）**，且**客户端也必须知道规则**（否则无法本地放行）。

要裁决：

1. **规则的字段集**：每个字段逐个定——key 表达式、速率（rate）、突发容量（capacity / burst）、在飞量上限（overshoot，**若票 04 选了令牌租约才有**）、租约时长、生效范围、优先级 / 默认规则、失败策略（fail-open / fail-closed）。⚠️ 字段集与票 04 的结论强耦合
2. **key 表达式的能力边界**：是"限流器解析占位符"（`user:{userId}` / `api:{method}:{path}`，需要在接入层做 parametrize）还是"调用方直接给最终 key"（限流器只当做字符串）？前者更好用但引入解析层与"规范化"问题（`/api/post/123` vs `/api/post/456`）
3. **规则源的接口形状与双实现**：接口定义（拉取 / 推送 / 版本）；Nacos 实现与本地文件实现各自的行为；**中心与客户端各从哪读规则**（客户端直连 Nacos？还是从中心拉？两条路的取舍）
4. **热更新生效语义**：新规则何时生效、**在飞令牌怎么处置**——立即按新规则（手里的旧额度作废？）、等租约自然过期、还是"规则收紧时可以没收客户端手里的额度"（需要一个"版本号 + 客户端主动作废"的动作）。这是本票最难的一问
5. **规则缺失 / 冲突 / 写错时的行为**：没匹配到规则 = 全放行还是全拒？配置写错（速率 0、负值、表达式语法错）要不要拒绝启动？两个规则匹配同一个 key 谁赢

> ⚠️ **2026-09-22 [票 04](04-grill-lease-model.md) 已裁，直接定住本票 Q1 与 Q4**：①**字段集**——口径是速率租约，所以"在飞量上限（overshoot）"**这个字段不存在**（该机制撤销）；突发用 **`burstSeconds`**（"允许几秒的量"，K = R × burstSeconds，照 Guava `maxBurstSeconds` 的界面），**不写裸的桶容量数字**；另有租约 / 续租周期（票 04 取 Doorman 的 `refresh_interval` 5s 量级）。②**热更新（Q4）**——照 RLQS：**份额没变就只延有效期、视为租约未变**；份额变了（含规则改动导致份额变）才换租约、立即生效；本地桶衔接照 Guava `doSetRate` **按容量比例缩放存量令牌**。票 04 的 Q9 与本票 Q4 是同一件事的两面，口径已对齐。

> ⚠️ **2026-09-22 [票 05](05-grill-local-bucket-and-admission.md) 已裁，给本票三条**：① **`burstSeconds` 的默认值由本票落**（建议照 Guava `maxBurstSeconds = 1.0`）；**本地桶容量 = 份额 × burstSeconds 是派生量、不进规则**（规则里不写裸容量数字，票 04 Q2 已定）。② **"SDK 本地必须有完整规则集"**是票 05 Q10 第①格（无匹配规则即放行）的前提——所以 Q3 的"客户端规则从哪读"不再是"要不要"，而是**必须有**（直连 Nacos 还是从中心拉，仍由本票定）。③ **热更新导致份额变时本地桶的衔接**是"按容量比例缩放存量令牌"（票 05 Q6，照 Guava `doSetRate`，先乘后除、余数进 `roundingError`），**不是重置**；份额没变则本地桶什么都不动、只延有效期。

> ⚠️ **2026-09-22 [票 06](06-grill-center-sharding-and-ha.md) 已裁，给本票 Q3 添一条**：票 06 Q1 把**中心的分片拓扑**定成"**与规则源同一套抽象的配置**（v1 静态文件优先、可换 Nacos；中心与客户端读同一份；带**拓扑版本号**）"⇒ 本票 Q3 要处理的**配置对象不止"规则"一个**：规则 / **拓扑（含槽→实例映射表）** 两者各自是什么 dataId（或文件）、版本号怎么给、中心与客户端怎么各自读到**同一份**、热更新的传播顺序（票 06 Q10 明确**不靠"先中心后客户端"的部署纪律**兜正确性——版本不同时客户端按 redirect 的版本比较单跳放弃）。⚠️ 票 06 定的"拓扑版本号"与规则版本是**两个独立的版本**，别合并成一个。

依赖票 04（租约口径决定字段集）。结论落 spec 的"规则模型与热更新"节。

## Answer

**裁决：规则 = `{ id?, match, rate, burstSeconds = 1.0, fallback = fail-open }`、per-key 语义（每个 key 独立限流）；核心 SDK 只收最终 key 字符串、占位符模板归参考接入器层；规则与拓扑共用 `ConfigSource<T>` 抽象，客户端与中心直连同一配置源（Nacos push / 本地文件轮询，Nacos 依赖 optional），不从中心拉；热更新继承票 04/05（份额变 → 立即生效 + 本地桶按容量比例缩放），版本错位接受一个 `refresh_interval` 的窗口、只做观测不阻断，客户端收到规则变更回调主动触发立即续租；匹配序 = 精确 > 前缀长度降序 > 声明顺序（无 priority 字段）；配置校验整份 all-or-nothing——中心非法配置 fail fast、SDK 永不因规则拒绝启动。**

> **编号约定**（供 [票 11](11-task-write-spec.md) 逐条汇总）：**Q1–Q5 照票面 `## Question` 的编号**；**Q6（匹配语义「限谁多少」）、Q7（`fallback` 字段与票 05 三分法的叠加）、Q8（规则删除的过渡行为）、Q9（前缀匹配的边界语义）是票面没列、本轮 grilling 新暴露的四条**。

### 决策依据

1. **票 04/05 已把 Q1 / Q4 的大半裁掉，本票是收口 + 补缝**：字段集的口径（`rate R + burstSeconds`、无 overshoot）与热更新语义（RLQS「份额没变只延有效期、变了立即生效 + 按容量比例缩放」）都是已裁结论，票面 ⚠️ 注记已带，不重开。
2. **票 05 Q10 ①格「无匹配规则 = 放行」的前提是 SDK 本地有完整规则集** ⇒ 客户端读规则的那条路必须在**中心挂掉时仍然可得**——这直接把「客户端从中心拉规则」这条路堵掉了（见 Q3）。
3. **票 06 已把拓扑定成「与规则源同一套抽象的第二个配置对象」** ⇒ 配置分发机制全设计只有**一条**，规则不另起一路；规则版本与拓扑版本是**两个独立的版本**（票 06 Q1），不合并。

### 逐条结论

**Q1 字段集** → 每条规则 `{ id?, match, rate, burstSeconds = 1.0, fallback }`：

- `rate`：R，req/s（协议建议 double、SDK 内部定点化且**量化一律向下取整**——票 05 Q6 给票 08 的输入照搬）
- `burstSeconds`：默认 **1.0**（照 Guava `maxBurstSeconds = 1.0`；本地桶容量 = `份额 × burstSeconds` 派生，**规则里不写裸容量数字**——票 04 Q2 / 票 05 Q5 已定）
- `fallback: fail-open | fail-closed`，默认 fail-open；**语义见 Q7**（只作用于「曾有租约」的断租情形）
- **不做「默认规则」对象**：票 05 Q10 ①格「无匹配规则 = 放行」本身就是默认规则，再引入第四个概念只会让「规则集 + 默认规则 + fallback」三者互相覆盖
- `id`：可选，日志 / 指标 / 冲突告警要用；描述字段不要

**Q2 key 表达式** → **核心 API 只收最终 key 字符串**（`tryAcquire(key)` 只当做字符串、规则按 key 匹配）；**占位符模板（`user:{userId}`）与路径规范化（`/api/post/123` vs `/api/post/456`）归参考接入器层**（票 10）——它天然持有请求上下文与模板。依据：① Doorman 的 resource、RLQS 的 bucket key 都是调用方给定的最终字符串，同形最近邻没有解析层；② 解析层放进核心会把「规范化」变成限流器的正确性问题，而它其实是接入器的映射问题。规则的匹配语法 = **显式两值 `matchType: exact | prefix` + `pattern`**，不发明通配符语法（前缀能覆盖绝大多数场景且语义无歧义）。前缀的边界语义见 Q9。

**Q3 规则源接口与「客户端从哪读」** → **客户端直连配置源（与中心同一条路），不从中心拉**。理由：① fail-open 语义要求**中心挂掉时规则仍可得**——从中心拉会把「规则可得性」绑死在中心可用性上，与降级语义自相矛盾；② 票 06 拓扑已是「中心与客户端读同一份配置源」，规则走同一条路 ⇒ 全设计只有**一条**配置分发机制；③ 同形先例：RLQS 的 assignment 由中心下发，但**策略本身就是 Envoy 本地配置**。接口抽象（规则与拓扑共用，票 06 定的「同一套抽象」）：

```java
interface ConfigSource<T> {
    Snapshot<T> get();                    // (内容, 版本) 原子快照
    void addListener(Consumer<Snapshot<T>> listener);  // 变更回调
}
```

- **Nacos 实现** = 订阅 dataId（原生 push）；**本地文件实现** = **轮询 mtime/size（1–2s）**——不用 `WatchService`（Windows/macOS 行为差异是已知坑，秒级延迟可接受）。
- **Nacos 依赖 Maven optional**（按类路径 / 显式配置选实现），通用件不绑 Nacos。
- ⚠️ 双实现是**二选一的实现选择，不是主备链**——不做「Nacos 失败降级读本地文件」的第二条路；Nacos 不可达时 SDK 按 Q5 的启动行为兜（空规则集 = 全放行 + 重试）。
- **配置对象全景**：规则 = `gatekeeper-rules.yml`（一个 dataId / 一个文件装全部规则），拓扑 = `gatekeeper-topology.yml`（槽→实例映射表 + 拓扑版本号）；格式统一 **YAML**（人手写规则、注释有用；本仓 shared config 也是 `.yml`）；group 沿本仓惯例放 `DEFAULT_GROUP`（namespace / group 可配）。与既有 Nacos 的关系 = **共处一个集群、逻辑独立**——gatekeeper 是通用件、不读写 better-school 代码，只是部署时连同一个 Nacos、用自己的 dataId（`better-school-shared.yml` 是「共享配置放 DEFAULT_GROUP」的先例），将来拆出去不受影响。**两个对象的版本号各自独立自增、由 ConfigSource 实现自产**（Nacos：内容 md5 对比 + 单调序号；文件：size + mtime 指纹）——规则版本与拓扑版本不合并（票 06 Q1）。

**Q4 热更新** → 已裁部分（票 04 Q9 / 票 05 Q6）不重开：**份额没变只延有效期、份额变立即生效 + 本地桶按容量比例缩放；不设「版本号 + 主动作废额度」的机制**（那是票面 Q4 的原问法之一，票 04/05 已裁掉）。本票补三格：

- **版本错位**（客户端拿到规则 v9、中心还在 v8）→ **接受一个 `refresh_interval` 的错位窗口，只做观测、不阻断**。错位的后果 = 全局放行 ≤ `max(R_old, R_new) × 一个 refresh_interval`——与票 06 Q4 的 `2R` 过渡窗口**同成因、同自愈窗口、同量级**，fail-open 精神下不值得养一套协议状态机；拓扑 redirect 那套硬机制服务的是「双发」这个**正确性**问题，规则错位只是超发瞬态。「先中心后客户端」的部署纪律同样不靠（票 06 Q10 已否过同一条路：一次发布顺序搞错就是静默失效）。
- **协议请求 / 响应带各自的规则版本号**——**观测面**：中心发现错位打日志 + 出指标（票 09），不阻断。
- **客户端收到规则变更回调后主动触发一次立即续租**（复用票 05 Q9 的客户端侧抖动防惊群）——没有这条，规则收紧最坏要等 `refresh_interval` + 抖动才生效，「热更新立即生效」只剩半截。

**Q5 缺失 / 冲突 / 写错** → 三个格子：

- **缺失**：没匹配到规则 = **放行**（票 05 Q10 ①格，不重开；其前提「SDK 本地有规则集」由 Q3 落地）。
- **冲突**（两条规则匹配同一个 key）：**不设 `priority` 字段，用确定性匹配序**——**精确 > 前缀按 pattern 长度降序 > 声明顺序**，第一条命中即用。理由：① `priority` 是个会被滥用的旋钮（调优先级变成调限流，靠猜）；② 精确 > 前缀符合直觉（`user:1` 的专属规则天然压过 `user:` 前缀规则）；③ 确定性序让规则集**静态可校验**——加载时能检出「永远打不中的死规则」（被更长的前缀完全遮蔽）并告警。启动时把有效匹配序打一行日志（几条规则、几条 prefix），排查成本趋零。
- **写错**：**整份 all-or-nothing**——新配置里任何一条非法（`rate ≤ 0`、`burstSeconds ≤ 0`、match 非法、id 重复）⇒ **整份拒收 + 告警 + 继续用旧份**。理由：配置源是整份发布的，「半新半旧」的规则集不可推理——恰好一半规则被跳过时「这个 key 现在归哪条规则管」没有答案；旧份是最后已知可用状态，向它降级与 fail-open 同精神。**启动行为分裂**：**中心 = fail fast**（配置非法拒绝启动——它是部署单元，错配置必须立刻让人看见，静默跑一份旧规则更危险；运行中配置源短暂不可达 ⇒ 继续旧份 + 重试 + 告警）；**SDK = 永不因规则拒绝启动**（无规则 / 首份配置非法 / 规则源连不上 ⇒ 空规则集 = 全放行 + 「配置非法」告警指标 + 持续重试）——库不打死宿主应用，与票 05 Q10 ①格同精神。

**Q6（新）匹配语义「限谁多少」** → **per-key**：每条规则声明的是「**每个 key** 的速率」，命中同一规则的不同 key（`/api/post/1`、`/api/post/2`）各自独立限流。依据：Doorman / RLQS 逐字同形——resource 即 key、每 resource 一份配额。**「聚合一组 key 共享一份 R」不做**——那是另一族语义（中心账本与份额分配的记账单位要从 key 变成组，直接牵动票 04 的分配算法与票 06 的账本形状），与「熔断 / 并发限流不做」同一条边界纪律，spec 写明「聚合一组 key 共享额度在边界之外」。

**Q7（新）`fallback` 字段落在哪（跨票自洽检查）** → **只作用于「曾有租约」的断租 / 分片挂掉情形**：

| 情形 | fail-open 规则 | fail-closed 规则 |
|---|---|---|
| 曾在册、续租断掉（中心不可达 / 分片挂掉） | 继续按最后份额跑（票 05 Q3 已定） | **停止自补、存量花完**（等价于收到主动 `ttl = 0`，票 05 Q3 表第二行） |
| 首租失败（从未拿到份额） | **拒**（票 05 Q10 ②格） | 拒 |

- **②格不分档、一律拒**：fail-open 的规则在「从未拿到份额」时也没有速率可跑，fail-open 无处着力——这样票 05/06 的已裁格子**一个不动**，字段落在它们留出的缝里（票 06 Q9 ③「档位由规则级配置提供」的落点即此）。

**Q8（新）规则删除 / key 不再匹配的过渡** → **红线：规则删除绝不能让该 key 从「限流」翻成「被拒」**——那比不限流严重得多。

- 中心对**不匹配任何规则的 key**，在续租响应里回**显式「未匹配」状态**（区别于 fail-closed 的拒——票 08 的协议输入）；
- 客户端收到 ⇒ **停止续租 + 逐出整条在册条目 + 该 key 放行**（回到票 05 Q10 ①格语义）；
- 版本错位窗口内（本地规则集还认为有规则）同样放行——「是否限流」的裁决以**中心的显式回答**为准（它与中心读同一份、更新序一致）。

结果：删除规则 = 全网一个 `refresh_interval` 内收敛为不限流，无拒绝窗口。

**Q9（新）前缀匹配的边界语义** → **朴素 `startsWith`，不引入分段边界判定**；用**文档惯例**消歧：pattern 建议以分隔符结尾（`user:1:` 匹配 `user:1:xxx` 而非 `user:12`），加载时对「pattern 是另一 pattern 的前缀且未以分隔符结尾」打**告警日志**（不拒绝——合法，只是容易误配）。理由：分段感知的匹配器要定义「分隔符是什么」，而 key 是自由字符串、核心不解析内容（Q2 刚裁的）——那会把解析问题从前门扔出去又从后门请回来。

### 与上游票的交接（复核结果）

- **票 05 Q10 ①格的前提**（SDK 本地必须有规则集）→ 由 Q3 落地：`ConfigSource<T>` 抽象 + 客户端直连配置源；**①格还得到一个新触发面**：首份配置非法 / 规则源连不上 ⇒ 空规则集 = 走①格放行 + 告警 + 重试（Q5）。
