## 摘要（8 条）

1. **瞬时突发 ≤ R × burstSeconds 在正常路径是硬上界，且仿真实测全程贴着 1.0000000×R 的份额和**——"上一轮高份额 + 本轮新份额"的放大**不发生**，因为份额落地是**覆盖**（存量按容量比例缩放，票 04 Q9 的 rescale），不是叠加；中心账本侧由 `minF(gets, unused)` 保证 Σ租约 ≤ R 的不变量（unused 必须**排除请求者自身**——Doorman `algorithm.go:239` 逐字 `unusedCapacity := capacity - store.SumHas() + old.Has`，这个 `+ old.Has` 是不变量成立的全部，票 04 Q13 引的注释里没有它）。
2. **带收敛项的形式**：正常路径放大系数 = 1；**唯一的超发通道是 fail-open 陈旧份额**（断租客户端继续按最后份额跑 + 账本过期后份额被再分配给活跃者）⇒ 降级期 ≤ `2R × burstSeconds`，仿真实测 1.1R（s4 全程稳定 1100.0/s，与手算逐位吻合）。
3. **窗口 Δ 的放行量 ≤ Σ生效份额 × (burstSeconds + Δ)**；正常路径 = `R(Δ + burstSeconds)`。**稳态准确度验收窗口回填票 09：Δ = 60s**（要 ε=2% 则 Δ ≥ burstSeconds/ε = 50s；Δ=60s 时上界余量 1.7% < 2%）。
4. **收敛 = 1 个续租周期**：请求者自己的新份额在自己下次续租即到位；热实例最多 2 轮（等释放方续租腾出 unused）。s2 实测：翻转后 5.01s 达终值 95%（= 1×T + 相位）、全局放行率 3.77s 回到 R±2%。**无震荡**（每轮零基重算、不累加；时间线波动 ±2% 是 wants 的 Poisson 噪声）。Doorman 的 106% 超发出自**层级部署**（其文档原文自述），本设计单层、无此通道。
5. **中心 CPU 账 = Σ_k n_k²/T 次条目扫描/秒**（重算总是的上界），实测与理论吻合（s5：563M 次 / 120s = 4.69M/s，理论 5M/s）。量级结论：**CPU 不是瓶颈**（满配算例 ≈ 每分片 2% 核）；真正的约束是 §5 的内存账。QPS 账沿用票 06（≤ 实例数 × min(订阅 key 数, 分片数) / T，与 key 数无关）。
6. **内存账**：每 `(key, 实例)` 一条 ≈ **91 B**（Java、压缩指针、含 wants/expiry 双字段，手算 ±20% 未 JOL）。满配算例（10k key × 200 实例）= 2M 条 ≈ 200 MB，8 分片后 25 MB/实例——**可行**。**票 09 拍的两个 10k 默认值复核通过**：本地桶表 10k ≈ 1 MB/实例；每实例订阅 10k ⇒ 单实例贡献 ≈ 1 MB 条目，全局账 = Σ_k n_k 随分片摊。
7. **⚠️ 新发现（已裁）**：**份额 × burstSeconds < 1 个请求时本地桶永远装不满 1 个请求 → `tryAcquire` 恒拒**（s5 实测：R=1000/N=5000 时 99.98% 实例恒拒、翻转前全网放行 = 0）。**用户裁决（2026-09-22）：乙案——本地桶容量下限 1 个请求**，`capacity = max(份额 × burstSeconds, 1 请求)`；代价 = 突发上界改写为 **Σ max(份额×burst, 1)**（对照臂 s5b 实测最坏 3.6×R×burst）。传播：票 04 Q2 / 票 05 Q6 / 票 09 Q3。
8. **⚠️ 新发现（无需新决策）**：**闲置清零**——客户端一个上报窗口零到达 ⇒ wants=0 ⇒ 份额清零 + 存量令牌 ×0，恢复后要等 ≤ 1 轮续租才能重新放行（Doorman 同款，出自"分配吃实测 wants"的固有性质）。缓解钩子**票 04 Q4 已经有了**（配置基线：分配取实测与基线的较大值），spec 要写"突发型 key 应声明基线"，不新增机制。

## 0. 模型与记号

沿用 research/03 §4.1 的记号，按速率口径重定义：

| 符号 | 速率口径含义 | 默认值 |
|---|---|---|
| `R` | 规则的全局速率（该 key 全体实例的份额之和的上界） | — |
| `burstSeconds`（`W`） | 规则字段："允许几秒的量"；单实例本地桶容量 = `份额 × W` | 1.0 |
| `T` | `refresh_interval`（续租周期） | 5s |
| `ttl` | 租约有效期（中心过期清理的迟滞） | 2T = 10s |
| `N` | 该 key 的在册实例数 | — |
| `n_k` | key k 的在册实例数 | — |
| `s_i` | 实例 i 的**生效份额**（客户端本地桶当前速率） | — |
| `S(t) = Σ_i s_i` | **生效份额和**（上界的主角） | ≤ R |
| `H_i(t)` | 实例 i 本地桶当前持有令牌数 | ≤ 容量 |

中心账本 = 每 `(key, instance_id, generation)` 一条 `{share, wants, lastRenew, expiry}`（票 08 的三元组键）。分配 = Doorman `ProportionalShare` 逐字（[research/01](01-prior-art.md) §1.1 + 本次拉取源码核对，`go/server/doorman/algorithm.go:213-292`）：

```
equalShare = R / count
unused_i   = R − Σ_{j≠i} has_j          ← algorithm.go:239 逐字：
                                             unusedCapacity := capacity - store.SumHas() + old.Has
若 Σwants ≤ R 或 wants_i ≤ equalShare:    gets_i = min(wants_i, unused_i)
否则:  gets_i = equalShare + (wants_i − equalShare) × (extraCapacity/extraNeed)
       gets_i = minF(gets_i, unused_i)   ← "We cannot give out more than the currently unused capacity…"
```

**模型与真实现的三点对齐说明**：① `unused` 排除请求者自身（`+ old.Has`）——这是 Σ ≤ R 不变量的成立条件，下文 §1.1 给证明；若实现时把 `SumHas()` 全额计入（不 `+ old.Has`），续租会把已有份额清零，**这是 spec 必须逐字写对的实现约束**。② 客户端本地桶 = 微令牌整数域、容量 = 份额 × `burstSeconds`、份额变化时存量按容量比例缩放（票 05 Q6 / 票 04 Q9）——**本次裁决追加下限 1 请求（§7）**，仿真两种口径都跑了。③ wants = 上报的 `(放行数 + 被拒数) / 经过时间`（票 04 Q4）。

## 1.（Q1）瞬时突发上界：形式化 + 收敛项

### 1.1 账本不变量：Σ租约 ≤ R

**断言 A**：任意时刻，中心账本内所有条目的 `share` 之和 ≤ R。

**证明**：初始为空。每次续租只改写请求者 i 自己一条：新值 = `min( gets_i, unused_i )`，其中 `unused_i = R − Σ_{j≠i} has_j`。更新后总和 = `Σ_{j≠i} has_j + min(gets_i, unused_i) ≤ Σ_{j≠i} has_j + unused_i = R`。过期清理只删条目、总和单调不增。∎

**断言 B（正常路径）**：客户端的生效份额 = 账本中自己的条目值。理由：条目 ttl = 2T，客户端每 T 续租一次，健康客户端的条目永远在过期前被刷新（票 08：ttl 默认 2T"容忍丢一轮续租"）；断租客户端的条目过期删除后，其生效份额成为"陈旧份额"（见 1.3）。

由 A + B：**正常路径 Σ生效份额 = S(t) ≤ R，恒成立**。仿真实测：s1/s2/s3/s3b 四个场景全程 `max_sum_share / R = 1.0000000`（浮点尾差 2×10⁻¹⁵）——不变量被压到构造极限，一次都没有超出。

### 1.2 客户端侧：持有量 ≤ 容量，容量随份额覆盖式更新

本地桶两条纪律（票 05 Q6 已裁，此处给它们在上界里的角色）：

- **存量 ≤ 容量**：补令牌封顶在容量；份额变化时 `stored ×= newCap/oldCap`（先乘后除），该式天然保证 `stored ≤ newCap`。
- **覆盖不是叠加**：票面 Q1 问"一个实例可能同时握有上一轮的高份额与本轮的新份额，上界会不会放大到 R × burstSeconds × (1 + T/…)"——**不会，机制上不可能**。份额落地是对同一个桶的**改写**：速率变、容量变、存量按比例缩放，桶里不存在"两轮份额相加"的时刻。T 依赖项在瞬时上界里**不出现**；它只出现在窗口界（§2）里，且身份是"补令牌速率 × 窗口长"，与收敛无关。

于是：

```
(1)  任一时刻持有总量  Σ_i H_i ≤ Σ_i (s_i × W) = S(t) × W ≤ R × W      （正常路径）
     瞬时突发（Δ→0 的放行量）≤ Σ_i H_i ≤ R × burstSeconds
```

**乙案后的修正（⚠️ 2026-09-22 用户裁决，见 §7）**：容量 = `max(份额 × W, 1 请求)`，故

```
(1') Σ_i H_i ≤ Σ_i max(s_i × W, 1)  ≤  R × W + 微份额实例数
     （微份额实例 = s_i × W < 1 的实例；每个的贡献比自己的 s_i×W 至多多出 1 − s_i×W < 1 个请求）
```

正常区间（份额 ≥ 1/W）`(1')` 退化为 `(1)`，票 04 Q2 原式不变；微份额区间上界抬到"每实例 1 个请求"。**注意 `Σ max(s_i×W, 1)` 不等于 `max(R×W, 实例数)`**——混合区间（一部分实例份额 ≥ 1/W、一部分 < 1/W）下两项都存在，s5b 自身即反例（热点 282 + 4999 个下限 1 ⇒ 上界 ≈ 5281 > max(1000, 5000)）。s5b 实测最坏持有 3572 = 3.6 × (R×W)（5000 实例 × 下限 1 的满闲状态）。

### 1.3 收敛项：唯一的超发通道是 fail-open 陈旧份额

正常路径 `(1)` 已封死。超发只可能来自**生效份额 ≠ 账本份额**的时刻，恰好一类：

- **断租 fail-open**（票 05 Q3 第二行）：客户端续租失败仍按最后份额跑；其账本条目在 ttl 内过期删除，份额被再分配给活跃者。此时 Σ生效 = 账本内（≤ R）+ 陈旧（≤ R）**≤ 2R**。
- 中心重启 / 分片拓扑变更同构：账本清空后第一轮保守发放（Σ ≤ R），客户端手里的旧份额（Σ ≤ R）与之并存——同一个 ≤ 2R。
- 不构成通道的两条：幽灵条目（世代交替）只**稀释**份额（票 08 已裁，安全侧）；`throttled` 首租不产生份额。

**带收敛项的最终形式**：

```
(1'') 瞬时突发 ≤ Σ生效份额 × max(·, 1)  ≤  { R × burstSeconds          （正常路径，系数 1）
                                            { 2R × burstSeconds        （降级期，系数 ≤ 2）
```

s4 实测（N=200 全饱和、20 实例断租 40s ≫ ttl）：降级段生效份额和 = **1100.0 = 1.1R**（手算：180 活跃 × 5.55 + 20 陈旧 × 5），放行率 1100.04/s，降级 1s 窗峰值 1109 ≤ 2R×(1+1) = 4000 的界；恢复后 999.4/s。**与票 06"过渡窗口超发上界 2R"对账**：2R 指**速率**上界（正常 R + 陈旧 R），实测形态是"降级期持续 1.1R、恢复即收敛"；票 06 写的"窗口 = 一个 refresh_interval"应读作**拓扑变更的收敛时间**（全体在一个 refresh_interval 内完成续租切换），分区情形的 2R 形态会持续到分区恢复为止——s4 里就是 30s。这条对账注记要回票 06。

## 2.（Q2）任意窗口 Δ 的放行量上界与 ε 验收窗口

窗口 `[t, t+Δ]` 的放行量：每实例放行 ≤ 持有（窗口初）+ 期间自补（`s_i × Δ`）：

```
(2)  放行量(Δ) ≤ Σ_i H_i(t) + Σ_i s_i × Δ ≤ Σ生效份额 × (W + Δ)
     正常路径：        ≤ R × (burstSeconds + Δ)
     降级期（fail-open）：≤ 2R × (burstSeconds + Δ)
```

`Δ→0` 退化为 `(1)`，两节自洽。**超额部分是固定的一项 `R × W`（窗口起点可能满桶），不随 Δ 增长**——这是"长期速率准、瞬时突发超标"在速率口径下的定量版本（research/03 §4.9 的形态保持，`R·T + 2K` 换成 `R × burstSeconds`，量级从"10 秒的流量"缩到"1 秒的量"）。

**票 09 回填（Q2 接口）**：要窗口平均放行率落在 `R × (1+ε)` 内：

```
R(Δ + W)/Δ ≤ R(1+ε)   ⇔   Δ ≥ W/ε
```

| ε | Δ 下界（W=1.0） | 拍定建议 |
|---|---|---|
| 2%（票 09 临时值） | **50 s** | **Δ = 60 s**（余量 1.7% < 2%，且是 0.5×refresh_interval 的整数倍便于取窗） |

**Δ = 60s、ε = 2% 建议直接落票 09 / 票 11**；降级窗口不进稳态准确度验收（故障验收另测，恢复口径 ≤ 1 个 refresh_interval，票 09 已裁）。仿真窗口读数（s1 稳态、滑窗最坏值）：1s=968、5s=901、10s=891、30s=878、60s=873——全部 ≤ R（该场景 offered = R 的临界负载，实际是"低于 R"，因为放行 ≤ 份额、份额 = 实测需求）；超上界的构造性最坏值（满桶起点）在任何实测窗口都没出现。

## 3.（Q3）中心租约 QPS 与处理成本

**QPS**（沿用票 06 Q12 已裁形状，此处只复述 + 归位）：客户端按分片拆批，全中心 QPS ≤ `实例数 × min(订阅 key 数, 分片数) / T`（5000 × 8 / 5s = 8000 QPS），**与 key 数无关**（封顶于分片数）——批量接口是硬要求不是优化（research/03 §6.3 的结论原样成立）。

**CPU 账（本票新增）**：每次续租对所在 key 跑一遍 O(n_k) 分配（extraCapacity/extraNeed 遍历 + SumHas/SumWants）。上界（**重算总是**）：

```
(3)  条目扫描速率 = Σ_k n_k² / T    （每 key：n_k 次续租/周期 × 每次 O(n_k) 扫描）
```

**实测对账（s5，单 key N=5000、T=5s、120s 模拟）**：115,084 次分配、563,032,584 次条目扫描 = 4.69M 次/s；理论 `5000²/5 = 5M/s` ✓（差值 = 首轮未满员的轮次）。

| 部署形态 | Σ n_k²/T | ÷8 分片后 | 核占比（~2ns/次） |
|---|---|---|---|
| 10k key × 200 实例 | 80M/s | 10M/s/分片 | ≈ 2% |
| 100k key × 平均 20 实例 | 8M/s | 1M/s/分片 | ≈ 0.2% |
| 1M key × 平均 10 实例 | 2M/s | 0.25M/s/分片 | ≈ 0.05% |
| 单 key 5000 实例（倾斜） | 5M/s（该 key） | 0.6M/s/分片 | ≈ 0.1% |

**T 的变体**（票面 Q3 要求 R、N、T、key 数各取几组）：(3) 对 T **线性反比**——上表形态配 `T = 2s` 全部 ×2.5（10k key × 200 实例 → 25%/分片，开始有感）、`T = 10s` 全部 ×0.5；**R 完全不进 (3)**（上表对 R=1/s 与 R=10⁶/s 同样成立）——这正是"中心成本是规模量的函数、不是业务量的函数"这个口径在 CPU 维度的落点，与 QPS 账（票 06）同性质。

**结论：CPU 不是瓶颈**（两位数 MHz 级），倾斜 key 也不破账（n² 被 key 数摊平）。真正的约束是内存（§5）。**优化空间留档不依赖**：票 04 Q9 的"份额未变只延有效期"（RLQS 语义）可以做成"上报 wants 与上一轮逐字相等 + 规则版本未变 ⇒ O(1) 跳过重算"，代价是其他实例释放的份额要晚一轮才被它拿到（再分配延迟）——v1 按重算总是做，spec 记优化方向。

注意 **R（速率值）完全不进 (3)**——与票 03 式 (9') 的"N/(C·W) 与 R 无关"是同一种"规模量与业务量解耦"，但这里的账是良性的（CPU 随实例数多项式增长、可分片摊），不像 (9') 是被在飞上限逼出来的指数兑换。

## 4.（Q4）分配算法的收敛速度与震荡

**收敛时间 = 1 个续租周期（自己的份额），热实例至多 2 轮**：

- 请求者自己的新份额在**自己下次续租**即到位——不用等别人。lag ≤ T。
- 流量突增的实例第一轮可能拿不满：它的 `gets` 被 `unused` 封顶，而 unused 要等**其他实例续租时交回**（释放方的节奏）。释放方在一个 T 内全部轮到 ⇒ 热实例第二轮到位。**最坏 2T。**

**s2 实测（N=200、冷实例 2/s、t=100s 实例 0 跳到 1000/s）**：

- 热实例份额：t=104 仍是 1.7（翻转前），t=105 一次跳到 **619.8**（= 手算的公式值 602 被 unused 上限修正后的形态），随后稳定在 592–620（wants 的 Poisson 噪声 ±2%）。
- **份额达到终值 95% 用时 5.01s ≈ 1×T + 相位**；全局放行率回到 R±2% 用时 **3.77s**（< 1 个 refresh_interval）。
- **无震荡**：份额是每轮从零重算的（不是旧份额 + 增量），无正反馈回路；minF 封顶杜绝过冲后再回调的振铃。时间线的微小波动来自 wants 估计的 Poisson 噪声，量级 ±2%，不发散。

**Doorman 的 106.05% 超发与本设计无关**——成因是其**层级部署**（逐字，[research/01](01-prior-art.md) §1.3 转引其设计文档）：

> `when a server asks for a capacity from its downstream server it can potentially get a new capacity which is less than it currently has in outstanding leases to clients and upstream servers. During that situation (which will have corrected itself in a single refresh interval) that server has given out more capacity than it currently has.`

中间层"上游给的新额度 < 已发给下游的在租额度"才产生 overshoot；本设计单层（客户端直连中心），等价通道只有 §1.3 的 fail-open 陈旧份额，且被 ≤ 2R 封顶（实测 1.1R）。**票 04 留的"收敛速度与超调幅度需要定量"至此回填：收敛 ≤ 2T、无震荡、正常路径零超调（份额和贴 R 不超）。**

## 5.（Q5）中心账本内存账（map 指名由本节复核两个 10k 默认值）

### 5.1 每条记录的成本（方法照 research/03 §6.2：64 位 HotSpot + 压缩指针，手算 ±20% 未 JOL）

字段由协议反推（票 08：账本键 = `(key, instance_id, generation)` 三元组；用量三字段进公式前换算成 wants 存储，原始计数器不落账本）：

```
Lease 对象（头 12 + share double 8 + wants double 8 + lastRenewNanos 8 + expiryNanos 8 → 对齐 48）  ≈ 48 B
HashMap.Node（头 12 + hash 4 + key 引用 4 + val 引用 4 + next 4 → 32）                             ≈ 32 B
table 槽位（8 B × 1.33 负载因子）                                                                  ≈ 11 B
─────
每条 ≈ 91 B     （记账取 100 B，±20%）
```

- key/实例身份对象（instance_id + generation）**每实例一份、被它的所有 key 条目共享**，摊销后每条可忽略（10k key 摊薄 80B → 0.008B）。
- 与 research/03 §6.2 当年估的 99 B 同量级——"Doorman 两个 float64 + time.Time 可以更紧凑"在 Go 里成立，但 Java 侧 `wants` 是分配算法的必需输入（票 04 Q4），省不动。**选速率租约认下的这笔账比 §6.2 当年"不可行"判决的背景少了两个数量级的场景差异**：当年按"10k key × 每 key 全部 200 实例"是上限想象，真实账 = Σ_k n_k（只有真正用该 key 的实例占条目，票 04 Q5①）。

## 6.（Q6）大 N 行为：research/03 §4.8 逐条复核

|---|---|---|

## 7. ⚠️ 新发现一：微份额区间——份额 × burstSeconds < 1 个请求时本地桶恒拒（已裁决）

### 7.1 机制

票 05 Q6 裁的本地桶：微令牌整数域（1 请求 = 10⁶ 微令牌）、容量 = 份额 × burstSeconds、**无下限**、`tryAcquire` 要求水位 ≥ 1 请求。当 `份额 × W < 1`（例：份额 0.2/s、W=1.0 → 容量 0.2 请求）时，桶水位**永远到不了 1 个请求** → `tryAcquire` 恒 false，`nanosToWaitForNextToken` 恒为常数 `(1 − 份额×W)/份额` 秒（0.2/s 时 = 4s → Retry-After 上取整 5s）。

### 7.2 仿真实读数（s5：R=1000/s、N=5000、每实例份额 0.19/s）

- **翻转前（50s 内）全网放行 = 0**：R=1000 的 key，一个请求都放不出去。
- **99.98% 实例**（4999/5000）份额 × W < 1 → tryAcquire 恒拒。
- 唯一能放行的是一个被 wants 噪声抬到份额 282 的热点实例（账本其余实例的份额和因此塌缩到 712.6、37.2% 实例份额为零——零到达轮报 wants=0、份额清零，见 §8；两条读数已进 `results/r-s5.json` 的 `ledger_sum_excl_hot_end` / `frac_ledger_zero_end`），它独享 99.96% 的放行量。
- 不是罕见配置：**N 个实例分一个 key 时，份额 = R/N，落进该区的条件是 N > R × W**。票 09 harness（4 客户端 JVM）配 rate ≤ 4/s 的 key 即触发；票 10 演示（rate=2/s）单实例部署才安全。

### 7.3 裁决（2026-09-22 用户拍板：乙案）

**本地桶容量下限 1 个请求**：

```
capacityMicro = max(份额 × burstSeconds, 1.0) × 10⁶
```

- 微份额行为：容量被下限顶到 1 请求、补令牌速率仍是份额 ⇒ 每 `1/份额` 秒放 1 个、**无囤积**；tryAcquire 每 5s 成功一次（0.2/s 时），速率语义正确。
- **代价（对照臂 s5b 实测）**：瞬时持有峰值 3572 = **3.6 × (R×W)**——`(1)` 的上界改写为 `(1')`：`Σ max(份额×W, 1) ≤ R×W + 微份额实例数`（**不是** `max(R×W, 实例数)`，混合区间两项都存在，见 §1.2）。正常区间（份额 ≥ 1/W）与原式逐字相同；只有微份额区间上界抬到"每实例 1 请求"。
- **传播站点（本次已逐处加注）**：票 04 Q2（全局突发公式）、票 05 Q6（容量公式 + 下限）、票 09 Q3（突发验收口径改 `(1')`）。research/03 §3.2 的"Guava 默认 maxBurstSeconds=1"对照不受影响。

### 7.4 落 spec 的实现约束（易错点）

- 下限作用于**容量**，不作用于**补令牌速率**（速率 = 份额，错加下限会超发）。
- rescale（票 04 Q9）的比例要用**新旧容量**（含下限）而非新旧份额算——份额穿越 1/W 边界时存量缩放才正确（仿真 s5b 已按此实现）。
- `share = 0`（票 08 合法值）时容量仍是下限 1，但补令牌速率为 0、存量按"花完为止"（票 05 Q3 的 ttl=0 语义）——不会凭空多放。

## 8. ⚠️ 新发现二：闲置清零——零到达轮把份额和存量一起清掉（无需新决策）

**机制**：分配吃实测 wants（票 04 Q4）。客户端一个上报窗口零到达 ⇒ wants = 0 ⇒ `gets = min(0, ·) = 0` ⇒ 份额清零，且 rescale 把存量令牌 ×0（票 04 Q9：份额变了就缩放）。流量恢复后：桶空 + 份额 0，全部拒绝，**直到下轮续租报回 wants > 0 才恢复**——恢复延迟 ≤ 1 个 refresh_interval。

- s5 里 37.2% 实例的份额间歇为 0、账本其余实例的份额和塌缩到 712.6（§7.2，读数在 `results/r-s5.json`），就是这个机制在微份额 + Poisson 零到达下的放大形态。
- **正常份额区间同样存在**：任何空闲 ≥ 1 个上报窗口的实例，恢复期要吃 ≤ 1 轮拒绝。这是"分配吃实测需求"的固有性质（Doorman 同款——它的 `AdaptiveQPS` 移动平均一半动机就是这个），**不是缺陷，但要在 spec 里写明**。
- **缓解钩子已存在**：票 04 Q4 的**配置基线**——"`wants` 字段留给配置基线（应用自己声明），分配时取『上报换算出的实测需求』与『配置基线』的较大值"。突发型 key（间歇流量、拒绝敏感）声明基线即可免疫。spec 落"参考接入器"节时加一句使用建议，**不新增机制、不改裁决**。

## ⚠️ 未核实项

以下条目**没有验证过**，不得当成已定论引用或写进 spec。

1. **内存账 91 B/条是手算**（64 位 HotSpot + 压缩指针规则推算），未做 JOL / heap dump 验证，±20%——与 research/03 §6.2 同一性质。量级结论（200 MB 级满配、25 MB/分片）有大幅余量，具体数字不要直接引用。
2. **仿真是单一 key、单中心、无分片**。分片只做了除法账（÷S），没有仿真多分片交互（拓扑变更时客户端跨分片的部分成功部分失败、421 重定向风暴等）——票 06 的分片行为要靠票 09 的故障验收实测，本仿真不背书。
3. **流量模型是 Poisson 到达 + 阶跃 profile**，没有长程相关（突发聚集、周期性负载）与多 key 资源竞争（一个实例订阅多个 key 时 wants 的耦合）。窗口读数在真实流量下会更差，但**上界是构造性证明、不依赖流量假设**——读数差只影响"贴得多紧"，不影响"破不破"。
4. **`min_renew_interval` 与 `throttled` 状态未进仿真**（续租周期恒 ≥ T 不触发）；首租合批窗用 0.1s 近似（真实现 10ms）。两者都只影响瞬态，不影响界。
5. **仿真读数依赖种子与负载形态**（每场景单种子 seed=7/11），不构成统计证明；报告里"实测 X"均指该配置下可复跑的读数，纸面推导（§1.1/§1.2/§2）才是证明。
6. **Doorman 源码核对只覆盖 `algorithm.go` 的 ProportionalShare**（本次拉取 master 快照核对 unused 语义与公式形状）；`store.SumHas()` 是否含未过期但已失联的条目、`Clean()` 的调用时机（research/01 记 `resource.go:106` 每次决策前）未逐行核。本报告按"过期清理先于决策"建模，与 research/01 记载一致。
7. **Δ = 60s 的拍定基于 W=1.0 默认值**；规则把 `burstSeconds` 配大（如 10）时 Δ ≥ W/ε = 500s——票 11 落 spec 时要把"Δ 随规则的 burstSeconds 走"写成公式而非常数。
