# 01: 口径基线（charting 阶段 grill 定）

## Question

本票是 **2026-09-14 charting 阶段的那几轮 grill 的答案之家**——后续所有票据的「Blocked by」都隐含依赖本票的口径。

## Answer

**2026-09-14 收敛**：charting 阶段分四轮 grill（Q1–Q19），用户在架构粒度上推翻了助手两轮推荐（改选「三个服务」「多 pom 模块」「独立 project」），其余按推荐采纳。

### 1. 边界与终点

- 终点 = `.scratch/marketing/spec.md` 定稿，**三节**：① 营销域（三个服务）② 市集入口行 ③ 消息迁移。
- 三块进同一份 spec（②③ 是 ① 的入口与配套，拆开会产生跨 spec 的接口耦合）。
- **落地票另起 `.scratch/marketing-impl/`**（沿用 `chat-impl` / `ui-revamp-impl` 先例）。
- 本 effort **只产出决策与 spec，不落地代码**。

### 2. 架构：三个独立微服务 + 事件编排

| # | 决策 | 结论 |
| --- | --- | --- |
| Q2 | 真拆微服务还是留单体 | **真拆**，且用户再推一步：**积分 / 抽奖 / 拉新各是一个微服务**（三个独立服务，不是三个包） |
| Q17-1 | 目录结构 | **案 A**：单体**原地不动**（`backend/pom.xml` 即其聚合器）；三个服务是平级独立 project，根目录都在 `backend/` 下 |
| Q17-2 | 模块结构 | **多 pom 模块**：每个服务各一个聚合器 + 各 7 个模块（`<svc>-types/api/domain/case/infrastructure/trigger/app`），与单体同构；**每个服务自带 types**（不复用 `bs-types`——否则改一个常量三个服务一起重发） |
| Q17-3 | Dubbo 引用写在哪 | 域内定义自己的 port（`IUserQueryPort` / `INotificationPort`，放 `<svc>-domain/adapter/port/`），`<svc>-infrastructure` 用 Dubbo 实现它；**域层与 case 层不认识单体契约**（本仓 `IWsTicketPort` 既有写法） |
| Q18 | 依赖方向 | **单向**：三个营销服务 → 单体（Dubbo 消费）。单体**不反向调**营销服务（否则成环） |
| Q19 | 前端怎么到营销 | **直连**，Vite/反代按前缀分流（`/api/points`、`/api/lottery`、`/api/referral` → 三个端口；`/api/**` → 8080）。**不做网关**。同域 + 反代 ⇒ 无跨域问题 |
| Q19 | 鉴权 | 共享同一份 `jwt.secret`（建议从 Nacos 下发，轮换只改一处），各服务内自带 JWT 校验过滤器；**不做**每请求回调单体验票 |
| Q19 | 库 | **各自独立 schema**（同一个 MySQL 实例）；**跨库不 join**——用户昵称头像经 Dubbo 取回后应用层拼装 |

**跨服务编排（用户 2026-09-14 拍板「乙 · 三个服务 + 事件编排」）**——这是本架构的全部成本所在，写清：

- **异步边（事件编排）**：
  - `成团成功`：拉新服务发（自己的 outbox → MQ）→ **抽奖服务**消费（双方各 +1 抽奖次数）、**积分服务**消费（+N 积分，默认 0）、**单体**消费（落通知）。
  - `抽奖中奖`：抽奖服务发 → **积分服务**消费（积分档奖品加分）、**单体**消费（落通知）。
  - `积分变动`：积分服务发 → **单体**消费（落通知）。
  - **拉新服务不认识抽奖与积分**：抽奖服务不部署，拉新照样成团（事件没人消费而已）；积分服务不部署，抽奖照样跑（只是积分档没人兑付）。这才真正兑现用户反复要的「三个独立、缺一个也能跑」。
  - 复用本仓现成机械：业务事务内写 outbox（`msg_id` 唯一）→ afterCommit 异步发 → `bs-<topic>-group` 消费者；形状先例 = `bs-errand-paid`。
- **同步边（Dubbo）**：只有**兑换**——「用积分兑抽奖次数」「用积分兑奖品」必须同步（用户点完要立刻看到），走 `抽奖服务` 的端点 → 同步 Dubbo 调积分服务扣分 → 本地加次数 / 扣奖品库存；**幂等键 = 兑换单 id**，失败由客户端重试（本仓「幂等 + 重试」铁律，无需真补偿回滚）。
- **查用户信息**是唯一的其它同步边（填码判「活动开始后注册」、列表拼昵称头像）。

**知道但不做的取舍**（写进 spec，便于将来判断）：
- 三个服务若共用同一个 MySQL 实例，**隔离的是应用层不是物理资源层**，共同上限还在（MySQL / Redis / RocketMQ 是共享的）。要物理隔离得给独立 DB 实例，是另一个量级的运维动作。
- 三条窄边没被切断（查用户信息、通知落库——通知已改为事件订阅，所以实际只剩查用户）。
- 微服务固有代价：本地要跑 **4 个 JVM**、前端三个前缀、三套日志与健康检查、三份 outbox 表。
- 只有**抽奖**的负载特征（热点写）值得独立扩容，拉新与积分都是低频；三个都拆，收益在「架构叙事 + 真解耦」，不在弹性。

### 3. 拉新拼团口径

| # | 问题 | 结论 |
| --- | --- | --- |
| Q3 | 团的构成 | **恒为 2 人**（邀请人 + 被邀请人），一次成功的邀请 = 一个团 |
| Q3 | 邀请码粒度 | **每人一个专属邀请码**，全局唯一、永久有效、**可被多人使用**（一个邀请人拉 N 个新用户 = N 个团）；排除易混字符 |
| Q3 | 「两个人只能一个团」的精确定义 | **① 被邀请人的账号注册时间 ≥ 活动 `start_at`**（排除老用户）**② 每人一生只能作为被邀请人一次**（入度 ≤ 1）**③ 不能邀请自己**。于是成团图是一棵**树**：a→b→c 合法；b→a 非法（a 注册早于活动）；同一人不能被两人各邀一次 |
| Q11 | 「新用户」判据 | **账号 `bs_user.created_at >= 活动 start_at`**——唯一零漂移、可测、且真排除老用户的判据；**不**引入「注册后 N 天内」（随日历漂移、说不清）、**不**给存量用户打快照（多一张表且与 `created_at` 语义重复） |
| Q3 | 老用户填码 | **明确报错**（不静默不发奖）；老用户**仍可当邀请人**，只是不能当被邀请人 |
| Q16 | 成团触发点 | 只有活动页能填码，**提交即成团，无中间态** |
| Q4 | 成团奖励 | 双方各 **+1 抽奖次数**。**⚠️ 2026-09-14 票 05 反转**：原文另有「默认 0 的『成团送积分』配置」一条边，用户拍板「**成团只加抽奖次数**」⇒ 该配置与「拉新 → 积分」边**取消**（见 [票 05](05-marketing-data-model.md) 决策依据第 6 条） |

**验收注意**：种子活动的 `start_at` 要设成一个过去的日期，否则演示时自己注册的测试号填码会被拒——那是**预期行为**不是 bug。

### 4. 三个域的解耦

- 三个服务**零互相注入**；集成靠**事件**（异步边）与**同步 Dubbo**（兑换边）。
  - **⚠️ 2026-09-14 票 04 反转**：原文的「**零编译期依赖**」**取消** —— 用户拍板「这种依赖可以成立，必要时可以依赖」（理由：积分兑抽奖次数把两者绑在一起，没有积分服务抽奖的兑换就工作不了）。本期唯一一条 = **抽奖服务编译期依赖 `points-api`**（见 [票 04](04-service-skeleton-and-wiring.md) §3）。「零互相注入」（不跨服务注入 Spring bean）**仍然有效**，与编译期依赖是两回事。⇒ §4 的**验收项随之精确化**：积分服务停掉时，**抽奖（抽一次）与成团照跑，但兑换（兑次数 / 兑奖品）不可用**。
- 「抽奖次数」归**抽奖服务**（抽奖权账本）；拉新服务只记「这个团成了」，**表里没有「发了几次」**。
- 抽奖中奖抽到积分档：抽奖服务**发事件**，积分服务自己订阅加分——抽奖服务不认识积分服务。
- **验收解耦的方式**（写进 spec 当验收项）：把积分服务停掉，拉新照样成团、抽奖照样跑（只是积分档没有兑付出口）。

### 5. 积分口径

- 独立服务，独立 schema；~~表照 `wallet` 指纹建（余额表 + 流水表 + 唯一键幂等 + **流水先行 INSERT IGNORE**，流水是事实源）~~ **⚠️ 2026-09-14 票 05 反转**：改为**桶化（lot）模型**——每笔入账是一行带自己 `expire_at` 的桶、消费 FIFO 扣 `remain`、**余额 = `SUM(remain)`（无余额列）**、懒过期 + job 清零（见 [票 05](05-marketing-data-model.md) 决策依据第 5 条）。「唯一键幂等」与「流水是事实源」两条保留（落到 `points_lot` 的 `uk_user_reason_ref`）。
- **不复用 credit 域**（信用分是规则引擎分值、不可消费，语义完全不同）。
- 本期 earn 来源：**抽奖中奖**（唯一）。**⚠️ 2026-09-14 票 05 反转**：原文的「+ 可配的成团送积分（默认 0）」**取消**——成团只加抽奖次数，不给积分。积分因此只有 3 个 `reason_type`（`LOTTERY_WIN` / `REDEEM_DRAW_COUNT` / `REDEEM_PRIZE`）。
- 本期 spend 去向：兑换抽奖次数、兑换奖池内的实物奖品。
- 兑换定价：奖品表加 **`redeem_points` 列**（NULL = 不可兑换）；「一次抽奖次数」的价格配在抽奖服务（它给自己的抽奖权定价）。
- **通胀环**：积分兑次数 → 再抽奖 → 又中积分。spec 里写明约束：**兑换比率的期望值为负**（兑一次次数的积分价 > 单次抽奖的积分期望产出）。
- 本期不做优惠券。

### 6. 抽奖口径

- **单活动**（本期只有一个「拉新抽奖」活动，活动页直接就是它；不做活动列表 / 活动状态机）；**单抽**（不做十连）。
- 奖池 = **3~5 档奖品 + 一档「谢谢参与」**；每档配**权重**与**剩余库存**。
- 概率：**权重法**；命中档若库存已扣光 → **跳过该档，在剩余有库存的档位重新归一**再滚（**不**直接判「谢谢参与」）。
  - 推论：**积分档不占库存**（无限量供给），只有**实物档**进 `sq/lq/oq` 与桶 ⇒ `deduct_detail` 只为实物档产生。
- **不做保底**；做**每日抽奖上限**（防刷）——口径 = 每天最多抽几次；~~**次数永不过期、可累积**~~ **⚠️ 2026-09-14 票 05 反转**：用户改口「**抽奖次数也会过期**」，且采用与积分相同的桶化独立过期模型（`draw_count_valid_days` 种子 **30**）——次数**不再永不过期**，但「可累积 + 受每日上限约束」不变（见 [票 05](05-marketing-data-model.md) 决策依据第 **7** 条）。
- 中奖记录落**当时的奖池快照**（各档权重 + 剩余量）且**记录每次抽奖的随机值**（可审计，最低成本的公平性交代）。
- 实物奖品发放：中奖即记「**待领取**」→ 领取时填**收件人 / 手机号 / 地址**（存在领取单上，**不建通用地址簿**）→ 已领取；**不做物流状态机**。虚拟（积分）**无待领取态、即时入账**。

### 7. 奖池库存口径（`实现方案3.md` + 用户 2026-09-14 修订）

- **去掉 `wq`**：库存表只留 `sq` / `lq` / `oq` + `version`。语义重定义为：`sq` = 可中奖库存、`lq` = 拨给 redis 的池子、`oq` = 已中奖 / 已兑换待发放。
- **单桶**：一个奖品一个桶（不做多桶分摊）。
- **扣减（中奖即占用）**：`DECR` 桶 key 成功即占用成立 → 落 `deduct_detail`；撞幂等键视为已扣；明细落库失败 → `INCR` 回桶并返回失败。**不碰库存表的四个字段**。
- **合并提交**（xxl-job 单实例、路由「第一个」、阻塞「丢弃后续调度」）：走覆盖索引扫 `status=0` → 事务内 `sq 减 / lq 减 / oq 加` + 桶配置表 `remaining` 减同量 + **按本批带回的 biz id 列表翻 `status=1`**（**绝不**写 `where status=0`，否则扫描后新插入的明细被误翻 ⇒ 少扣 ⇒ 超卖）。
- **DB 直扣兜底（用户明示「至少要做」）**：redis 挂 → `update inventory set sq = sq - 1 where inv_id = ? and sq - lq - 1 > 0`，只卖非池部分。**桶不动** ⇒ redis 恢复后桶余额天然正确（这是兜底不会双重卖的原因）。**⚠️ 2026-09-14 票 05 修正**：① 表名/主键改为 `lottery_prize` / `id`（票 05 把奖品表与库存表**合并**，不再有独立 `inventory` / `inv_id`）；② 该语句补 `oq = oq + 1`（原文只减 `sq`，会让「已中奖」台账漂移）；③ **开桶默认只拨 80%**、留 20% 非池，否则 `sq - lq` 恒为 0、本兜底形同虚设。
- **开桶**：`lq += N` + 插桶配置行 + redis 用 `SET` 写入（**不是 INCR**，避免同桶开两次额度叠加）；`sq` 不动。
- **本期不做**：关桶、多桶、redis 重建看门狗、取消回补（抽奖不可取消）。已知取舍：`DECR` 成功但明细未落库即进程挂掉这笔会丢（`实现方案3.md` §9.1），本期不额外处理。
- **幂等键**：~~`(prize_id, biz_id)`~~ **⚠️ 2026-09-14 票 05 修正**：改为 **`(prize_id, biz_type, biz_id)`** —— 原文漏了 `biz_type`，而 `biz_id` 有两个 id 空间（`LOTTERY` 用抽奖记录 id、`REDEEM` 用兑换单 id），自增 id 各表局部、不跨表可比 ⇒ 撞键会把一次合法兑换误判为「已扣过」而**少扣库存 / 超卖**。`deduct_detail.status` 只保留 0/1（「取消」场景本期不存在，不引入第三态）。
