# 06: `review_task` 工单模型 + 入池 + 队列切换 + 计数

**Spec:** `.scratch/errand-lock-review-hub/spec.md` §5.1（数据模型）、§5.2（工单态定义）

**What to build:** 审核中台的持久化基座：新增独立 `review_task` 表承载**在途工单**（单生命周期、可变），与 `content_review` 的「只插入审计／历史裁决」语义严格分离。工单态为 `PENDING`（在池）/ `CLAIMED`（租约中）/ `DONE`（已裁决，唯一终态；判决结论落在 `content_review`，工单不必再分通过/拒绝态）。唯一键为「类型 + 内容 + 审核轮次」，同一轮同一内容只开一张在途工单，入池用幂等插入吸收重复。排序锚点是「业务行进入待审的时刻」，不是工单创建时间——回收不改它，等待时长继续累加；且各表字段不齐：有 `review_entered_at` 的直接取，评论取发布时刻、跑腿取支付成功时刻。

**入池点＝各域进入待审的同一事务**（4 类内容：帖子发布/草稿提交、商品提交/草稿提交/在售改内容回审/重新上架、评论发布、跑腿支付成功）——状态迁移与开单原子，不会出现「已待审但没工单」。索引按「排队取候选（跨类型 / 按类型过滤）」与「租约回收」两组建。

队列读取口径切到工单（按工单态 + 类型过滤 + 先到先审），并按类型给出积压计数供审核端计数条与派单信号使用。

**迁移口径**：存量审核记录**不回填**成工单（历史裁决＝已完成，不该入池）；本仓无编号迁移脚本，改 `schema.sql` 重建库生效。
