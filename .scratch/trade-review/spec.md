# 闲置商品（先审后售）与求购（先付后审）的审核机制

术语遵循根目录 `CONTEXT.md` 的"闲置商品"一节；审核基础设施复用跑腿审核重构（`.scratch/errand-order-review/`）的成果，裁决收敛于统一用例 `decide()`。**商品与求购不同构**：商品走"先审后售"（无资金环节）；求购走"先付后审"（预算冻结，机制与跑腿同构、冻结标的不同——跑腿冻结悬赏，求购冻结预算）。

## Problem Statement

二手商品和求购目前发布即对外可见（仅信用分门槛），没有任何内容把关：卖家可以发布含违禁词或不当配图的内容直接进入信息流。商品需要"先审后售"——提交后先经同步初筛与人工审核（后续升级 agent），通过才对外可见，并配草稿箱作为停靠点。求购价值更高、更易被滥用（诱导线下交易、钓鱼），采用与跑腿一致的"先付后审"——先支付冻结预算，支付成功才进入人工审核，让审核资源只花在真实发布的求购上。

## Solution

**商品（先审后售）**
- 提交 → 同步初筛（标题+描述，命中即失败）→ 待审（仅卖家本人可见，不可编辑）→ 人工审核 → 通过对外可见 / 拒绝带理由
- 草稿箱：未提交、待审被撤回、被拒、上架后下架、到期的商品都停靠在此；可编辑、删除、重新提交
- 上架后改价直接生效；改标题/描述/图片回待审（期间对他人隐藏）

**求购（先付后审）**
- 创建（同步初筛，命中不落库）→ 待支付 → 支付（钱包冻结预算）→ 待审 → 人工审核 → 通过对外可见 / 拒绝终态并全额退回预算
- 未支付超 15 分钟自动取消；待审撤回先解冻退回预算、再进草稿箱
- 下架/到期同样解冻退回预算进草稿箱；**预算仅在求购对外可见期间保持冻结**
- 草稿箱同样适用：草稿提交后进入待支付

**通用**
- 人工审核复用现有管理端队列（带图、看图裁决、拒绝理由必填）
- 通知：裁决结果（通过/拒绝含理由）；求购支付后"进入人工审核"（对齐跑腿）；超 24h 未审提醒管理员
- agent 自动审核仅预留接入位置（`decide()` 已是统一裁决入口），本次不实现

## User Stories

1. 作为卖家，我提交商品时写了违禁词，我想立即被告知提交失败，以便马上改文案重新提交
2. 作为卖家，我想给商品配最多 6 张图片，以便把成色拍清楚给买家看
3. 作为卖家，我想把没填完的商品存进草稿箱，以便稍后继续编辑再提交
4. 作为卖家，我想在草稿箱里删除不要的草稿，以便草稿箱只留有用的东西
5. 作为卖家，我想商品进入待审后自己能在"我的发布"里看到它，以便知道它正等审核而不是丢了
6. 作为卖家，待审期间我想撤回商品进草稿箱，以便反悔时改完再发
7. 作为卖家，我想审核通过后商品立即对外可见并收到通知，以便尽快卖出
8. 作为卖家，审核不通过时我想收到通知，并在详情看到具体理由，以便知道该怎么改
9. 作为卖家，商品被拒后我想把它转入草稿箱、修改后重新提交，以便不用从零重填一遍
10. 作为卖家，已上架商品我想直接改价格且立即生效，以便跟进行情不用走审核
11. 作为卖家，我修改商品的标题/描述/图片后，我想它重新进入审核，以便平台对最终展示的内容把关
12. 作为卖家，我想把不想卖的商品下架进草稿箱，以便以后改主意再重新提交
13. 作为求购方，我想创建求购并配图（标题、描述、预算），以便卖家主动联系我时对得上需求
14. 作为求购方，我想创建成功后先支付冻结预算、支付成功才进入审核，以便平台审核的是真实发布的求购
15. 作为求购方，未支付的求购超 15 分钟我想被自动取消，以便不占用发布流程
16. 作为求购方，待审期间我想撤回并拿回全额预算、求购进草稿箱，以便反悔时不被套住、信息也不丢
17. 作为求购方，审核不通过时我想收到终态通知、全额退回预算并看到具体理由，以便知道该怎么改、不损失钱
18. 作为求购方，我下架求购（或到期下架）时我想预算立即解冻退回并进草稿箱，以便钱不被无谓占用
19. 作为买家/访客，我想只看到审核通过的商品与求购，以便信息流内容可信
20. 作为买家/访客，卖家改内容重审期间，我想暂时看不到该内容而不是看到新旧不一的内容
21. 作为管理员，我想在审核队列同时看到待审商品和待审求购的文字与图片，以便综合裁决
22. 作为管理员，我想裁决时拒绝必须填理由，以便用户知道被拒原因
23. 作为平台，我想超 24h 未审的商品/求购提醒管理员，以便审核不被遗忘（绝不自动裁决）
24. 作为平台，我想同一内容被多次审核（改内容重提、下架重发）时审核记录互不冲突，以便历史裁决留痕完整
25. 作为平台，我想裁决继续走统一用例 `decide()`，以便将来引入 agent 审核时不动业务编排
26. 作为卖家，我想"我的发布"里能看到待支付/待审/被拒的内容和拒绝理由，以便全程掌握发布进度

## Implementation Decisions

**数据模型**

- `product`：状态新增 `DRAFT` / `PENDING_REVIEW` / `REJECTED`；**废弃 `OFF_SHELF` 并入 `DRAFT`**（存量迁移）
- `want_to_buy`：状态从单值 `NORMAL` 扩展为 `DRAFT` / `PENDING_PAYMENT` / `PENDING_REVIEW` / `NORMAL`（=过审可见，存量数据零迁移）/ `REJECTED` / `CANCELLED`；新增 `images` 列（JSON 数组，上限 6 张，同商品/跑腿存储约定）
- 增量 ALTER 脚本 + init.sql 原地更新（同跑腿先例）；字段值沿用跑腿命名 `PENDING_REVIEW`/`REJECTED`，领域术语按 CONTEXT.md 区分

**状态机**

商品：
```
DRAFT --提交(初筛)--> PENDING_REVIEW --通过--> ON_SALE --售出--> SOLD
PENDING_REVIEW --撤回--> DRAFT          ON_SALE --改内容--> PENDING_REVIEW（对他人隐藏）
PENDING_REVIEW --拒绝--> REJECTED       ON_SALE --下架/到期--> DRAFT
REJECTED --转草稿--> DRAFT              DRAFT --删除--> DELETED
```

求购：
```
DRAFT --提交(初筛)--> PENDING_PAYMENT --支付(冻结预算)--> PENDING_REVIEW --通过--> NORMAL
PENDING_PAYMENT --超15min--> CANCELLED
PENDING_REVIEW --撤回--> DRAFT（解冻退款）
PENDING_REVIEW --拒绝--> REJECTED 终态（解冻退款）
NORMAL --改内容--> PENDING_REVIEW（对他人隐藏，不重新支付）
NORMAL --下架/到期--> DRAFT（解冻退款）
DRAFT --删除--> DELETED
```

**同步初筛**：复用现有关键词初筛服务，查标题+描述；直接发布命中即失败不落库（同跑腿）；草稿保存不做初筛（私有内容），草稿提交命中则停留草稿。

**求购支付（复用跑腿支付模式）**：钱包余额冻结预算（流水先行插入 + 唯一键幂等）；支付成功事务内条件 UPDATE 转待审 + 同事务写 outbox 消息；消费者发"进入人工审核"通知（消费者位置即未来 agent 接入点，同跑腿约定）；15 分钟未支付由超时扫描自动取消（终态，预算未动）。

**预算冻结规则**：预算仅在求购对外可见（NORMAL）期间保持冻结；撤回、拒绝、下架、到期一律全额解冻退回。资金操作一律流水先行 + 唯一键幂等（复用跑腿钱包基础设施）。

**裁决（复用统一用例）**：目标类型新增商品与求购，`decide()` 各加分支：商品通过 → `ON_SALE`、拒绝 → `REJECTED`（无资金环节）；求购通过 → `NORMAL`、拒绝 → `REJECTED` 终态 + 解冻退款 + 通知带理由。`content_review` 幂等键加入审核轮次，支持同一目标多次审核。管理端队列带出待审商品/求购及配图，复用跑腿看图裁决能力。

**可见性**：对外列表/详情只放行 `ON_SALE`（商品）/ `NORMAL`（求购）；待审、待支付、草稿、被拒仅卖家本人经"我的发布"可见；改内容重审期间对他人隐藏（不保留旧版展示、不做内容版本化）；详情对卖家带出 `rejectReason`。

**编辑语义**：待审中不可编辑（撤回转草稿）；商品上架后改价直接生效、改内容回待审；求购上架后改标题/描述/图片回待审（不重新支付）、**改预算 v1 不支持**（想改预算就下架重发，避免冻结差额补退的复杂度）。

**通知与超时**：裁决结果通知（`AUDIT_RESULT`，通过/拒绝都发、拒绝含理由）；求购支付成功后发"进入人工审核"通知（对齐跑腿），商品不发（提交即知）；24h 待审超时提醒（ADMIN+AUDITOR，通知去重，绝不自动裁决）。

**为 agent 预留**：`decide()` 已是统一裁决入口；求购支付消费者位置与商品提交事件位置留好，本次不实现 agent。

## Testing Decisions

- 只测外部行为，不测实现细节：HTTP 接口驱动全链路，用数据库/通知断言结果
- **完全复用现有 seam，不新增**：全链路集成测试基座（真实 Spring 上下文 + 数据库；HTTP 接口直接打；MQ 消费者/定时任务直调方法驱动）
- 先例：跑腿票 07 全链路集成测试（初筛命中/双链编排/超时扫描的写法直接对照）
- 必测场景：初筛命中改后重提（含草稿提交命中停留草稿）；商品发布→裁决→可见/拒绝→转草稿→重提→轮次幂等；求购创建→支付冻结→裁决→可见/拒绝→退款；待支付超时取消；待审撤回（商品进草稿 / 求购退款进草稿）；改价不重审 vs 改内容重审且期间隐藏；下架/到期（求购含解冻）；求购配图全链路；24h 提醒

## Out of Scope

- agent 自动审核（仅预留接入位置）
- 待审数量限流（信用分门槛 + 初筛已挡掉大部分灌水，真实被刷再补）
- 图片同步初筛（与跑腿对齐，仅人工看图裁决）
- 内容版本化 / 改内容重审期间展示旧版
- 求购修改预算（下架重发替代）
- 被拒内容的申诉通道
- 真实支付渠道（求购支付走虚拟钱包，同跑腿）
