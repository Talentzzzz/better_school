## Question

   - 背景：ADR-0011 的续命链在「起点很少落在整秒」时几乎必然触发，导致每格消费者数不可控（1~12）。
   - 决策：消息带 `cellTime`、定时投递到 `s+1` 封口后、固定合两格、删续命。

   - 边界 1 的接受记录：毫秒级跨秒漏格，概率 <0.01%，兜底收口。
   - 被否决的替代方案：秒对齐窗口（Redis/MySQL 时钟不同源）、三格方案（空转 67%）、只改延迟不改载荷（续命仍在、并发不可控）。

2. **`backend/marketing/docs/db/inventory.md`**：
   - 「触发」一节：延迟级别 1 → 定时消息 + `deliver_time_ms`；删掉「续命（窗口尾巴）」整段。

   - 「与主链路相接」：补一句「消息带 `cellTime`，一次合两格」。
3. **`CONTEXT.md`**：
   - 「预扣」词条：载荷说明（时间由明细回答）现在半失效——要改成「消息带责任起点秒」。

## Answer

### 1. 新 ADR：`docs/adr/0012-inventory-merge-cell-bound.md`

沿用 0011 的骨架（开篇四段「为什么必须换 / 难逆 / 反直觉 / 真权衡」→ `## Decision` → `## Considered Options`
→ `## Consequences`），另加一节 `## 边界 1：毫秒级跨秒漏格（已接受）` 记接受记录。票面要求的五项逐条落位：

| 票面要求 | 落在哪 |
| --- | --- |
| 背景：续命在「起点很少落在整秒」时几乎必然触发、每格消费者 1~12 | 「为什么必须换」。写清了机制：到达时（≈1.1s）当前秒未封口，而 `existsUnmergedDetail` 只看 `state = 0` ⇒ 「还有余量」恒真 ⇒ 持续流量下每秒续一条、永不收敛；叠上「循环合 ≤10 格」，同一格被「自己那条 + 前 10 条的顺带 + 续命」指到，消息量也从 1 条/秒/桶 变 2 条/秒/桶 |
| 决策：`cellTime` + 定时投递到 `s+1` 封口后 + 固定合两格 + 删续命 | `## Decision` 六条（载荷 / 2000ms 相对延迟的推导 / `mergePair` 两格串行 / 删续命且 `mergeKey` 降级兜底 / 判重口径不变 / 旧载荷丢弃） |
| 代价写全 | `## Consequences` 前四条：延迟 1.1s→2~3s（附实测）；丢消息从「下一跳顺手救」变「必等 60s」且兜底升为必需件；50% 空转是设计值（所以日志只能 `debug`）；滚动发布的载荷兼容（含发布顺序：先消费侧能丢弃、后生产侧带 `cellTime`） |
| 边界 1 的接受记录 | 末节：是什么 / 为什么不修 / 接受记录（概率 <0.01%、影响是延迟不是错误、**不要再提三格**） |
| 被否决的替代方案 | `## Considered Options` 五条：保持现状、**只改延迟不改载荷**（续命仍在、合并几格仍取决于到达时刻）、**秒对齐窗口**（TTL 按 Redis 时钟、格边界按 MySQL `create_time`，不同源 ⇒ 静默漏格）、**三格**（为万分之一付 +17% 常驻空转）、一条消息循环合到没有为止 |

数字一律取前五票的实测，不新造：裸投递 2.28~3.03s（票 02）、端到端 2931/2993/2967ms（票 05）、
旧延迟级别 1 的 1.07~1.12s（票 02 探针）、139 tests + 1 skipped（票 05）。

### 3. `backend/marketing/docs/db/inventory.md`

| 位置 | 改动 |
| --- | --- |
| 「触发」节标题 | 「1 秒延迟消息」→「定时消息（+2 秒）」；开篇点明「也没有续命这一层」 |
| 触发表 | 延迟级别 1 → `delay_ms = 2000` + 实测值；「何时」列删掉「合并仍有余量时自我续命」；兜底「负责什么」补上「滚动发布期被丢弃的旧载荷」「边界 1 的跨秒漏格」 |
| 载荷条目 | 三字段 → **定位三字段 + 责任起点秒**，写明由 INSERT 后同事务回读、只定位格不参与延迟、缺 `cellTime` 丢弃 |

| 「合并」节标题 + 首段 | 「时间格 + 最老一格 + `affected` 判重」→「固定两格 + `affected` 判重」；正文由「`mergeKey` 循环合最老一格 ≤10 格」换成 `mergePair` 的两格串行 + 为什么是两格 |
| 约束 3 | 「只合最老一格」→「顺序恒为 `s → s+1`、永不并行」，并写明**一格由相邻两条消息覆盖、第二条空转是设计值**；兜底的 `MIN` 循环降级为「兜底那条入口不知道格」才用 |
| 「合不了怎么办」 | 「不抛也不续命」→「不抛也不补发消息」；`affected != cnt` 的日志级别按实际代码改成 `debug`，暴露点从「下一跳就合掉」改成「对方事务里已对齐 / 真没合掉等兜底」；补一句「已无可合行」也走 `debug` |
| 兑换确认 3. | 「恒 1 条 `delay_level = 1`」→「恒 1 条 `delay_ms = 2000`」，并补 `cellTime` 取自 `type = 2` 那一行 |
| 「与主链路相接」 | 票面要求的「消息带 `cellTime`、一次合两格」放在末尾，并补一句它对这个域之外的含义：主链路要看到台账变化就得等这个节奏 |
| 索引说明 | `idx_key_cell` 从「找最老一格 + 翻转」改成「按 key + 秒翻转（消息路径只用这一半）+ 兼给兜底找最老封口秒」 |

> 票面第 2 条写的是「定时消息 + `deliver_time_ms`」，那是**票面撰写时**的方案（绝对投递时刻）。票 01 已把它推翻：
> `RocketMQTemplate` 的毫秒级延迟只有同步方法、且绝对时刻要把无时区的 `create_time` 按 `Asia/Shanghai` 转 epoch；
> 改用**相对延迟**后时区坑整条消失，列名也随之变成 `delay_ms`（票 02 落库、票 03 接线）。文档按**代码事实**写，
> 不按票面的旧字段名写——否则又把已经被否掉的方案写回文档。

### 4. `CONTEXT.md` 三个词条

- **预扣**：唤醒从「1 秒延迟消息 + 60 秒兜底」改成「定时消息（+2 秒）+ 60 秒兜底」，并补上载荷口径——
  「消息带这一笔的**责任起点秒**，投递时那一秒与下一秒都已封口，消费侧只合这两格」；`_Avoid_` 加一条
  「消息只带定位不带时间（时间已由消息回答，不再靠明细表推断）」，把这次半失效的旧口径钉在反例里。
- **时间格合并**：「一次唤醒只合最老一格」→「一条消息固定合 `s` 与 `s+1` 两格」，并按要求加
  「**一格由相邻两条消息覆盖，第二条空转是设计值**」；`_Avoid_` 加「一条消息循环合到没有为止」「合完再自我续命」。
- **超时任务**：「库存合并的 1 秒唤醒用的正是延迟等级」→「库存合并的唤醒用的正是延迟消息（毫秒级相对延迟，
  ≈2~3s 到达后合两格）」；`_Avoid_` 里「不用延迟等级」同步改成「不用延迟消息」——这一条是本次最容易读错的地方：
  边界没变（结算节拍 vs 逐对象 deadline），变的只是合并这一侧用的是哪档延迟能力。
