# 资金链路与抽奖预扣的跨事务一致性收口（ADR-0014 模式推广）

## Problem Statement

「扣积分 + 加抽奖次数」链路已按 ADR-0014 落地最终一致性（组合事务 + 状态表 + 定时补偿 + 幂等 + 死信），但全局排查发现项目里还有一批同型问题：**两个关键写操作不在同一事务、中间态宕机或普通业务失败会造成永久不一致、且没有任何服务端收敛机制**。对用户来说，后果是钱和资产莫名消失或凭空出现：

- 跑腿发布方支付成功，订单进了大厅可被抢，**悬赏却没被冻结**（余额不足的用户也能发布成功）；订单后来取消/超时，悬赏**永久悬置**在冻结态，只能人工 SQL 解冻。
- 送达 24h 自动完成或确认收货，**接单方的悬赏收入永久不结算**；发布方的钱解冻回余额，接单方什么都没拿到。
- 商品订单支付后买家钱未冻结，确认收货时**买家从未扣钱、卖家却拿到钱**。
- 抽奖用户点了抽奖，次数被扣、库存被预扣，但中奖记录没落库——**这一次抽奖凭空消失**，库存还白占一份。

共性缺口：钱包资金动作（冻结 / 解冻 / 收入）只有唯一键幂等（防重复），没有「漏做」的收敛（防缺失）；better-school 侧没有任何补偿或对账 job。而现有重试机制（客户端重试、超时中心回调重投）会被终态幂等判定**吞掉**——重试命中「已取消 / 已完成」直接返回，第二段资金动作永远不补跑，重试基建形同虚设。

## Solution

把 ADR-0014 的模式按各链路的实际情况推广落地，核心是两条裁剪原则：

1. **单体同库红利优先**：跑腿 / 商品与钱包同库同进程，中间态能被**组合事务端口**直接消灭——资金动作与订单状态翻转并在**一个物理事务**里，「单在 ⇒ 钱已动」由物理事务保证，不需要新表、不需要补偿 job。这正是 ADR-0014 购买单与扣积分同事务的同一根支柱。
2. **跨合并器窗口的缝靠对账补偿**：抽奖「预扣 → 落库」跨库存合并器事务，无法并成一个物理事务（合并器 5ms 批量窗口是有意设计），补一个**孤儿预扣对账 job**（照 `drawCountPurchaseScan` 口径：0/30 cron、条件更新抢占、指数退避、死信），让孤儿预扣在一个扫描周期内收敛。

所有资金动作继续踩现有唯一键幂等（`uk_order_type` / `uk_award_biz` / 次数桶 refId），重复执行零副作用；终态短路重放天然安全（资金已随终态在同一事务内完成）。不引入 Seata / TCC / 2PC / RocketMQ 事务消息。

## User Stories

1. 作为跑腿发布方，我在支付时希望「订单对外可见」与「悬赏被冻结托管」要么都发生要么都不发生，这样我的订单不会以零担保状态进入大厅。
2. 作为跑腿发布方，我希望余额不足时支付直接失败、订单停在待支付，这样不会出现「发布成功但钱没冻」的假成功。
3. 作为跑腿发布方，我在支付响应丢失后用同一凭证重试，希望拿到与首次相同的结果且不会重复冻结，这样重试是安全的。
4. 作为跑腿发布方，我取消一个已冻结悬赏的订单时，希望解冻退款与订单取消同时生效，这样我的钱不会悬置在冻结态。
5. 作为跑腿发布方，我的订单因超时被系统自动取消时，我希望悬赏被解冻退回，即使取消那一刻服务刚好崩溃也不会丢。
6. 作为跑腿发布方，我的订单超时且接单方已开工时，我希望解冻与信用分扣减一起生效，这样任何一侧都不会单独生效。
7. 作为跑腿接单方，我送达后订单 24h 自动完成时，希望悬赏结算进我的余额与订单终态同时生效，这样我的收入不会因为某次宕机永久丢失。
8. 作为跑腿接单方，我希望确认收货与仲裁的现有结算行为保持不变，这样已收敛的链路不被回归破坏。
9. 作为系统（超时中心），我重投一个已处理的超时回调时，希望读到终态即安全返回而资金动作已随终态完成过，这样重投永远无害。
10. 作为买家，我支付商品订单时希望「订单转已支付」与「货款冻结」在同一事务生效，这样已支付订单必然带着真实冻结额。
11. 作为买家，我余额不足时商品支付直接失败，这样不会产生「已支付未扣款」的订单。
12. 作为买家，我取消订单时希望解冻退款与取消同事务生效，这样我的货款不会被永久悬置。
13. 作为卖家，我希望买家确认收货时的解冻与给我的入账继续按现有口径收敛，这样我的收入只依赖已验证的幂等机制。
14. 作为抽奖用户，我的某次抽奖在「预扣成功但记录未落库」的窗口被中断时，希望服务端在一个扫描周期内替我补出抽奖结果，这样我不需要自己重试才能拿到本该有的结果。
15. 作为抽奖用户，当补偿重放时活动已结束导致决策不可重放，我希望库存预扣被回补、抽奖次数被退还，这样我不用为一次没发生的抽奖买单。
16. 作为运营，我希望孤儿预扣对账 job 的重试耗尽后进死信并留日志，这样我能人工介入而不是无声丢失。
17. 作为运维，我希望资金链路收敛后不再需要人工 SQL 解冻悬置冻结额，这样资金异常处置从例行工作变成真正的例外。
18. 作为运维，我希望对账扫描复用既有 xxl-job 注册口径与任务 seed 模式，这样我不需要学新的调度形态。
19. 作为审计，我希望每一笔资金动作仍以带唯一键的流水行落库，这样重复与缺失都可用流水与订单对账。
20. 作为开发者，我希望组合事务收口在基础设施层端口里、域之间不反向写对方的表，这样域边界不破在编译期。
21. 作为开发者，我希望 API 文档与代码口径重新对齐（支付「同事务」的宣称与实际实现一致），这样文档不再漂移。
22. 作为开发者，我希望这些链路的修复实现完成后不运行测试套件，由维护者自行验证，这样交付口径与仓库既有约定一致。

## Implementation Decisions

- **统一模式（ADR-0014 四支柱按同库红利裁剪）**：资金链路全部用**组合事务端口**消灭中间态——基础设施层新增组合事务端口（照营销侧积分扣减端口的形状：一个 `TransactionTemplate`（REQUIRED）内编排多域动作，参与域仓储同为 REQUIRED 自动并入同一物理事务）；域 A 不写域 B 的表，跨域动作经端口委托。**不新增状态表、不新增资金补偿 job**——状态表与定时补偿留给跨物理事务的缝，本范围只有孤儿预扣一条需要。
- **跑腿支付收口**：冻结流水（带订单幂等键）+ 余额条件扣减 + 订单「待支付 → 已发布」条件翻转 + 事件 outbox + feed 索引行诞生，并入**一个物理事务**；余额不足整事务回滚、订单留待支付（支付超时关闭照常生效）。每条链路实现完成后**不跑测试**（用户自行验证）。
- **商品订单支付收口**：货款冻结流水 + 余额条件扣减 + 订单「待支付 → 已支付」条件翻转并入一个物理事务；确认收货路径不改（现有幂等口径已收敛）。实现完成后**不跑测试**。
- **跑腿终态资金收口（取消 / 超时取消 / 自动完成）**：状态翻转 + 对应资金动作（发布方解冻退款；超时场景另含开工接单方的信用分扣减；自动完成的接单方悬赏收入）并入**一个物理事务**，资金动作经端口委托钱包域。终态短路保持现状语义——重放读到终态直接返回，资金已随终态完成过；唯一键幂等吸收事务提交后响应丢失窗口的重复。三处各自独立实现，**每处完成后不跑测试**。
- **商品订单取消收口**：与跑腿取消同型，取消翻转 + 解冻退款一个物理事务。完成后**不跑测试**。
- **回放样板不作强制迁移**：确认收货与仲裁的「终态短路回放完整结算结果」口径保持现状（它们已收敛）；新收口的链路靠物理事务消灭中间态后，短路天然安全，不引入回放对象。
- **孤儿预扣对账 job**：扫库存预扣明细中「预扣型（等待态）且对应抽奖记录不存在、且超过补偿阈值（10 分钟）」的行，两种收敛路径：① 决策可重放（活动仍有效）→ 以原幂等键重放抽奖落库后半段（不重复扣次数、不重复预扣，撞唯一键回放已扣），决策重跑可能得到与原决策不同的奖品，**接受该漂移**；② 决策不可重放（活动已结束 / 下线）→ 库存回补（等待态 → 剩余量的条件转移）+ 抽奖次数退还（次数桶幂等键入账，退还本身即幂等，不产生新的两步缝）。重试按 `drawCountPurchaseScan` 口径：0/30 cron、条件更新抢占、指数退避（1/2/4/8/16 分钟）、耗尽进死信（只日志 ERROR + 人工 SQL 重置，不建告警通路）。job 注册进既有营销侧任务 seed。**实现完成后不跑测试**。
- **文档对齐**：跑腿 API 文档中「支付（冻结悬赏），成功事务内转已发布」的宣称随本次实现成真，同时核对商品侧文档口径。
- **术语沉淀**：本规格引入的口径（组合事务端口 / 孤儿预扣收敛 / 资金收口）落 `GLOSSARY.md`，沿用「购买 / 购买单 / 死信 / 对账」既有词条的措辞风格。
- **明确不采用**：Seata / TCC / 2PC（重、无反向补偿需求）；RocketMQ 事务消息（回查要求本地状态表，省不掉任何东西）；为资金链路另建 outbox 状态表（同库红利下单体事务已消灭中间态，建表是负资产）。

## Testing Decisions

- **只测外显行为**：测试断言「两步之间任意一步失败后，系统状态是否收敛」「幂等重放是否返回原结果」「余额不足是否阻止状态翻转」，不测事务内部编排顺序、不测 mock 之间的调用次数。
- **主缝 = 用例编排层**：跑腿订单用例层与商品订单用例层的公开支付 / 取消 / 超时回调 / 自动完成方法，是本次改动对外的最高缝；失败注入点放在端口委托（钱包动作）边界上。新缝数量理想为 0——全部复用现有缝。
- **第二缝 = 触发层**：孤儿预扣对账 job 只测「job 触发 → 调用域扫描入口」一条断言，扫描逻辑的收敛行为在域层缝上测。
- **先例**：营销侧购买次数链路的测试（购买单三态状态机 + Stripe 语义重放 + 补偿扫描），本范围的测试形状与其对齐。
- **交付口径**：按用户指示，**所有链路实现完成后不运行测试套件**（不执行 mvn），由维护者自行验证；测试代码照常随实现交付，但不在本次交付流程内执行。

## Out of Scope

- 抽奖发货闭环的 MQ 死信巡检兜底（现链路收敛良好，另开票）。
- 营销行为返利的业务接入（当前入账侧无调用方、无第一步，接入时按本模式设计，另立规格）。
- ADR-0014 遗留的 T+1 对账 job（购买链路对账，等链路稳定后另开票）。
- 死信告警通路（`alarm_email` 现状为空，接监控时第一个上报死信条数）。
- 购买单 DONE 行归档策略。
- 引入任何分布式事务框架或 MQ 事务消息。

## Further Notes

- 排查来源：2026-11-19 全仓事务边界扫描（better-school 单体 + marketing 营销工程全部非测试 ServiceImpl / Case / 仓储 / job / MQ 消费方）。
- 对照组事实：跑腿确认收货与仲裁的终态短路会把结算所需金额完整回放进结果对象、由编排层重放资金动作、靠钱包流水唯一键去重——这是仓库内跨事务编排的正面样板，也是「为什么其余终态链路必须修」的判据。
- 「余额不足仍进大厅」比宕机窗口更严重：它是**普通业务路径**即可触发的永久不一致，本次收口后由组合事务的余额校验前置一并消灭。
- 已判无风险、不动的链路：钱包 / 信用各动作（流水先行 + 唯一键幂等 + 单事务原子）、用户注册、库存合并器、超时任务注册、搜索 / 通知 / feed 索引（outbox 或可重建 job 收敛）、中奖积分入账与 `bs-lottery-drawn` / `bs-points-changed` 广播（outbox + MQ 重投 + 幂等消费）。
- 关联文档：`docs/adr/0014-draw-count-purchase-eventual-consistency.md`（本规格的模式源头）；根目录 `GLOSSARY.md`（术语真源）。
