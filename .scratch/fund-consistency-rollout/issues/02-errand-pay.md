# 02 跑腿支付收口（冻结悬赏 + 转已发布一个物理事务）

## 问题

spec User Stories 1–3、9：跑腿发布方支付成功后订单进大厅可被抢，悬赏却没被冻结（余额不足用户也能发布成功）；支付响应丢失后重试必须安全（不重复冻结）。API 文档宣称「支付（冻结悬赏），成功事务内转已发布」与实现不符。

## 交付

在跑腿订单用例层 / ServiceImpl 的支付路径上，经 01 的组合事务端口把以下动作并入**一个物理事务**：

1. 冻结悬赏流水（带订单幂等键，踩钱包流水唯一键）；
2. 余额条件扣减（余额不足 → 抛异常整事务回滚，订单留待支付）；
3. 订单「待支付 → 已发布」条件翻转；
4. 事件 outbox 行 + feed 索引行诞生（沿用现有写法）。

重复支付重试：命中幂等键零副作用，返回与首次相同结果。

## 约束

- 测试形状对齐营销侧购买链路（外显行为断言：余额不足阻止状态翻转、幂等重放返回原结果、两步间失败后状态收敛）；失败注入点在端口委托（钱包动作）边界。**不运行测试套件**。
- 支付超时关闭链路照常生效，不改。

## 验收

- 支付成功 ⇒ 订单已发布且悬赏已冻结，无「发布成功但钱没冻」。
- 余额不足 ⇒ 支付失败、订单留待支付。
- 文档宣称成真（文档回写在 09）。
