# 跑腿订单审核机制重构（先付后审）

术语遵循根目录 `CONTEXT.md` 的"跑腿订单"一节；架构决策见 ADR-0003（先付后审）。

## Problem Statement

现状的跑腿订单审核有两处错位：其一，创建时同步敏感词命中的订单转人工待审，**未支付的订单占用人工审核资源**；其二，通过初筛的订单支付瞬间即对外可见，**人工把关对主链路形同虚设**。此外：审核不通过只有默认文案、没有具体理由可看；订单不支持配图，审核员只能看文字；后端连图片上传通道都没有（图片只是 URL 字符串）；审核裁决也没有可复用的统一接口。

## Solution

- **创建**：同步初筛只覆盖标题+描述，命中即创建失败、不落库；通过则创建成功（待支付），支持配图（最多 6 张）
- **支付**：支付成功事务内转入已付款待审 + 同事务写 outbox 消息；consumer 发"已进入人工审核"站内通知
- **人工审核**：裁决收敛为独立用例接口 `decide(目标类型, 目标ID, 通过?, 理由, 操作者)`，管理员调用该接口裁决；通过 → 对外可见（PUBLISHED）；拒绝 → REJECTED 终态 + 全额退款（解冻）+ 通知（不通过必须给理由）
- **待审期**：作者可取消并解冻全额退款；超 24h 未审由现有超时扫描提醒管理员，不自动通过也不自动退款
- **拒绝理由**：订单详情接口对作者带出 rejectReason（REJECTED 时）
- **配图**：引入 MinIO 对象存储 + 上传接口，前端从手填 URL 改为真上传；配图仅人工审核环节查看裁决

## User Stories

1. 作为发布者，我创建订单时写了违禁词，我想立即被告知创建失败且订单未被创建，以便马上改文案重发
2. 作为发布者，我想给订单配最多 6 张图片，以便把需求说清楚
3. 作为发布者，我想创建成功后先支付再进入审核，以便平台审核的是真实想下单的订单
4. 作为发布者，支付成功后我想收到"订单已进入人工审核"的通知，以便知道接下来发生了什么
5. 作为发布者，待审期间我想取消订单并拿回全额退款，以便反悔时不被套住
6. 作为发布者，我想审核通过后订单立即对外可见并收到通知，以便尽快有人接单
7. 作为发布者，审核不通过时我想收到通知，并在订单详情看到具体不通过理由，以便知道该怎么改
8. 作为发布者，被拒订单的冻结金额我想全额退回，以便不损失钱
9. 作为管理员，我想在审核队列看到待审订单的文字与配图，以便综合裁决
10. 作为管理员，我想裁决时给出通过/不通过，不通过必须填理由，以便用户知道被拒原因
11. 作为平台，我想未支付的订单不进审核队列，以便审核资源只花在已付款订单上
12. 作为平台，我想超 24h 未审的订单提醒管理员，以便审核不被遗忘（但绝不自动裁决）
13. 作为平台，我想裁决收敛为统一的用例接口，以便审核方式演进时不动业务编排
14. 作为访客，我想只看到审核通过的订单，以便信息流内容可信

## Implementation Decisions

**数据模型**

- `errand_order` 新增 `images`（URL 列表，沿用 `post.images` 的存储约定），上限 6 张
- 状态枚举新增 `REJECTED` 终态；`PENDING_REVIEW` 语义重定义为"已付款待审"（见 ADR-0003）
- `content_review` 表沿用（已有 `reason` 字段），跑腿拒绝理由存这里，不另建表
- 增量 ALTER 脚本供现有联调库（init.sql 原地更新，同 comment-nesting 先例）

**状态机（反转后）**

- `PENDING_PAYMENT → PENDING_REVIEW`：支付事务内条件 UPDATE + 同事务写 outbox（topic 如 `bs-errand-paid`）
- `PENDING_REVIEW → PUBLISHED`：裁决通过；`PENDING_REVIEW → REJECTED`：裁决拒绝，同事务/编排层解冻退款（复用 unfreeze + `uk_order_type` 流水幂等）+ 通知带理由
- `PENDING_REVIEW → CANCELLED`：作者待审期主动取消，解冻退款（钱在冻结中，不打回说不过去）
- 既有超时扫描逻辑随之调整：`PENDING_REVIEW` 不再是免付款状态，其超时语义改为 24h 提醒管理员（不自动裁决）；`PENDING_PAYMENT` 超时取消逻辑不变

**同步初筛**

- 命中 → 业务异常"内容包含违规词汇，请修改后重试"，订单不落库（标题+描述）；误伤由用户改文案重发，不设申诉通道

**裁决接口**

- case 层独立裁决用例：`decide(targetType, targetId, approve, reason, operatorId)`；现有 `ReviewCase` 三类内容的裁决收敛走此用例或转发
- 人工 = 管理员登录态
- 拒绝时 reason 必填；通过时 reason 可空

**配图与 MinIO**

- docker-compose 新增 MinIO 服务；后端 MinIO SDK，上传接口仅登录用户，jpg/png/webp、单张 ≤5MB，返回由后端签发的访问 URL
- 前端 `ImageUrlPicker.vue` 从手填 URL 改为真上传；订单创建请求带 images 列表
- 配图无同步初筛，仅人工审核环节查看（不接第三方图像识别）

**通知**

- 支付成功 consumer：给作者发"订单已进入人工审核"（复用 ORDER_UPDATE 或审核结果类型，实现票里定）
- 裁决通过/拒绝：复用 `AUDIT_RESULT`；拒绝通知含理由
- 24h 未审提醒：发给管理员（通知类型实现票里定）；通知写入失败只吞不回滚主流程

**API 契约**

| 端点 | 语义 |
| --- | --- |
| `POST /api/files/upload` | 图片上传，返回访问 URL |
| `POST /api/errand/orders` | 创建订单；同步初筛命中返回业务错误 |
| `POST /api/errand/orders/{id}/pay` | 支付（冻结）；成功即转待审 |
| `POST /api/errand/orders/{id}/cancel` | 取消；待审期可取消并解冻 |
| `GET /api/errand/orders/{id}` | 详情；作者视角 REJECTED 时带 rejectReason |
| `POST /api/admin/reviews/decide` | 统一裁决（管理端签名） |

## Testing Decisions

- 沿用 comment-nesting 先例：trigger 层 seam（HTTP + 消费者入口直接驱动，不等 outbox 定时器）、Testcontainers、数据库可观察状态断言
- 覆盖：初筛命中不落库、创建含配图、支付转待审 + outbox 落库、待审取消解冻、裁决通过转 PUBLISHED、裁决拒绝转 REJECTED + 退款流水 + 通知带理由、重复裁决/重复消费幂等、24h 提醒、图片上限 6 张与格式大小校验
- 冒烟：真实 docker compose（含 MinIO、RocketMQ）走通 上传 → 创建 → 支付 → 审核通过/拒绝 全链路

## Out of Scope

- 第三方内容安全服务 / 图像识别（配图无同步初筛）
- 帖子与评论的图片审核、评论配图
- 帖子发布链路（同步敏感词）的任何改动
- 第三方支付接入（仍是 mock 虚拟钱包）
- 审核工作台性能优化、审核统计报表
