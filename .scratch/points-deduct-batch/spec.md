# 积分扣减：从逐桶写改为先算后批量写

Status: ready-for-agent

## Problem Statement

学生在抽奖页点「100 积分兑换 1 次抽奖」时，如果他的积分分散在许多张不同批次入账的券上，这次兑换要在数据库里逐张券来回读写二三十次。

积分有效期是 365 天，意味着桶只进不出——只有被扣才会减少，不会被时间清走。所以一个活跃用户攒到几十张券是必然的，兑 100 分跨十几张券属于常态。

跨 N 张券就是 2N 条语句，全部落在同一个事务里、全程持有这些券的行锁。可观测的后果有三个：

- 兑换接口的响应时间随用户攒的券数增长，与「兑 100 分」这个固定业务量脱钩
- 扣减进行期间该用户的全部积分券被锁着，他自己并发的另一笔操作（比如刚中的奖到账）只能排队
- 桶碎到极端情况时可能触及锁等待超时，用户看到的是系统错误而不是「积分不足」

另外，扣减前置的幂等预检带着一条 `FOR UPDATE`，但它在「这笔没扣过」时查不到记录，加的是间隙锁；间隙锁彼此兼容、并不互斥，这条锁根本拦不住并发重复。它唯一的实际效果是在「空查 + 后续插入」这个 InnoDB 常见组合上，埋了一份死锁可能。

## Solution

把扣减从「一边算一边写」改成「先算完整笔方案、再一次写完」：

一次加锁读取出该用户全部可用券 → 在内存里算出每张券各扣多少 → 用固定三条语句落库（一次写全部消费明细、一次把扣光的券清零、一次扣减唯一那张部分扣的券）。

跨 1 张券和跨 50 张券，落库语句数都是三条，事务长度不再随桶的碎裂度增长。

同时移除幂等预检上那条 `FOR UPDATE`。它挡不住并发重复，真正的互斥点一直是由消费明细的唯一键承担的。去掉它不影响任何正确性，只消掉了那份死锁可能。

对外的兑换接口、响应形状、业务码、FIFO 语义、凑不够整笔拒绝的规则，全部不变。这是纯粹的内部重构。

## User Stories

1. 作为学生，我想在积分分散在十几张券时也能快速完成兑换，这样点「兑换」不用盯着转圈。
2. 作为学生，我想兑换期间自己的其他积分操作不被长时间卡住，这样刚中的奖能马上到账。
3. 作为学生，我想在积分不够时立刻看到「积分不足」，而不是等半天后收到一个系统错误。
4. 作为学生，我想手抖连点两次兑换只扣一次积分，不多花冤枉分。
5. 作为学生，我想兑换成功后看到准确的余额，不用怀疑系统算错。
6. 作为学生，我想最早过期的那张券先被花掉，这样不会因为过期白白丢分。
7. 作为学生，我想已经过期但还没被定时任务清理的券永远不参与扣减。
8. 作为学生，我想在流水里看清每笔兑换是从哪几张券扣的，出问题时能对得上账。
9. 作为抽奖服务，我想通过同一个兑换入口拿到明确的三态结果（成功 / 积分不足 / 系统故障），这样好决定给前端返什么业务码。
10. 作为抽奖服务，我想扣减是幂等的，同一个兑换单号重放不会多扣一次。
11. 作为抽奖服务，我想「扣分成功但次数入账失败」这种中间态可以用同一个 token 安全重试补齐。
12. 作为维护者，我想扣减事务的语句数不随桶数增长，这样最坏情况的锁持有时间是可预期的。
13. 作为维护者，我想跨桶场景下的所有可观察结果（余额、明细行数与金额、变动事件）与逐桶版本完全一致，这样重构不改变任何对外语义。
14. 作为维护者，我想扣减失败时整笔回滚，不留半扣的中间态。
15. 作为维护者，我想消费明细的唯一键仍然是并发重复兑换的唯一互斥点，不依赖预检的锁。
16. 作为维护者，我想每一条批量写入都校验影响行数，任何一条对不上就整笔回滚，而不是静默继续。
17. 作为维护者，我想跨一张券时退化为单行写入，不为最常见的单桶场景引入额外开销或额外分支。
18. 作为维护者，我想这次改动不需要改表结构、不需要数据迁移、不需要动调用方。
19. 作为维护者，我想预检查询不再引入间隙锁，从根上消掉「空查 + 插入」的死锁可能。
20. 作为维护者，我想并发重复兑换有一条专门的测试证据，而不是只靠代码注释声称「唯一键兜底」。
21. 作为运维，我想极端碎桶情况下不会再因为单事务语句数过多而撞上锁等待超时。
22. 作为数据库，我想每次扣减的写入次数有明确上界，不给单个事务堆积几十条语句的机会。

## Implementation Decisions

### 范围与不变量

- 对外契约零变化：兑换入口、请求与响应形状、业务码（成功 / 积分不足 / 参数错误 / 系统错误）全部不动。
- 表结构零变化：积分桶表与消费明细表的列与唯一键都不动，无需迁移。
- 领域语义零变化：扣减按过期时间 FIFO、凑不够整笔拒绝不产生半扣、过期由读路径懒判、余额恒为「未过期且未扣完的桶剩余量之和」、消费明细逐桶记账——全部保留。
- 事务边界仍在积分仓储实现内（`TransactionTemplate` REQUIRED），位置不变。

### 改动一：扣减路径拆成「算」和「写」两段

阶段一（只读）：幂等预检 → 一次加锁读该用户全部可用券（`remain > 0 AND expire_at > NOW()`，按 `expire_at` 升序、`id` 升序，`FOR UPDATE`）→ 内存求和判断够不够。

不够：不进写阶段，事务空提交，返回积分不足。沿用现状——不用回滚来表达业务失败。

阶段二（纯内存，不碰数据库）：算每张券的扣减量，得出两个集合——「被扣光的券」与「至多一张部分扣的券」。

> 这条性质由 FIFO 顺序本身保证：一旦某张券的面额大于还差的额度，扣掉差额后剩余归零、循环即止。所以不存在「两张券各扣一半」，部分扣的券最多一张。

阶段三（写，固定 3 条）：

1. 一条多值 `INSERT IGNORE` 写全部消费明细，行数等于被碰到的券数
2. 一条 `UPDATE ... SET remain = 0 WHERE bucket_id IN (...)` 把扣光的券清零
3. 一条 `UPDATE ... SET remain = remain - ? WHERE bucket_id = ? AND remain >= ?` 扣那张部分扣的券；若整笔恰好扣完、没有部分扣的券，这条跳过

判定：第 1 条的影响行数必须等于明细条数，第 2 条必须等于「扣光」集合大小，任一不等即整笔回滚。撞唯一键表现为行数偏少，语义与逐桶版一致——判为重复兑换、回滚，事务外重读余额按成功回报。

跨一张券时第 2、3 条退化为单行更新，总语句数仍是 3，不为单桶场景引入额外分支。

第 3 条保留 `remain >= ?` 守卫（这是唯一还在用减法的语句）；第 2 条用精确赋值 0，因为「扣光」的定义就是归零，且券已在本事务行锁内。

消费明细的写入必须发生在任何桶余量变更之前。这不只是仓库惯例：唯一键是全链路最早的重复判定点，先插明细才可能在动余额之前发现重复。

### 改动二：移除幂等预检上的 `FOR UPDATE`

- 预检查询改为普通快照读。
- 理由：该查询在「未扣过」时结果为空、加的是间隙锁，而间隙锁彼此兼容、不互斥，拦不住并发重复。真正的互斥是消费明细的唯一键。
- 副作用收益：消除「空查 + 插入」这一 InnoDB 常见死锁组合。
- 代价：在「本事务开始之后才提交的重复请求」这一极窄窗口内，预检会漏判，改由阶段三的明细唯一键兜底——与现状的最坏结果一致（回滚、按成功回报），无正确性损失。
- 同步更新该方法与 SQL 上的注释，删掉「加锁读让并发写落在同一间隙上」这类已被证伪的表述。

### 被否决的方案（记录以免重走）

- 单条 `CASE bucket_id WHEN ... THEN ... END` 覆盖所有券：把「扣光」和「部分扣」统一成赋值语义，会同时丢掉 `remain >= ?` 守卫，还必须靠 `ELSE remain` 防止未匹配行被写成 NULL；且是一条超长 SQL。不如三条短语句。
- 改用乐观锁（版本号 / CAS）：跨 N 张券要 N 次 CAS，任一失败整笔重来，重试成本高于悲观锁的收益。积分扣减是低频、低冲突、强一致要求的场景，悲观锁的代价可以接受。
- 把同批次入账合并成一张「大券」以减少桶数：破坏「桶即发放流水、每笔入账一行」的事实源语义，不做。

### 接口层变更清单（按模块，不给路径）

- 积分仓储接口：`deduct` 的签名与返回类型不变，内部拆成「算」与「写」两段私有步骤。
- 积分 DAO / Mapper：新增两个语句（批量写明细、批量清零），保留既有的单桶扣减语句供部分扣使用，预检语句去掉 `FOR UPDATE`。
- 调用方全链路（兑换编排、积分扣减端口、Dubbo Provider、HTTP 入口）：零改动。

## Testing Decisions

### 什么算好测试

只断言外部可观察状态：Dubbo Provider 返回的响应对象，加上数据库里的积分桶剩余量、消费明细行、outbox 载荷。不断言 SQL 条数、不断言私有方法调用、不 mock 任何 Bean。

批量写入是内部实现形状，不该进 seam——它没有独立于「扣减」这个用例的对外可观察行为。

### Seam

沿用现有 seam，不新增。测试基类已提供「Dubbo Provider Bean 发起 + JDBC 直查落库 + outbox 载荷断言」这套能力，逐桶版与批量版走的是同一个 Seam，正好用来证明两者行为一致。

前置态沿用基类直接插入历史桶的方式（可指定过期时间与面额）。

### 用例

在既有扣减测试集上扩充，不另起一套：

| 用例 | 断言重点 | 状态 |
| --- | --- | --- |
| 跨 3 张以上券的 FIFO 扣减 | 余额、每张券剩余量、明细行数与每行金额、事件 delta 与 balanceAfter | 新增 |
| 恰好整笔扣完（无部分扣） | 第 3 条语句不执行，结果仍正确 | 新增 |
| 跨 1 张券 | 退化为单桶，结果与现状一致 | 新增 |
| 并发重复兑换（同一单号两线程） | 最终只有一笔明细、只扣一次 | 新增 |
| 积分不足 | 一行都不动、无明细、无事件 | 保留 |
| 同一兑换单号重放 | 只扣一次、只发一条事件 | 保留 |
| 跳过过期桶 | 过期券剩余量不被改动 | 保留 |
| 非兑换类原因 | 参数错误，不当作扣分 | 保留 |

并发那条是「唯一键兜底」这个决策的直接证据，改造前不存在，需要新建。

### 回归基线

改造前先在现有测试集上跑一遍全绿，改造后逐条比对。跨桶用例的断言要与改造前完全一致——如果为了实现批量而改了任何一条断言，说明语义被改动了，要停下来重新审视。

## Out of Scope

- 不改表结构、不加索引、不做数据迁移
- 不改入账路径（含它那条快照读算余额的做法）
- 不改抽奖次数域的扣减（那套桶虽然同构，本次不动）
- 不改「桶即发放流水」的模型，不做同日 / 同源入账合并
- 不改过期落账任务
- 不处理行为返利 `refId` 跨业务复用的隐患（同用户签到与支付都用返利原因时，两笔业务若拿到相同的业务 ID 会撞唯一键、被误判为重复入账）——另开票
- 不做压测与容量评估

## Further Notes

- 收益是「事务语句数从 2N+4 降到 6~7，且与桶数无关」，不是缩短单条 SQL 的执行时间。真正的价值在锁持有时间可预期。
- 改造前建议先量一次真实分布：消费明细按（用户，原因，业务 ID）分组后的行数分布。若实测 95% 以上集中在 1 行，说明桶没有预期地碎，本次收益有限，应重新评估优先级再动手。
- 365 天有效期是桶会碎裂的根本原因：桶只进不出，只有被扣才减少。想从源头减少桶数就得动「每笔入账一行」这个模型，那是另一件事。
- 幂等三件套的位置关系不要动：兑换单号由「用户 + 本次点击 token」确定性映射 → 消费明细唯一键兜底 → 重放回放同一份结果。三者的顺序和职责不能互换。
- 同一用户的扣减之间是串行（排队），不同用户完全并行；入账只追加不改旧行，彼此不冲突，但会被扣减的间隙锁短暂挡住——这条特性在本次改动后不变，只是变短了。
