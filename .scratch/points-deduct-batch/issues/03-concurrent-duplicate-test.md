# 03: 并发重复兑换测试：证明消费明细唯一键才是唯一互斥点

**What to build:** 一条专门的并发用例：同一个兑换单号，两个线程同时发起兑换，最终只落一笔消费明细、只扣一次积分、只发一条变动事件。

它是两个决策的共同证据——「预检那条加锁读拦不住并发重复，真正的互斥一直由消费明细唯一键承担」和「批量落库后撞唯一键表现为影响行数偏少、整笔回滚、事务外重读余额按成功回报」。改造前就要建起来，且要在现有实现上也是绿的；如果不绿，说明现状本身就有并发漏洞，先记录再继续。

两线程要真的同时在场（同一把起跑线），不能靠 sleep 宽度凑时序；断言看落库结果与响应，不看线程谁先谁后。

**改动范围**：只动一个测试文件
`backend/marketing/marketing-app/src/test/java/com/betterschool/marketing/integration/points/PointsDeductIntegrationTest.java`
——既有 8 条用例一字未改（含断言），新增 1 条用例 + 1 个并发小工具 `deductConcurrently`。

**用例形状**（`deduct_sameRedeemOrderFromTwoThreads_chargesOnce`）

| 项 | 值 |
| --- | --- |
| 前置桶 | 60 分 / 1 天后到期、300 分 / 10 天后到期（合计 360） |
| 两线程请求 | 同一 `userId`、同一 `reasonType=REDEEM_DRAW_COUNT`、**同一 `refId=99001`**、`amount=100` |
| 起跑线 | `CyclicBarrier(2)`：两方都到场才放行，不靠 sleep 宽度凑时序 |
| 断言 | 两侧响应都 `success` 且 `balance=260`；最早那张 → 0、后一张 → 260；明细 2 行 = 60 + 40、合计 100；`bs-points-changed` 恰 1 条 `delta=-100 / balanceAfter=260` |
| 不看的 | 线程谁先谁后、SQL 条数、私有方法、任何 Bean 的 mock |

**前置余额为什么要留出「扣完还剩 ≥ 100」**：这是把「唯一键才是互斥点」隔离出来的必要条件。
若余额恰好只够一笔（比如只有 100），重复者拿到桶锁后可能先撞上「可用余额不足」的闸门、根本走不到写明细那一步，
测出来的就变成余额判断而不是唯一键。本票的口径是「唯一键拦重复」，所以场景刻意让它有余量。

**结果：本票用例在未改动的实现上是红的——现状确有并发漏洞。**

连跑 **9 轮（评审改稿前 8 轮 + 改稿后复核 1 轮），9 轮全红**，失败点完全一致：`DeadlockLoserDataAccessException`（MySQL 1213）；
其中逐条定位过 SQL 的 8 轮，死的那条**都是** `selectAvailableBucketsForUpdate`（`FROM points_bucket ... FOR UPDATE`），
不是偶发抖动，是这条路径的稳定结果。

`SHOW ENGINE INNODB STATUS` 的现场（`2026-10-18 16:08:07`）：

| 事务 | 持有 | 等待 | 角色 |
| --- | --- | --- | --- |
| (1) | `points_detail.idx_user_ref` 上 `lock_mode X` 的 supremum **间隙锁**（预检空查留下的） | `points_bucket.idx_user_expire` 记录锁 | 后到者（会被调用方当成「重复兑换」的那一侧），undo=0 |
| (2) | `points_bucket` 两行 X 记录锁 | `points_detail.idx_user_ref` 上 X **insert intention** | 先到者（真正扣分的那笔），undo=1 |

`*** WE ROLL BACK TRANSACTION (1)` —— 被回滚的是**后到那一笔**，也就是本该被唯一键按幂等挡下的那个请求。

**机制（与 spec 的预判逐字对上）**：两线程的预检都查到空、都在 `idx_user_ref` 上留下间隙锁（间隙锁彼此兼容）；
先到者拿到桶行锁后 `INSERT IGNORE` 明细，需要往同一个间隙插 insert intention 锁，被后到者的间隙锁挡住；
后到者此时正要拿桶行锁，被先到者挡住——环成了。**消费明细唯一键根本没轮到出场，死锁先把它截胡。**

**结论（两条，都直接决定后续票怎么接）**

1. 预检那条 `FOR UPDATE` 不只是「无效」，它是**主动有害**的：把「并发重复兑换」从可以按幂等成功回报的场景，
   变成了调用方收到的**系统错误**——`PointsExchangeDubboService` 只吞 `AppException`，
   `DeadlockLoserDataAccessException` 会原样抛出、跨 Dubbo 落到抽奖侧。这恰好违反本票要钉住的不变量
   「两侧都不因并发重复拿到系统错误」。
2. 所以 spec 里「真正的互斥一直由消费明细唯一键承担」这句话，**在现状下不可观测**：唯一键要能兜底，
   前提是预检不再留间隙锁。本票用例在 04 落地前不可能转绿——不是用例写得刁，是现状就这样。

**给 04 的交接**：04 的「预检去掉 `FOR UPDATE`」因此不再只是消掉死锁可能性的优化，而是本票用例转绿的**必要条件**。
04 落地后用同一条用例连跑 ≥10 轮确认，预期变为：先到者落库；后到者要么预检直接命中、要么撞唯一键整笔回滚、
事务外重读余额按成功回报，两侧都不抛异常。

**另一条本票没覆盖、但 04/05 该看一眼的窗口**（未单独验证，只从代码路径读出，记录以免被当成已覆盖）：
若重复者的预检发生在先到者提交之前（快照漏判），而先到者恰好把余额扣到不足以支付本次额度，
重复者拿到桶锁后会先走「积分不足」分支返回 `4101`——唯一键同样没机会出场，重复者本该 `success` 却拿到业务失败。
本票场景刻意留了余量，测不到这一支。要么在「不足」分支里于桶锁内再查一次明细，要么明确接受这个窄窗口——
需要 04 或 05 做决定。
