# 跑腿多人单（组队协作）

术语遵循根目录 `CONTEXT.md` 的"跑腿订单"一节（多人单、成团、每人报酬、散团、补位）；"系统群"基建（建群/成员进出/封盘）已由 chat 域就绪，本功能是其首个生产调用方。

## Problem Statement

现有跑腿订单是单人单接（`taker_id` 单字段，条件 UPDATE 先到先得），无法表达"一件活需要多个人一起干"的真实需求（如搬大件、多人配送）。需要引入多人单：发布方设定所需人数，接单者进团凑人数，成团后订单开始并进入系统群协作；执行中途有人退出、发布方反悔等异常路径需要明确的处理规则。

## Solution

- **发布**：发布方可选"需要人数"（2~10；不选即默认 1 = 现有单人单，链路完全不变），并设定**每人报酬**；支付总额 = 每人报酬 × 所需人数，走现有先付后审链路（同步初筛 → 冻结总额 → 人工审核 → PUBLISHED）
- **组队期**：抢单改为"进团"——先到先得、不可挑选（并发约束：当前人数 < 所需人数即可加入），进团前可见"当前/所需人数"、不可见成员身份，进团后成员列表互相可见（只读昵称头像）；组队期随时可退出（不扣信用分、不动资金）；组队期无群聊，可用现有「联系」按钮与发布方开 1v1
- **成团**：最后一人加入的瞬间自动成团——订单开始（类比 TAKEN）、**执行 deadline 重算 = 成团时间 + time_limit_hours**（组队期用原 deadline = 支付 + time_limit_hours，两段各自计时）、创建系统群（发布方 + 全部接单者，GROUP_CREATED 系统消息）
- **执行期分阶段**：取货前接单方可退出（扣信用分 -20），订单进入补位状态等人；取货后锁定，退出与取消一律走仲裁（DISPUTED）
- **补位**：不设独立等待时限，执行 deadline 即上限——有人补位则继续执行，到 deadline 仍缺人则散团
- **散团**：组队超时未凑齐、或执行期补位未齐——订单 CANCELLED、悬赏**全额**退发布方、未完成**一律不结算**、无人扣分；系统群封盘并落 SYSTEM 说明
- **完成一刀切**：DELIVERED → 发布方一次确认（或 24h 自动完成）→ COMPLETED，全员同时结算：发布方 unfreeze 总额，每个接单者各得每人报酬（income 按人落流水）；系统群封盘
- **取消**：发布方在组队期与执行期取货前均可取消，全额退、接单者不结算、发布方不扣信用分（沿用单人单现状）
- **评价按人**：发布方逐一评价每个接单者，每个接单者评价发布方；好评 +2 各自计（每日上限不变）

## User Stories

1. 作为发布者，我想发布订单时设定所需人数与每人报酬，一次支付总额，以便让多个人共同完成一件活
2. 作为发布者，我想人数凑齐后订单自动开始并自动建群，以便不用手动确认、直接和团队沟通
3. 作为接单者，我想在进团前看到"已有几人/还需几人"，以便判断这单抢不抢得到
4. 作为接单者，我想进团后看到团里还有谁，以便决定要不要叫朋友一起进
5. 作为接单者，我想在成团前随时退出且不被扣分，以便反悔没有成本
6. 作为接单者，我想取货前因临时有事退出（承担扣分），订单补人继续，以便不逼我硬着头皮跑完
7. 作为发布者，我想组队超时自动散团并拿回全款，以便凑不齐人时不损失钱
8. 作为发布者，我想执行中有人退出后订单自动等人补位，到 deadline 没补齐就散团退款，以便不用手动处理缺人
9. 作为接单者，我想订单完成后和同伴一起各拿各的报酬，以便分配规则透明（每人报酬发布时可见）
10. 作为发布者，我想完成后逐一评价每个接单者，以便好差评落到人头上
11. 作为平台，我想"未完成一律不结算"成为铁律，以便避免按比例折算的仲裁泥潭
12. 作为平台，我想多人单成团即建系统群、终态即封盘，以便协作沟通有宿主且生命周期由系统驱动

## Implementation Decisions

**数据模型**

- `errand_order` 新增 `required_takers`（默认 1；1 = 单人单，现有 grab/taker_id 链路原样保留，**不**为多人单复用 taker_id）
- 新增订单成员表（多人单的接单者集合）：order_id + user_id + 加入时间/状态（在团/已退出/已补位），多人单的"当前人数"由此表 COUNT
- `errand_evaluation` 加 `to_user` 维度，唯一键扩展为 (order_id, from_user_id, to_user_id)
- 钱包流水幂等键 `uk_order_type(order_id, type, biz_round)` 扩展支持按人结算（biz 维度带 taker），INCOME 一次成团结算落 N 条
- 增量 ALTER 脚本供联调库（init.sql 原地更新，同 005/006 先例）

**状态机**

- 组队期 = PUBLISHED（多人单不新增组队状态，"组队中"由 人数 < 所需人数 派生）
- 成团 = 现有 TAKEN 语义的多人版本（最后一人加入的条件 UPDATE 事务内：写成员行、人数达标则置开始态 + 重算 deadline + 落建群 outbox/直接调 ChatGroupService）
- 执行期退出 → 回到差人状态（成员行标已退出 + 系统群 removeMember + SYSTEM 消息留痕）；补位 = 新人走同一条进团路径
- 散团/完成/取消 → sealGroup 封盘（终态），历史消息只读

**资金**

- 支付冻结总额（沿用现有 freeze，金额 = 每人报酬 × 人数）
- 结算仅在 COMPLETED 时刻发生：unfreeze 总额 + N 条 per-taker income；散团/取消全额退（unfreeze），未完成不结算无任何部分支付

**信用**

- 组队期退出：不扣分
- 执行期退出：`ERRAND_TAKER_CANCEL` -20（每次退出各扣一次，幂等键沿用 uk_user_reason_ref + order 维度）
- 散团：不扣任何人；好评加分：按人按次（每日上限不变）

**系统群接线（chat 首个生产调用方）**

- 成团：`createGroup`（发布方 + 全部接单者）
- 执行期退出/补位：`removeMember` / `addMember`（SYSTEM 消息：成员退出、成员加入）
- 终态：`sealGroup` 封盘；组队期不建群（成团才建，与「联系」1v1 并存）

**API 契约（增改）**

| 端点 | 语义 |
| --- | --- |
| `POST /api/errand/orders` | 请求体新增 requiredTakers（缺省 1）与每人报酬字段 |
| `POST /api/errand/orders/{id}/grab` | 语义扩展为进团：多人单人数未满即加入成功；单人单行为不变 |
| `DELETE /api/errand/orders/{id}/members/me`（或等价） | 退团：组队期任意时刻、执行期取货前 |
| `GET /api/errand/orders/{id}` | 详情带出 requiredTakers、当前人数、进团后带成员列表（进团前仅人数） |
| 现有 confirm / arbitrate / timeout / evaluate | 语义按一刀切完成、按人评价扩展，签名不变 |

## Testing Decisions

- 沿用先例：trigger 层 seam（HTTP + 消费者入口直驱）、Testcontainers、数据库可观察状态断言
- 覆盖：发布校验（人数 2~10、总额计算）、并发进团仅 N 人成功（条件 UPDATE）、成团原子性（成员行+状态+deadline 重算+建群同事务）、组队退出/散团退款幂等、执行期退出扣分 + removeMember、补位成功继续 / 补位超时散团、一刀切结算（N 条 income + unfreeze，重复结算幂等）、按人评价唯一键、单人单回归（required_takers=1 全链路不变）
- 冒烟：双端 Playwright——发布多人单 → 两个账号进团 → 成团建群 → 群内收发 → 一方退出补位 → 完成 → 各自到账

## Out of Scope

- 发布方筛选/邀请成员（先到先得定死）
- 部分完成/按比例结算
- 组队期群聊（成团才建群）
- 退出补偿机制（接单者时间无偿，留档接受）
- 补位等待的独立时限（执行 deadline 即上限）
- 多人单拆分发布（一单就是一件活，不拆子任务）

## Further Notes

- 访谈决策记录（wayfinder grilling 两轮，2026-09-10）：Q1 术语定「多人单」非"拼团"；Q2 属性化 required_takers（1=单人单链路不变）；Q3 **每人报酬**制（发布方设每人钱数、支付总额），否决总额均分（余数问题自然消失）；Q4 成团自动开始不设手动确认；Q5 退出规则三选一取 C（分阶段：取货前可退补位、取货后锁定仲裁），否决自由补位（悬置无限期）与开始即锁（逼用户弃单）；Q6 组队超时自动散团、已加入者无损；Q7 信用联动（组队期退不扣、执行期退 -20、散团不扣）；Q8 先到先得不可挑人、进团前只见人数不见身份；Q9 人数 2~10；Q10 群成员进出复用 ChatGroupService 不封盘重建；Q11 完成一刀切（全员同时结算每人报酬）；Q12 未完成一律不结算、散团全额退；Q13 补位等待期 = 执行 deadline，不设第二时钟；Q14 组队/执行两段各自计时（成团时重算 deadline）；Q15 发布方取货前可取消、不扣分、无补偿（留档接受接单者时间无偿）；Q16 评价按人（to_user 维度）；Q17 组队期无群、1v1 并存；Q18 进团后成员互相可见
- "未完成一律不结算"与"发布方取消无补偿"是两个已知粗糙点，均为简单性换公平性的有意取舍，勿在实现时"顺手补齐"
