## Destination

按 [hot-row-merge-l2w256 spec](../hot-row-merge-l2w256/spec.md)（`Status: 定稿`，唯一形态来源）与
[acceptance.md](../hot-row-merge-l2w256/acceptance.md)（唯一判据来源）完成全部编码落地：五条「逐笔打同一行」
的写换成「进程内分片缓冲 + 定时窗口 + 共享固定执行池 + 合并成一条 `UPDATE`」，两侧各实现一份合并器
（bs 计数 / marketing 库存），并交出可执行的切换包与 D9 收口。

## Notes

- **需求与形态问题一律查 spec 对应章节**，本 effort 不重开设计讨论；发现 spec 缺口回
  `hot-row-merge-l2w256/issues/` 补票。判据只在 `acceptance.md`，不新增。
- **拆票口径**（用户 2026-10-23 定）：10 张票。相对 spec §10 的 7 张做了两处细化——
  spec 的 03 拆成 03 / 04 / 05（同步写、异步丢、读路径缓存是三块独立风险），
  spec 的 04 拆成 06 / 07（预扣与确认是两个失败域，spec §4.5 明说不合成一条语句，测试组也分开）。
- **两条非显然的边**：04 依赖 03（计数 Consumer 只有在点赞也不再走消息之后才无引用）；
  05 依赖 03（C5 断言是「先赞 → 立刻读详情就是新值」，200ms 聚合器还在时做不到）。
- **marketing 侧 06 / 07 / 08 必须同一次部署**：新代码不写 `state`（列默认 0），旧兜底会把新明细当未合并
  再合一次账。bs 侧无此约束，但同样是「一个 PR 换掉」，不设开关。
- **测试先改后实现**（红 → 绿）：每票的测试处置写在该票验收项里，不集中在 10。
  10 只做全表核对与两份实现的对等检查。
- **不压测**：没有 TPS / p99 判据；`timedOut == 0` 是唯一时延判据。
- 领域词汇遵循仓库根 `CONTEXT.md`；后端分层与命名遵循 `backend/CLAUDE.md`。
