# 03 · 计数合并后读到的值：滞后窗口与缓存失效落点

Type: grilling
Status: resolved
Blocked by: —

## Question

合并把「写」变成了窗口批写，读路径就必须回答「读到的数是谁的数」：

1. **窗口取多大**：现在 `PostCountAggregator` 是 200ms；参考工程的窗口是 5ms（因为库存要等结果）。计数是 fire-and-forget，窗口越大越省事务、滞后越明显。**给出一个窗口值 + 理由**（写放大 vs 点赞后自己刷新列表看到数字没变）。
2. **读要不要叠加在途增量**：进程内合并器可以维护「本实例未刷盘的增量」，读路径 `DB 值 + 在途值` 就能在单实例下呈现「实时」效果（多实例下只在本地准）。做还是不做？代价是读路径要认识合并器（现在的读路径只查窄表，干净）。
3. **缓存失效落在哪**：`PostDetailCache` 现在由聚合器在「点赞刷库后」显式 `evict`，纯浏览不失效。换成新引擎后，引擎只交出一批 `(postId, delta)`，它不该知道缓存存在。失效逻辑放哪：落库回调里（infrastructure 层）、还是读路径不再缓存计数（只缓存正文）？
4. **热榜排序**：`hot` 排序读的就是这两张窄表，合并后排序源滞后一个窗口。接受，还是排序单独走「排序快照 + 定时重算」？

答案要能让实现者不假思索地写出读路径，不用回来问。

## Answer

（2026-10-22 定，前提已被票 02 改写：点赞是「同步等结果 + 同事务批量写」，不是异步近似。）

1. **窗口统一 5ms**（用户定）。点赞等一个窗口后返回；浏览虽然不等，也用同一个窗口参数——**一套参数好维护**，代价是浏览量的写放大比 200ms 窗口高（每片最多 200 次 flush/秒），但每帖仍是合并后的单条 `UPDATE`，可接受。
2. **详情缓存不存计数**（用户定）。`PostDetailCache` 只缓存正文 / 状态 / 作者 / 配图这类「变了要重建」的字段；`like_count` / `comment_count` / `view_count` 不进缓存，详情页读取时**单独一条 SQL 一次取回三个数**。
   - 连带改动：`PostDetailCache` 加载用的那段 `PostMapper.selectDetail`（带两张窄表 LEFT JOIN 的投影）要拆成「内容查询（进缓存）」+「计数查询（每次读）」；`PostEntity` 进缓存前把三个计数字段清掉，避免缓存里躺着一份会过期的数。
   - **收益**：`PostCountAggregator` 里那句「点赞刷库后 `postDetailCache.evict`」整条删除；合并器从此不知道缓存存在，失效问题消失。
   - **代价**：详情页多一次轻查询（按主键查三张窄表/主表列），换来计数永远不许「缓存里那份是旧的」。
3. **列表页仍走 LEFT JOIN 投影**（`PostMapper.xml:11`），不进缓存的场景下就是实时值，不需要改。
4. **热榜排序**：点赞已同步提交 ⇒ 排序读到的点赞数是准的；`hot` 公式里的 `comment_count * 2` 是否滞后，取决于票 04 把评论数定成精确还是近似——**本票不下结论**，留给票 04 一并回答。

**一句话读路径**：内容查缓存、计数每次查库、两者在 DTO 里拼起来；合并器不碰缓存、不叠加在途增量。
