# 02 · 计数合并的失败语义：至多一次还是至少一次

Type: grilling
Status: resolved
Blocked by: —

## Question

去掉 outbox + MQ 之后，「至少一次投递 + msgId 去重」这套保险一起消失：增量直接在进程内交给合并器，一次调用、没有重投。于是必须当场定死三件事：

1. **崩溃丢失**：进程在窗口内崩掉，最多丢一个窗口（200ms 或新窗口值）的增量。点赞/浏览是近似值，`CONTEXT.md` 已写「允许短暂滞后与极端情况下丢失窗口内增量」——**但去掉 outbox 后丢的窗口比现在更宽还是更窄？**（现在崩溃时 outbox 里已提交的消息还在，重投后仍会计入；新方案里这部分直接没了。）
2. **刷盘失败怎么办**：现在 `PostCountAggregator` 刷盘失败会把增量**并回窗口**下轮重试——这是 at-least-once，理论上可能重复加（重试成功但事务其实已提交）。新引擎要不要保留这个「并回」？三个选项：
   - **至多一次**：失败即丢，记一条 warning 与丢弃计数，不回补。口径最简单、永远不会多算，与「计数 ≤ 真实条数」自洽。
   - **至少一次（并回窗口）**：与现状一致，但在「提交成功、回包超时」的重试下会重复计入，破坏上面那条不等式。
   - **按差值重算**：定期用 `COUNT(*)` 校准（关系表是事实源），本票不实现、只判断要不要留口子。
3. **去重还要不要**：msgId 环形去重是给 broker 重投用的，进程内直调没有重投。新引擎里是否**彻底删掉**去重（`PostCountAggregator` 的 100k LRU 一并退休），还是保留一个「同一请求重复提交」的短窗去重（HTTP 重试/前端双击）？

答案要落到一句可写进 spec 的判定：**「窗口内增量最多丢一次、绝不重复计」** 还是别的表述。

## Answer

生效结论（2026-10-22 逐轮确认，含一次前提纠正）：

**总口径：点赞与库存同一个语义——「成功 = 已提交」；浏览量是唯一的 fire-and-forget。**（初稿曾把浏览也算作「成功=已提交」，已在同日第二次修正中推翻，见 `## Comments`。）

- **点赞（帖子 / 评论）**：请求进缓冲区（按 `postId` 分片）→ 窗口到点后**一个事务**完成「批量 `INSERT IGNORE` 点赞记录 + 一条 `UPDATE … like_count = like_count + N`」→ 每个请求各自拿 `SUCCESS` / `DUPLICATE`（重复点赞）。取消赞同理：批量 `DELETE` + 一条 `-N`。形状与参考工程 `StockRepository.deductMerged` 的「`INSERT IGNORE` 明细 + `UPDATE` 台账」完全一致。
- **浏览量（帖子 / 商品）**：**fire-and-forget，不等结果**（用户 2026-10-22 修正：前端不渲染浏览是否成功，失败也不告诉用户）。请求把 `+1` 放进缓冲区就返回，窗口到点批量 `UPDATE view_count = view_count + N`，失败只记丢弃计数。没有关系行 ⇒ 没有真相表可对账，也**不需要**任何校准口径——这正好是「丢了就丢了」唯一成立的场景。
- **对点赞与库存**，「偏小 / 偏大」整条讨论作废：事务失败即整体回滚，调用方拿不到成功、凭唯一键重试；计数不可能与关系行脱节，也不需要「校准口子」。**浏览量没有这一层保证**：它就是允许丢，且没有真相表可校准。

**三条实现约束**（移交票 06 的引擎规格）：

1. **批内部分撞唯一键要能定位到具体请求**：`INSERT IGNORE` 的 affected 只给行数、不说是哪几行。撞键时回查该批的 `(post_id, user_id)`（同参考工程 `listDetailsByBizNos` 的手法），只把 `DUPLICATE` 回给命中的那几个，其余照常成功。
2. **缓冲区满时的两种退化**：点赞（等结果）**不能拒绝用户**，降级为该请求单独同步写（一条 `INSERT` + 一条 `UPDATE`）；浏览量（不等结果）直接降级为一次独立 `UPDATE`，再满就丢弃并计数。两条都不允许像库存那样把 `REJECTED` 返回给用户。
3. **删掉 msgId 环形去重**（`PostCountAggregator` 的 100k LRU 与 `synchronized` 一并退休）：点赞的幂等由唯一键承担，浏览本来就没有幂等语义，重投的源头（MQ）也消失了。

**连带改写（词条要拆成两条，见票 04）**：`CONTEXT.md` 的「互动计数」把点赞数与浏览量捆在一条「近似值」里，本次两者**分家**：

| | 点赞数（帖子 / 评论） | 浏览量（帖子 / 商品） |
|---|---|---|
| 一致性 | 与关系行**同事务**提交，精确 | 异步 +1，允许丢 |
| 失败 | 整体回滚，调用方重试 | 丢弃，不告警、不回补 |
| 延迟 | 请求等一个窗口（≈5ms） | 请求立即返回 |
| 真相源 | `post_like` / `post_comment_like` 条数 | 无（自己就是唯一记录） |

## Comments

- **2026-10-22 第一次修正**：初稿按现状假设「点赞计数是 fire-and-forget」，因此整票在讨论「丢窗口 / 偏小 / 偏大」。用户指出参考模型是**一个事务里批量 `INSERT` 明细 + 一次 `UPDATE`**，点赞完全可以照抄。改为「同步等结果」后，偏小/偏大两条误差整条消失，本票从「选误差方向」变成「选要不要等 5ms」。
- **2026-10-22 第二次修正**：初稿把浏览量也定成「同步等」。用户指出前端根本不渲染浏览是否成功、失败也不告诉用户——「同步等」在这里没有收益，只有成本。改为 fire-and-forget，浏览成为三类计数里唯一允许丢的一类。
