# 04 · 计数口径的词条改写：评论总数要不要降级

Type: grilling
Status: resolved
Blocked by: —

## Question

用户已定：**评论总数（`post_comment_count`）也改成近似**。这直接推翻 `CONTEXT.md`「评论总数」词条里的「随审核通过与软删在**同一事务内同步**增减，是精确值」，而这条口径被下面几处依赖，必须一起收口：

1. **词条怎么改**：新表述是「与点赞同口径的近似值」还是「以关系表为准、读取时容差」？`_Avoid_` 要不要加「精确评论数」。
2. **同事务 ±1 退休后，计数动作放哪**：审核通过（`approveComment`）、软删（`deleteComment`）、驳回——现在是 `post_comment_count` 与评论状态同事务。改成「状态事务提交后进合并器」，就出现「评论已可见但计数还没加」的窗口（一个窗口 = 秒级以内）。可接受？
3. **「是不是热点」这件事本身**：用户说「评论数可能不是热点」。如果它不是热点，这次改动只有语义成本没有收益。**要不要保留「先量后改」的顺序**——先用一天的真实流量打点（同一帖子每秒通过审核的评论数）再决定动不动它？
4. **读口径**：列表页 `comment_count` 与评论区实际条数会短暂不一致；「展开更多」是否用计数分页（若是，计数偏大/偏小会让分页错位）。先查清 `countVisibleRootsByPostId` 这条读是不是独立计数（不是的话这条风险不存在）。

答案要包含：改 / 不改这个二选一的明确结论，以及若改，词条新文本。

## Comments

- 票 01 补充事实：**发布评论不计数**；`post_comment_count` 只在「审核通过 +1」「软删按可见子回复数扣减」时移动（`CommunityRepository.approveComment` / `deleteComment`，SQL 在 `PostCommentMapper.xml:173`）。所以它的热点强度取决于**审核吞吐**，不取决于评论量——这直接支撑「先量后改」的选项。

## Answer

（2026-10-22 定，推翻了本轮开始时「一起改成近似」的初判。）

**结论：评论总数与楼中楼子回复数本期不动**，保持「审核通过 / 软删与计数同一事务」的精确语义。

理由（用户在原问题「改不改」上明确选「不动」，与下面的事实一致）：

- 它的写入频率上限是**人工审核 / 批审动作**，不是评论量；爆款帖一天几百条评论，摊到审核动作上是几十次，与点赞的每秒上千次不在一个量级。
- 改成近似反而要付三笔成本：改词条、改 4 个锁计数的集成测试、以及处理「评论已可见但数字还是旧的」这个用户可见的不一致。
- 真到了要批的程度，正确的做法是**批审接口把同一帖的多条审核收成一个事务**（天然的批），而不是把计数拆成异步。

**词条改写（`CONTEXT.md` 已改）**：「互动计数」这一条原本把点赞数与浏览量捆在「近似值」里，本次**分家**：

- 新增「**点赞计数**」：与点赞关系行同事务提交的精确值，写入形态是「一批点赞记录 + 一条计数 UPDATE」合并落库。
- 原「互动计数」收窄为「**浏览量**」：异步合并写入、允许丢失与滞后、无真相源、不回补。
- 「评论总数」词条一字不改（精确、同事务）。

**连带**：`hot` 排序里的 `comment_count * 2` 因此仍是实时的；`like_count` 也已精确 ⇒ 热榜排序源不再滞后（票 03 第 4 问以此收口）。
