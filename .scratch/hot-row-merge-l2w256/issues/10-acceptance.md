# 10 · 验收：拿什么证明这次改对了

Type: grilling
Status: resolved
Blocked by: 02, 05, 06

## Question

现有锚点：单热点行逐笔写的天花板 ≈4,079 TPS（`loadtesting/REPORT.md`，200 线程）；现行 `merge` 策略 15,356 TPS；参考工程 L2W256 单热点 25,563 TPS。要定的是**这次验收的判据与工具**：

1. **复用还是重写压测**：`loadtesting/` 已经是三策略对照工程（`db` / `redis_mq` / `merge`，JMeter 脚本齐备）。加一个 `l2w256` 策略塞进去，还是另起一套？前者能直接和三条旧曲线同图对比，代价是要改那套 app。
2. **计数侧怎么压**：点赞没有「库存」判据，验收看什么——吞吐、p99、`flush` 次数、DB `UPDATE` 次数/请求数比值？给出目标值（例如「单帖 5k 点赞/s 下，`post_like_count` 的 UPDATE 次数 ≤ 20/s」）。
3. **正确性怎么断言**：库存侧是「零超卖 + 账目平 + `surplus + waiting + issued == 初值`」；计数侧是「计数 ≤ 关系表真实条数」还是「差值在容差内」。要不要写一条「停 5 秒后排空，计数收敛」的收敛断言。
4. **时延预算**：库存请求现在等 future，窗口 5ms + 落库 0.5ms，p99 会从多少变到多少；抽奖接口的整体 p99 允许多少（现在是 Redis 预扣 ≈1ms）。
5. **回归清单**：现有哪些测试会因为这次改动变红（`PostCountAggregationIntegrationTest`、`InventoryMergeEngineIntegrationTest`、`InventoryMergeDeliveryLatencyTest`、`RaffleShippingConsumerIntegrationTest`…），哪些应当删掉、哪些要改写成新语义。

结论要落成一张「验收表」：指标 / 基线 / 目标 / 用什么测。

## Answer

**划出范围，不是被解决**（用户 2026-10-22：压测暂时不用）。

- 本次不做吞吐/时延压测，不往 `loadtesting/` 加 `l2w256` 策略。`4,079 / 12,267 / 15,356 TPS` 与参考工程 `25,563 TPS` 只作为**讨论收益的锚点**，不作为验收判据。
- 验收改由**测试断言**承担，落在两张票里：
  - 引擎不变量（不丢件、单飞、背压、停机排空）→ 票 06 的单测清单；
  - 业务守恒（库存 `surplus + waiting + issued == 初值`、计数 `≤ 关系表真实条数`）→ 票 05 / 07 的集成测试断言。
- 参数（窗口、批大小、分片数、池大小）**没有扫参依据**，按参考工程的模型推导给默认值，并在票 06 里注明「未扫参，线上按观测调整」——这正是压测原本要回答的问题，现在诚实标为未知。
- 票 09 的「上线 8 步」里保留一步人工验证：切换后抽样对账，不压测也要看一眼真实流量下的 `flush 次数 / 请求数` 比值。
