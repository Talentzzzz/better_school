# 前端 UUID 业务 ID 适配

## Problem Statement

后端自 uuid-biz-id 起，所有业务 ID 一律是 36 位 UUID 字符串（DB `VARCHAR(36)`，API 全链路 `String`），契约文档明确要求「客户端把 id 当不透明字符串透传、不做数字化处理、路由正则不得限 `\d+`」。前端仍停留在数字口径：线契约类型模块把业务 ID 建模成 `number`、六条详情路由用 `(\d+)` 限死数字、视图里做 `Number(route.params…)`、api 层用 `number` 收参、store 用数值键建索引。

使用者能感知的后果：

- 点开任意帖子 / 商品 / 用户 / 会话详情，UUID 不匹配数字正则，路由落到 catch-all 被弹回首页 —— 表现为「点了没反应」。
- 即便强行进页，ID 变成 `NaN`，后续请求打到 `/post/NaN` 这类路径，接口报不存在或参数错误。
- 会话列表点进聊天后，按会话 ID 查房间用严格相等比对字符串与数字，恒不相等：判重、未读累加、已读水位线全部失效。
- 带业务卡片的入口（`?card=<类型>:<id>`）用「正整数」当合法性判据，UUID 直接被判非法，卡片消息发不出去。
- 营销「我的奖品」确认收货把 UUID 交给后端，请求被拒。
- 分享 / 刷新的 UUID 深链接永远落不到目标页，未登录访客同样打不开。

## Solution

一次把前端对业务 ID 的处理方式翻成「不透明字符串」：线契约类型定型、路由参数不限数字、视图原样透传、api 与 store 同步。序号、投递序号、已读水位线、计数、分页、金额这些数值语义保持 `number` 不变；后端契约、UI 版式与交互零变化。

对使用者：所有详情页与聊天恢复可用，分享链接与刷新不再丢失目标，所有携带 UUID 的请求正常成功。

## User Stories

1. As a 访客, I want 从主页信息流点开任意一篇帖子进入详情, so that 我能读到正文与评论而不被弹回首页。
2. As a 访客, I want 从市集推荐页点开任意一件闲置进入详情, so that 我能看价格、成色与卖家。
3. As a 访客, I want 点作者头像进入其主页, so that 我能看到 TA 的帖子、评论与闲置。
4. As a 访客, I want 站内搜索的帖子 / 商品 / 用户结果都能点开, so that 搜索结果真的可用。
5. As a 访客, I want 直接打开别人分享的 UUID 详情链接, so that 未登录也能先看内容。
6. As a 访客, I want 刷新详情页后仍停在同一个帖子 / 商品, so that 刷新不等于丢失上下文。
7. As a 登录用户, I want 在帖子详情点赞、发根评论、回复子回复都成功, so that 评论用的 UUID 不会被拦。
8. As a 登录用户, I want 楼中楼「展开更多回复」按根评论 ID 正确加载, so that 每个楼的展开互不串台。
9. As a 登录用户, I want 删掉自己的评论后该条在本楼立即消失, so that 列表按评论 ID 比对正确。
10. As a 登录用户, I want 从个人主页点开我赞过 / 我发过的帖子, so that UUID 帖子都能进。
11. As a 作者, I want 从「我的」点开草稿继续编辑（`?draft=<id>`）, so that 草稿 id 是 UUID 也能回填。
12. As a 作者, I want 草稿箱里每条草稿的编辑 / 提交 / 删除只作用于我点的那条, so that UUID 作为操作键不会张冠李戴。
13. As a 买家, I want 从订单列表点开订单详情, so that 订单 ID 是 UUID 也能进。
14. As a 买家, I want 在订单详情取消订单 / 确认收货, so that 资金动作作用在正确的订单上。
15. As a 买家, I want 支付成功后从收银台回到对应订单详情, so that 支付单号与商户订单号都是 UUID 也能回跳。
16. As a 买家, I want 订单详情里点卖家头像进卖家主页, so that 交易链路各跳转都不塌。
17. As a 卖家, I want 从订单详情「联系买家」直接进到与该买家的会话, so that 对方用户 ID 是 UUID 也能建会话。
18. As a 卖家, I want 市集「联系卖家」把商品 ID 带进会话待发卡片, so that 商品 UUID 不被误判为非法。
19. As a 卖家, I want 发出的商品卡片在会话里渲染出标题, so that 卡片按 `类型:UUID` 能查到对象。
20. As a 私信用户, I want 从会话列表点进任一聊天, so that 会话 ID 是 UUID 也能打开。
21. As a 私信用户, I want 聊天里发出的消息在推送回来后按（会话, 消息序号）正确判重, so that 同一条消息不会重复上屏。
22. As a 私信用户, I want 对方阅读后我的消息显示已读, so that 已读回执按对方 UUID 查到水位线。
23. As a 私信用户, I want 长按删除会话只删我选中的那个会话, so that 会话 ID 作为选中键不失配。
24. As a 私信用户, I want 点消息里的业务卡片跳到被引用的商品 / 帖子, so that 卡片跳转带 UUID 也能命中。
25. As a 私信用户, I want 从互动通知 / 顶部横幅点进关联内容, so that `refId` 是 UUID 也能定位到帖子或评论。
26. As a 私信用户, I want 断网重连后补齐漏掉的消息, so that 补拉游标与判重键在字符串口径下仍然自洽。
27. As a 营销活动参与者, I want 奖池目录与我的奖品正常渲染, so that 奖品 ID 是 UUID 也不影响展示。
28. As a 中奖用户, I want 点「确认收货」把这条奖品推进到已完成, so that 奖品 UUID 被正确提交。
29. As a 中奖用户, I want 用积分购买抽奖次数后看到兑换凭据, so that 兑换单号只当标识展示、不被当成数字计算。
30. As a 用户, I want 信用分流水里关联的业务对象能点开, so that `refId` 是 UUID 也能跳转。
31. As a 用户, I want 旧格式（纯数字）链接不会白屏, so that 打不开时看到「内容不存在」而不是空白页。
32. As a 开发者, I want 业务 ID 只有一处定型, so that 新增字段不会又冒出 `number`。
33. As a 开发者, I want 「哪些字段是数值」有明确边界, so that 消息序号、水位线、计数不会被顺手改成字符串。
34. As a 开发者, I want 路由参数一律原样字符串, so that 以后新增详情页不必重新想一遍。
35. As a 维护者, I want 后端零改动、UI 版式与交互零变化, so that 这是一次纯口径对齐、可独立验收。

## Implementation Decisions

**缝①（唯一 ID 定型处）：线契约类型模块**

- 业务 ID 一律 `string`：`userId`、`peerUserId`、`postId`、`commentId`、`parentId`、`replyToUserId`、`productId`、`orderId`、`buyerId`、`sellerId`、`roomId`、`messageId`、`fromUserId`、通知 id 与 `senderId`、`refId`、营销侧 `prizeId` / `recordId` / 我的奖品 `id` / `redeemOrderId`。
- 保持 `number`（数值语义，不参与 ID 口径）：消息序号 `seq`、投递序号 `deliverySeq`、时间线游标 `nextCursor`、已读水位线 `readSeq`、未读数 `unread`、各类计数（点赞 / 评论 / 浏览 / 收藏 / 子回复数 / 获赞数）、分页（`page` / `pageSize` / `total`）、抽奖档位 `tier`、抽奖次数与积分余额、金额、以及**物理自增流水 id**（信用分流水 id、营销积分流水 id —— 后端 DTO 里本就是 `Long`，不是业务 ID）。
- 判定规则收敛成一句：**后端 DTO 是 `String` 的前端就 `string`，是 `Long`/`int` 的就 `number`**，以后新增字段照此判断，不再逐字段讨论。

**缝②：路由参数契约**

- 六条业务详情路由（帖子、商品、用户主页、会话、订单、`/trade/order` 兼容重定向）去掉数字限制，参数作为不透明字符串取用。
- 视图层禁止对路由参数做数值解析（`Number` / `parseInt`），取到即字符串、直接交给 api 层。
- 旧数字形链接不做迁移映射：后端按 UUID 解析失败即「不存在」，前端落到统一的空态兜底；不为已下线的形态写兼容分支。

**复合参数（ID 编进字符串的入口）**

- `?card=<refType>:<id>` 按第一个冒号切分、ID 段原样收下；合法性判据从「正整数」换成「非空且形如 UUID」，避免把任意垃圾串带进发送链路。
- `?draft=<id>` 原样作为字符串承载。

**状态与索引**

- 两个按 ID 建索引的映射改为字符串键（会话 ID、用户 ID）；按 ID 查房间的比对关系不变，只是两侧同为字符串。
- READ 推送的载荷类型与线契约一致（会话 ID、用户 ID 为字符串，水位线为数字）。
- 视图内承载 ID 的局部状态一并改字符串：会话菜单选中项、草稿操作中的 id、奖品确认收货中的 id、回复目标 id 与楼根 id、楼中楼状态表的键。

**api 层**

- 41 处业务 ID 形参（含随请求体复用的 id 字段）改字符串；返回类型中承载业务 ID 的（新建资源返回 id、确认收货返回的奖品 id 等）同步改。

**不做的事**

- 不改后端任何契约；不改 UI 版式、文案与交互；不做 ID 截断展示；不引入运行时校验库。
- 交付口径：按用户明确要求，**不运行任何测试、不运行构建与类型检查命令**，由维护者本地自验（与 platform-escrow 票 06 同口径）。

## Testing Decisions

- 前端目前没有自动化测试基建（无单测、无 e2e 用例），本批**不新建**，也不为它开新的测试缝。
- 好测试的定义（若将来补）：只断言使用者可见行为 —— URL 能被路由命中、详情页渲染出实体、请求路径携带正确 UUID、卡片消息能发出；不断言内部调用了几次 `Number()`、也不断言类型声明本身。
- 本批采用的两道验证缝就是缝①与缝②，它们的可验证形式是**全量类型检查**与**静态检索口径**（ID 语境下的数值解析、数字路由正则、数值键映射三处归零），而不是新增用例。
- 先例：platform-escrow 票 06「只做静态自查，未跑 mvn / 测试 / 构建」；本批沿用同一交付口径。
- 建议维护者自验清单（人工，不跑测试）：主页 → 帖子详情 → 点赞/评论/展开楼中楼；市集 → 商品详情 → 联系卖家 → 发商品卡片；会话列表 → 聊天 → 对方已读；我的 → 草稿箱 → 编辑草稿；我的 → 订单 → 详情 → 取消/确认收货；营销 → 我的奖品 → 确认收货。

## Out of Scope

- 后端任何改动（含新增 UUID 校验、错误码细分）。
- 历史数字 ID 的数据迁移或兼容映射。
- 前端测试基建（单测 / e2e 框架）搭建。
- UI 版式调整、ID 展示截断或美化。
- `/trade/*` 兼容路由的下线（保留，参数原样转发）。
- 物理自增 id 的语义调整（信用分流水、积分流水保持数值）。
- 本轮之外的新功能。

## Further Notes

- **权威来源**：后端 API 文档的「ID 口径（uuid-biz-id 起）」一节 ——「客户端把 id 当不透明字符串透传即可，不要做数字化处理（JS `Number()` 会精度丢失，路由正则不得限 `\d+`）」。本 spec 就是把这句话在前端完整落实。
- **为什么必须一次改完**：类型一处转字符串后，全仓不匹配点会同时暴露；分批改会长期停在「编译不过但没人跑构建」的状态 —— 本次收口前 master 正是因为同类问题（合并产物重复定义）编译不过约 7.5 小时没被发现。
- **为什么路由不做数字兼容**：两套口径并存会再次引入分支判断，而数字形链接只可能来自改造前的本地书签；统一到「UUID 或不存在」更干净。
- **已知风险**：若某处仍把 ID 拼进模板字符串（不经过类型），类型检查不会报错，需靠上面的人工自验清单覆盖。
- **与领域词条的关系**：涉及「会话」「消息序号」「已读水位线」「业务卡片」「草稿箱」「收银台」「支付单号」等词条，语义均不变，只换 ID 的承载类型；领域词汇与 `CONTEXT.md` 保持一致。
