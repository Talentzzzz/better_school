# 跑腿状态机扩展：草稿 / 锁单 / 已确认（"抢 ≠ 开工"）

跑腿订单状态机在支付流转的链条两端各插一态、并细分接单侧：发布侧前插**草稿**（`DRAFT`，可编辑可软删、不付款、不对外，提交才进待支付并起付流程）；接单侧把原 `TAKEN` 拆成两态——**锁单**（`LOCKED`，抢单成功后的 5 分钟持有态，超时或放弃均回落 `PUBLISHED`）与**已确认**（`CONFIRMED`，即原 `TAKEN` 改名，接单方核对信息后自己确认）。本 ADR 记录的核心语义决策是：**抢 ≠ 开工**。抢单只是锁定名额，不构成承诺；确认接单才是承诺，其后的取消才扣信用分。这条语义是**不可逆**的：一旦把"抢单"当作承诺时点（扣分、限制、通知都锚在它上面），用户就会先确认再弃单，问题后移且更难收回——所以放弃路径（`LOCKED→PUBLISHED`，不扣分）与取消路径（`CONFIRMED→PUBLISHED`，扣分）必须从第一天就分开。

## Considered Options

- **保留 `TAKEN` 字面量、只加锁单超时**：改造面最小，但"已接单"的文案在锁单可放弃的世界里成了一句谎——用户看到"已接单"却可能被秒放弃，且代码里 `TAKEN` 语义与实际行为永久分叉。改名触点（枚举 / 条件 UPDATE / 前端文案）本来就要动，且本仓 DB 重建制、无存量数据，改名零迁移负担。否决。
- **多人单全局反转"先抢后确认"**：`.scratch/errand-multi-taker` 曾定"成团自动开始、不设手动确认"，与本决策冲突。该 effort 的在线实现已随 `project-rework` 整体下线（`required_takers` / 成员表已删，当前恒单人单），"先抢后确认"只对单人单生效、不按 `required_takers` 分叉；多人单若恢复属另一 effort，届时再裁。否决（全局反转无宿主）。
- **锁单期放弃扣信用分**：锁单放弃是设计内的正常动作（不合适就放回），未产生承诺、未造成对方损失；而信用分只减不增且单档 -20，扣三次即触禁接单线，量刑与过错严重不成比例。惩罚载体改用限权（接单冷却，与信用分正交）。否决。

## Consequences

- 与支付时序的关系：本 ADR 在支付链条两端各插一态——前插草稿（草稿态不起支付钟）、后插锁单（`PUBLISHED→LOCKED→CONFIRMED`），支付环节的语义原样保留。
- 枚举最终 13 值（新增 `DRAFT` / `LOCKED` / `DELETED`，`TAKEN` 改名 `CONFIRMED`）；事件撞名随之修正：抢单事件 `TAKEN` → `LOCKED`，"发布方确认完成"事件 `CONFIRMED` → `COMPLETED`。
- 锁单 5 分钟超时接入既有超时中心（taskType `ERRAND_LOCK_TIMEOUT`，复合 `bizId={orderId}:{lockSeq}` 轮次区分，回调轮次守卫）；防占单按 `LOCK_ABANDONED` 事件计数触发接单冷却——二者依赖"放弃与取消分事件、分惩罚"这一前提，读 ADR-0008 才能理解其上下文。
- `lock_seq` 列随每次抢单 +1，既是超时轮次也是回调守卫比对值；锁单期不进仲裁（`DISPUTED` 语义是履约纠纷，锁单未开工无可争议事实）。
