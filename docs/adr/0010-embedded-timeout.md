# 超时中心内嵌进业务工程：16 分表 + 分片广播换同事务注册

超时能力原先是一个独立部署单元：独立工程、独立库、独立的 xxl 执行器，业务方经注册 outbox 异步投递注册意图，中心扫到期行再经 Dubbo 回调到业务方配置的回调分组；管理面另占 8083。本次把它整体内嵌进单体，独立工程与其独立库一并下线；营销侧本期只落规格、不落代码。核心是一次**形态互换**：用「16 张同库分表 + xxl 分片广播 + 有界并行」换掉「注册 outbox + Dubbo 注册/回调 + 独立扫描池」，让超时任务行与业务写入落进**同一个本地事务**。

**为什么难逆**：删掉的是整个工程、两条 Dubbo 边（注册与回调）、一张 outbox 表、一整套动态引用与兜底扫描链路，以及一个契约 jar；回滚要把这些全部重建，把 trade / errand 等已改成同事务直插的注册点改回 RPC 形态，还要反向搬迁两库数据。不是配置开关能切换的。

**为什么反直觉**：按「关注点分离」，超时中心作为独立服务更"架构正确"——独立扩容、独立发布、业务库不受它的表结构影响。但在这个项目里，独立服务带来的不是解耦而是**注册路径上的跨进程一致性缺口**：业务事务提交与注册成功之间有一个窗口，只能靠 outbox + 兜底扫描把"最终注册"补齐；而那套 outbox 最终也不得不放进业务库、写在业务事务里才可靠——解耦只发生在"中心"这一侧，代价是多一张表、一条异步链路和两条 RPC 边。内嵌把这个窗口从根上去掉。

**为什么是真权衡**：16 张分表 + 分片广播 + 有界并行确实比"一张表 + 单机扫描"复杂；换来的是同事务、删掉 outbox/RPC/契约 jar，以及「注册在途 vs 取消」这类残留竞态窗口结构性消失。代价也真实：扫描与用户请求共享 10 条连接（所以并行度定 4，而不是按表数开线程）、业务库多 16 张表、营销将来要复制一份。

## Decision

- **存储**：超时任务行落业务自己的 schema——`better_school` 里的 16 张同构分表 `timeout_task_00..15`；营销本期不落表，只把同构落法写进 `backend/marketing/docs/architecture/timeout.md`。分片键只在超时表内部自洽，业务表完全不进路由。
- **注册**：业务仓储在**自己已开启的事务**里直接插入分表（trade / errand 等显式例外，见 `backend/CLAUDE.md` §1）。不再有注册 outbox、afterCommit 发送器、兜底扫描 job、注册契约与双清单 DTO；幂等分支收敛为「新插入 / 在途同键不改期 / 终态复活」三分支。
- **路由**：ShardingSphere-JDBC 5.5.3 挂在业务主 datasource 上。YAML 先 `!SINGLE`（`tables: ["*.*.*"]`）让 29 张业务表透明，再 `!SHARDING` 用两个 CLASS_BASED hint 算法把全局槽位 `g` 拆成「库 × 表」两维；槽位 `g = floorMod(hash(biz_id), 16)`，写入与扫描共用单点函数。`HintManager` 是 `TransmittableThreadLocal`，纪律是「hint 作用域先于子线程创建/提交」。
- **调度**：xxl-job `SHARDING_BROADCAST`，实例按 `g % shardTotal == shardIndex && g < 16` 认领；`timeout.scan.parallelism = 4`，宽度取 `min(并行度, 认领表数)` 的每 tick 固定池，绝不为一张表开一条线程。
- **回调**：进程内方法调用，按 taskType 分发到各域 case；幂等由业务状态机吸收（未命中 = 幂等成功）。失败退避从 30s 起指数翻倍、单次封顶 1h，第 16 次进 FAILED。
- **管理面**：死信列表 / 重发 / 取消落 8080 的 `/api/admin/timeout-tasks/**`，走 JWT + ADMIN；「谁有超时表谁才有管理面」。
- **硬约束**：`dbCount > 1` 与「同事务注册」互斥——超时行按 hash 落到另一个库时同事务立刻失效。本期 `dbCount` 恒为 1；保留的是「库 × 表」两维**表达**，不是开关。

## Considered Options

- **保留独立服务，只把注册换成同事务直插对端库**：跨库本地事务不成立（同一 MySQL 实例的不同 schema 也仍要一条连接才能共享事务，而两个工程各有自己的 datasource）；退回 XA 或两阶段，等于把 outbox 换个名字。否决。
- **内嵌但用 MyBatis 表名后缀路由（不用 ShardingSphere）**：能避开 SS 挂业务 datasource 的爆炸半径，但「同 key 永远同表」退化成手写后缀 + 每处 SQL 自己算，扫描认领与写入共用公式的约束无法单点保证，运维按逻辑表名排查也会失效。票 01 实测确认 `!SINGLE` 后业务表透明且仍是同一本地事务，SS 方案成立，故不退化。否决。
- **内嵌 + 拆独立 datasource / 启用 `dbCount > 1`**：与核心前提互斥（见上）；真要做是另一次全库改造（29 张业务表 + 全部事务点一起分），不在本决策内。否决。
- **抽共享 jar 给两个工程复用一份超时域**：判据是「等第三处出现再抽库」；两工程依赖方向、包名与装配不同，先各持一份、共享 DDL 模板与语义文档。否决（暂缓）。

## Consequences

- **好**：注册与业务写入同事务，注册窗口消失；删掉 1 张 outbox 表、1 个独立工程、2 条 Dubbo 边、1 个契约 jar、1 个兜底扫描 job；业务 SQL 里不再出现跨进程回调的 group 概念；管理面并回单体，复用既有 JWT/ADMIN。
- **坏**：扫描与用户请求共享 10 条连接，并行度被硬压在 4；业务库多 16 张表，DDL 与迁移面变大；业务工程与 ShardingSphere 的启动配置耦合（`!SINGLE` + hint 纪律是硬要求，配错即业务表不可见）；营销将来接入要复制一份域与表。
- **测试与运维**：多实例不重不漏由 `shardIndex/shardTotal`（如 0/2、1/2）集成测试验收；死信只能经管理面重发/取消，扫描不再触碰；终态行的归档口径仍未定（开放项）。
- **规范例外登记**：回调端口 `ITimeoutTaskCallbackPort` 定义在 domain、实现落 case 层（分发要调各域 case，infrastructure 看不到 case 层），已写进 `backend/CLAUDE.md` §4；「业务仓储在自己的事务里调用超时仓储注册」写进 §1。两处都是显式例外，不反向改依赖。
