# 库存合并换轨（二）：消息带责任起点秒 + 定时投递 + 固定合两格

[ADR-0011](0011-inventory-merge-delay-message.md) 把库存合并的唤醒源从「每秒全表扫」换成了「每笔预扣一条 1 秒延迟消息
+ 60 秒兜底」，但保留了两条从全表扫时代继承下来的假设：**消息只带定位三字段**（合哪一格由消费侧自己查
`MIN(create_time)` 推断），以及「**合完还有余量就自我续命**」。本次把这两条一起换掉——消息带上**责任起点秒**
`cellTime`，用**定时消息**在「`s + 1` 封口之后」投递，消费侧**固定合 `s` 与 `s + 1` 两格**后结束，**续命整段删除**。

**为什么必须换**：ADR-0011 的续命链在「起点很少落在整秒」这个日常事实下**几乎必然触发**。消息到达时（发送后
≈1.1s）当前这一秒还没封口（合的条件是 `create_time < NOW()`），而 `existsUnmergedDetail` 不看封口只看
`state = 0`，于是「还有余量」恒为真——只要这个 key 有持续流量，它就每秒续一条，**永远不会收敛到零**。
叠上「一次唤醒循环合 ≤10 格」，同一格会被**自己那条 + 前 10 条消息的顺带 + 续命**重复指到：
**每格的消费者数在 1~12 之间浮动，且不可从配置或流量推出**，其中最多 1 个真干活。消息量也从「1 条/秒/桶」
变成「2 条/秒/桶」。这些都不是正确性问题（续命本身是收敛的、也不漏格），是**并发度不可控**——空转量、DB 命中、
日志噪声都没法预估，也没法给「合并延迟」一个常量。

**为什么难逆**：载荷语义从「定位三字段」变成「定位三字段 + 责任起点秒」，消费侧认不出旧载荷就丢弃；
消费入口从 `mergeKey`（查 MIN 循环）换成 `mergePair`（按消息的位置合两格），`mergeKey` 降级为兜底专用；
续命的代码、常量、DAO 方法整体消失，outbox 从 `delay_level` 换到 `delay_ms`（新列 + 发送三分支 + 扫描重发让定时行直发）。
回滚要把续命重建、把消费侧改回「自己查 MIN」、把 outbox 的定时能力退回延迟级别——不是改一个常量。

**为什么反直觉**：ADR-0011 明确写过「1 秒粒度已经够」「续命让低流量 key 多等一分钟的极端情形消失」，那两句
当时都不错，现在也仍然成立。反转的理由不在「续命会不会漏格」，而在**它把「谁合哪一格」留在消费侧的推断里**：
一条消息能合几格取决于到达时刻的 `NOW()`，于是同一格被几个消费者碰过、空转多少次，都随流量形态漂移。
固定两格把这个答案搬进消息本身——代价是确定性的 50% 空转，换来每格恒 2 个消费者（1 干活 1 空转）、
消息恒 1 条/秒/桶。

**为什么是真权衡**：延迟从 1.1s 抬到 2~3s；消息整条丢了不再有「下一跳顺手救」，**只能等 60s 兜底**；
一半的 `mergeCell` 调用注定空转；滚动发布窗口里的旧载荷全部落兜底。这些都是真实的、可见的代价，
而不是「顺手优化掉」的副作用。

## Decision

- **载荷 = 定位三字段 + `cellTime`**（`{"segment","invId","bucketId","cellTime":"2026-10-20T10:00:10"}`）。
  `cellTime` 是这一笔明细的**责任起点秒**——即该行 `create_time` 的秒值，由 INSERT 之后**同事务回读**得到
  （`create_time` 由 DB 的 `NOW()` 写，应用事先不知道）。它只用于**定位格**，不参与延迟计算。
- **投递 = 定时消息，相对延迟 2000ms**（`outbox_message.delay_ms = 2000`，`delay_level` 落 0）。
  延迟从**发送时刻**起算，而发送必然发生在明细 INSERT 之后，于是 `now + 2000 ≥ insert + 2000 ≥ s + 2.0`，
  「`s + 1` 已封口」自带 0~1s 余量；broker 的时间轮按秒槽对齐且槽过完才排空，方向只会更晚。
  正因为是相对延迟，**不需要**把无时区的 `create_time` 按 `Asia/Shanghai` 转 epoch，时区坑整条不存在。
- **消费 = `mergePair(segment, invId, bucketId, cellTime)` 固定合两格**：先 `cellTime`、再 `cellTime + 1s`，
  同线程串行，各自一格一事务；某一格返回 0 **不中断**另一格。合两格而不是一格，是因为**被 throttle 吞掉的
  那些扣减没有再发消息**——一笔窗口的尾巴可以落到下一秒，而它自己不会叫醒任何人。
- **删掉续命**：`existsUnmergedDetail` + `enqueueMergeMessage` + `INVENTORY_MERGE_DELAY_LEVEL` 一并清掉。
  `mergeKey` 保留但只服务 60 秒兜底（仍查 MIN 循环 ≤10 格、失败即停、**不发消息**）。
  两条入口**不合并成一个方法**：消息路径知道该合哪两格，兜底不知道；用 `cellTime == null` 退化查 MIN
  会让「载荷坏了」与「兜底调用」不可区分。
- **判重口径不变**：仍是「按格条件翻转 + `affected == c1 + c2`」，不是 id 清单。顺序必须是 `s → s+1`——
  同一 key 上 `type = 1` 的 `create_time` 必然早于 `type = 2`，先合 `s` 才能让 `waiting_qty >= s2` 是结构保证。
- **旧载荷（无 `cellTime`）直接丢弃**，不退化查 MIN：退化会让坏载荷变成一条合法的 `mergeKey`，
  把「消息丢了」与「消息坏了」混成一种观测。代价是切换窗口内的旧消息落到 60s 兜底——兜底本来就是
  「消息整条丢了」的收口，这条路径本来就必须能用。

## Considered Options

- **保持 ADR-0011 现状（延迟级别 1 + 查 MIN 循环 + 续命）**：延迟最好（实测 1.07~1.12s），且续命保证收敛。
  否决的理由是并发度：每格 1~12 个消费者、消息 2 条/秒/桶（见上「为什么必须换」），空转与 DB 命中随流量形态
  漂移，观测（`merged=[x, y]` 之类）也没法定义基线。**不否定它的延迟**——那是本次明确付出的代价。
- **只把延迟抬到 2s，不改载荷（续命照旧）**：`s + 1` 确实封口了，`mergeKey` 一次能把两格都合掉，看起来
  也能少发消息。但续命**仍在**：「当前这一秒没封口所以还有余量」依然恒真，于是依然每秒续一条，
  消费者数依然不可控；而且「一条消息合几格」仍取决于到达时刻，等于把不可控原样留着。
  否决——它治的是延迟，不是并发。
- **秒对齐窗口（去重 TTL 取 `1000 - now % 1000`）**：让每笔扣减恰好落在自己的窗口里、每格只有 1 个消费者、
  **零空转**，看起来比固定两格更优。但 TTL 由 **Redis 时钟**计，`create_time` 由 **MySQL 时钟**写，两个时钟
  不同源：一旦有偏移，窗口边界与格边界就错开，**某一格没有任何消息指向**，只能等 60s 兜底。用可见的 50% 空转
  换静默的漏格，不划算。否决。
- **消息带三格（`s - 1, s, s + 1`）**：能把边界 1 的漏格概率压到零。代价是空转从 50% 抬到 67%，
  而边界 1 的概率是万分之一量级（见下节）。为万分之一付 +17% 的常驻空转，否决。
- **一条消息里循环合到没有为止（不设两格上限，但仍带 `cellTime`）**：等于把「合几格」重新交给到达时刻，
  空转率又变成流量的函数。否决——两格是「覆盖一个窗口的尾巴」的最小充分集，不是性能参数。

## Consequences

- **延迟 1.1s → 2~3s**。裸投递实测 2.28~3.03s；端到端「预扣 → 定时消息 → 消费合完」三次实测
  2931 / 2993 / 2967 ms，全部 ≥2000ms。上界按 3.2s 断言（真机用例 `InventoryMergeDeliveryLatencyTest`，
  需 `-Dbs.inventory.mq-e2e=true` 才跑）。**这是本次最直接的代价**：合并延迟翻倍多，对账读数在途时间同比变长。
- **消息丢了从「下一跳顺手救」变成「必等 60s」**。旧形态下每条消息都顺手把前面几格合掉，丢一条几乎无感；
  现在一条消息只负责自己那两格，丢了就是那两格停在 `state = 0` 直到 `inventoryMergeBackstop`（`0 * * * * ?`）
  捞回来。所以**兜底从「保险」变成「必需件」**——删掉它等于删掉自愈能力。重投不保留延迟（首次 10s 起），
  也不能当快速恢复手段。
- **50% 空转是设计值，不是故障**。一对格子 `(s, s+1)` 会被 `cellTime = s` 与 `cellTime = s+1` 两条消息各指一次，
  其中一次必然「已无可合行」。因此 `mergeCell` 的「已无可合行」与「翻转行数对不上」两条日志只能是 `debug`
  （`error` 会误报不变量破坏，`info` 会按秒刷屏），空转率靠 `mergePair` 那条 `merged=[x, y]` 观测。
- **滚动发布的载荷兼容**：旧格式（无 `cellTime`）在消费侧 `log.error` + 丢弃，切换窗口内这些消息对应的格
  落到 60s 兜底；**不双跑**（新旧逻辑并存会让「这条消息该合哪格」有两种答案）。发布顺序：先发消费侧
  能丢弃旧载荷的版本，再发生产侧带 `cellTime` 的版本。
- **每格消费者数固定为 2、消息量固定 1 条/秒/桶**：这是本次真正换到的东西，也是「空转 50%」的定价依据。
  它让 `pendingDeductQty` 的稳态有了可描述的形态（0~2 格在途），而不是「取决于流量」。
- **不变量破坏仍不重试、不续命**：桶守卫不过、`waiting` 不足、翻转行数对不上，一律整格回滚、不抛。
  暴露口径仍是对账读数（`pendingDeductQty` / `pendingClaimQty` 长期 > 0）。
- **升级判据（将来真需要时）**：pending key 数 × 唤醒频率逼近单轮消费耗时，就先抬**消费者并行度**
  （拆消费组 / 加线程）或抬兜底单轮的格数上限；**不要**退回「一条消息循环合到没有为止」——
  那正是本次要摆脱的不确定性（消息量已经是 1 条/秒/桶 的硬上界，产能只能加在消费侧）。

## 边界 1：毫秒级跨秒漏格（已接受）

**是什么**：去重窗口的 TTL 由 Redis 计时、格的边界由 MySQL 的 `create_time` 决定，两者不同源。窗口内的行
理论上只落在 `s` 或 `s + 1`（`s` = 开窗那笔的 `create_time` 秒），正好被一条消息的两格覆盖；但两个时钟的
毫秒级偏移会把窗口在 MySQL 时间轴上整体挪一点，使末尾那几行落进 `s + 2`。这些行被 throttle 吞掉了、
**自己不发消息**，于是 `s + 2` 那一格没有任何消息指向。

**为什么不修**：修法只有两条，都更差——「秒对齐窗口」引入静默漏格（见 Considered Options），
「三格」为万分之一付 +17% 常驻空转。而这条缺口**不影响正确性**：`state = 0` 的行留在原地，
`inventoryMergeBackstop` 每 60 秒按最老未合时间捞 key，必然合掉；台账只是晚一分钟对齐，对账读数会显示出来。

**接受记录**：触发条件是「毫秒级跨秒 + 时钟偏移超出一格」，概率估计 **< 0.01%**，影响是**延迟**而非**错误**
（不丢量、不多发、不需要人工修数据）。用户已就该边界明确接受，**不要再提三格方案**——那是把一个
万分之一量级的延迟问题，换成 17% 的常驻成本。
