# 库存合并换轨：1 秒延迟消息 + 时间格合并 + 60 秒兜底

> **「合并触发」与「续命」两部分已被 [ADR-0012](0012-inventory-merge-cell-bound.md) 取代（superseded，2026-10-20）**：
> 唤醒改由「消息带责任起点秒 `cellTime` + 定时消息（相对 2000ms）+ 固定合两格」承担，续命整段删除。
> 时间格、按格翻转判重、两段分叉、兑换确认异步化仍以本文为准；原文保留作为决策史。
>
> **表名与模型已变（2026-11，award 域重构）**：本文引用的 `virtual_inventory_quota*` /
> `physical_marketing_quota*` / `inventory_allocation_flow` 等配额池与分配表已整条删除，库存收窄为
> 单一 `award_inventory`(+detail) 台账、运营直接投放。本文只作为合并机制演进史保留；
> 现行表口径见 `backend/docs/marketing/db/award.md` 与 `better-school/sql/schema.sql`。

库存合并（把 Redis 桶已扣、台账未动的预扣明细翻进台账）原先由**每秒一次的 xxl 任务**驱动：`inventoryMerge`
全表扫 `state = 0`，聚合 SQL 产出 `(inv_id, bucket_id)` 工作清单，分片广播并行执行（[ADR-0005](0005-inventory-merge-aggregate-scan.md)）。
本次把**唤醒源**换成「每笔预扣自己带一条 1 秒延迟消息 + 60 秒兜底扫描」，把**工作清单**换成
「一条消息 = 一个 `(segment, inv_id, bucket_id)`，合它最老的时间格」，并把合并事务的判重从「id 清单」
换成「按格翻转 + 翻转行数校验」。同时把实物档的兑换确认从**同步转移**改成**落 `type = 2` 明细、由合并转移**。

**为什么难逆**：`inventoryMerge` 这个 job 及其全表扫描 SQL 整体消失，`xxl_job_info` 里的注册被显式删除；
明细分了 `type` 两段、两段明细各加业务唯一键与两条新索引；`outbox_message` 加 `delay_level` 列且扫描重发也按列走；
`INVENTORY_WAITING_SHORTAGE(4312)` 整条码退休，发货消费者里「确认撞 4312 → 重投等合并」的剧情随之删除。
回滚要把这些逐项重建，不是配置开关。

**为什么反直觉**：ADR-0005 明确写过「引入 MQ 是本次明确排除的方向」，且它当时的判断并不错——如果只是想要
「按 key 1 秒后叫醒我」，RDQ 比 MQ 更贴切。反转的真正理由是另一条：**每秒全表扫的成本随 pending 行数重复支付，
而流量低时它照样每秒扫一遍空表**。延迟消息把成本变成「每笔预扣一条消息」，与流量同阶、空载为零；
而 ADR-0005 的聚合扫描无论如何优化，都摆脱不了「每秒替所有 key 付一次扫描」。

**为什么是真权衡**：换来的是「单次合并有界、消费者可并行、丢消息能自愈、空闲零扫描」；
代价是 at-least-once（重复投递必须靠 DB 判重扛住）、**1 秒量化**（延迟级别只有 1s 档，且窗口尾巴要自我续命）、
以及 **60 秒兜底变成必需件**（重投不保留延迟，首次重投是 10s 后，不能把重投当快速恢复手段）。

## Decision

- **唤醒 = outbox + MQ 延迟级别 1**。预扣的 Lua 脚本在「扣减成功」之后用 `SET NX PX 1000` 决定这一笔要不要发消息
  （固定窗口 throttle，从第一笔算；窗口内的后续扣减只落明细）。要发就在**明细同一个事务**里写一行
  `outbox_message`（`delay_level = 1`），提交后异步发出。topic `bs-inventory-merge`，消费组
  `bs-marketing-inventory-merge-group`。生产方与消费方在同一进程，但**仍走 MQ 而不是 Spring 事件**：
  要的是跨进程、可重投、可观测，以及与 outbox 的至少一次语义。
- **延迟级别必须随消息持久化**（`outbox_message.delay_level` 列）：扫描兜底重发是从 DB 读行再发的，
  按 destination 查表的映射会随配置漂移，且会把「1 秒后合并」变成「立刻合并」。默认 0，
  只有库存合并传 1——共享 sender 不能把积分 / 抽奖的事件也拖慢 1 秒。
- **工作清单 = 一个 key 的最老时间格**。消息载荷只有 `{segment, invId, bucketId}` 定位三字段，
  不带数量也不带时间：数量由明细表回答，时间由 `create_time`（INSERT 时 DB 的 `NOW()`，秒精度）回答。
  一次唤醒最多合 10 格；合完若该 key 仍有未合并行就**自我续命**再发一条同 key 消息（收敛，且只在有剩余时发）。
- **判重 = 按格条件翻转 + `affected == c1 + c2`**。秒已封口 ⇒ 这一格不会再长新行 ⇒ 条件翻转与「携带 id 清单」
  等价，还省掉把几百行 id 拉回应用。行数对不上 = 没抢到，整格回滚。**只合最老一格**：同一 key 上
  预扣行的 `create_time` 必然早于确认行，先合最老格才能让「确认时 `waiting` 足够」成为结构保证。
- **兜底 = 60 秒 `inventoryMergeBackstop`**，两段各取 ≤ 200 个 key（按最老未合时间升序）逐 key 直调合并、
  不发消息。它只负责「消息整条丢了」：outbox 进死信、Redis 扣了但事务失败、进程崩在两步之间。
- **分叉只看「明细落在哪张表 + 行内 `type`」**：`segment` 选目标表（实物配额 / 虚拟配额），
  `type = 1` 进 `waiting`（虚拟直接进 `issued`），`type = 2` 从 `waiting` 转 `issued` 且**从不碰 Redis**。
  不看 `draw_record.award_type`——奖品实际改发兜底档时，行落在兜底奖品的池子里，账、行、记录三者本来就一致。
- **兑换确认异步化**：`confirmIssued` 从「同步做 `waiting → issued`」改成「回查预扣行拿桶号 → 同事务落
  `type = 2` 明细 + 一条合并消息」，撞明细唯一键按成功回放。同步失败态（4312）随之退休，
  确认没结清只表现为对账读数 `pendingClaimQty > 0`。

## Considered Options

- **保持每秒全表扫（ADR-0005 现状）**：单轮合并本身已被聚合 + 保险丝 + 分片压住，但「每秒替所有 key 付一次扫描」
  与流量无关；且它把「有没有活干」的判断压在 DB 上，而正常的库存 key 绝大多数时间是空的。否决——
  不是因为它错，而是因为延迟消息用同样的代价换到了「空载零扫描」。
- **Redisson `RDelayedQueue`（ADR-0005 预留的升级路径）**：定时精度最好（每 key 自己的 1 秒），但消费是
  at-most-once（`BLPOP` 交出即无 ack），可靠性仍然全靠兜底扫描；每个 key 一个延迟队列对象，运维面多一套
  Redisson 结构，且与仓库现有 outbox 的至少一次语义对不上。**否决，但不否定它的诉求**——「按 key 精确定时」
  这个诉求被 MQ 延迟级别 1 以更低成本满足：合并本来就是秒级批，1 秒粒度已经够。
- **用 DB 唯一键做消息去重**：`outbox_message.uk_msg_id` 已经保证「一行一条」；把业务唯一键（`biz_type, biz_id`）
  拿来给消息去重，会把「同一业务在不同批次的多次流转」误判成重复（实物档预扣与确认共用 `biz_id`，
  必须带 `type` 才不互撞），而且 Redis 扣减是否真的发生过与 DB 行无关。唯一键只做业务幂等——
  撞键 = 这条流转已落过，回补 Redis 扣减后按成功回放。否决。
- **秒级令牌列（批次号 / `batch_token`）**：每行多写一列、多一个生成器，只为回答「这一批是哪些行」。
  `create_time` 的秒精度已经天然切格，且「过完的秒不会再长新行」这条性质就够用；令牌还要额外回答
  「谁生成、何时失效」。否决。
- **认领态（`state = 2`）/ 分布式锁 / `FOR UPDATE`**：挡不住并发 insert，还会让 Redis 成为合并的可用性前置
  （Redis 挂了合并就停）。`affected == cnt` 已经给了「谁抢到这一格」的答案。否决（ADR-0005 已否，此处重申）。
- **同一进程内用 Spring 事件替代 MQ**：少一次序列化，但丢掉重投、可观测与 outbox 的至少一次语义，
  且「消息发出」不再是一个可断言的事实（测试里只能断言内存调用）。否决。

## Consequences

- **重复投递是常态**：消费者 at-least-once，同 key 可并行消费（不追求串行，也不改消费模式）。
  正确性由 DB 的「按格翻转 + 行数校验」承担，不靠 MQ 顺序或队列锁。
- **1 秒量化**：合并延迟 ≈ 1.0–1.1s；窗口尾巴（最后一笔正好落在消息到达的同一秒）不会被这一跳看到，
  由合并侧的自我续命补上——这使得「低流量 key 多等一分钟」的极端情形消失。
  必须接受：**用延迟换扫描成本**，必然换来一个有下界的延迟。
- **兜底是必需件，不是保险**：重投不保留延迟（首次 10s 后，阶梯 10s / 30s / 1m …），
  所以「消息发不出去 / 发出去但没被消费」只能靠 60 秒兜底收敛。删掉它等于删掉自愈能力。
- **不变量破坏不再重试**：桶守卫不过、`waiting` 不足、翻转行数对不上，一律整格回滚、不抛、不续命
  ——抛出去只会给 broker 一条注定失败的消息（刷 DLQ 噪声），续命只会变成 1 秒一次的日志风暴。
  暴露口径是对账读数：`pendingDeductQty` / `pendingClaimQty` 长期 > 0。
- **运维口径变化**：`inventoryMerge` 从 xxl 摘除（`xxl-job-tasks.sql` 里先 `DELETE` 旧注册），
  新增 `inventoryMergeBackstop`（`trigger_status = 1`）。漏删旧注册会让调度一直刷「找不到执行器任务」。
- **outbox 语义多一维**：`delay_level` 随消息持久化，扫描重发的消息照样晚 1 秒变 SENT；
  积分 / 抽奖的既有消息默认 0，行为不变（`RaffleShippingOutboxIntegrationTest` 的两条断言是这条共用件的回归哨兵）。
- **升级判据（将来真需要时）**：pending key 数 × 唤醒频率逼近单轮消费耗时，就先抬「每次最多合并的格数」或拆消费组；
  **不要**退回全表扫——那正是本次要摆脱的成本形态。
