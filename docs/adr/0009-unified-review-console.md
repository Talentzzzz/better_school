# 统一审核中台：独立工程 + "推信号 + 拉工单"派单模型

审核工作面从主工程的 `/admin/review` 工作台收敛为一个统一审核中台。本 ADR 记录的是**同一决策簇的三件事**——它们共同构成"审核中台的产品形态"，拆开写会碎，合起来才是完整决策：

1. **独立审核端工程**：仓库根新建 `front-review/`（与 `front/` 并列、独立构建、独立发版），审核工作面迁入其中，同屏审多种内容（帖子 / 评论 / 商品 / 跑腿，类型复用 `ReviewTargetTypeVO` 可审值）。
2. **"推信号 + 拉工单"派单模型**：在途工单落独立 `review_task` 表；推送通道 `/ws/review` 只广播粗粒度"有新工单"信号（只唤醒、不指定给谁、不锁单）；审核员**领单**（claim，条件 UPDATE 原子指派，一次一条、FIFO、类型只作过滤器）后持 5 分钟**租约**，到点未裁决经超时中心（`REVIEW_LEASE_TIMEOUT`，复合 `bizId={taskId}:{claimSeq}`）自动**回收**回池。
3. **替换旧 `/admin/review` 工作台**：主工程删路由、入口卡与旧视图，替换是单向门（干净、单一口径，回滚依赖 git 历史）——并存会出现两处口径漂移（一处读旧队列、一处读工单池）。

否决"抢审"（审核不像抢单，抢无意义）与"纯指派"（无法适配审核员快慢差异）：推送只负责唤醒，取件的节奏与类型偏好在拉取侧表达；"先领单后裁决"强绑定（裁决接口反查持单人，未领单 409），杜绝"未领单直接裁决"绕过租约。

## Considered Options

- **在主工程里改 `/admin/review`**：改动最小，但审核是多类型同屏的专属工作面，与用户面主站的信息架构、迭代节奏、发版诉求完全不同；留在主工程永远受主站构建发版绑架。否决。
- **纯指派 / 消息队列抢任务**：纯指派无法适配审核员快慢差异、离线即堵；MQ 抢任务把工单状态搬进 broker、裁决与工单状态难对账。拉取模型 + DB 持久化池让"无人在线"只是静默积压（上线补推），不上锁、不丢单。否决。
- **保留旧工作台与新中台并存**：两处取数口径必然漂移，且"同一内容在哪审"变成人为选择。否决——替换收口为单向门。

## Consequences

- 工单（单生命周期、可变）与审核记录 `content_review`（历史裁决、只插入）严格分离；裁决仍是 `ReviewCase.decide` 唯一内核，工单关闭与其同事务。
- 推送复用 chat 已实装的 WS 连接层骨架（票据 / 心跳 / 互踢），泛化出 `/ws/review`；presence 存 Redis（仅 AUDITOR/ADMIN）。
- 部署形态：独立构建发到主站同域 `/review/` 路径、仅内网可达；沿用既有 JWT 与角色门控，不建账号体系；共享类型手抄、后端枚举为事实源（技术债，已知）。
- 旧队列接口 `GET /api/moderation/queue` 改读 `review_task`；遗留裁决入口 `POST /api/moderation/review` 收口为"反查我持有的在途工单"，无绕过路径。
- 审核员工作量视图、工单风险标记、入池兜底对账等派生能力未含在本决策内（开放项，另议）。
