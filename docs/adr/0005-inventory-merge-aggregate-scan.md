# 库存合并扣减改造：聚合扫描 + 分片广播（票 12 的触发层升级）

> **已被 [ADR-0011](0011-inventory-merge-delay-message.md) 取代（2026-10-18）**：反转的是本文
> 「Considered Options」的**第 2 条**（MQ 延迟消息：当时以「引入 MQ 是本次明确排除的方向」否决，现在采纳）
> 与**第 4 条**（RDQ 升级路径：现在不再走——1 秒延迟消息 + 时间格合并已经消化了「扫描成本跟随 pending 行数」
> 这个升级动因）。第 1 条（保持全量行拉取）、第 3 条（ZSET 脏集合）、第 5 条（放弃 Redis 预扣）的否决理由仍然成立。
> 原文保留作为决策史；现状以 `backend/marketing/docs/db/inventory.md` 为准。

票 12（库存两段式）的预扣与合并事务骨架不变，本次只改造合并任务的"工作清单怎么来、由谁执行"：全量行拉取 + 内存分组 + 串行单实例，替换为**聚合 SQL 直接产出工作清单 + XXL-Job 分片广播并行执行**，并加高阈值保险丝。不引入 MQ。

## 决策

### 1. 工作清单：聚合 SQL

```sql
SELECT inv_id, bucket_id, SUM(quantity) AS total
FROM virtual_inventory_detail        -- 实物段为 physical_marketing_quota_detail
WHERE state = 0
GROUP BY inv_id, bucket_id
ORDER BY inv_id, bucket_id
LIMIT 2000                            -- 保险丝，见下
```

三个不可省的细节：

- **必须按 `(inv_id, bucket_id)` 分组**：守卫递减按桶进行，只按 inv_id 聚合会混桶，守卫对不上。
- **必须加覆盖索引 `idx_pending (state, inv_id, bucket_id, quantity)`**：现有 `idx_scan` 以 inv_id 打头，state=0 过滤用不上，会退化为全索引扫描，而已合并历史行永久累积，等于每秒扫全表历史。新索引使扫描只覆盖未合并行、零回表。
- **明细必须按 id 翻转**：SUM 是查询瞬间的快照，翻转若用 `WHERE inv_id=? AND state=0`，会把 SELECT 之后新落的明细也翻掉——那部分数量进了 state=1 却没进台账，账实不符。沿用现状的"携带 id 列表翻转"。

注意：GROUP BY 必须完整聚合后才能应用 LIMIT，**LIMIT 不省扫描成本**。它的唯一职责是给单轮事务数封顶（见"保险丝"）。

### 2. 执行：XXL-Job 分片广播

`inventoryMerge` 由 `SERIAL_EXECUTION` 改为分片广播。每实例只处理自己分片的数据：

- 单体阶段（未分库分表）：按 `shardIndex` 过滤聚合结果（`inv_id % shardTotal == shardIndex`），聚合仍各实例全量拉，内存过滤；
- 分库分表后：每实例直连并只扫自己的分表，天然分摊。

组间无依赖，可安全并行；同一组不会跨分片重复（inv_id 归属确定）。

### 3. 保险丝：LIMIT 2000 组/轮（可配）

正常流量下 pending 仅数十组，阈值永不触发，行为等价于全量处理。它只在积压时生效：任务停跑 10 分钟后重启，若无上限，第一轮会一口气开数千个事务、单轮跑数分钟，串行执行堵塞、积压恶化——恰好在系统最扛不住的时刻失控。保险丝把积压收敛速度钉死为"每轮 2000 组"，单轮秒级结束。**分片解决数据分布，保险丝解决单轮节奏，两者正交，都要。**

### 4. 不变的部分

单组事务三步（桶守卫递减 → 台账结算 → 按 id 翻明细）、桶表 `redis_qty` 守卫与对账副本语义、恒等式 `redis_qty − 未合并明细和 = Redis 实际余额`、每分钟全量扫 state=0 的兜底扫描，全部保持现状。

## Considered Options

- **保持现状（全量行拉取 + 内存分组 + 串行单实例）**：invId 多且活跃时单轮无界，1 秒跑不完则任务堆积、pending 滚雪球，下游实物发货确认（依赖 `waiting_qty` 翻账，缺账抛 4312 重投）被拖住。否决。
- **MQ 延迟消息单 inv 防抖合并**：语义最优（预扣即设 1s 闹钟，负载随流量平滑），但引入 MQ 是本次明确排除的方向。否决。
- **Redis ZSET 脏集合 + 每秒 tick**：预扣时 `ZADD NX` 记 invId，任务按脏集合驱动。扫描成本从"pending 行数"降到"活跃 invId 数"，ZREM 原子抢单。秒级轮询带来 1~2s 延迟与提交脉冲（线程池已削峰）。作为中间形态被本方案取代，保留为备选。
- **Redisson RDelayedQueue 单 inv 防抖**：底层即"ZSET + 按最近到期时间自调度的搬运任务 + BLPOP"，是 ZSET 方案的精确化极限（每 inv 自己的 1 秒，无周期脉冲）。代价：消费为 at-most-once（BLPOP 交出即无 ack），可靠性全靠兜底扫描；多实例竞态空抢为微秒级无害开销。**作为本方案的升级路径保留**：pending 行数涨到每秒聚合扫不动时，只替换"工作清单来源"，`mergeOne` 单组事务原样搬迁。
- **放弃 Redis 预扣，直接 DB 行锁扣减**：零漂移零对账，但热点行锁使吞吐天花板在数百 TPS，爆款活动不可用。否决——这是合并方案存在的理由本身。

## Redis 的固有问题（接受并驯服，而非消除）

只要用 Redis 做扣减层，漂移不可避免。三种故障、三种后果：

| 故障 | Redis 相对真实库存 | 后果 | 兜底 |
|---|---|---|---|
| 连不上/超时 | 不变（扣不动） | 预扣失败，抽奖失败，可用性受损 | 无脏数据，不需要兜 |
| 扣成功但响应丢失 | 偏小（扣了没记明细） | 在途丢账，少卖 | 对账发现差值；低峰重灌或接受 |
| 宕机丢尾部数据 | 偏大（已扣的还回来） | **超卖方向** | 守卫/对账发现即冻结，绝不自动修，人工核 |

处理的不对称性：**少卖可修可容忍（偏小），超卖不可逆（偏大）**——故对偏宽容、对偏严苛。桶表 `redis_qty` 的全部意义在于让上述漂移变成"一行 SQL 可裁决"：哪个桶、偏大偏小、差多少。发货确认在 DB 侧二次校验 `waiting_qty`（Redis 层决定须 DB 确认才算数），是超卖的最后一道闸。

## 本方案自身的代价与已知问题

- **扫描成本跟随 pending 行数，每秒重复支付**：覆盖索引使单次扫描便宜（索引内聚合、零回表），但不消除重复。pending 行数长期高位时，此方案劣于 ZSET/RDQ（扫描只随 invId 数）。升级路径已预留。
- **合并延迟为秒级量化（1~2s）**：对库存场景无感；实物发货确认撞 4312 窗口的概率随之存在（重投即收敛，属已知口径）。
- **快照一致性是硬约束**：SUM 与翻转必须锚定同一批 id，任何"图省事"的 `WHERE state=0` 式翻转都是资损 bug。已写入实现注释与测试断言。
- **分片广播的代价**：热分片不均（爆款 inv 集中于单分表时该实例独大）；分片数变更涉及数据重分布；每实例需持有 DB 连接池。单体阶段（内存过滤分片）无迁移成本，分表后需按分片路由。
- **对账存在瞬时误报窗口**：对账读取与 Redis 核对非原子，高峰期在途量变化可能造成假阳性差值，需按"连续 N 轮不一致才告警"消除。
- **聚合查询每秒全量打 DB**：即使覆盖索引，也是每秒一次全 pending 索引扫描；分片与保险丝均只摊薄/封顶，不根除。这是本方案与 RDQ 的本质差距，也是升级判据（pending 行数 × 每秒频率逼近索引扫描耗时 1s 时毕业）。

## Consequences

- 两张明细表各加覆盖索引 `idx_pending (state, inv_id, bucket_id, quantity)`（虚拟段、实物段）。
- `VirtualInventoryMapper` / `PhysicalQuotaMapper` 新增聚合查询，替换 `listUnmerged*DetailRows` 的全量行拉取。
- `InventoryMergeServiceImpl` 按聚合清单驱动，组内事务与守卫逻辑不动；`InventoryMergeJob` 改分片广播并读取分片参数。
- 集成测试补三类断言：多桶分组正确性、SUM 快照与翻转 id 集一致、积压超保险丝时分轮收敛。
- 监控沿用 pending 指标：持续上涨即分片吞吐不足，触发升级评估（RDQ 或分表）。
