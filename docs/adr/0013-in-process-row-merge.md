# 热点行写入换进程内合并：五条链路共用一套合并语义（两份实现）

取代 [ADR-0011](0011-inventory-merge-delay-message.md)（1 秒延迟消息 + 时间格合并 + 60 秒兜底）与
[ADR-0012](0012-inventory-merge-cell-bound.md)（消息带责任起点秒 + 固定合两格）。那两份 ADR 描述的是
**「把并发摊到时间格上、再用消息与兜底调度」** 的路子；本次把整条调度链搬进进程——请求进分片缓冲，窗口到点
**合并成一条 `UPDATE`**，调用方在进程内等提交。库存、帖子点赞、评论点赞、帖子浏览、商品浏览五条「逐笔打同一行」
的写全部换成这一套。

**为什么必须换。** 今天这五条链路的冗余不在同一层，但都指向同一个原因：**没有地方能安全地攒批**，于是每一笔
都得自己穿一遍中间件。计数侧是「outbox + `bs-post-count` + 20 万条/秒也照样单线程的 200ms 聚合器」，库存侧更重：
Redis 桶 Lua 预扣 → 明细 → 同事务 outbox（`delay_ms = 2000`）→ 消费侧按时间格合两格 → 60 秒兜底 job 补漏。
它们共同的代价不是某一次写入慢，而是**同一条链路要维护三份状态**（DB 台账、Redis 余量面、明细的 `state`），
任何一份落后都要靠「消息 + 兜底 + 对账」追回来。同机同表实测，单热点行逐笔写的物理天花板 ≈ **4,079 TPS**
（200 线程、Avg 49ms，加线程只加延迟），`merge` 策略 15,356 TPS、参考工程 L2W256 单热点 25,563 TPS。
天花板是真存在的，而它不在数据库，在「一笔一个事务」这件事上。

**为什么难逆。** 新形态把旧形态依赖的东西整层删掉：桶两张表与 Lua、台账的 `redis_qty`、去重 key、明细的
`state` / `bucket_id` 两列两条索引、`bs-post-count` / `bs-product-count` / `bs-inventory-merge` 三个 topic 与消费组、
`PostCountAggregator`、`inventoryMergeBackstop` / `inventoryBucketWarmup` 两个 xxl 注册。删完之后**旧代码不是
「关掉开关就能跑」，而是启动就报 `Unknown column`**。所以回滚只能靠「停新 jar → 回滚 jar → 重灌桶 → 放开注册」
四条动作，不能靠一次配置切换。

**为什么反直觉。** 这份 ADR 里有四条结论是反着直觉的，都写在 Decision 里：
① **两个工程各写一份合并器，不共享构件**——共享构件看起来更 DRY，但会把 `@Transactional` / `@PreDestroy` /
配置绑定倒推给一个无框架的回调；
② **`flushThreads` 不吃满连接池**——参考工程是独立服务（池 20、线程 20），本仓库池是共享的 10 + 虚拟线程，
吃满的后果是普通查询在 `connection-timeout: 3000` 上排队；
③ **长尾下合并器是净成本**——合并比 ≈ 1 时它只多一次排队，收益全在热点，统一一条路的理由是「热度不可预测」；
④ **这次不做压测验收**——参数没有扫参依据，写了阈值也只是编的，判据改由测试断言承担。

**为什么是真权衡。** 点赞从「立即返回」变成「等 5ms 窗口 + 一次 flush」；库存预扣从 Redis ≈1ms 变成
「窗口 + 落库」并把 `TIMEOUT_UNKNOWN` 变成需要编排层处理的一等出口；账不平在生产上**零自动信号**（没有
metrics 端点、`alarm_email` 为空）；两份实现要靠「同批提交 + 同名单测」而不是编译器来防漂移。这些都是真实代价。

## Decision

- **进程内合并，五条链路一套语义**：`shardKey` = 要更新的那一行的主键（由调用方显式给，合并器不解析 payload），
  `(key ^ key >>> 32) & mask` 选片，窗口 5ms，批上限 200，合并成一组一事务的一条 `UPDATE`。
- **两个工程各一份实现，不共享构件**：`better-school` 的 `CountMerger`（两个入口 `submitAndWait` / `submitAsync`）
  与 `marketing` 的 `QuotaMergeBuffer`（只有 `submitAndWait`）。对齐的是算法、5 条不变量、`MergeMetrics` 与参数名。
- **库存「成功 = 已提交」不放宽**：请求在进程内等 future，HTTP 只可能在 `COMMIT` 之后说成功；崩溃时调用方拿不到
  成功，凭 `bizId` 重试，`uk_biz_type` 是唯一裁决者。三个出口：成功 / `INSUFFICIENT`（确定没扣，切兜底）/
  `TIMEOUT_UNKNOWN`（大概率会扣，不切兜底、不落库、抛可重试）。
- **计数分三档**：点赞（帖子 / 评论）与关系行**同事务、精确**；浏览量**异步、允许丢**；评论总数与子回复数**不动**。
- **桶整层废除**：分片的「把并发摊开」职责取代了桶；台账三列成为唯一真相；明细删 `state` / `bucket_id`，
  `type = 2` 的兑换确认**常留**（幂等键 + 出库审计）。
- **兑换确认进合并器**：与预扣同分片、同形状的另一组（`waiting -= c, issued += c`）；`waiting` 不足是**不变量破坏**，
  整组回滚 + 抛可重试进死信，不静默、不部分确认。
- **60 秒兜底整条退休，不建替代 job**：ADR-0011 列的三种丢失（消息丢 / Redis 扣了事务失败 / 崩在两步之间）在内存
  合并下一种都不剩；兜底本来就只按明细搬账、从不上门核对，连「孤儿预扣」都碰不到。对账读数瘦成台账三列，
  守恒等式降级为集成测试断言。
- **不设开关，按进程切换**：计数（bs）先切、库存（marketing）后切，间隔 = 一个日间高峰 + 一次抽样对账。
  切流窗口只做可逆动作（`state SET DEFAULT 1`、xxl `trigger_status = 0`、清桶前先对账），**不可逆点推到 D9**
  （删列 / 删表 / 删注册），于是回滚不需要反向 DDL、不需要恢复备份；回滚形态里 `inventoryMergeBackstop` 必须回来。
- **不做压测验收**：不给 TPS / p99 阈值，判据是引擎 5 条不变量 + 库存守恒 + 计数精确 + 一次人工抽样
  （`.scratch/hot-row-merge-l2w256/acceptance.md`）。参数按参考工程模型推导，标注未扫参，线上按观测调。

## Considered Options

| 方案 | 为什么否 |
|---|---|
| 保留 `redis_mq` 策略（Redis 预扣 + MQ 合并） | 受理 12.3k/s 但落库 5.9k/s、收尾要 130s：真正的瓶颈没动，只是把积压藏进 MQ；且要维护 Redis 余量面与 DB 台账两份真相 |
| 只换库存，计数维持 outbox + 聚合器 | 计数侧的热点同样被「一笔一消息 + 单线程聚合」压住；两套心智模型并存，等于长期维护两种正确性论证 |
| 抽一个跨工程共享的合并构件（第三个 reactor） | 用户 2026-10-22 否决：为「无框架」付 `@Transactional` / `@PreDestroy` / 配置绑定的成本；且新机器上多一道「先 install 构件」的坎 |
| 一批一个事务（而不是一组一个事务） | 两个分片以不同顺序锁同两行，多一个死锁面；失败要回滚整批，无法精确回填到件 |
| 照抄参考工程的售罄短路 + 二分拆批 | 抽奖每笔恒为 1 件，批内数量相同，「二分」基本用不上；改成「扣不动再探再切」，临界点最多 2 次事务 |
| 保留 msgId 环形去重（100k LRU） | 重投的源头（MQ）消失；点赞幂等由唯一键承担，浏览本无幂等语义 |
| 保留 60 秒兜底做「双保险」 | 它只按明细搬账，不从业务事实证明；合并器在进程内、调用方等结果，补合对象已不存在。留着只会让人以为账有人看着 |
| 设 `merge.enabled` 开关做双跑 | 物理做不到：旧路径踩在将被删的列 / 表 / 桶 / 注册上，关掉开关启动即报错 |
| 先压测拿基线，再定验收阈值 | 用户 2026-10-22 明确本轮不压测；基线跨主机跨表不可比，阈值只能是编的 |

## Consequences

**正向**

- 三条链路的中间件依赖摘干净：3 个 topic / 消费组、`PostCountAggregator`、Redis 桶与 Lua、去重 key、
  两个 xxl 注册。RocketMQ / Redis / xxl 本身仍在线（还有 11 个 topic 与缓存 / 票据 / 概率表在用），收益按
  「少几条链路」算，不按「下线中间件」算。
- 点赞与库存回到「成功 = 已提交」，不再有「以为成功其实没落」的缺口；库存不存在「Redis 扣了事务失败」这类跨系统不一致。
- 台账三列成为唯一真相，对账读数从 7 个字段瘦到 4 个，等式变成测试断言而不是运行时读数。

**负向（已接受）**

- 点赞 / 预扣多等一个窗口（5ms + 一次 flush，预算 100ms）；长尾路径上合并器是净成本。
- 库存账不平在生产上零自动信号；「长期挂在 `waiting`」退化成一句人话（看 `draw_record` 停在待发货）。
- 删掉的东西里有一整套故障用例（`InventoryMergeEngineIntegrationTest` 12 条、`InventoryMergeDeliveryLatencyTest` 1 条、
  `InventoryMergeTriggerIntegrationTest` 7 条），`waiting` 不足这类不变量今后只有测试守着。
- 两份实现靠纪律对齐，漂移只能在 review 里被看见。
- 观察期内 `schema.sql` 与线上库形状有 7 天不一致（新装库走新 DDL，存量库等 D9）。

**后续**

- 搜索索引里的 `likeCount` 不随计数更新（索引按内容变更回写），本次接受。
- `view_count` 仍在主表行上，与「审核 / 软删 / 编辑」抢行锁；要彻底分开得把列挪进窄表。
- 多实例部署需要网关按 key 分流（口子已留，不在本期）。
- 接入监控时第一个该上报的是「死信条数」与「孤儿预扣条数」，不是台账读数。
