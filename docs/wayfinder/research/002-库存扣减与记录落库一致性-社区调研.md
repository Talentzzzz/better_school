## 1. 问题定义：宕机窗口在社区资料中的对应提法

本仓库的窗口：**事务2（库存预扣：明细 + 台账）已提交 → 进程宕机 → 事务3（中奖记录 + outbox）未落库**。结果是台账已扣、记录未落——库存被"幽灵占用"，用户没拿到奖品。三个独立事务之间没有原子性保证，这正是社区文档反复描述的场景：

- dtm《秒杀》：**"创建订单和扣减库存不是原子操作，如果两个操作中间，遇到进程 crash 等问题，就会导致数据不一致……即使库存扣减不放在 Redis 中，而是放在数据库，不一致问题也通常是存在的。只要是分开的服务，那么数据不一致的情况就是无法避免的。"**（https://dtm.pub/app/flash.html 《秒杀》）
- 小傅哥 bugstack 大营销公开口径直接承认同一窗口的后果是**少卖**："decr 操作和数据操作不是一个事务，有可能库存扣减完了，但最终操作库失败了。那么这个库存就丢失了，可能会少卖。"（https://bugstack.cn/md/project/big-market/notes.html 《面试：技能、简历、问题汇总（大营销项目）》Q&A）
- RocketMQ 5.0 官方文档把"本地事务成功、下游动作丢失"列为普通消息方案的失败模式："The order is executed, but the message is not sent. In this case, the message has to be resent for consumption."（https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/ 《Transaction Message》）
- 美团对账体系文章的统计口径：清结算系统自建立以来 **70% 左右的问题都属于一致性问题**，成因是"幂等、并发控制不当；基础环境故障：网络、数据库、消息中间件故障；其他代码 bug"（https://tech.meituan.com/2018/03/21/balance-accounts.html 《美团配送资金安全治理之对账体系建设》）

社区的全部方案可以归纳为五个流派：**强一致大事务（XA/AT）、补偿类（TCC/SAGA）、消息类（事务消息/本地消息表）、对账类（对账单+幂等+退避+死信）、前置库存类（Redis 预扣+异步落库+恢复 job）**。它们不是互斥的：大促系统几乎都是"前置库存（e）+ 消息或补偿（c/b）+ 对账兜底（d）"的叠加，对账类是所有最终一致方案的共同底座。

## 2. 方案分类综述

### 2a. 强一致大事务：XA / Seata AT —— 为什么大促场景不选

**机制**（来源：https://seata.apache.org/zh-cn/docs/dev/mode/at-mode 《Seata AT 模式 | 开发者指南》；https://seata.apache.org/zh-cn/docs/user/mode/at 《Seata AT 模式 | 概述》）：

- 一阶段：**业务数据和回滚日志（undo_log 前后镜像）记录在同一个本地事务中提交，释放本地锁和连接资源**；提交前须先拿到该行的**全局锁**（"拿不到全局锁，不能提交本地事务"）。
- 二阶段：提交异步化（异步批量删 undo_log）；回滚通过 undo_log 反向补偿，且要做数据校验（后镜像与当前数据比对，防脏写）。
- 隔离性：默认全局读未提交，需读已提交要代理 `SELECT FOR UPDATE`，同样走全局锁。
- 使用形态：`@GlobalTransactional` 注解 + DataSourceProxy，业务侵入最小（"这里只是引入了一个注解就轻松实现了分布式事务能力"）。

**为什么大促场景不选**：

1. RocketMQ 官方对 XA 的定性："系统封装四个调用分支进一个大事务……**a large number of resources need to be locked to achieve this**. This number increases with the number of branches, which results in low system concurrency."（https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/ 《Transaction Message》 Scenarios 节）
2. AT 的全局锁把跨库冲突压回热点行串行：本仓库库存台账单行就是写热点（合并器之所以"一组一个事务"就是为了让热点收敛成批量单事务），若再叠加全局锁，热点行吞吐退化为行级串行 + 重试等待，秒杀峰值下是吞吐杀手。
3. 额外成本：undo_log 前后镜像落库、TC 协调器部署与状态存储；回滚窗口内数据处于"全局未提交"中间态，与营销场景"落库即占位、异步收敛"的语义不合。
4. 美团口径佐证："这些手段的目标都是在**事中**避免问题的发生。但是在实际场景中，无论是系统的内部逻辑还是外部环境都十分复杂多变、不可预知，我们很难完全避免问题。因此**事后**对于问题数据的发现以及修复就显得尤为重要。"（https://tech.meituan.com/2018/03/21/balance-accounts.html）——即便强一致能降低事中概率，事后对账仍不可省，故大促系统普遍放弃强一致换吞吐，把一致性交给事后收敛。

**结论**：XA/AT 解决的是"跨资源同时成功/同时失败"，代价是锁范围大、热点串行；对营销库存这种"宁可短暂不一致、不可丢吞吐"的场景，社区无一例外绕开它。

### 2b. 补偿类：TCC 与 SAGA

#### 2b.1 TCC（Try 预扣冻结 / Confirm / Cancel）

**机制**（来源：https://seata.apache.org/zh-cn/docs/user/mode/tcc 《Seata TCC 模式》）：

- Try 作一阶段"资源的检查和预留"，**且 Try 必须提交本地事务**——官方博客原话："try 阶段必须是要提交本地事务的，比如扣减订单金额，必须把钱从客户账户扣掉，如果不扣掉，在 commit 阶段客户账户钱不够了，就会出问题。"预留形态是"资源转入中间态/中间表"（https://seata.apache.org/zh-cn/blog/seata-tcc-fence 《阿里 Seata 新版本终于解决了 TCC 模式的幂等、悬挂和空回滚问题》）。
- Confirm 二阶段提交执行真正业务；Cancel 二阶段回滚释放预留。
- 不依赖底层数据库事务，"可用于解决跨数据库、跨服务业务操作的数据一致性问题"；代价是"侵入式的……需要业务系统自行实现 Try，Confirm，Cancel 三个操作"。
- 性能优势："TCC 模式在 try 阶段的锁定资源并不是真正意义上的锁定，而是真实提交了本地事务，将资源预留到中间态，并不需要阻塞等待，因此效率比其他模式要高。"（TCC Fence 博客第 2 节）
- 本地 dtm-examples 的 Try/Confirm 语义示例：`tccAdjustTrading` 把余额搬进 `trading_balance`（冻结池），SQL 自带余量守卫 `where trading_balance + ? + balance >= 0`；Confirm 用 `tccAdjustBalance` 把冻结转实扣（Z:/better_school/github-ref/dtm-examples/busi/data.go L126-144）。

**三大异常与 tcc_fence_log 防御**（来源：https://seata.apache.org/zh-cn/blog/seata-tcc-fence，Seata 1.5.1 起内建，注解 `@TwoPhaseBusinessAction(..., useTCCFence = true)`）：

| 异常 | 场景 | fence 防御 |
|---|---|---|
| 幂等 | TC 没收到二阶段响应，Confirm/Cancel 重试 | commitFence 先查 `tcc_fence_log`，状态已是 COMMITTED 则"幂等拒绝"直接返回成功 |
| 空回滚 | Try 因故障没执行，Cancel 先到 | rollbackFence 查不到记录 → 不执行回滚逻辑（返回成功）；Try 未到时 Cancel 插 SUSPENDED 记录占位 |
| 悬挂 | Cancel 已执行完，拥堵的 Try 才到 | Try 的 prepareFence 插入 TRIED 记录撞 SUSPENDED 占位的主键冲突，"Branch transaction has already rollbacked before"，拒绝执行 Try |

表结构核心：`tcc_fence_log(xid, branch_id, action_name, status[tried/committed/rollbacked/suspended])`，主键 (xid, branch_id)；`queryTCCFenceDO` 用 `for update` 保证判断与并发安全；fence 表操作与业务操作在同一个本地事务（代理数据源）。Seata Saga 文档对同一问题给出的是手工版口径：**允许空补偿（找不到要补偿的业务主键时返回补偿成功并把主键记下来）、防悬挂（检查主键是否已在空补偿记录里，存在则拒绝执行）、幂等控制**（https://seata.apache.org/zh-cn/docs/user/mode/saga 《Seata Saga 模式 | 最佳实践》）。

**适用/优劣**：核心系统（资金/库存）对性能要求高、且业务能自然表达"预留"语义时选 TCC；侵入大、三个接口都要写且都要幂等。对本仓库，**实物档的 `surplus → waiting → issued` 状态机本质上就是 DB 版的 TCC**（预扣=Try、兑换确认=Confirm、孤儿回补=Cancel），只是没有独立 fence 表——防幂等靠明细唯一键、防"Cancel 后 Try 又到"靠明细撞键按成功回放。

#### 2b.2 SAGA（状态机 + 补偿 + 对账）

**机制**（来源：https://seata.apache.org/zh-cn/docs/user/mode/saga 《Seata Saga 模式》；https://dtm.pub/practice/saga.html 《SAGA事务模式》）：

- 长事务拆为多个短事务，每步配一个补偿分支；失败时按正序的反向调用补偿。dtm 明确："TransIn 返回失败，……DTM 的做法是，**统一进行一次调用**（补偿）"——因为"可能出现数据源1成功，数据源2失败，这种情况下，需要确保补偿被调用"（dtm SAGA 文档《如何做补偿》节）。
- Seata 的实现是**状态机引擎**：状态图 JSON 定义（参考 AWS Step Functions），节点可配补偿节点（CompensateState）、Choice 路由、子状态机；引擎持久化状态日志，"状态机实例在本地数据库有记录日志，**通过日志恢复。seata server 会触发事务恢复**"（Saga 模式 FAQ 宕机恢复问）——这就是"对账"在补偿框架里的形态：状态日志 + 恢复重放。
- 重试策略内建退避：`Retry: [{IntervalSeconds, MaxAttempts, BackoffRate}]`，异常后按倍率退避重试；重试耗尽由人决策。还提供**向前恢复**："在回滚不了的情况下可以继续重试完成后面的流程，所以状态机引擎除了提供'回滚'能力还需要提供'向前'恢复上下文继续执行的能力（forward），让业务最终执行成功"（Saga 模式《缺乏隔离性的应对》+ FAQ）。API 层面即 `StateMachineEngine.forward / compensate / skipAndForward`。
- 隔离性缺失的应对是行业级共识原则：**"业务流程设计时遵循'宁可长款，不可短款'的原则……所以在业务流程设计上一定是先扣款。"**（Seata Saga 文档《缺乏隔离性的应对》）——映射到抽奖即"先扣库存/次数、后落记录，窗口内宁可库存被幽灵占用（长款，可回补），不可记录已落而库存未扣（短款，追不回）"。

**适用/优劣**：流程长、参与者多（含遗留系统/外部公司）时选 SAGA；不保证隔离性、补偿接口必须幂等可空补偿。编排引擎（状态机 + 状态日志 + 恢复）对"哪一步断了从哪一步续"的表达力最强，但引入引擎本身是一套中间件。

### 2c. 消息类：事务消息 / 本地消息表 / 二阶段消息

#### 2c.1 RocketMQ 事务消息（半消息 + 回查）

**机制**（来源：https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/ 《Transaction Message》（5.0 官方）；https://github.com/apache/rocketmq/blob/master/docs/cn/RocketMQ_Example.md 《RocketMQ_Example》第 6 节消息事务样例（4.x 官方））：

1. 生产者发送**半消息**（half message）：broker 落盘但"标记为暂不能投递"，对消费者不可见。
2. 生产者执行**本地事务**，回传三态之一：`CommitTransaction` / `RollbackTransaction` / `Unknown`（4.x 接口：`TransactionMQProducer` + `TransactionListener.executeLocalTransaction`（半消息成功后执行本地事务）/ `checkLocalTransaction`（回查））。
3. Commit 则投递；Rollback 则删除；**网络断开/应用重启/Unknown 时，broker 等待一段时间后向生产者集群发起事务状态回查**，生产者"根据业务 ID（例如订单 ID）检查本地事务是否正确提交"，再回 Commit/Rollback。
4. 兜底参数（4.x 文档《事务消息使用上的限制》）：
   - 单条消息**默认最多回查 15 次**（`transactionCheckMax`），超次 Broker 丢弃该消息并打错误日志（可重写 `AbstractTransactionalMessageCheckListener` 改行为）——注意：**超次即丢**，意味着 RocketMQ 事务消息自身也留了"对不上就人工/日志"的尾巴；
   - 首次回查在 `transactionTimeout` 之后，消息可带 `CHECK_IMMUNITY_TIME_IN_SECONDS` 覆盖；
   - 回查期间事务进行中应返回 Unknown（5.0《Usage notes》："do not return Rollback or Commit for a transaction in progress. Instead, keep the Unknown status"）；
   - **长时间无法判定时 broker 默认回滚**（5.0《Usage limits》："if the broker cannot determine whether to commit or roll back the transaction after a certain period of time, the broker rolls back the message by default"）；
   - 其他限制：不支持延时/批量消息、事务消息生产者 GroupName 独占（MQ 靠它反向找到生产者）、消息"可能不止一次被检查或消费"（消费端必须幂等）。
5. 语义边界（5.0《Usage limits》）：**只保证"消息生产与本地事务"的最终一致，"不保证消息消费结果与上游执行结果一致"**；中间态可见（最终一致性），只适合接受异步执行的场景。

**对本仓库的映射**：事务消息解决的是"扣次数事务 + 事件投递"的原子性，等价于本仓库 outbox（本地消息表）的角色；它并不直接解决"库存预扣 vs 中奖记录"的跨库一致——那两个动作仍要靠幂等键与对账。

#### 2c.2 本地消息表 / outbox

- big-market 的 task 表即此形态：抽奖落库同事务写 task 表 → `SendMessageTaskJob` 每 5s 分库扫描未发送任务 → 发 MQ → 成功置完成/失败置失败（Z:/better_school/github-ref/big-market/big-market-trigger/src/main/java/top/codingshen/trigger/job/SendMessageTaskJob.java）。本仓库"发货闭环"同构：抽奖落库同事务写中奖事件（本地消息表），失败重发与状态推进两个独立事实各自幂等（CONTEXT.md《发货闭环》）。
- dtm 对该方案的评述："如果采用本地消息表，需要的工作包括：在本地事务中执行本地业务逻辑，将消息插入消息表并最后提交；编写轮询任务，将本地消息表的消息，发给消息队列；消费消息，并将消息发给相应的处理服务。"优点是不依赖 MQ 事务特性，代价是要自己维护轮询与消费两端（https://dtm.pub/practice/msg.html 《二阶段消息》"二阶段消息 vs 本地消息表"节）。

#### 2c.3 dtm 二阶段消息（对 2c.1/2c.2 的改良，含回查技巧）

**机制**（来源：https://dtm.pub/practice/msg.html 《二阶段消息》）：

- `msg.DoAndSubmitDB(queryPreparedUrl, db, func(tx))`：**在业务本地事务内提交业务 + 写 gid（进 barrier 表，reason=committed），事务成功后 Submit**；Prepare（DTM 记下全局事务但不调分支）与 Submit 两阶段，业务成功与全局事务提交"要么同时成功，要么同时失败"。
- **提交后宕机**：DTM 轮询超时"只 Prepare 未 Submit"的事务，调用回查接口。回查实现只需 `barrier.QueryPrepared(db)`，其判据分四类：已提交→继续调分支；已回滚→终止；进行中→等待；未开始→往 RM 本地库插数据保证最终失败。
- **回查的核心技巧**（"回查原理剖析"节）：不是"查 gid 是否存在"（查不到分不清进行中还是已回滚），而是**再 `insert ignore` 一条同 gid、reason=rollbacked 的记录**——若本地事务还在进行中，插入会被行锁阻塞；插入正常返回则本地事务必已结束，查到 reason=committed 即已提交、reason=rollbacked 即已回滚。dtm 借此批评 RocketMQ 社区常见回查方案："两分钟还查不到 gid，并不能认为本地事务已回滚，极端情况下……最后数据又提交了，那么这个时候，数据就不是最终一致了，就需要人工介入处理了"——这与本仓库"对账单收敛前先查记录现状"的判据设计同构：**回查判据必须能区分"还没完"与"永远不会有"。**
- dtm 自评与对比："二阶段消息在二阶段提交方面，与 RocketMQ 的事务消息相似，是受到 RocketMQ 的事务消息启发后提出的新架构"；相对两者"无需学习或维护任何消息队列、不需要处理轮询任务、不需要消费消息"。

### 2d. 对账类：对账单 + 幂等键 + 退避重试 + 死信人工

这是与本仓库孤儿预扣对账最直接同构的流派，两条一手资料：

#### 2d.1 dtm 子事务屏障（幂等/空补偿/悬挂"三件套"的算法化）

来源：https://dtm.pub/practice/barrier.html 《异常与子事务屏障》；实现样例 Z:/better_school/github-ref/dtm-examples/busi/barrier.go（所有 TCC/SAGA 分支一律 `barrier.CallWithDB` 包裹）。

- 问题背景：**NPC（Network Delay / Process Pause / Clock Drift）**导致子事务乱序——空补偿（Cancel 先于 Try 到）、悬挂（Try 在 Cancel 后到）、重复请求。
- 对"常见建议"（先查空补偿表再决定）的批评："上述做法中的**'先查后改'在并发情况下是容易掉坑里的**"——Try 查完无空补偿记录、事务提交前进程暂停 P，全局事务超时 Cancel 判空补偿返回，Try 恢复后提交 → 悬挂成真。"解决这一类问题的关键点是要**利用唯一索引，'以改代查'来避免竞态条件**。"
- 算法：本地库建 `dtm_barrier` 表，唯一键 gid-branchid-op（try|confirm|cancel）：
  1. 开本地事务；
  2. 当前 op `insert ignore` 一条 gid-branchid-op，插不进 = 重复请求 → 幂等返回成功；
  3. 若当前 op 是 cancel，再 `insert ignore` 一条 gid-branchid-**try**，**插入成功**（说明 Try 从没来过）→ 空补偿，直接返回成功不执行业务；
  4. 业务执行，成功提交/失败回滚。
  防悬挂由此免费获得：Try 后到时，第 2 步的 insert 撞 Cancel 已插的 gid-branchid-try 记录 → 不执行业务。
- 竞态完备性（"竞态分析"节）：Try/Cancel 并发重叠时靠唯一索引冲突 + 行锁等待收敛到"要么 Try 先成、要么 Cancel 空补偿"两种结局；再遇宕机则 dtm 重试最终收敛。正常路径开销：每分支一个 SQL。
- 屏障覆盖 TCC/SAGA/MSG（"所有这些请求，到了子事务屏障后：不正常的请求，会被过滤；正常请求，通过屏障"）。

#### 2d.2 美团配送对账体系（轧账/平账的工程化）

来源：https://tech.meituan.com/2018/03/21/balance-accounts.html 《美团配送资金安全治理之对账体系建设》。

- 问题归类：数据流转不一致统一归结三类——**漏结**（发起方有、接收方无）、**重复结**（接收方重复处理）、**错结**（金额/状态字段不一致）。本仓库孤儿预扣正是"漏结"：库存域有明细、抽奖域无记录。
- 对账三阶段（专业名词：数据核对=轧账、差错处理=平账）：
  1. **数据准备**：拉取/推送/文件上传三种接入，统一格式进对账数据池；
  2. **数据核对**：对账方式（单向/双向，"条件允许优先双向"）、对账粒度（**"以明细对账为主，定位具体问题。以总数对账为辅，对明细对账的结果进行复核兜底"**）、对账口径（两方比对一对一/多对一/一对多 + 条目/金额匹配 + 重复性与异常状态自检，模板化）、对账时机（**离线 T+1 周期为主；实时对账耦合在结算链路中可拦截，准实时对账异步不拦截**）；
  3. **差错处理**：统一差错记录（对账场景/批次/来源/错误类型/处理状态）→ **二次核对**（防日切错报）→ 系统自动修复或报警人工。
- 在线对账实例（准实时）：监听运单与结算单元 Binlog，"收单运单消息后，我们会把对应的运单以 List 的形式存储到 Squirrel(Redis) 中，当结算消息来了以后，就把对应运单记录 Delete 掉。如果有运单记录一直停留在 List 当中，也就是说明结算消息没有来，应该是发生了漏结算。我们通过定时任务轮询运单 List 将问题数据输出"——**与孤儿预扣"种单+轮询"机制完全同构**：以"必然成对出现"的两类事件互为哨兵，停留者即不一致。

#### 2d.3 大促口径的对账兜底（Redis/DB 双源校准）

- aliyun《商城小程序高并发下单怎么设计？库存超卖、重复支付》：**"每天凌晨用 MySQL 实际库存与 Redis 对账，修复因进程崩溃、消息丢失导致的偏差"**，以数据库为事实源（https://developer.aliyun.com/article/1771592）。
- 掘金《库存系统如何避免超卖和少卖？》：对账系统指标"每日凌晨对比：Redis 库存总量 + 预占库存 = 数据库库存总量，若不相等，触发告警并自动修复"；监控报警规则如"库存扣减失败率 > 1%、库存回补延迟 > 5 分钟"（https://juejin.cn/post/7496345865231368203）。

### 2e. 前置库存类：Redis 预扣 + 占位锁 + 异步落库 + 恢复 job

#### 2e.1 big-market（bugstack 大营销）口径与本地 fork 代码

公开口径（https://bugstack.cn/md/project/big-market/notes.html）：

- "抽奖也是一种峰值流量高的业务场景，因此在设计奖品库存扣减上，采用了 **Redis decr 分段消费和加锁兜底**的设计，同时对于消费成功的库存，**异步队列方式 + 定时任务更新库存**。这样可以不超卖的同时，又减少数据库的压力。"
- 兜底锁的形态："对每一条产生从 decr 值，与抽奖的策略 ID 组合一个 key，进行 **setnx 加锁兜底**，来保证不超卖——这样的设计是颗粒度更小的锁方案设计，性能接近于无锁化。"（decr 后的余量值本身就是令牌：`cacheKey:surplus` 做 setnx，同一余量只被一单占用）
- 最终一致性三步（Q18）："首先是每次扣减完库存，都会写入到 Redis 延迟队列 / MQ 延迟消息，**缓慢更新数据库库存**。之后是 Redis 内的预热库存消耗完毕后，发送最终 MQ 消息，**更新数据库的剩余库存为 0**。最终活动结束后，还有**任务补偿，扫描抽奖所产生的的参与记录单，更新最终的库存消耗**。"
- 少卖的处理（Q&A）：承认"少卖是有可能的……库存就丢失了"；"一般并不会对少卖做过多的流程，如果想管理，也可以把**少卖的库存异常，加入单独的 redis 队列来重新消费**就可以了。"
- 本地 fork 对应实现（Z:/better_school/github-ref/big-market）：
  - `ActivityRepository.subtractionActivitySkuStock`：`redisService.decr(cacheKey)`，余量 `<0` 则重置 0 返回失败；`setNx(cacheKey + ":" + surplus)` 为库存锁，"加锁为了兜底，如果后续有恢复库存，手动处理等，也不会超卖。因为所有的可用库存 key，都被加锁了"（big-market-infrastructure/.../ActivityRepository.java L162-186）；
  - 扣减成功后 `activitySkuStockConsumeSendQueue` 投 Redis 延迟队列（3s），`UpdateActivitySkuStockJob` / `UpdateAwardStockJob` 每 5s `takeQueueValue` → `updateActivitySkuStock` 落库（big-market-trigger/.../job/）；
  - 库存清零事件 `ActivitySkuStockZeroMessageEvent` → RabbitMQ `ActivitySkuStockZeroCustomer` → `clearActivitySkuStock` 置 DB 库存 0 并清队列。

#### 2e.2 京东云：防超卖与持久化分离（"抗写"）

来源：https://www.cnblogs.com/Jcloud/p/16541216.html 《电商库存系统的防超卖和高并发扣减方案 | 京东云技术团队》。

- "扣减库存其实包含两个过程：第一步是**超卖校验**，第二步是**扣减数据的持久化**……抗写的实现原理其实是巧妙的利用了分离的思想，分离开防超卖和数据持久化；首先防超卖是由 Redis 来完成的……落库通过任务引擎，业务数据库使用商品分库分表，任务引擎任务通过单据号分库分表，**热点商品的落库会被状态机分散开，消除热点**。"
- Redis 侧用 Hash `hincrby` 扣减，"对 Redis 的 hincrby 命令返回值是否为负数，来判断是否发生高并发超卖，如果扣减后的结果为负数，需要反向执行 hincrby，把数据进行加回"；
- **网络抖动下的结果判定**："如果应用调用 Redis 扣减后，不知道是否成功，可以针对批量扣减命令增加一个防重码，对防重码执行 setnx 命令，当发生异常的时候，可以根据防重码是否存在来决定是否扣减成功"——用唯一键把"不知道成没成"变成可查询的事实，与本仓库明细唯一键"撞键=已落过"同源。
- DB 侧"傻瓜扣减"：过了 Redis 校验后落库 SQL 不再判断数量是否大于 0，只保留防重幂等。

#### 2e.3 淘宝系（知乎《库存合并扣减》）：Redis 分桶 + 预锁 + 明细为准 + 合并提交

来源：《库存合并扣减：一种基于分布式缓存的强一致性热点库存扣减方案》（知乎原文 https://zhuanlan.zhihu.com/p/1992918453867279678 ，镜像全文 https://www.xinfinite.net/t/topic/16952 ）。

- 传统 Redis 分桶扣减的定性："整体是业务有损的，所以 Redis 分桶扣减方案一般是用在**卖家限购、权益这类非实物类库存扣减的场景，这类场景业务接受少卖**。"
- 方案四件套：
  1. **锁库存模块**：DB 行库存从 `sq`（可售）锁到 `lq`（预锁），"不是通过将 sq 减去然后加到 lq，而是 sq 不动，锁库存直接加到 lq；DB 扣减时通过 `where sq-lq>0` 控制最终 sq 的数量不能小于 lq"；锁出的量初始化进 Redis 分桶计数；
  2. **下单扣减模块**："先扣减 redis 库存，redis 库存够扣的情况下，**再往 DB 插入扣减明细，明细插入成功最终才算扣减成功**"；
  3. **合并提交模块**："热点下单延迟 1s 后，通过扫描扣减明细，计算实际应该扣减的数量，一次提交库存变更到 DB"——提交前"先失效合并提交对应的 redis 分桶，防止后续继续有交易流量扣减此 redis 分桶"；
  4. **库存回收模块**：预锁量释放回可售（商家编辑、临界场景），"可以直接通过调用分桶合并提交来完成"。
- **不少卖的判据**："如果 Redis 数据丢了，实际这个 Redis 分桶库存扣减了多少，**以 DB 合并下单明细为准，也不会少卖**"——明细表是事实源、Redis 只是计数器；合并提交 SQL 用 `set sq = sq - δq where sq-lq-δq>0` 保 DB 不超卖。
- 并发防护："高并发场景下，下单扣减和合并提交单据扫描并发的情况下，可能会出现少扫描了单据……我们通过 **Redis 扣减屏障**防止此并发场景下的超卖。"
- 效果：压测单行热点非合并 1.4w TPS → 合并 3.2w；线上扣减成功率 80%→100%、耗时 15ms+→7ms+。
- **与本仓库合并器的关系**：这是全网与本仓库设计最同源的公开方案——"Redis/内存预扣计数 + DB 明细 INSERT + 延迟窗口合并翻账 + 明细为准对账"。差别只在预扣计数器放在 Redis 分桶（大流量）还是进程内合并器（本仓库 5ms 窗口），以及它有显式的 lq 预锁字段而本仓库用台账 `waiting` 列承担同一语义。

#### 2e.4 dtm 秒杀架构：扣库存与全局事务都在 Redis

来源：https://dtm.pub/app/flash.html 《秒杀》。

- 架构："扣减库存是在 Redis 中进行的，与 dtm 相关的注册全局事务和取消全局事务也是在 Redis 中处理的，**全程依赖 Redis，与数据库无关**，因此能够支持极高的并发。"
- 原子性由二阶段消息保证：`msg.DoAndSubmit("/QueryPreparedRedis", func(bb){ bb.RedisCheckAdjustAmount(...) })`——扣减 Lua 脚本同时"记录库存已扣减成功，这样可以保证这个操作幂等，并且保证后续的反查能够获得正确的结果"；**"一旦发生这类进程 crash，导致两个操作过程中断，那么 dtm 服务器会轮询超时未完成的事务……他会调用反查接口，询问应用，库存扣减是否成功扣减。如果已扣减，则将全局事务提交，并进行后续的调用；如果未扣减，则将全局事务标记为失败，不再处理。"**
- 防重复下单靠 gid 设计："一般秒杀活动一个用户仅能购买一次，因此按照**活动 id+用户 id 作为全局事务 ID**，能够保证用户最多生成一个全局事务，最多创建一个订单"——与 recordId=hash(userId,token) 同构。
- 性能：实测 1.2w 秒杀单/秒（"Requests per second: 11970.21"），理论 9w/s；文中引用"阿里双十一的峰值订单：58.3万笔/秒"作为量级参照。

#### 2e.5 支付/订单口径：预扣是占位、支付状态机为准、超时回滚

来源：https://developer.aliyun.com/article/1771592 《商城小程序高并发下单怎么设计？库存超卖、重复支付》。

- "Redis 预扣只是'占位'，真正的库存所有权在支付成功后才转移；未支付订单设置超时（如 15 分钟），超时后通过延迟消息回滚 Redis 库存"；"若用户在临界点支付成功，**以支付状态机为准，避免误关已支付订单**"。
- 消费落库时 DB 不足则"发延迟消息回滚 Redis 预扣"；幂等三件套：下单 reqNo 判重、支付回调状态机乐观更新（影响行数 0 即重复回调吞掉）、前端一次性 token（SET NX）。
- "MySQL 乐观锁做最后防线——落库时再用乐观锁兜底，防止 Redis 与 DB 对账前的极端不一致。"

#### 2e.6 通用综述口径（掘金）

来源：https://juejin.cn/post/7496345865231368203 《库存系统如何避免超卖和少卖？》（雷渊，2025-04）。

- DB 层三方案排序：条件更新 `UPDATE ... SET stock=stock-? WHERE sku_id=? AND stock>=?`（"简单高效，依赖数据库原子性"）、乐观锁版本号（"无锁竞争……高并发下大量请求失败需重试"）、悲观锁 FOR UPDATE（"强一致性保证……并发性能差"）。
- Redis 层 Lua："判断库存 + 扣减"原子；预占库存机制：预占→待支付→超时延迟队列（RocketMQ 延迟消息）触发释放恢复。
- TCC 版冻结：Try `stock_frozen+1`、Confirm `stock-=num, stock_frozen-=num`、Cancel `stock_frozen-=num`。
- 少卖专项：未支付订单定时扫描回补、取消即回补、**幂等回补接口**（`@Transactional` 里"累加库存 + `markStockRestored` 标记避免重复回补"——状态标记防重复回补，与本仓库回补守卫同构）。
- 选型表：普通电商（千级 TPS）→ DB 乐观锁+预占；秒杀（万级 TPS）→ Redis 分片+异步对账；分布式复杂业务 → TCC+本地缓存合并；"高可靠：对账系统兜底数据一致性"。

| 回查（崩溃后判定"做没做"） | RocketMQ checkLocalTransaction（15 次上限后丢弃）；dtm QueryPrepared 四态判据 + insert-rollbacked 技巧 | 孤儿对账单种单后"先查记录现状（已落=漂移归还，未落=重放），重放不可行才回补+退次数"——同构 dtm 的"区分进行中/已回滚"判据 | **已具备**（自建对账单替代 MQ 回查） |
| 退避重试 + 死信人工 | Seata Saga Retry(IntervalSeconds/MaxAttempts/BackoffRate) + forward；美团差错处理二次核对+人工；RocketMQ transactionCheckMax 后人工日志 | 退避 1/2/4/8/16 分钟、COMPENSATE_MAX_RETRY=5 进死信，管理面重发/取消 | **已具备** |
| 对账轮（周期性全量校准） | 美团：明细为主总数兜底、T+1+准实时；aliyun/掘金：凌晨对账 Redis+预占=DB | 无周期性"台账 vs 明细汇总"全量对账轮；孤儿对账只扫"有预扣无记录"单点窗口 | **缺口（可选加固）**：社区惯例是再加一层每日/每小时全量对账（sum(明细) vs 台账）兜住未知形态的破坏（如手改数据、历史 bug 遗留），本仓库靠不变量校验+ERROR 留人工，覆盖面窄一些 |
| Redis 前置库存 + 占位锁 | big-market decr+setnx；京东云抗写；dtm 秒杀全程 Redis | **已主动删除**（CONTEXT.md《库存配额》："库存域已不用 Redis"；两阶段 Redis 预扣整条删除） | **有意不采用**：校园营销流量下合并器已够，Redis 前置引入"少卖可接受"口径与双真源对账成本，得不偿失 |
| 事务消息（半消息+回查） | RocketMQ TransactionMQProducer | 不用 MQ 承载事务，outbox+扫描替代 | **有意不采用**：等价物已自建，省去 broker 依赖与 15 次丢弃尾巴 |
| 前向恢复（重放不可行→补偿） | Seata Saga forward/compensate 双轨；dtm"统一调用一次补偿" | 决策可重放→原幂等键补落库；不可重放（活动结束/下线）→回补+退次数 | **已具备**（双轨语义与 Saga forward/compensate 对齐） |
| 超时占位回收（预占有效期） | aliyun 15min 延迟消息回滚；juejin 预占超时释放 | 抽奖同步即决，无"待支付"中间态；兜底奖品位不写原档占用防悬挂（CONTEXT.md《兜底奖品位》） | **不需要**（业务形态不同：抽奖无支付等待窗口） |

一句话总结：本仓库在**幂等、回查判据、退避/死信、明细为准**四个点上与社区最佳实践同构甚至更强（强一致明细、短合并窗口）；社区有而本项目没有的三样——Redis 前置库存、独立 fence 表、MQ 事务消息——前两样分别被"合并器+唯一键"和"状态守卫"以更少组件覆盖，第三样是 outbox 的等价物；真正值得考虑借鉴的只有**周期性全量对账轮**（台账 vs 明细汇总）这一层兜底，以及若未来库存热点超出 DB 承载时再评估 Redis 分桶预扣（届时应连同学知乎合并扣减的"明细为准+屏障"一起搬）。
