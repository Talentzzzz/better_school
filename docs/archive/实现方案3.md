# 实现方案3：redis 单桶库存扣减

砍掉热点识别器与多桶分摊，redis 单桶 + 上架即开桶，三张表落账。

与 实现方案2.md 的主要差别：

- 不再识别热点、不再把一份库存摊到多个桶，一个 inv_id 一个桶（配置表按 bucket_id 预留了多桶能力）
- 开桶由「上架」触发，不是识别到热点才开
- 合并提交直接落库存表：sq 减、lq 减、wq 加（方案2 走的是 LQ→WQ、不动 sq）

---

## 1. 表设计

### 1.1 库存表 inventory

```sql
CREATE TABLE inventory (
  `inv_id`  bigint NOT NULL COMMENT '库存记录ID，一颗SKU一条',
  `sq`      int NOT NULL DEFAULT 0 COMMENT '可售库存：前端展示的唯一来源，兜底路径从这里扣',
  `lq`      int NOT NULL DEFAULT 0 COMMENT '预锁库存：圈占 sq 的缓冲区，拨给 redis 池的额度台账',
  `wq`      int NOT NULL DEFAULT 0 COMMENT '下单未付款占用',
  `oq`      int NOT NULL DEFAULT 0 COMMENT '付款后占用，发货后减少',
  `version` int NOT NULL DEFAULT 1 COMMENT '合并提交与 DB 兜底直扣并发更新同一行时用',
  PRIMARY KEY (`inv_id`)
);
```

`version` 属于方案正确性所需的承重字段：合并提交和兜底直扣会并发更新同一行，落地时也可以用等价的原子条件更新替代。

### 1.2 redis 分桶配置表 bucket_config

```sql
CREATE TABLE bucket_config (
  `inv_id`     bigint       NOT NULL COMMENT '库存记录ID',
  `bucket_id`  varchar(64)  NOT NULL COMMENT '桶标识，随机生成，用于摊到不同 redis 分片',
  `status`     tinyint      NOT NULL COMMENT '桶状态：开启 / 关闭 / 重建中',
  `remaining`  int          NOT NULL COMMENT '该桶剩余额度（分桶粒度的 lq 余额），合并提交时同步减',
  `create_time` datetime    NOT NULL,
  UNIQUE KEY `uk_inv_bucket` (`inv_id`, `bucket_id`)
);
```

这张表承担四件事：记录 lq 分给了哪几个桶、存分桶粒度的余额、关桶时据此查 bucket_id 删 redis key、redis 重建时用它写回余额。单桶下它只有一行，多桶时各桶 `remaining` 之和等于库存表的 `lq`。

### 1.3 扣减明细表 deduct_detail

```sql
CREATE TABLE deduct_detail (
  `id`          bigint      NOT NULL AUTO_INCREMENT,
  `inv_id`      bigint      NOT NULL,
  `bucket_id`   varchar(64) NOT NULL COMMENT '从哪个桶扣的，合并与重建按此对齐',
  `order_id`    bigint      NOT NULL COMMENT '订单ID，兼作幂等键',
  `quantity`    int         NOT NULL,
  `status`      tinyint     NOT NULL DEFAULT 0 COMMENT '0=待合并，1=已合并',
  `create_time` datetime    NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_inv_order` (`inv_id`, `order_id`),
  KEY `idx_merge` (`inv_id`, `bucket_id`, `status`, `order_id`)
);
```

`idx_merge` 是合并任务的覆盖索引。`uk_inv_order` 用于幂等：重试、重复请求撞唯一键即视为已扣过。成立前提是 `inv_id` 为 SKU 粒度（一单多 SKU 会拆成多条、inv_id 不同）；若库存记录的粒度不是 SKU，唯一键要改成含 SKU 的组合。

---

## 2. 核心不变式

- `sq - lq` = 非池可售，即 DB 直扣（兜底）能卖的范围
- 各桶 `remaining` 之和 = `lq`
- `(sq - lq) + Σ(remaining)` = 真实可售库存
- 展示读 `sq`。`sq` 比真实可售多出「已扣减但还没合并的量」，窗口等于合并延迟，合并一落即刻回正

---

## 3. 开桶

接口传参决定拨多少：可以传数字，也可以传百分比；优先级 数字 > 百分比 > 默认 50%。

动作：

1. 生成随机 `bucket_id`
2. `lq += N`
3. 插配置表一行（status=开启，remaining=N）
4. redis 用 `SET` 写入桶 key = N（不是 INCR，避免同一桶被开两次时额度叠加）

圈占式：`sq` 不动。所以 `sq - lq` 那个既有守卫 `where sq - lq - δ > 0` 不用改，语义也没变。

---

## 4. 扣减

1. `DECR` 桶 key；返回值不足（< 0）→ `INCR` 回补，返回库存不足
2. DB 事务内：insert 明细（status=0，bucket_id=本桶）+ insert 本地消息表（超时未付款的延迟取消消息，见第 6 节）
3. 撞 `uk_inv_order` → 视为已扣过，按幂等返回成功
4. insert 失败 → `INCR` 回补 redis，返回失败
5. 全程不碰库存表的四个字段

---

## 5. 合并提交

调度：xxl-job 单实例，路由策略「第一个」+ 阻塞处理策略「丢弃后续调度」。这样同一时刻只有一个任务在扫，不会有第二个实例把同一批明细各合并一次。

每批流程：

1. 走 `idx_merge` 扫 status=0（限定 inv_id / bucket_id，limit 固定批大小）
2. 带回本批 `order_id` 列表，后端算合并量 = 明细 quantity 之和
3. 事务内落账：库存表 sq 减、lq 减、wq 加；配置表该桶 remaining 减同量；按第 2 步带回的 order_id 列表把 status 置 1

**必须守住的点**：翻转范围要基于第 2 步带回的 order_id 列表，不能写成 `where status=0`。否则扫描之后、更新之前新插入的明细会被一起翻成已合并，而那部分量没进合并量，等于 DB 少扣 —— 超卖。

本批没扫到的（扫描时还没落库的）下批自然会扫到，不需要补偿逻辑。

---

## 6. 付款与取消

付款：`wq` 减、`oq` 加。

取消（含超时未付款的自动取消）：

- **只对已合并订单生效**：更新条件带 status=1，未合并时更新 0 行
- **字段动作**：`sq` 加、`lq` 加、`wq` 减（已付款的则 `oq` 减）；redis 同量 `INCR` 回桶
- **为什么 sq 和 lq 同增**：redis 存活时是唯一售卖入口，取消的货必须回到桶里才能再卖；要让 `sq - lq` 保持恒定、桶总额回到开桶状态，两个字段必须一起加
- 合并前到达的取消：更新 0 行，直接返回失败并提示用户重试（此时通常很快合并就完成了）
- 自动取消没有「用户」可提示，走 RocketMQ 延迟消息 + 本地消息表兜住重试，重投到合并完成后再执行

---

## 7. 关桶

触发：关闭接口，运营手动调用；也可以由 MQ 延迟消息或定时任务调用（接口本身不关心触发方）。

顺序：

1. 桶状态置关闭，应用层据此拒绝新扣减
2. 等在途明细落库（宽限窗口）
3. 最后一次扫描合并（同第 5 节）
4. 回收：`lq` 减掉桶剩余（等于配置表 remaining），`lq` 归零，`sq` 不动
5. 按 bucket_id 删 redis key，配置表该行状态置关闭

第 4 步注意不能给 `sq` 加回。开桶时 lq 加了多少、合并时又减掉多少，剩下的就是桶余额；给 sq 加回等于 N 被销两次账。关桶后剩余额度全部并入非池可售，商品自然回到 DB 直扣路径继续卖。

实现注意：不要用「直接 DEL key」当作拒绝新扣减的手段 —— key 不在时 `DECR` 会从 0 开始返回负值，而取消回补的 `INCR` 又会在 key 缺失时把桶造出来。用状态标记拒单，`DEL` 放在回收之后。

---

## 8. redis 宕机与重建

- 运行期：redis 存活时所有扣减都走 redis，任何请求都不走 DB；redis 挂了才切 DB 直扣兜底
- DB 兜底：`update inventory set sq = sq - ? where inv_id = ? and sq - lq - ? > 0`，只卖非池部分，卖不进被 lq 圈占的池子额度 —— 这是兜底不会和 redis 双重卖的原因
- 恢复重建：停写（不放开访问）→ 全量合并一次，把待合并明细全部落账、配置表 remaining 更新到准确值 → 用 remaining `SET` 写回 redis → 放开访问

先合并再写回的顺序是关键：合并会把所有 pending 归零，写回的余额才等于 redis 真实剩余；顺序反了会把已扣未合并的量重复放出去。

桶需要状态机（开启 / 关闭 / 重建中），重建流程要带超时与看门狗 —— 否则重建任务中途失败，商品会永久停在停写状态，谁也卖不了。

---

## 9. 已知风险与当前决策

**1. DECR 成功、明细未落库、进程随即挂掉**

这笔在配置表和明细里都不存在，重建时会把它当成可卖量还回去（超卖方向），而且两张表互相印证、自查发现不了。要兜住得靠 redis 累计扣减量（AOF 保真）或订单系统当裁判。发生面是「宕机瞬间的在途请求」。当前决策：不额外处理。

**2. 池子卖完**

`DECR` 返回不足即拒单，此时展示读 `sq` 仍显示有货（还有非池部分），会出现「页面有货、下单被拒」。当前决策：先按现状实现，不加告警打点、不加专门错误码，补桶机制后续再议。

**3. 补桶靠人工**

热点商品默认拨 50% 也可能卖光，补额度靠运营调开通接口（新桶即为新 bucket_id），暂无自动补桶。

## 10. 待定

- **取消后的明细记账**：明细表目前只有 0/1 两态，取消后这行仍是 status=1，若直接拿「明细合计」当已售量会对不上。需要定：加第三态（已取消）还是插一条反向明细行。
- **唯一键粒度**：`(inv_id, order_id)` 成立的前提是 inv_id 为 SKU 粒度，落地前核对。
- **下架与关桶是否同一个动作**，还是下架走单独流程。
