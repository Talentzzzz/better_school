# Spec：合并引擎去掉批间等待窗口（队列非空即发，三处同改）

> 状态：ready-for-agent
> 决策来源：2026-11-24 引擎评审对话——per-invId leader / 专属虚拟 leader 两模型对比 + 逐项对照 PolarDB-X 内核组提交后，用户拍板「等待窗口该去掉」。本 spec 是对前两份引擎 spec 中「收集窗口同口径平移」条款的**修订**：该条款作废。

## Problem Statement

现行两套合并引擎（请求线程 leader 的 `merge`、专属虚拟 leader 的 `mergevirtual`）的收集段都是「窗口到点 / 攒满 / 停机」三条件发车：**每批发车前都要等满收集窗口（生产 5ms），哪怕队列里已经有货**。批间隔 = 窗口 + flush 耗时，其中窗口那段在队列非空时是纯白等。

从使用方看：单件提交的延迟永远多付一个窗口（5ms）却换不来任何合并收益（后面没有件来）；热点流量的合并比被窗口人为压扁（到达 10k/s × 5ms = 50 件/批，而「落库期间天然进件」本可以自己平衡）。数据库内核的组提交（PolarDB-X Inventory Hint）正是对照物：**收集窗 = leader 持行锁处理的时间本身**——落库期间 follower 源源进队，提交即清空立即下一轮，没有额外 sleep。

## Solution

**发车条件改为「队列非空即发」**：攒满 maxBatch 提前发车、停机提前发车保留；「窗口到点」条件删除。收集窗 = flush 耗时本身——执行事务的过程就是一次天然的等待，落库期间新件自然进队，落库完队列有货就立即发下一批，源源不断。

结构安全性（本决策的核心论证，实现时写入类注释）：

1. **DB 打不穿**：串行形态下事务速率 = 1/flush 耗时，而 flush 耗时（行锁临界区 + 提交）≈ DB 单行事务周期，所以事务速率**天然 ≤ DB 天花板**（loadtesting 实测锚点 ≈4,079 事务/s）——节流阀就是 flush 耗时本身，不需要窗口保护；
2. **合并比自动伸缩**：合并比 = 到达速率 × flush 耗时。低速率（1k/s × 0.5ms ≈ 0.5~1 件/批）立即发车延迟最低；高速率（10k/s × 0.5ms = 5 件/批）事务速率仍 = 1/flush，稳态自动平衡，不积压、不拒收；
3. **突发头部已有覆盖**：瞬时大量涌入时「攒满 maxBatch 提前发车」接管，头部顶多多付一个小事务；
4. **窗口的残值趋零**：唯一理论价值（突发头部聚拢）已被上一条覆盖——纯延迟负担，全删。

## User Stories

1. As a 点赞用户, I want 我的点赞在落库完成后立即返回, so that 我看到的结果与数据库真实状态一致且没有白付的窗口延迟
2. As a 点赞用户, I want 队列里有货就立即发车, so that 我的请求不被前面批次的固定停顿拖着走
3. As a 秒杀用户, I want 热点行的合并比随到达速率自动伸缩, so that 高峰期 DB 压力被天然压平、低谷期我不等白窗
4. As a 秒杀用户, I want DB 事务速率被 flush 耗时天然节流, so that 不出现「合并器把 DB 打穿」的新故障形态
5. As a 秒杀用户（突发头部）, I want 瞬时涌入靠攒满提前发车承接, so that 头部只多付一个小事务而不是硬等窗口
6. As a 计数写入组件开发者, I want commit / awaitIdle / pending / close 对外语义不变, so that 调用方零改动
7. As a 计数写入组件开发者, I want count 引擎的 TIMEOUT 出口保留, so that DB 真变慢时调用方仍拿到确定的可重试失败而非悬挂
8. As a 引擎维护者, I want 三处发车逻辑同一口径同改, so that 不出现「库存没窗、计数有窗」的漂移
9. As a 引擎维护者, I want 窗口参数退役但 yml 键保留一个版本, so that 现网配置不用动、回滚不用改配置
10. As a 引擎维护者, I want 结构安全性论证（事务速率 = 1/flush ≤ 天花板、合并比 = 到达 × flush）写入类注释, so that 后人不会把窗口当「DB 保护」加回来
11. As a 引擎维护者, I want 两套引擎并存定位显式化（请求线程版 = 通用后备、虚拟线程版 = 有虚拟线程环境的终态）, so that 通用组件在无虚拟线程的项目里仍可用
12. As a 通用组件使用者（无虚拟线程的 JDK 8/17 项目）, I want 请求线程版继续可用且行为一致, so that 升级引擎不要求先升级运行时
13. As a 通用组件使用者（JDK 21+ 项目）, I want 虚拟线程版同语义可用, so that 结构性单飞与零交接空档的收益可直接享用
14. As a 运维, I want 观测口径文档更新（合并比指标会「变难看」但事务速率与延迟变好）, so that 不会被旧指标吓到而误判回归
15. As a 运维, I want 停机三步、保序、一组一事务全部不变, so 上线/回滚与台账推理心智不变
16. As a 测试维护者, I want 发车时机类用例断言同步改写（窗口到点发车 → 队列非空立即发车）, so that 测试描述的就是现行行为
17. As a 项目所有者, I want 实现票完成后**不执行单测**（明确写入，见 Testing Decisions）, so that 不在代理网络受限的环境里空耗，欠账集中补
18. As a 后续验证者, I want 欠账（全套 surefire）挂在显式的补跑条件上, so that 调用方切换/退役决策前有人必须还账

## Implementation Decisions

- **三处同改（一票落地，防漂移纪律）**：`merge` 根包库存引擎的组收集段、`merge/count` 计数引擎的收集段、`mergevirtual` 的组收集段——三处发车条件统一改为「队列非空即发」，攒满 maxBatch / 停机提前发车保留，「窗口到点」条件删除。任何一处只改自己 = 违规。
- **窗口参数退役口径**：三份 `MergeConfig` 的 `maxFlushDelayMillis`（及其 yml 键 `merge.batch.max-flush-delay-millis` / `merge.count.max-flush-delay-millis`）**读入不参与发车判定**，javadoc 标注退役原因与决策出处；校验放宽为 `>= 0` 现状即可，不新增参数、不加新调优面（背压不加新闸门的拍板延续）。
- **窗口删除后的收集循环形态**：进入收集段时队列非空即发车；队列空的等待仅剩「等新件 / 等停机 / 等攒满信号」——探测间隔机制保留（它是防信号丢失的兜底，不是收集窗口）。请求线程版的执行权协议、虚拟版的 claim-CAS / supervisor / 退出谓词**均不动**——本 spec 只删批间停顿，不碰谁当 leader。
- **双引擎并存定位（用户拍板）**：保留请求线程版（`merge` 根包含 `count` 子包）作为**通用组件的兜底形态**（JDK 8+ 可用、零后台线程，兼容不能用虚拟线程的项目）；虚拟线程版（`mergevirtual`）定位为**有虚拟线程环境的终态形态**（结构性单飞、零交接空档）。两者是「不同运行时前提下的形态」，不是性能档位；语义变更必须两包（含 count 子包共三处）同票落地。
- **count 引擎 TIMEOUT 出口保留**：`waitTimeoutMs` 是「等终态的上限」，与收集窗口正交——窗口删除后它只剩 DB 慢时的兜底作用，语义不变、参数不动。
- **类注释与文档口径**：三处收集段 javadoc 补「为什么没有窗口」（内核对照 + 两条结构安全性论证）；两份既有引擎 spec 的「收集窗口同口径平移」条款标注作废并指向本 spec；CLAUDE.md 相关措辞（若有窗口描述）同步。
- **观测口径**：合并比指标的期望值含义变化（从「到达 × 窗口」变「到达 × flush」），文档注明——合并比数字下降不是回归，事务速率贴近 DB 天花板、单件延迟下降才是健康信号。

## Testing Decisions

- **只测外部行为**：提交 → 终态、批上限、同 key 单飞与保序、停机排空、背压有界——不测内部结构（发车判定、CAS 标志、摘除时机）。
- **Seam 复用，零新增**：三处引擎各自的纯内存单测骨架（录制型落库桩 + 闸门后并发起跑 + 后台提交）原样沿用；理想 seam 数为零。
- **断言同步改写**（两包对称）：「窗口到点才发车（单件返回时间 ≈ 收集窗口）」类用例改写为「**单件立即落库**（返回时间 ≈ 一次 flush）」；「攒满提前发车」用例保留（口径从「不等窗口走完」变「天然发车」）；同 key 保序、单飞、停机三步、背压、吞 Throwable / 退出谓词 / 双 spawn / claim 死亡窗口等既有断言不受影响。
- **实现票不执行单测（用户拍板，明确写入）**：实现完成的验收标准 = **代码改完 + 全 reactor test-compile 绿**，surefire 不跑——代理网络受限环境下的既有欠账（两套引擎既有单测也未跑过）不在本票清。**补跑欠账挂显式条件：调用方切换、旧包退役、任何替换决策之前，必须先补跑 merge + merge/count + mergevirtual 全套单测并全绿**——这条写进票面，谁做切换谁先还账。
- **行为验证的真实判据（后续）**：压测观察事务速率是否贴天花板、单件延迟是否下降、合并比是否如「到达 × flush」预期伸缩——本次不做压测验收（延续 L2W256 以来的拍板惯例）。

## Out of Scope

- 调用方切换（库存写入组件 / 计数侧换引擎）与旧包退役——另立票，且以「补跑全套单测并绿」为前置
- mergevirtual 的调用方接线、`merge`（含 count 子包）向 mergevirtual 的收敛终态执行
- 收集与落库流水线重叠（内核双执行单元乒乓；需独立落库权标志，属后续演进）
- Connector/J 8.3.0 → 9.x 升级与 JDK 升级（pinning 缓解，对两模型同等有益，独立小票）
- count 引擎 `waitTimeoutMs` 语义调整、任何参数调优
- 压测验收与 TPS/p99 阈值

## Further Notes

- 本 spec 是对 2026-11-24 两份引擎 spec 决策的修订，不是推翻：per-invId leader 模型、专属虚拟 leader 模型、乐观删除闭环、supervisor、退出谓词、背压不加闸等全部沿用；**唯一变更 = 收集窗从「固定等待」变「flush 耗时本身」**。
- 决策链回放：①「谁来执行」两模型对比中 pinning 与排障差异因 tomcat 已虚拟线程化而打平（Connector/J 8.3.0 的 pinning 对两模型同等存在）；②「要不要等窗口」的洞察来自用户：「执行事务的过程就是一次天然的等待」——与 PolarDB-X 内核形态逐字同构；③「窗口是 DB 保护」的反方论证被结构安全性推演消解（事务速率 = 1/flush ≤ 天花板，合并比 = 到达 × flush 自动平衡）；④保留请求线程版是通用组件的兼容性拍板，不是性能裁决。
- 双维护纪律重申：两包 + count 子包三处，语义变更同票落地、测试用例对称、谁改一半谁违规。
