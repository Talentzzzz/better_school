# 库存扣减三策略压测报告

**环境**：三台阿里云 ECS，均 4C8G，应用与中间件分机部署；JMeter 5.6.3 单机施压。

| 角色 | 内网 | 部署 |
|---|---|---|
| 中间件机 | 172.31.88.255 | MySQL 9.7 / Redis 8.8 / RocketMQ 5.5 |
| 应用机 | 172.31.89.1 | `lt-inventory-app:1.0.0`（Tomcat 400 / Hikari 200 / JVM 4G） |
| 施压机 | 172.31.89.0 | JMeter 5.6.3（堆 2G） |

**参数**：200 线程 / 30s 爬坡 / 120s 持续；单 SKU 单热点；`BUCKET_COUNT=1`；初始库存 **5,000,000**（未售罄）。

---

## 一、结论摘要

1. **三种策略结果都正确**：零超卖、账目全对平、Redis 与台账一致（`redisMatchesLedger=true`）。
2. **单热点行的物理天花板是 ≈4,100 TPS**。`db` 跑满 120 秒稳定在 4,007~4,015/s，且 10 线程时已达 3,225/s——加线程只加延迟，不加吞吐。
3. **`redis_mq` 受理 12.3k/s，但落库只有 ≈5.9k/s**，多出来的全部堆在 MQ 里，跑完后还要 **130 秒**才排空。端到端算下来只比 `db` 快 1.4 倍。
4. **`merge` 受理 15.4k/s、零积压**，台账只被 UPDATE **996 次**（`db` 是 49 万次）。端到端是 `db` 的 **3.8 倍**。
5. **`merge` 并不减少写入量，它消除的是争用**：每单仍要写一条预扣明细，但它不和别人抢同一行。
6. **抢购实测零超卖**：1000 件库存在 200 线程下两轮都恰好卖出 1,000 件，且 1,000 单被合并成 **1 次**台账事务。

## 三、数据库写入

| 策略 | 台账 UPDATE 次数 | 写放大（相对受理数） | 说明 |
|---|---|---|---|
| db | **490,071** | 1 : 1 | 每单一个事务（UPDATE + INSERT），全部串行在同一行 |
| redis_mq | **1,474,443** | 1 : 1 | 每单成本与 db 相同，只是挪到消费端延后执行 |
| merge | **996** | 1 : 1,852 | 平均每次合并 1,852 行 |

> `merge_runs=996` 而不是 120 的原因有两层：
> ① `create_time` 是**秒精度**，而 15.4k/s 的明细在持续流入同一秒，一次合并只标记到 `id <= maxId` 的快照边界，
> 剩下的留给下一次——所以同一秒会被反复合并（实测平均每 120 ms 一次，每次约 1,852 行 ≈ 120 ms 的流入量）；
> ② 合完若仍有 `state=0`，就再发一条延迟消息自我续命（`merge_chain=1044`）。
> 最终实际频率是 8.3 次/秒，而非设计上的 1 次/秒。

## 五、四条关键结论

### 1. 单热点行的天花板 ≈ 4,100 TPS，与线程数无关

`db` 的三个完整区间：4,015 / 4,006 / 4,008 /s，Avg 稳定 49 ms，Max 只有 73 ms。

用 Little's Law 验算：`200 ÷ 0.049s = 4,082/s`，与实测 4,078/s 吻合——200 个线程全程 100% 忙碌，
说明是**服务端饱和**，不是施压机没用力。

再推临界区：`1 ÷ 4,084 ≈ 0.245 ms`，这就是单热门行一次扣减的锁持有时间。
**旁证**：10 线程冒烟时 3,225/s、Avg 2.38ms，`10 ÷ 0.00238 = 4,202/s`，同一个天花板。

> 含义：给 `db` 加线程、加连接池、加机器都没用，**瓶颈是那一行**。要提升只能减少对同一行的争用。

### 2. `redis_mq` 只是把排队从应用挪到 MQ，落库仍是 5.9k/s

受理 12,267/s，但消费端 250 秒才把 1,474,443 条全部落完 → **落库速率 ≈5,898/s**。
按这个速率回推，施压结束时 MQ 里积压约 **76.7 万条**，正好对应 130 秒的排空时间。

**落库速率 5.9k/s 高于 `db` 的 4.1k/s**，原因不是 MQ 更快，而是消费端只有 32 个线程：
线程越少，行锁的"护航效应"（convoy）越轻。同一把锁，200 个线程抢比 32 个线程抢效率更低。

> 含义：**MQ 削峰不假，提吞吐是假的**。它把 4.1k/s 的写入压力摊到时间轴上，代价是 130 秒的一致性延迟。

### 3. `merge` 赢在"没有热行"，不在"少写"

`merge` 每单仍要写一条预扣明细，写入**行数并不比 `db` 少**（1,845,079 条明细 + 同样数量的批量状态更新）。
它做到的是：

- 受理路径只写一条"不同行"的 INSERT，互不阻塞 → 15.4k/s
- 台账由 996 次批量合并推进，`merge_rows` 平均每批 1,852 行
- 合并不碰竞争热点，`merge_busy` 只出现 109 次，`drained` 立即完成

> 含义：合并扣减的收益是**把"争用同一行的 N 次写"变成"N 次互不争用的写 + 1 次批量推进"**。
> 所以它的吞吐上限由应用机 CPU、Redis 单实例和明细表的 INSERT 能力决定，而不是数据库行锁。

### 4. 兜底扫描被真实触发并且有效

`merge_lost_cell=49` —— 49 个时间格的唤醒消息丢了，但最终 `drained=true`、账目对平。
**没有兜底扫描，这 49 个格子的库存会永远卡在 `pending`**。这是"延迟消息 + 兜底"这套设计必须成对出现的直接证据。

## 六、施压机没有成为瓶颈（可信度校验）

用 `vmstat 2` 在压测期间按 2 秒区间采样，最忙的 5 个区间：

```
r(运行队列)  us+sy  id
0            20     81
0            20     81
2            21     79
2            79     21
2            80     20
```

- 峰值 CPU（用户+系统）**80%**，空闲仍有 20%
- 运行队列 `r` 最大 **2**，4 核机器上没有出现排队

结论：**JMeter 不是瓶颈**，15.3k/s 是服务端真实上限。但余量只剩 20%，
若要继续往上压（比如 400 线程），必须改用分布式施压，否则测到的会是施压机极限。

## 七、能落到生产上的三条建议

1. **单热点 SKU 不要用纯 DB 行锁方案**。4C8G 上 4,100 TPS 是硬上限，加线程/加连接池/加机器都无效，只能把热点拆开。
   注意：**单纯把 `BUCKET_COUNT` 调大没有用**——Redis 是单线程，多个 key 仍走同一实例；
   要让分桶真正生效，必须「多 Redis 实例（或 cluster）+ 台账按桶拆行」，当前压测工程未实现后者。
2. **`redis_mq` 适合"可以接受秒级延迟"的场景**。它能把受理能力做到 3 倍，但必须配足够的消费并发 + 对账补偿；只要落库速率跟不上，积压会线性增长，没有上限。
3. **`merge` 是唯一吞吐与一致性都好的方案**，代价是"台账有 1 秒级延迟"和"必须有兜底扫描"。

## 八、这轮数据的局限

- 只测了 **单 SKU 单热点**，这是有意为之（三策略比的就是同一行上的竞争）。多 SKU 会把行锁摊薄，`db` 的数字会显著变好。
- MySQL 是**压测口径**（`innodb_flush_log_at_trx_commit=2`、关 binlog）。生产默认配置下三个数字都会下降，`db` 降得最多。
- `db` / `redis_mq` 各只跑了 **1 轮**；`merge` 跑了 2 轮（15,356 与 15,159，差 1.3%），复现性尚可。
  正式对外报告建议每档 3 轮取中位数。
- 未采集这两轮的 `Innodb_rows_updated` 增量；`merge_runs` 已能等价说明台账写入次数。

## 九、抢购场景实证（1000 件，200 线程）

| 轮次 | 参数 | 总请求 | 成功受理 | 售罄拒绝 | 拒绝吞吐 | `merge_runs` | 超卖 |
|---|---|---|---|---|---|---|---|
| 1 | ramp 30s / 30s | 584,957 | **1,000** | 583,957 | 19,389 /s | 1 | false |
| 2 | ramp 1s / 20s | 376,231 | **1,000** | 375,231 | 18,468 /s | **1** | false |

三条结论：

1. **两轮 `ok` 都恰好是 1,000**，一件不多一件不少。防超卖靠的是 Redis Lua 里
   `if surplus >= qty then decr` 的原子判断，不是"先查再改"。
2. **`merge_runs=1`、`merge_rows=1,000`**：1000 单落在同一个秒格，被合并成**一次**台账事务。
   这就是"合并扣减"在秒杀场景下最直观的样子。
3. **售罄后拒绝路径能扛 19.4k/s**，比实际成交能力（15.4k/s）还略高——
   卖光之后的流量不会把服务打垮。

一个必须说明的异常值：`RAMP=1` 那轮 **`Max=838ms`**，出现在 200 并发瞬间涌入的头几百毫秒
（JVM 冷启动 + Redis Lua 串行化），稳态 `Max` 只有 77~86ms。
秒杀场景的尾延迟要按 838ms 这个数来评估，不能拿稳态的 80ms。

## 附录：分桶在单 Redis 实例上没有收益（实测否定）

有人会自然想到"加大 `BUCKET_COUNT` 就能扩展"。实测 4 桶 vs 1 桶：

| 配置 | 吞吐 | 收敛耗时 | `merge_runs` | 每批行数 |
|---|---|---|---|---|
| 1 桶 | 15,356 /s | 0 s | 996 | 1,852 |
| 4 桶 | 15,213 /s | **22 s** | 516 | 3,543 |

**吞吐没有提升，尾部收敛反而变慢。** 原因有两条：

1. **Redis 是单线程的**：4 个 key 落在同一实例上，仍走同一个事件循环，
   `BUCKET_COUNT` 只是把"1 次/秒"变成"4 次/秒"，没有把压力分摊到任何地方。
2. **续命链路是按桶触发的**：1 桶时合并可以一路 chain（996 次/120s ≈ 8.3 次/s），
   4 桶时每条链被稀释到约 1 次/s（516 次/120s ≈ 4.3 次/s），
   每批从 1,852 行涨到 3,543 行，尾部要多花 22 秒才追平。

> 要让分桶真正生效，必须同时满足：**多个 Redis 实例（或 cluster）+ 台账按桶拆行**
> （`inventory_ledger` 从"每 SKU 一行"变成"每桶一行"）。当前压测工程没有实现后者，
> 所以这条路径**没有可测的收益**。

## 附录：压测口径 vs MySQL 默认值（逐项对照）

本轮 MySQL 参数写在 `docker-compose-middleware.yml` 的 `command` 里，不在默认值上跑。逐项列清，
并区分「改语义」「加容量」「只是余量」「写了但没改」四种性质——只有第一类会让绝对值失真。

| 参数 | MySQL 默认 | 本轮 | 性质 | 对 `db` 4,079/s 的影响 |
|---|---|---|---|---|
| `innodb_flush_log_at_trx_commit` | 1 | **2** | 改持久性语义 | **决定性**：commit 不回 fsync |
| `log_bin` | ON | **OFF**（`--skip-log-bin`） | 无 binlog / 无 PITR | **决定性**：少 prepare+commit 两阶段与一次刷盘 |
| `sync_binlog` | 1 | 0 | 随 binlog 关闭而失效 | 决定性（同上，同一项收益） |
| `innodb_deadlock_detect` | ON | OFF | 压测专属，多行场景有风险 | 中：省掉每次等锁的锁图遍历 |
| `performance_schema` | ON | OFF | 去插桩开销 | 小～中 |
| `innodb_redo_log_capacity` | 100M | 1G | 容量 | 中：避免 checkpoint 抖动 |
| `innodb_io_capacity` / `_max` | 200 / 2000 | 2000 / 4000 | 容量 | 中：后台刷脏不挤压提交 |
| `innodb_buffer_pool_size` | 128M | 2G | 容量 | 小～中 |
| `innodb_log_buffer_size` | 16M | 64M | 容量 | 小 |
| `innodb_flush_method` | fsync | O_DIRECT | 生产也常用 | 小 |
| `max_connections` | 151 | 2000 | 余量 | 无（只为连得上） |
| `max_connect_errors` | 100 | 100000 | 余量 | 无 |
| `wait_timeout` / `interactive_timeout` | 28800 | 600 | 余量 | 无 |
| `innodb_buffer_pool_instances` | 8 | 4 | 反而更保守 | ≈0 |
| `innodb_lock_wait_timeout` | 50 | 50 | **写了但没改** | 0 |
| `innodb_thread_concurrency` | 0 | 0 | **写了但没改** | 0 |
| `innodb_autoinc_lock_mode` | 2（8.0+） | 2 | **已是默认** | 0 |
| `table_open_cache` / `table_definition_cache` | 4000 / 自动 | 4000 / 2000 | 默认附近 | 0 |
| `character_set_server` | utf8mb4 | utf8mb4 | 已是默认 | 0 |

未动的项：隔离级别仍是 REPEATABLE READ，`innodb_doublewrite` 仍开启，`innodb_flush_log_at_timeout` 未调。

**为什么前两项的影响在本压测里被放到最大**：生产上 `flush=1` 的 fsync 成本通常由组提交摊薄——
并发事务越多，一次 fsync 摊到的提交越多。但这把测的是**单热点行**：行锁让同一行一次只能有一个
事务在提交，组提交队列永远是空的，**每一次 commit 的 fsync 都实打实加进那 245 µs 的锁持有窗口**。
所以这条参数在别处可能只值 20%，在这里值 3~5 倍。

### 双1（`flush_log_at_trx_commit=1` + `sync_binlog=1` + 开 binlog）会掉到多少

唯一未知量是这块盘的单次 fsync 延迟 `L`。在单热点行上，一次事务提交要走
「redo fsync → binlog fsync」两次串行落盘，且两次都在锁持有窗口内、**都无法被组提交摊薄**，
所以窗口直接被加上 `2L`：

```
吞吐 ≈ 1 / (240 µs + 2L)        # 240 µs = 245 µs 去掉现在几乎不花钱的那次 commit
```

代入不同的 `L`：

| 单次 fsync `L` | 窗口 = 240 µs + 2L | 单行吞吐 | 200 并发下的 Avg |
|---|---|---|---|
| 50 µs（本地 NVMe） | 0.34 ms | 2,940 /s | 68 ms |
| 100 µs | 0.44 ms | 2,270 /s | 88 ms |
| 200 µs | 0.64 ms | 1,560 /s | 128 ms |
| **400 µs（ESSD 常见）** | **1.04 ms** | **960 /s** | **208 ms** |
| 800 µs | 1.84 ms | 543 /s | 368 ms |
| 1 ms（普通云盘） | 2.24 ms | 446 /s | 448 ms |

结论：**改双1 后 `db` 大概率落在 700~1,500 /s，即 4,079 的 1/3 ~ 1/6**；同一时刻 200 个线程的
平均等待会从 49 ms 涨到 150~300 ms。注意这不是"生产会掉这么多"——生产的写入落在互不相干的
散行上，组提交能把一次 fsync 摊给几十上百个事务；**单热点行是把 flush 成本 100% 暴露出来的最坏配置**。

连售罄后的拒绝路径也跑不掉：它仍然要执行一次 `UPDATE`（affected=0），双1 下同样是两次 fsync，
吞吐约 `1/(160 µs + 2L)` ≈ 1,000 /s。也就是说 `db` 方案在双1 下**没有便宜的拒绝路径**，
「卖光后能扛 19k 拒绝」这个结论只在压测口径下成立，生产必须靠 Redis 前置挡板。

复现方法：改掉 compose 里这两个参数、保留数据卷重启 mysql，然后 `./scripts/run-test.sh db`。
三策略的**横向排序不受影响**，而且对 `merge` 更有利——它 120 秒只提交 996 次台账事务，
受理路径的 INSERT 落在散行上，正好是组提交能摊薄的形态，而 `db` 摊不了。
